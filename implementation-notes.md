# Заметки реализации

Спека — `SPEC.md`. Сюда пишется то, что реализация вынудила решить иначе.

## Как снять замеры

```sh
# Граница ОС: B1a, B1b, двунаправленно, латентность.
go run ./cmd/b1 -mode boundary -duration 5s

# Linux: реальный TUN-fd + контрольный замер GSO. Нужен свой netns;
# unshare -Urn даёт CAP_NET_ADMIN внутри него, root не нужен.
go build -o b1 ./cmd/b1 && unshare -Urn ./b1 -mode tun -duration 5s

# Этап 3, поверх netstack. Прав не требует.
go run ./cmd/b3 -mode rtt        # RTT коротких TCP-обменов, без порога
go run ./cmd/b3 -mode fullcone   # B3: NAT-таблица под нагрузкой

# Оракул.
go run ./cmd/realtimelint .   # настоящее время только в internal/clock
go run ./cmd/negcheck         # каждая политика краснит свой тест
go test -run TestMetaCheck ./internal/negcheck   # негативная задача сама исправна
```

Гейт применяется автоматически и только на Windows (`-gate=false` снимает).

## Как гонять L3 (этап 2, Linux)

```sh
go test -c -o /tmp/l3.test ./internal/l3
HOP_L3=1 unshare -Urn /tmp/l3.test -test.v
```

`unshare -Urn` даёт `CAP_NET_ADMIN` в собственном netns — root не нужен. Без
`HOP_L3=1` тесты пропускаются: цена лишнего пропуска — строка в логе, цена
лишнего запуска в общем namespace — сеть машины.

В CI бинари собираются заранее и подсовываются через `HOP_L3_BIN_HOPD` и
`HOP_L3_BIN_HOP`: под `sudo` `go build` пошёл бы в чужой кеш и полез бы в сеть.

Проверить, что политика краснит свой тест:

```sh
HOP_L3=1 HOP_DISABLE=orphan_reject   unshare -Urn /tmp/l3.test -test.run 'T23'
HOP_L3=1 HOP_DISABLE=orphan_deadline unshare -Urn /tmp/l3.test -test.run 'T24'
HOP_L3=1 HOP_DISABLE=snapshot_restore unshare -Urn /tmp/l3.test -test.run 'T22'
```

## Как гонять L2 этапа 3

Прав не нужно, TUN не нужен, работает на трёх ОС:

```sh
go test ./internal/netstack        # T12, T13, T15, T16, T17
go test ./internal/bench           # TCP-путь насквозь через настоящую границу

HOP_DISABLE=verdict_order go test -run T16 ./internal/netstack
HOP_DISABLE=reject_mode   go test -run 'T12|T13' ./internal/netstack
HOP_DISABLE=nat_key       go test -run T15 ./internal/netstack
HOP_DISABLE=nat_key       go run ./cmd/b3 -mode fullcone   # рост таблицы втрое
```

## Как гонять L2 этапа 6 (резолвер, шаг 10 регистра)

Настоящие узлы (Xray за инжектором отказов), без TUN и без прав:

```sh
go test ./internal/l2 -run 'TestT14SwitchResolvesToNewIP|TestT16DNSToLocalRouterIsHijackedRealResolver|TestD33TruncatedAnswerRetriesOverTCPRealNode'

HOP_DISABLE=dns_cache_flush_on_switch go test ./internal/l2 -run TestT14SwitchResolvesToNewIP
HOP_DISABLE=verdict_order            go test ./internal/l2 -run TestT16DNSToLocalRouterIsHijackedRealResolver
HOP_DISABLE=dns_tcp_retry            go test ./internal/l2 -run TestD33TruncatedAnswerRetriesOverTCPRealNode
```

## Deviations

Разделы идут в том порядке, в каком записи появлялись, а не по номерам этапов:
сперва реализация этапов 0–5, затем заготовки этапов 6–9 со второй машины, затем
сверка регистра решений со спекой (пас 0), затем этапы, сделанные по принятым
решениям, — 7 и С.

Раздел «Этапы 6–9» со второй машины писался до паса 0 и местами противоречит
принятым там решениям; расхождения названы прямо внутри него. Он оставлен как
след, а не как руководство.

### Этапы 0–5 — оракул, граница, сервис, netstack, движок, живость

**B1 меряет транспорты, а не `PacketDevice`.** Прежняя редакция §8.6 говорила
«прогон синтетического потока через `PacketDevice`», но этап 1 по построению
идёт до того, как реализации `PacketDevice` появятся: их стоимость и есть
предмет замера. _Расхождением быть перестало: §8.6 переписан и говорит теперь
«через границу»._ Меряются транспорты напрямую — named pipe на Windows,
socketpair и TUN-fd на Unix — с тем же framing и батчингом, что понесёт
реализация. Консервативно: реализация добавит к этим числам, а не убавит.

**B1b на Windows моделирует кольцо Wintun, а не открывает адаптер.** Настоящий
`ReceivePacket` требует прав администратора и `wintun.dll` рядом с бинарём — это
открытый на тот момент вопрос §7 про `wintun.dll` и этап 8 (ныне закрыт, см.
C19). Модель: копия каждого пакета из 8-МиБ staging-буфера (порядок
receive-кольца Wintun) перед записью в трубу. Она воспроизводит то, что в замере
дорого, — лишний memcpy и давление на кэш, — но не стоимость самого вызова
драйвера. Число завышено на эту стоимость.

**Контрольный замер GSO сделан на UDP GSO, а не на TSO.** `UDP_SEGMENT` +
`TUN_F_USO4` дают многопакетный read() без TCP-рукопожатия; TSO потребовал бы
терминировать TCP-соединение прямо в харнессе. Форма разбора — как в
`handleVirtioRead` (wireguard-go, MIT): virtio-заголовок, затем нарезка на
сегменты с копированием заголовков и полезной нагрузки. Контрольная сумма UDP не
пересчитывается (для IPv4 нулевая сумма легальна), поэтому число слегка завышает
выигрыш GSO — ровно на ту работу, которую virtio-заголовок и договаривается
отдать железу.

**Замер пути «ядро → агент» на Linux считает и стоимость отправителя.** Пакеты
порождает UDP-сокет внутри netns, у него на пакет тоже приходится syscall.
Отправителей четыре, чтобы узким местом был читатель. Число — нижняя граница, не
верхняя.

**Поддельный `PacketDevice` живёт в `internal/packettest`, а не в
`internal/packet`.** `ExpectRST`/`ExpectICMPUnreach` принимают `testing.TB`;
импорт `testing` в продуктовый пакет протащил бы тестовые флаги в каждый бинарь,
который его слинкует.

**Реестр политик — центральный литеральный список, а не регистрация через
`init()`.** При регистрации из пакетов-владельцев полнота реестра зависела бы от
того, что слинковано в конкретный бинарь, и negcheck молча пропускал бы
политики. Список в `internal/policy/policies.go` полон по построению.

**Отказ в `orphaned` делает респондер сервиса, а не reject-маршруты ядра.** План
(раздел 0, D1) предполагал подмену маршрутов туннеля на `unreachable` /
`-reject`, и привилегированного кода на Linux и macOS не прибавлялось бы вовсе.
Замер `TestRouteReplaceOnEstablishedConnection` (`internal/l3`) показал, что
подмена закрывает только новые соединения: у уже установленного сокета `Write`
возвращает успех, а данные молча уходят в ретрансмиты — за 8 секунд наблюдения
ни одной ошибки. Это то самое молчание, против которого §5.6, только сдвинутое.
Совместить нельзя: с reject-маршрутом пакеты до устройства не доходят, и
отвечать не на что. Выбран консервативный вариант — сервис становится читателем
устройства и отвечает RST/ICMP; один механизм на трёх ОС, и на Windows он был
нужен в любом случае. §6.2 переписан по факту замера.

**Attach-token переживает `kill -9` агента, значит лежит на диске.** Задача
говорила «агент держит его только в памяти». Так нельзя: реаттач (T24) по
определению делает новый процесс, а память убитого ему недоступна, — токен
только в памяти означает, что T24 не проходит никогда. Токен лежит в
`$XDG_RUNTIME_DIR/hop/attach-token`, каталог 0700, файл 0600 (§6.14 это прямо
разрешает: «каталог агента 0700, файлы с ключами 0600»). Остальные требования
§6.14 соблюдены буквально: тип `tunnel.Token` форматируется заглушкой, поэтому в
лог он не попадает ни через один глагол `fmt`, включая `%#v` по объемлющей
структуре; в `status` его нет; сервису он уходит только в самом `Attach`.
Следствие, которое надо понимать: для процессов того же UID токен — не граница,
границей остаётся проверка UID/SID плюс права на сокет. Токен добавляет второй
рубеж против процесса, который до каталога агента не достаёт.

**`Detach(reason=restart)` не минует окно отказа, а сокращает его.** План писал
«чистый рестарт минует окно отказа целиком». Буквально это означало бы, что в
зазоре пакеты не отвергаются, — то есть молчаливое окно, ровно запрещённое §5.6.
Реализовано так: `Detach` даёт то же ребро и тот же отказ, но сервис знает
причину и показывает её в `status`, а окно схлопывается до времени respawn.

**Смерть сервиса переживает все разложенные им правила.** T29 первоначально
показал десять правил: `31000` исключения §5.6, прежнее `31500` с UID-диапазоном
§6.8 и `32000` туннельное. Новая сборка больше не создаёт `31500`, но переходный
`platform.Reclaim` всё ещё подбирает его после обновления. Уборка идёт **до**
снятия снапшота, иначе снапшот закрепил бы мусор как исходное состояние.

**Уровень L3 написан только для Linux.** macOS и Windows остались скелетами
рабочих процессов с `workflow_dispatch` (§8.4: они и так по расписанию). Причина
не в объёме: L3-Windows упирается в вопрос §7 про `wintun.dll` — без подписанной
библиотеки рядом с бинарём адаптер не поднимается, и план держит этот вопрос
блокером этапа 8. macOS-слой (utun через `AF_SYSTEM`, `SIOCAIFADDR`, `PF_ROUTE`)
писать вслепую, без раннера, значило бы получить непроверенный привилегированный
код. `platform.New()` на этих ОС отказывает явно, а не молча: молчаливая
заглушка дала бы зелёный L3 там, где ничего не проверено.

**gvisor поднял требование к Go до 1.26.3.** `gvisor.dev/gvisor` нужен ради
`pkg/tcpip/header` (§6.2, Apache-2.0) и понадобится целиком на этапе 3. Его
`go.mod` требует 1.26.3, поэтому столько же требует и наш; CI поставлен на
`1.26`. Версия берётся с ветки `go` (генерируемой), а не с `master`: на master в
дереве лежат шаблоны `*.tmpl.s`, которые ассемблер Go принимает за исходники и
не собирает.

**Исключения линта настоящего времени — построчные, `//hop:realtime`.** Файловых
исключений нет намеренно. Бенчмарк меряет время через `clock.System`, то есть
через тот же интерфейс, и исключений не требует; пометки стоят только внутри
`internal/clock`.

**`StopTunnel` сверяет владельца, хотя §3.1 этого не требует.** Спека задаёт
проверку личности только для `Attach`, а список операций даёт `StopTunnel()` без
условий. Но модель доверия §3.1 — «сокет доступен лишь владельцу, и внутри
одного пользователя случайный процесс не должен уметь перехватить чужой
дескриптор» — на снятие туннеля распространяется ровно так же: посторонний,
снявший чужой привилегированный туннель, наносит больше вреда, чем перехвативший
его. Консервативный вариант: `Machine.StopBy` требует совпадения UID/SID с
владельцем.

Сверяется именно личность, а не соединение, как у `Detach` и `Heartbeat`:
`hop -down` — отдельный процесс, он подключается заново, и владельцем соединения
не является по построению. Гейт по соединению сломал бы CLI.

**Право открыть канал даётся классу, а не конкретному пользователю.** §6.1 —
одна фраза: «Unix-сокет с правами владельца / named pipe с SDDL», и кто такой
владелец, спека не говорит. Стороны границы живут под разными пользователями:
сервис под root (нужны `/dev/net/tun` и `ip`), агент — под обычным. Сокет строго
владельцу означал бы EACCES у агента.

Выбрано: на Unix сокет 0660 с группой из `-group` (дефолт `hop`), на Windows ACE
для `IU` (интерактивные пользователи) вместо SID слушателя. Владение конкретным
туннелем при этом держит измеренная личность — SO_PEERCRED и
`ImpersonateNamedPipeClient`, — поэтому широкий ACE не даёт перехватить или
снять чужой туннель.

Несуществующая группа валит старт, а не понижает права молча до 0600: сервис,
поднявший сокет, к которому агент не достучится, выглядит рабочим и не работает.
L3 передаёт `-group ""` — там обе стороны идут под root в своём netns.

**UDP не проходит через gvisor вовсе. Это материал для §5.1.** План этапа 3
говорит «gvisor `tcpip` поверх `PacketDevice`»; по факту gvisor обслуживает
только TCP. Причина в устройстве его UDP-форвардера: `CreateEndpoint`
(`pkg/tcpip/transport/udp/forwarder.go`) делает `net.Bind` на адрес назначения и
`net.Connect` на адрес источника, то есть отдаёт **connected**-эндпоинт на пару
(src, dst). Это ровно NAT по паре — то, что §5.3 запрещает и что T15 обязан
ронять. Full-cone на этом API выражается только так: заводить отдельный эндпоинт
на каждого нового отвечающего и писать ответ в него, то есть держать в gvisor
структуру, которая живёт не по правилам gvisor.

Выбран консервативный вариант: UDP разбирается и собирается своими руками
(`internal/packet.BuildUDP` на заголовках gvisor, Apache-2.0), NAT — своя
таблица по source addr:port, исходящее — один `net.PacketConn` на исходный порт,
ровно как отдаёт `core.DialUDP`. Это то же, что делает собственный TUN Xray
(`proxy/tun/udp_fullcone.go`), на который §5.3 и ссылается. UDP не нуждается ни
в машине состояний, ни в окнах, ни в сборке потока — всё, ради чего берут
netstack; за вычетом NAT он состоит из разбора заголовка.

Чего это стоит §5.1. **Форка не потребовалось, костыля через `PacketEndpoint`
тоже, и перехвата ниже заявленного уровня нет.** Но утверждение §5.1 «свой
TUN-слой убирает второй netstack в горячем пути» держится теперь на меньшем:
netstack в горячем пути — это TCP, а UDP идёт мимо него. Выбор gvisor этим не
опровергнут — для TCP он даёт именно то, что нужно, — но его доля в продукте
меньше, чем читается из §5.1.

**Вердикт принимается до gvisor, а не внутри него.** §3.4 требует решения по
первому пакету потока. Из четырёх вердиктов три обязаны сработать раньше, чем
пакет попадёт в стек: bypass-пакет в стек заходить не должен вовсе, reject
отвечает `internal/reject` (тот же код, что обслуживает `orphaned`), hijack-dns
над UDP до стека и не доходит. Поэтому вердикт живёт в насосе, на сырых пакетах,
и в gvisor попадает только то, что признано proxy или DNS-над-TCP.

Что при этом даёт gvisor и чего пришлось бы городить без него: `tcp.Forwarder`
вызывает обработчик на SYN и **откладывает рукопожатие до `CreateEndpoint`**.
Поэтому исходящее соединение устанавливается раньше SYN-ACK, а его неудача
превращается в RST, а не в «соединение установлено, но мертво». Это свойство
проверяется `TestRefusedUpstreamNeverCompletesHandshake`. Своими руками оно
означало бы собственную реализацию TCP-рукопожатия — то, ради чего netstack и
берут.

**Вердикт кэшируется в таблице потоков; таблицы в спеке нет.** «Вердикт на
первом пакете» буквально означает, что он не пересматривается. Без таблицы
вердикт считался бы заново на каждом пакете, и смерть последнего узла посреди
установленного соединения превращала бы его следующий пакет в RST **в обход
gvisor**, который этим соединением в этот момент владеет. Таблица —
`internal/netstack/flow.go`, ключ 5-кортеж, уборка по простою на фейковых часах.
Новые потоки при этом отвергаются немедленно: fail-close закрывает новое, а не
чужое.

**Пятый вердикт — `block`, молчаливый дроп.** §3.4 перечисляет четыре, но §6.10
велит блокировать широковещательный NetBIOS и прочий multicast и broadcast, а
§6.9 — IPv6. Отвечать на них нечем: RST в multicast бессмысленен, а ICMP на
broadcast — это ответ самому себе. Дроп здесь не нарушает §5.6: тот запрещает
молчание там, где приложение ждёт ответа от конкретного собеседника, а не в
обнаружении служб. Сюда же уходит всё, что не TCP и не UDP, включая ICMP от
клиента: исходящего для него на этапе 3 нет.

**Список bypass §6.10 не переиспользует `reject.Excluded`, хотя они похожи.**
Вопросы разные: `Excluded` отвечает «на что респондер не имеет права отвечать» и
консервативно относит туда весь multicast; bypass отвечает «что выпустить в
локальную сеть», а §6.10 делит multicast на разрешённое обнаружение служб (mDNS,
SSDP) и блокируемое остальное. Шов между двумя списками закрыт тестом
`TestRejectVerdictNeverEndsInSilence`: ничто, получившее вердикт reject, не
должно оказаться исключением `internal/reject` — иначе fail-close стал бы
молчаливым дропом, ровно тем, что запрещает §5.6.

**T15 в том виде, как он записан в §8.3, краснеет не по заявленной причине.**
§8.3 обещает, что при NAT по паре src+dst «ответы потеряются». Три ответа от
трёх контактированных адресов доходят при любом ключе: запись под них есть.
Теряется ответ с адреса, на который клиент **не** слал, — а это и есть
определение full-cone. Тест проверяет обе половины: одна NAT-запись на исходный
порт (при `nat_key=src+dst` их становится три) и ответ от четвёртого, никогда не
контактированного адреса. Первая половина краснеет по счёту, вторая — по
существу.

**Bypass — приёмник за интерфейсом, а не настоящая локальная сеть.** В продукте
таких пакетов на устройстве нет вовсе: исключения выражены правилами
маршрутизации выше туннельного и в таблицу туннеля не заходят (§6.2). Вердикт
bypass в netstack — второй рубеж на случай, если правило не встало, по образцу
`reject.Excluded`. Куда он отдаёт пакет, решает вызывающий; на этапе 3 это
запись в памяти, на этапе 8 — сокет, привязанный к дефолтному интерфейсу.

**hijack-dns над TCP терминируется уже сейчас, хотя резолвер — заглушка.** §3.4
говорит «dst-порт 53 (UDP или TCP)», а до запроса в TCP не добраться, не
терминировав поток. Поэтому DNS-над-TCP идёт в gvisor и разбирается по RFC 1035
§4.2.2 (двухбайтовый префикс длины), после чего попадает в тот же `Resolver`,
что и UDP. Этап 6 меняет только реализацию `Resolver`.

**Строители IPv4-пакетов переехали в `internal/packet`.** `BuildUDP` нужен
netstack (ответ NAT и ответ резолвера), оракулу и замеру B3 — трём разным
пакетам, из которых один компилируется в бинарь, а значит не может тянуть
`testing`. Три копии арифметики контрольных сумм разошлись бы молча;
`internal/packettest` теперь на них делегирует.

**Замер RTT ставит по обе стороны границы по стеку gvisor.** Настоящим ядром на
дальней стороне был бы TUN, то есть права и платформенный код, то есть уровень
L3. Замер остаётся L2 ценой того, что «приложение и ядро» — тоже gvisor, и его
стоимость входит в число. Абсолютные значения поэтому завышены; переносимо здесь
сравнение Linux с Windows, где меняется только граница. Та же логика, что в
B1-строке про загруженный прогон 3.

### Этап 6 — резолвер

**Р27. Сброс кэша: резолвер подписан сам, связка дожидается подтверждения.**
§5.7 требует, чтобы кэш сбрасывал сам резолвер по подписке, и связка «не
участвовала в самом сбросе». Но `health.Manager.Events()` — одноконсьюмерный
канал, который уже читает `agent.pumpEvents`, а Р33 (`switch_order`, W11, W13)
требует, чтобы кэш был выкинут **раньше**, чем событие ушло наружу: иначе
приложение, разбуженное событием, успевает перерезолвить имя и получить адрес,
добытый через мёртвый узел, — и §5.7(в) оказывается выполнен формально.

Совместить два требования буквально нельзя: подписчик живёт в своей горутине.
Решение: резолвер получает `Config.Events` и флашит сам, а связка после отправки
ждёт `Config.Acked`. Подтверждение приходит и тогда, когда сброса не было
(политика выключена), — иначе выключенный флаг подвешивал бы связку вместо того,
чтобы покраснить проверку. Цена: точка синхронизации между двумя горутинами на
каждом переключении узла.

**Р28. Транспорт клиента приезжает вторым интерфейсом, а не параметром.**
D33–D36 требуют разного поведения для клиента по UDP (флаг TC плюс потолок его
буфера EDNS0) и по TCP (полный RRset), а `netstack.Resolver.Query`, замороженный
с этапа 3, транспорта не несёт. Рядом объявлен `netstack.StreamResolver` с
`QueryStream`, и `tcp.go` делает type assertion — тот же приём, каким сделан
`FlushableResolver` в связке. Замороженный интерфейс не тронут, все прежние
call-site и фейки работают как были, а счётчик `TruncToClient` остался в
резолвере, как требует §2 регистра.

**Р29. Разбор DNS свой, по смещениям, а не `x/net/dns/dnsmessage`.** У6 требует,
чтобы ответ собирался копированием байт: секция вопроса из запроса как есть, всё
остальное от апстрима байт в байт, включая TTL (C4). Значит нужны не разобранные
структуры, а точные смещения — где начинается и кончается каждый RR, где лежит
OPT, где внутри него ECS. `dnsmessage` смещений не отдаёт, и для ECS и EDNS0
пришлось бы считать байты руками поверх него, то есть держать два разбора вместо
одного. `internal/dnsmsg` — свой, без новых зависимостей.

**Р30. Состояние DNS видно в логе агента, а не в `hop status`.** Р15 отдаёт
клиенту `SERVFAIL`, когда живых узлов нет, и прямо называет цену: приложение не
отличает «VPN закрылся» от «DNS сломался», а внятная причина «видна в
`hop status`». Но `hop -status` спрашивает по IPC **сервис** и получает
`tunnel.State`; резолвер живёт в процессе агента, и канала от второго процесса
`hop` к работающему агенту нет вовсе — по C9 это разделено сознательно. Строить
его сейчас значило бы втащить в этап 6 работу этапа 9. DNS печатается там же,
где уже печатается фаза трафика, — в `cmd/hop/watch.go`.

**Р31. Фаза `bypass` в продукте до резолвера не доходит.** Р25 и D20 описывают
поведение резолвера в `bypass`, а C8 — что перехваченный DNS идёт там мимо
узлов. Но `agent.Bypass(true)` по Р35 (`bypass_teardown`) снимает туннель
целиком, вместе с ним уходит стек, и запросов на :53 больше не приходит: система
резолвит своим резолвером напрямую. Ветка прямого апстрима остаётся живой ровно
при выключенной `bypass_teardown` и потому реализована. Сброс кэша на краях
`bypass` (D20) от этого не зависит и нужен всегда: резолвер переживает
`Down`/`Up`, а адреса, добытые напрямую, указывают на CDN настоящего региона.

**Р32. Край `bypass` резолверу показывает связка, но решает он сам.** Фаза
приходит функцией, то есть опрашивается; заметить край опросом можно было бы
только по таймеру, а это либо задержка в размер шага, либо сотни тиков на каждое
удержание в `waiting`. Связка зовёт `Resolver.PhaseChanged()` из `refreshPhase`,
который и так вызывается на каждом переходе. Что считать краем и что при этом
сбросить, решает резолвер: связка говорит «посмотри», а не «сбрось».

**Р33. Имена узлов резолвит связка до Xray, а не Xray сам.** §5.7(а) называет
петлю, но не место, где она разрывается. Xray резолвит адрес узла своим сокетом,
который через перехваченный :53 уходит в туннель — то есть в резолвер, которому
нужен живой узел, которого нет, пока имя не разрешилось. Поэтому
`agent.reloadNodes` резолвит имя через `Bootstrap` и подставляет адрес в
`engine.Node.Server` до сборки конфига. Подстановка сохраняет рукопожатие:
`engine.tlsSettings` берёт `serverName` из `sni`, иначе из `host`, иначе
оставляет Xray взять адрес — и последнее после подстановки упёрлось бы в чужой
сертификат, поэтому при непустом `security` и пустых обоих параметрах `sni`
выставляется исходным именем. Отказ bootstrap узел не выбрасывает: иначе один
недоступный апстрим сокращал бы подписку молча.

### Этапы 6–9 — стор, подписки, резолвер, связка, CLI, поставка

Записи ниже приехали со второй машины и описывают код, которого **в этом
репозитории пока нет**: `internal/store`, `internal/subscription`,
`internal/resolver`, `internal/supervisor`, `packaging/`, `docs/wintun.md`.
Держим их здесь, потому что это уже принятые решения с обоснованием, а не
намерения, — но пока код не приехал, читать их надо как «что выяснилось там», а
не «как устроено здесь». Нумерация C1–C21 сквозная: в исходном файле номера
C11–C14 стояли дважды.

**C1. `store` импортирует `health` ради типа `NodeHealth`.** §3.4 говорит «store
не знает ни про кого», но §3.4 же вменяет ему персистентность `NodeHealth`, а
сама модель принадлежит `health`: окно, состояние и счётчик ошибок трафика
меняет только он. Варианты были — продублировать структуру в `store` или вынести
её в `node`. Дубль означал бы две модели одного состояния и ручную конверсию на
каждой пробе; `node` — модель узла, и живость в неё не входит по прямому
указанию §2. Выбран импорт: `store` берёт из `health` **только тип данных**, ни
одной функции; обратного импорта нет и быть не должно.

**C2. Решение «рвать ли соединения» выражено в `health`, а не у потребителя
события.** §5.5 формулирует его как свойство сигнала: событие несёт `reason`, а
что с ним делать — дело того, кто событие получил. Реализовано методом
`health.Switch.Interrupts()`. Причина: §8 требует, чтобы у политики
`switch_reason` был охраняющий тест, а он по контракту фазы живёт в
`./internal/health` — значит и развилка обязана быть там же. Потребитель события
(супервизор, netstack) вызывает метод и не воспроизводит его логику у себя;
второе место означало бы второй ответ на тот же вопрос.

**C3. Апстрим-DNS ходит сначала по UDP и только на флаг TC — по TCP.** Контракт
фазы предполагал один путь наверх — поток с префиксом длины (RFC 7766), потому
что `Engine.DialUDP` отдаёт `PacketConn` на исходный порт клиента и второй
модели full-cone под резолвер не хотелось. Но TCP-сессия на каждый запрос — это
рукопожатие узла на каждый резолв, то есть лишний RTT там, где его считает
пользователь. Добавлено **необязательное** поле `Config.DialUDP` того же вида,
что `Dial`: датаграмма пишется и читается целиком, без префикса. `nil` оставляет
прежнее поведение — весь апстрим по TCP, — поэтому проводка, собранная по
контракту, продолжает компилироваться и работать. Усечённый ответ (TC) в обоих
случаях перезапрашивается потоком: RFC 1035 §4.2.1.

**C4. TTL в отданном из кэша ответе не уменьшается.** §5.7в требует, чтобы кэш
уважал TTL, — он и уважает: запись живёт ровно столько, сколько назвал апстрим
(в рамках `MinTTL`/`MaxTTL`), и по истечении перезапрашивается. Но само
сообщение отдаётся клиенту байт в байт, с исходным TTL и подменённым
идентификатором. Честный вариант — разобрать ответ на записи и пересобрать его
на каждом попадании в кэш; `dnsmessage.Builder` требует для этого типизованного
метода на каждый тип записи, то есть switch по всему перечислению RR ради
вычитания секунд. Цена ошибки мала и ограничена сверху: клиент держит запись
дольше нас не более чем на `MaxTTL`, а при смене узла кэш всё равно сбрасывается
целиком.

**C5. Clash YAML из каскада §6.12 распознаётся, но не разбирается.** §6.12
ставит его второй ступенью каскада
(`base64 → Clash YAML → построчно → по схеме`). Ступень на месте — тело с ключом
`proxies:` определяется и отвергается одной внятной ошибкой, — но конвертации
YAML в узлы нет: она тянет за собой YAML-зависимость и вторую, независимую от
ссылок, модель разбора. Выбран консервативный вариант: явный отказ вместо
разбора YAML построчно, при котором на каждую строку приходит своя бессмысленная
ошибка, а настоящая причина тонет. Первая, третья и четвёртая ступени каскада
работают полностью.

**C6. `security=reality` остаётся отдельным значением, а не сводится к `tls`.**
§6.12 пересказывает nekoray («reality → tls плюс pbk/sid/spx»), но §2
перечисляет `security` как `none | tls | reality`, и `engine.buildConfig`
разбирает `reality` отдельной веткой (`realitySettings` — не то же самое, что
`tlsSettings`). Сведение к `tls` на разборе означало бы, что различать их
придётся по наличию `pbk` в params, то есть восстанавливать выброшенное знание.
Нормализации §6.12 по значениям (`none/0/false`, `1/true`) сохранены полностью.

**C7. Классификация §6.15 видит только те отказы, о которых Xray сообщил явно.**
`core.Dial` возвращает трубу немедленно, а исход соединения приезжает позже и в
другое место — через `session.SubmitOutboundErrorToOriginator`
(`common/session/context.go:119`). Движок ставит в контекст приёмник этих
ошибок, и `classify` считает смертью узла только то, что в него пришло. Всё
остальное — обрыв, устроенный целевым хостом, и узел за него не отвечает.

Цена решения найдена измерением, а не рассуждением: если узел рвёт соединение
**корректным закрытием** посреди рукопожатия VLESS (режим стенда
`cut-after-handshake` из §8.1), Xray сводит ошибку к `io.EOF`
(`app/proxyman/outbound/handler.go:246` фильтрует EOF, `io.ErrClosedPipe` и
`context.Canceled`), ничего не сообщает, и для нас это неотличимо от сайта,
закрывшего соединение первым. Такой узел классификацией трафика **не
убивается**. Разрыв через RST — убивается, тест `TestNodeTornByInjectorIsDeath`.

Выбран консервативный вариант. Альтернатива — считать смертью всякое соединение,
закрывшееся без единого байта от узла, — ловит `cut-after-handshake` и вместе с
ним всякий сайт, который принимает соединение и закрывается молча. Это ровно тот
отказ, против которого написан §6.15 и стоит T20. Дыра закрыта не здесь, а §6.7:
проба идёт тем же outbound, ничего не получает и уходит в окно k-из-n (§6.3).
Классификация трафика остаётся вторым сигналом, а не первым.

**C8. В фазе bypass наружу выпускается TCP, но не UDP.** §5.6 обещает, что
`hop bypass --on` осознанно выпускает трафик напрямую. Прямой путь у агента
ровно один — outbound `direct` движка (`Engine.DialDirect`, §6.8 биндит его к
дефолтному интерфейсу), и он отдаёт только `net.Conn`. Датаграммного прямого
исходящего у движка нет: `Engine.DialUDP` ключуется тегом узла, потому что
full-cone §5.3 держится на `core.DialUDP` с инбаунд-тегом. Поэтому в фазе bypass
TCP и перехваченный DNS идут мимо узлов, а UDP-поток исходящего не находит и
датаграмма не выпускается.

Выбран консервативный вариант: обычный `net.Dial` из процесса агента выпустил бы
UDP на Linux (правило §6.8 по UID-диапазону), но на macOS и Windows петля
закрывается `sockopt.interface`, который ставит Xray, — сокет мимо движка ушёл
бы обратно в туннель. Один механизм на трёх ОС дороже, чем недостающий UDP в
режиме, который сам по себе аварийный: §С6 описывает его как «починить подписку
либо осознанно выпустить трафик», и веб с DNS для этого работают.

**C9. `supervisor.Status` не содержит `device` и не умеет `orphaned`.** §2
перечисляет `TunnelState` как один объект с полями `phase`, `active_node`,
`last_switch`, `device`. Разделено по владельцу: `device` и фаза `orphaned`
известны только сервису (§6.2), активный узел и причина последнего переключения
— только агенту. `hop status` показывает то и другое, склеивая
`ipc.Client.Status()` с `supervisor.Status()`. Общий объект означал бы, что одно
и то же поле заполняют двое, и расхождение (агент считает себя `up`, сервис уже
в `orphaned`) осталось бы незамеченным.

**C10. Форс-проверка §6.6 приходит сигналом, а не от наблюдателя за сетью.**
§6.6 перечисляет смену интерфейса, пробуждение из сна и правку таблицы
маршрутизации. Наблюдатели за всеми тремя — платформенный код (netlink,
SCDynamicStore, WMI), то есть этап 8. До него ребро выражено `SIGHUP`:
`supervisor.Force(health.Trigger)` уже на месте и проверен T6, меняется только
источник события. Юнит systemd и тест умеют дать его руками.

**C11. При отсутствующем агенте `hop status` и `hop down` говорят с сервисом
напрямую.** §3.3 требует, чтобы клиенты ходили к сервису только через агент —
одна привилегированная граница, одна точка аудита. Но оба состояния, ради
которых эта пара команд существует, наступают именно тогда, когда агента нет:
`orphaned` по определению означает «агента не стало» (§6.2), а §2 обязывает
`status` его показывать; `hop down` (§С7) обязан снять туннель и в этом случае,
иначе интерфейс держится до истечения `orphan_deadline`, и пользователю нечем
вмешаться. Пока агент жив, оба ходят через него, и склейка состояний остаётся в
одном месте (C9). Прав это не расширяет: `StopTunnel` сверяет владельца сам
(`Machine.StopBy`), а `Status` не отдаёт ни узлов, ни ключей.

**C12. Подписки и узлы правит процесс CLI, а не агент.** §3.3 говорит «вся
логика в агенте», но §С2 (`hop sub add`) идёт раньше §С3 (`hop up`): требовать
живого агента для добавления подписки значило бы требовать туннеля до того, как
появился хоть один узел. Поэтому `sub add/update/rm/list` и `node add/rm` — это
прямая работа со стором из процесса команды.

Следствие, о котором CLI предупреждает вслух: живой агент состава узлов не
перечитывает — список кандидатов он собрал в `supervisor.New`, и новые узлы
вступают в силу после `hop down` и `hop up`. Второе следствие — две записи в
один стор из разных процессов: файлы пишутся целиком, поэтому одновременные
правки состава агентом и CLI теряют одну из них. Сейчас агент в стор не пишет
вовсе, так что окна нет; появится запись здоровья на диск — понадобится либо
блокировка файла, либо перенос этих команд в агент.

**C13. `hop up` не демонизируется: это и есть агент.** §С3 описывает `hop up`
как «поднимает туннель», из чего читается фоновый запуск. Реализовано иначе: без
команды и по `hop up` бинарь работает агентом в переднем плане, пока туннель
жив, — так его и запускает менеджер служб при логине (§6.13), и так же его
запускает стенд L3. Своей демонизации (fork, pid-файл, перезапуск) нет
намеренно: §5.2 отдал жизненный цикл процессов сервису и менеджеру служб, и
второй такой механизм внутри агента дублировал бы их с худшим качеством. Если
агент уже работает, `hop up` не поднимает второй туннель, а делает то
единственное, чего от него в этом случае ждут: `--node` фиксирует узел.

**C14. `hop node rm` и `hop node ping` выражены имеющимися API.** Удаления узла
поштучно в сторе нет — есть слияние состава группы (§5.8), и `node rm`
выражается через него: применяется остаток группы, узлы-соседи сохраняют id и
историю проб, удалённый уходит вместе со своей. Цена — два ручных узла с
совпавшим ключом слияния (§6.16) в группе `manual` неразличимы, и после удаления
третьего один из них получит новый id.

Пробы поштучно не умеет расписание: `Scheduler.Force` гоняет горячий ярус
целиком (§6.5), и залп по всей подписке ради одной команды запрещён тем же §6.5.
Поэтому `hop node ping <id>` — это форс-проверка (§6.6) и состояние узла после
неё; узел из редкого яруса может ответить прежним состоянием.

**C15. Сценарий С1 закрывается поставкой, а не командой.** §1/С1 («ставит пакет,
инсталлятор регистрирует сервис, агент стартует при логине») — это `packaging/`
и I1–I4 (§8.5), и от CLI ему нужно ровно одно свойство: агент запускается как
`hop up` в переднем плане, а глобальные флаги идут **до** команды
(`hop -socket … up`), потому что разбор аргументов останавливается на первом
не-флаге. Юниты systemd и LaunchAgent написаны именно так. Остальные сценарии —
С2–С8 — выполнимы командами §5.9 целиком.

**C16. Сокет на macOS — `/var/run/hop.sock`, а не умолчание `ipc.DefaultPath`.**
§3.1 не называет пути, но код называет: `defaultPath()` отдаёт `/run/hop.sock`
на всём, что не Windows. На macOS каталога `/run` нет, а корневая файловая
система только для чтения — создать его нечем, и сервис с умолчанием не
поднимется вовсе. Инсталлятор macOS передаёт `-socket /var/run/hop.sock` в обоих
plist (`packaging/macos/*.plist`). Правка самого умолчания была бы честнее, но
это чужой пакет и чужой этап; путь задан там, где он всё равно обязан быть
записан дважды — в plist демона и агента.

Побочное следствие для порядка аргументов агента: разбор флагов останавливается
на первом не-флаге, поэтому в plist стоит `hop -socket … up`, а не
`hop up -socket …`. Во втором виде флаг остался бы неразобранным и агент искал
бы несуществующий `/run/hop.sock`.

**C17. L4 не поднимает туннель и не перезагружает машину.** §8.5 требует от I1
«агент стартует при логине», от I2 — перезагрузку. Ни того, ни другого на
hosted-раннере нет: сессии логина не существует, перезагрузка убивает задачу, а
поднятый туннель отобрал бы у раннера сеть — ровно поэтому L3 живёт в netns.
Заменено на проверяемое: I1 — сервис активен и включён в автозапуск, автозапуск
агента зарегистрирован, а член группы `hop` действительно открывает сокет, тогда
как посторонний получает `EACCES` (§6.1); I2 — юнит включён в
`multi-user.target`, и убитый `SIGKILL` сервис возвращается сам. Настоящая
перезагрузка и настоящий логин остаются ручной проверкой перед релизом.
Инсталлятор при этом намеренно **не** запускает агента: установка, меняющая
маршруты машины, не может быть прогнана в CI ни разу.

**C18. §6.14 на Windows выражается не режимом каталога.** «Каталог агента
`0700`, файлы `0600`» — это POSIX-режимы, которых на Windows нет:
`os.MkdirAll(0700)` там не значит ничего. Гарантия держится профилем
пользователя — `%USERPROFILE%` уже закрыт для других непривилегированных учётных
записей, и стор наследует его ACL. Инсталлятор Windows каталог стора не создаёт:
он работает с повышением и, будучи запущен под другой учётной записью, создал бы
каталог не тому человеку. На Linux и macOS `0700` с владельцем-человеком
выставляется установкой явно, в том числе при обновлении.

**C19. §6.13 на Windows не выполняется до обработчика SCM в `hopd`.**
Инсталлятор регистрирует службу правильно (автозапуск, LocalSystem) и
регистрирует автозапуск агента задачей планировщика, но запуск службы падает с
1053: `cmd/hopd` — обычная консольная программа, диспетчеру служб она не
отвечает (`golang.org/x/sys/windows/svc` не подключён). Скрипт говорит это
прямым текстом в ошибке, а L4-Windows гоняет только то, что уже работает —
закреплённую версию и подпись `wintun.dll`. Вопрос §7 про `wintun.dll` при этом
закрыт решением, а не кодом: `docs/wintun.md` — версия и sha256 закреплены,
библиотека скачивается при сборке и в репозиторий не кладётся.

**C20. Режим `rst` инжектора рвёт соединение после первых байт клиента, а не
мгновенно по accept.** §8.1 называет `rst` «немедленным RST». Буквальная
реализация — `SetLinger(0)` и `Close` сразу после `accept` — оказалась
недетерминированной: когда данные клиента ещё в полёте, ядро завершает такое
закрытие штатным FIN, и клиент получает `EOF` вместо `ECONNRESET`. На стенде это
давало ~14% ложных падений `TestRSTGivesConnectionReset`, а хуже того —
подрывало сам смысл §8.1, где `rst` и `blackhole` обязаны быть **разными**
наблюдаемыми: `EOF` неотличим от «сервер ответил и попрощался». Замерено на 500
прогонах: чтение перед разрывом убирает гонку полностью (0 из 500 против 13 из
500). Выбран консервативный вариант — дождаться первого байта и только потом
рвать. Наблюдаемое клиента не изменилось (первое, что он получает, — RST, и
никогда не данные), а молчащего клиента разблокирует `Close` стенда, ровно как в
`blackhole`. Реальный потребитель — VLESS-клиент Xray — всегда говорит первым,
поэтому «немедленность» на нём неотличима.

**C21. Бюджет T9/T11 берётся подтверждающей пробой, а не таймаутом трафика.**
§8.3 даёт пять секунд от отказа узла до переключения, а §6.3 требует двух неудач
из трёх. По периодам ярусов §6.5 это две пробы активного узла, то есть минута.
Закрыто двумя вещами: `ScheduleConfig.ConfirmDelay` подтягивает срок отказавшего
узла горячего яруса к 500 мс вместо периода яруса, а `ProbeTimeout` (2 с)
снимает зависшую пробу — без него `blackhole` держал бы ярус вечно. Смерть,
увиденную трафиком (§6.15), выбор замечает через `Monitor.SetOnDeath`: трафик
идёт вне расписания. Политика `confirm_probe`, охранники — T9 и T11 в
`internal/supervisor`.

Что здесь осталось нечестным: отсчёт пяти секунд идёт от первой неудачной пробы,
а не от самого отказа узла. Между отказом и первой пробой лежит период активного
яруса — до 30 секунд, если в этот момент через узел не идёт трафика. Трафик этот
разрыв закрывает (его ошибки идут в то же окно), но молчащий клиент за
blackhole-узлом узнает о переключении позже бюджета. Закрыть до конца можно
только детектором зависшего потока на датаплейне; в v1 не делаем — §4 не просит,
а цена — состояние на каждый поток.

### Найдено при сверке регистра решений со спекой (пас 0)

**Пакеты v1 неподписанные, и двойным кликом они не ставятся.** Решение
«настоящие пакеты под три ОС» столкнулось с §4, который выносит Developer ID и
нотаризацию за v1. Совместить буквально нельзя: скачанный `.pkg` без нотаризации
Gatekeeper не пропустит, неподписанный MSI ловит SmartScreen. Консервативный
вариант — оставить исключение §4 в силе, а пакеты собирать настоящими и ставить
из командной строки: `sudo installer -pkg` и `msiexec /i` идут мимо обеих
проверок. Цена записана в §4 прямо: строка установки — часть инструкции, а не
удобство. Отказываться от `.pkg` в пользу tarball было бы хуже — `postinstall`
даёт регистрацию демона (§5.10) и автозапуск (§6.13), которые иначе пришлось бы
писать скриптом трижды. Проверяется I1 на чистой машине; если ОС всё же упрутся,
выбор возвращается (записано в этапе 9 плана).

**Bypass через сокет агента — это NAT.** Решение «сокет, привязанный к
дефолтному интерфейсу» на Linux не реализуемо в заявленном виде:
`SO_BINDTODEVICE` требует `CAP_NET_RAW`, а §6.8 уже отказался на это полагаться.
Находка в том, что привязка там и не нужна — правило с UID-диапазоном уводит
мимо TUN-таблицы весь трафик агента. Но ОС подставляет в исходящий пакет свой
адрес, а сохранить адрес клиента можно было бы только raw-сокетом, то есть снова
`CAP_NET_RAW`. Значит обратный путь идёт через таблицу трансляций — ту же, что
UDP full-cone. Для обнаружения служб (§6.10) этого достаточно; прозрачным
форвардом bypass не является, и §6.8 теперь это говорит.

**Стартовый бюджет §5.6 не имел своего значения в `TunnelState.phase`.** Всплыло
при разделении фазы на две. Спека описывает состояние «ни один узел не проверен,
трафик ждёт» и отводит ему 30 секунд, но перечисление §2 его не содержало:
`status` в эти секунды показывал бы либо `up`, либо `failing`, и оба ответа
неверны. Добавлено значение `waiting`. Не отклонение от спеки, а её внутреннее
противоречие, найденное при правке.

**Нумерация §7 содержала два пункта «3», и `PLAN.md` ссылался на неё со
сдвигом.** Список открытых вопросов получил пункт про лицензию первым уже после
того, как таблица привязки к этапам в плане была написана, — с тех пор её номера
указывали не на те вопросы. Оба файла приведены к нумерации §7 в нынешней
редакции; в таблице плана закрытые вопросы помечены прочерком вместо номера,
чтобы сдвиг не повторился.

### Этап 7 — стор и подписки

**Таблица `user_id` §6.16 заполняется только для четырёх протоколов из шести.**
Ключ слияния читает `user_id` из `params` по таблице §6.16, но разбор ссылок
кладёт туда `uuid`, `password` и `method` только для vless, vmess, trojan и
shadowsocks — ровно для тех, что умеет наша сборка Xray. У hysteria2 `auth`
лежит в userinfo ссылки, у wireguard публичный ключ пира — в своём поле, и
построчный разбор их не достаёт: эти протоколы всё равно уходят в узлы с
`supported: false`. Следствие — два узла hysteria2 на одном `host:port` с
разными учётными данными сливаются в один, потому что ключ вырождается в
`protocol + server + port`. Вырождение само по себе законно (§6.16 называет его
прямо), но здесь его причина не «поля нет у протокола», а «мы его не разбираем».

Консервативный вариант — оставить как есть: неподдержанный узел не пробуется и
не выбирается (§6.11), истории проб у него нет, и терять слиянию нечего. Цена
ограничена списком узлов: провайдер отдал два, показали один. Чинится в тот же
день, когда hysteria2 или wireguard попадут в сборку Xray, — тогда их разбор
станет обязательным по другой причине, и таблица §6.16 заработает целиком.
Отдельная проверка на это не написана намеренно: она закрепила бы нынешний
пробел разбора как ожидаемое поведение.

**Два узла с одним `merge_key` в одной группе переживает только первый.** §6.16
задаёт ключ и молчит о том, что делать, если он совпал у двух узлов уже лежащих
в сторе. Такое возможно как след прежней ошибки или правки самого правила.
Решение: карта ключей хранит первый, второй неотличим от него и уходит в
`Removed`. Причина — карта иначе не строится, а выбирать между двумя
неразличимыми узлами всё равно не по чему. В группе `manual` случай невозможен
по Р10: ключа там нет вовсе.

**S37 проверен с одной стороны шва, и это не обойти внутри этапа 7.** Регистр
требует, чтобы восстановленный из файла узел в состоянии `alive` не считался
проверенным: иначе fail-close §5.6 не наступит там, где обязан. Проверка
отнесена к `internal/store`, но само утверждение — про `health.Manager`, а у
него нет никакого API засева состояния: `Config.Nodes` принимает только
`{ID, Supported}`, а `probed` выставляется исключительно внутри
`nodeState.record()`. Сквозная проверка потребовала бы функции восстановления в
`internal/health`, то есть правки зелёного этапа 5 ради теста этапа 7.

Сделано: стор доказывает свою половину — восстановленный срез приходит с пустым
окном и нулевым `traffic_failures`, и в `health.json` нет поля, которым «узел
уже пробовали» дошло бы до живости вообще. Отсюда `probed == false` по
собственному правилу `health`. Вторая половина — что живость действительно не
считает такой узел проверенным — остаётся за этапом С, где связка соединит стор
с менеджером; там же ей место и по §3.4, потому что соединяет их `agent`, а не
любой из них сам. Не за этапом 8: тот про L3 и защиту от петли.

Цена записана честно: пока связки нет, между «стор отдаёт пустое окно» и
«fail-close наступает» лежит непроверенный стык. Он единственный в этапе, где
восстановленное состояние может соврать, и потому вынесен сюда, а не оставлен в
списке §9 регистра.

### Этап С — связка

**`health` не умел менять набор узлов, и §5.8 из-за этого не выполнялся.**
`Manager` принимал узлы только в `New`. Обновление подписки означало бы
пересоздание менеджера, то есть обнуление окна, `rtt` и состояния всех узлов —
той самой истории, ради сохранения которой §5.8 отказывается от полной замены.
Стор при этом честно сохранял бы `id` на диске, а живость начинала бы с нуля
каждые несколько часов, и снаружи это выглядело бы как работающий diff.

Добавлен `Manager.SetNodes`: оставшийся узел сохраняет `nodeState` целиком,
исчезнувшие уходят, порядок берётся из нового набора (Р8). Единственная правка
зелёного этапа 5 за весь этап С, и она чистое дополнение — ни одна из 43
проверок этапа 5 не менялась.

**Первая редакция `SetNodes` внесла гонку данных.** Она мутировала
`nodeState.node` под замком менеджера, но `Manager.probe` читает `s.node.ID`
**вне** замка — по построению: проба идёт в сеть, и держать на ней замок нельзя.
Нашёл `go test -race`, не чтение. Консервативная починка: живой объект не
мутируется вовсе, заводится копия с той же историей и склонированным окном.
Проба, оставшаяся в полёте, допишет результат в осиротевший объект и потеряет
его. Цена — одна потерянная проба на изменившийся узел при обновлении подписки,
то есть один раунд; альтернатива — гонка в модуле, на котором держится
автопереключение.

**Таймер дренажа заводился внутри горутины.** Потолок §5.8 отсчитывался поэтому
не от смены набора узлов, а от того момента, когда планировщик доберётся до
горутины. На настоящих часах это незаметная неточность, которая не нашлась бы
никогда; на фейковых — прямой отказ проверки W21. Таймер заведён синхронно в
`swap`.

**Охраняющие проверки в первой редакции были зелены при обоих состояниях
флага.** Написаны ветвлением: «политика включена — проверяем хорошее, выключена
— проверяем плохое». Это ровно тот дефект, ради которого существует `negcheck`,
и он назвал семь проверок из восьми. Правило §8 требует не «тест знает про
флаг», а «тест краснеет без политики». Переписаны безусловными утверждениями.

Следствие, которое пришлось внести в продукт: с выключенным `xray_drain` прежний
инстанс Xray закрывается **синхронно** в `swap`, а не горутиной. Иначе
охраняющая проверка зеленела по расписанию планировщика, а не по существу. И W18
смотрит на само соединение, а не на флаг `closed`: §5.5 обещает соединение.

**`hop bypass --on` снимает туннель, а не разворачивает трафик внутри него.**
§5.6 говорит «осознанно выпускает трафик напрямую» и не говорит как. Второй
вариант — оставить интерфейс и гнать весь трафик в bypass-сокет — означал бы,
что весь трафик машины идёт через NAT пользовательского процесса (§6.8), который
для этого не строился. Цена выбранного варианта заметная и записана в регистре:
в состоянии `bypass` фаза туннеля равна `down`, и снаружи это выглядит как «VPN
выключен», поэтому `status` обязан объяснять разницу словами.

**Резолвер этапа С отвечает SERVFAIL, а не молчит.** Настоящий резолвер — этап
6, но связке надо что-то подставить уже сейчас. Молчание подвесило бы приложение
до таймаута — то, что запрещает §5.6. Пустой `NOERROR` хуже: он означает «имени
нет», приложение кэширует отрицательный ответ и не повторит запрос, когда этап 6
приедет. Следствие: до этапа 6 связка не резолвит имён, и её датаплейн
проверяется по адресам.

**`PacketDevice` не закрывается агентом.** §3.2 даёт ему чтение, запись и MTU —
закрывать нечем, и это правильно: устройством владеет тот, кто его выдал.
`Transport.Release` снимает туннель и закрывает устройство одним вызовом.

**§2 иллюстрировал разделение фаз невозможной комбинацией.** Пас 0 обосновал две
фазы примером «туннель `orphaned`, а трафик `bypass`». Такой не бывает:
`orphaned` означает отсутствие агента, а `bypass` держит агент и на диск не
пишет (§5.6) — реаттачившийся агент приходит без обхода. Довод от замены примера
не меняется, он в разных владельцах и в §5.2. Пример заменён на «`up` +
`failing`» — туннель поднят, живых узлов нет; истинны обе половины.

**Номер решения `Рn` сам по себе двусмыслен — всегда указывать регистр.**
Обнаружено при сверке этапа С. Серий две, и они пересекаются:

- регистр решений паса 0 (тот, что закрывался выбором в артефакте) — `Р1–Р26`;
- регистры верификации, где нумерация задумывалась сквозной, — `Р1–Р6`
  автопереключение, `Р7–Р14` стор, `Р15–Р26` DNS, `Р30+` связка.

Отсюда `Р15`–`Р26` означают разное в зависимости от того, какой документ имелся
в виду: `Р22` — это и «насколько живуч `hop bypass --on`» (пас 0), и «bootstrap
ходит на настроенные апстримы, а не на системные» (DNS). Один такой промах уже
случился в этих заметках и был исправлен.

Переименовывать серии задним числом дороже, чем ссылаться полностью: ссылка вида
«Р22 регистра решений» или «Р22 регистра DNS» однозначна и ничего не ломает.
Правило — всегда с названием регистра; голый номер считать опечаткой.

**Стартовое окно §5.6 отвечало RST вместо ожидания.** Нашлось рецензией со
стороны, а не проверкой: первая редакция регистра связки отнесла W33 к свойствам
`netstack` и не написала её. Шов лежал ровно в связке: `Healthy()` возвращает
`true` в стартовом окне, поэтому вердикт — `Proxy`, диалер идёт за активным
узлом, не находит его и отдаёт ошибку, а `netstack` превращает любую ошибку
дозвона в RST. То есть §5.6 нарушался ровно тем способом, который он сам и
называет: «иначе первое же приложение получает RST в те секунды, пока идёт
стартовый обход подписки».

Починка не могла быть ожиданием в диалере: он вызывается из обработчика
форвардера, то есть с цикла чтения устройства, и ожидание в нём остановило бы
весь туннель. Введена `netstack.ErrNotReady`: в стартовом окне диалер отдаёт её,
а `netstack` не отвечает на SYN вовсе — `Complete(false)` вместо
`Complete(true)`. Ожидание держит TCP клиента, а не наша горутина, и повтор SYN
приходит сам. Молчание здесь §5.6 не нарушает: тот запрещает молчание там, где
решение принято, а в стартовом окне оно ещё не принято. Проверка — W33.

### Этап С — шов с ОС (`cmd/hop`)

**`cmd/hop` оставался заглушкой этапа 2 и после того, как связка была
написана.** Коммит связки добавил три тысячи строк в `internal/agent` и ни одной
в `cmd/hop`. «Первый настоящий `hop up`» произошёл в `harness_test.go`, а не в
бинаре: собранный `hop` не содержал ни одного символа Xray, netstack, `agent`
или `store` — проверяется `go tool nm`. Датаплейном оставался `drain`, читавший
устройство и выбрасывавший прочитанное, при том что `hopd` заворачивал в туннель
весь трафик машины. То есть `hop up` означал не «трафик мимо прокси», а чёрную
дыру.

Нашлось не проверкой и не рецензией, а жалобой на рабочие конфиги, которые «не
идут через прокси». Ни один уровень регистра этого поймать не мог: L1 и L2
проверяют `internal/agent` на фейках, L3 этапа 8 ещё не написан, а связь «пакеты
модулей зелены» → «продукт работает» не проверял никто. Вывод для регистра: у
каждого этапа, кончающегося бинарём, обязана быть проверка на самом бинаре, и
она не бывает L1.

**`AgentUID` уходил нулём.** `cmd/hop` собирал `tunnel.Params` без этого поля, и
правило §6.8 раскладывалось как `uidrange 0-0` — то есть выводило мимо туннеля
трафик root, а не агента. При заглушке это было незаметно: агент никуда не
ходил. При живом датаплейне трафик Xray к узлу возвращался бы в туннель петлёй.
Правило §6.8 при этом выглядело выполненным — оно стояло в `ip rule`. Проверка —
W36, и она смотрит на число, потому что поведение здесь наблюдаемо только с
поднятым TUN.

**Проба засчитывалась дважды.** §6.7 требует, чтобы проба шла через outbound
проверяемого узла, а отказ дозвона на уровне системного диалера Xray уже уходит
в `ReportFailure` (`internal/engine/dialer.go`). Значит один провал пробы
попадал бы и в окно проб, и в счётчик ошибок трафика, а §5.4 требует **двух
разных** счётчиков: узел умирал бы вдвое быстрее порога §6.3 — в ту сторону,
которую `classify.go` сам называет худшей. Решение Р38: контекст пробы
помечается (`engine.WithProbe`), и `nodeDialer` по метке молчит. Отменяется
рассылка, а не классификация: вердикт по-прежнему возвращается вызывающему,
иначе проба не отличила бы смерть узла от отказа целевого хоста. Проверки — W37
в `engine` (близнец `TestDeadNodeGivesFatalVerdict`, разница ровно в метке) и
W37 в `agent`.

#### Deviations

**§5.5 в части разрыва соединений не выполняется в продукте.**
`health.Config.Interrupt` оставлен пустым: разрыв активных соединений при смерти
узла требует от `netstack` учёта живых потоков, а `flowTable` хранит вердикты,
не соединения, и `tcpStack` не ведёт реестра релеев. Это не новая дыра — W8 и
W14 красны в регистре с самого этапа С, — но до сих пор она была теоретической,
а теперь наблюдаема: при смерти узла установленные соединения повиснут до
таймаута вместо RST. Консервативный выбор здесь — оставить поле пустым, а не
подсунуть заглушку, возвращающую ноль: ноль означал бы «рвать было нечего», и
`interrupted_connections` в событии переключения врал бы вместо того, чтобы
отсутствовать. Закрывается вместе с W8/W14, реестр релеев — работа этапа 8, где
`netstack` и так переписывается под настоящий TUN.

**Закрыто.** См. ниже, «Этап 8 — реестр релеев netstack и разрыв соединений».

**Датаплейна на Windows нет.** Устройство там приезжает именованной трубой, а не
дескриптором (`ipc.Result.FD` всегда -1), и труба — работа этапа 8 вместе с
`wintun.dll`. `openDevice` на Windows отказывает named-ошибкой, а не отдаёт
заглушку: молчаливая заглушка означала бы ровно тот дефект, ради которого этот
этап делался, — «`hop up` прошёл, трафика нет».

### Этап 8 — реестр релеев netstack и разрыв соединений (§5.5, W8/W14)

Контракт снаружи был закрыт с этапа С и ждал только вызывающей стороны:
`health.Config.Interrupt` — `func() int`, и `emitLocked`
(`internal/health/manager.go:687`) зовёт его ровно при `reason: dead`, уже после
того, как `m.active` под тем же локом переехал на новый узел. Внутри `Interrupt`
поэтому не нужно решать, «чьи» соединения рвать: к моменту вызова `Active()` уже
отдаёт новый узел, а узел соединения фиксирован на дозвоне и не меняется (Р30,
`internal/agent/dialer.go:32`). Не хватало только того, что рвать:
`tcpStack.pipe` (`internal/netstack/tcp.go`) заводило на каждое TCP-соединение
два `io.Copy` и `stop()`, но не сохраняло ни то, ни другое.

**Решение.** Реестр открытых релеев в `tcpStack` — карта `*tcpRelay` под своим
мьютексом. Запись встаёт в `pipe` до старта горутин-насосов и снимается изнутри
того же `stop()`, которым релей закрывается и естественным концом потока (любая
сторона умолкла). `tcpStack.closeAll()` берёт снимок карты под локом и зовёт
`stop()` по снимку уже вне лока — иначе `removeRelay` внутри `stop()` дал бы
взаимную блокировку самим собой. `Stack.InterruptTCP()`
(`internal/netstack/netstack.go`) — тонкая обёртка наружу.
`Agent.InterruptConnections()` (`internal/agent/wire.go`) отдаёт 0, если стек не
поднят (агент в `Down`), и делегирует в `InterruptTCP` иначе; `cmd/hop/main.go`
подключает его в `health.Config.Interrupt` тем же приёмом отложенного замыкания,
что уже стоял у `Prober` (`var a *agent.Agent` объявлена до сборки живости,
потому что оба поля зовут метод ещё не собранного агента).

UDP в реестр не входит: SPEC и регистр (T9, T10, W8) говорят конкретно про TCP,
и `natTable` (`internal/netstack/udp.go`) им не тронут — то же расширение тем же
приёмом осталось следующим шагом, не этим.

**Чего не хватало для проверки и что построено.** Ни A18 (`internal/health`), ни
T9/T10 (`internal/l2`, `TestT9BlackholeBreaksLiveConnection` и сосед) не
проходят через настоящий `tcpStack.pipe` — оба рвут через стенд
(`harness.interrupt()` в `internal/l2/harness_test.go`, чей комментарий прямо
говорит: «в продукте это делает netstack; здесь — стенд»), и это остаётся верно:
они проверяют контракт вызова (сколько раз, с какой причиной), а не сам реестр.
Недостающая проверка — новый `internal/netstack/interrupt_test.go`: второй,
настоящий `gvisor`-стек (`gstack.Stack` с собственным `LinkEndpoint`) по другую
сторону того же `packettest.FakeDevice`, что и остальные тесты пакета — мост не
граница ОС (`internal/bench`), потому что важно настоящее TCP-рукопожатие через
`tcp.Forwarder`, а не сама труба. `fakenet.Dialer.DialTCP` отдаёт эхо-соединение
— им и доказывается, что реле живо (данные ходят) до `InterruptTCP`, а не только
«дозвон случился». Три теста: `TestInterruptTCPClosesLiveConnection` (одно
соединение, эхо, разрыв, клиент видит закрытие),
`TestInterruptTCPCountsAllOpenRelays` (три соединения, счёт и разрыв всех, не
первого попавшегося) и `TestInterruptTCPWithNoConnectionsReturnsZero` (рвать
нечего — не ошибка). `FakeDevice` получил маленький публичный метод `Written()`
— тот же канал, которым уже жил `WaitEmitted`, но для стенда, которому нужен
непрерывный насос, а не разовое ожидание известного числа пакетов.

Закрывает W8 и W14 (`docs/verification-agent.md:310,321`).

### §6.8 переписан по замеру, а не по рассуждению

**Спека утверждала неверный факт, и на нём стоял выбор механизма.** §6.8
говорил, что `SO_BINDTODEVICE` требует `CAP_NET_RAW` и потому непригоден
непривилегированному агенту, а значит на Linux нужен `ip rule` с UID-диапазоном.
Оба утверждения не выдержали замера.

Замерено под uid 1000 без capabilities (ядро 7.1.5), дважды и независимо:

| операция                                     | результат |
| -------------------------------------------- | --------- |
| `SO_MARK`                                    | `EPERM`   |
| `SO_BINDTODEVICE`, свежий сокет              | работает  |
| `SO_BINDTODEVICE`, повторно на том же сокете | `EPERM`   |
| `SO_BINDTODEVICE`, отвязка                   | `EPERM`   |

Ядро проверяет `CAP_NET_RAW` только когда `sk->sk_bound_dev_if` уже ненулевой.
Первая привязка разрешена всем — а это ровно тот режим, в котором привязку
применяют все изученные реализации: в `Control`-колбэке диалера, один раз, до
`connect`.

**Замер при поднятом туннеле** (решающий, делался последним):

```
uid 1000: без привязки → 192.168.0.125    с привязкой → 192.168.0.125
uid 0   : без привязки → 10.255.0.1       с привязкой → 192.168.0.125
```

Читается так. Под root непривязанный сокет уходит через `hop0` — **датаплейн
работает сквозняком**, соединение до внешнего адреса устанавливается через
netstack, диалер, Xray и узел. Привязанный уходит мимо туннеля при активных
туннельных правилах — **привязка годится как защита от петли**. Под uid 1000 в
туннель не попадает ничего: uid-правило §6.8 выводит мимо туннеля весь трафик
пользователя, потому что агент делит uid с рабочим столом.

Последнее и есть та поломка, с которой начался этот заход: «конфиги рабочие, а
трафик не идёт через proxy». Правило §6.8 при этом выглядело выполненным — оно
стояло в `ip rule` и делало ровно то, что написано.

**Ссылка на `sing-tun/tun_linux.go:791` была прочитана неверно.**
`NewRuleUIDRange` служит там пользовательскому split-tunneling'у по приложениям
(на Android uid = приложение). Защитой от петли uid-правило не пользуется ни
один из изученных проектов. У sing-box проксирующий процесс — root, поэтому
uid-правило у них по построению не может быть защитой от петли; nekoray и
hiddify-core, у которых расстановка процессов такая же, как здесь, опознают
трафик своего движка и выпускают его привязанным к интерфейсу аутбаундом.

**Урок для метода, а не только для §6.8.** Раздел был написан связно и
обоснованно, ссылался на настоящий механизм в настоящем чужом коде — и был
неверен в факте, который проверяется двадцатью строками на C. Утверждение вида
«системный вызов требует привилегий» обязано быть замерено до того, как из него
выведен выбор архитектуры.

#### Deviations

**Привязка не накрывает сокеты мимо Xray.** uid-правило выводило мимо туннеля
весь трафик процесса; привязка — только те сокеты, на которых поставлена.
Резолвер bootstrap (§5.7) и скачивание подписок (§5.8) обязаны биндиться своим
`Control`-колбэком. Пропущенный сокет образует петлю молча, и никакая проверка
уровня L1 этого не увидит.

**Перепривязка невозможна.** При смене дефолтного интерфейса установленные
соединения не переносятся — их надо рвать и передозваниваться. Записано в §6.8
следствием первым.

**Нижняя граница по версии ядра не установлена.** Замер сделан на 7.1.5. С какой
версии первая `SO_BINDTODEVICE` непривилегированна — не проверено; на старых
ядрах привязка может отказать, и тогда нужен либо отказ дозвона, либо
capability. Проверять до объявления поддержки дистрибутивов.

### Этап 9 — BypassSink: настоящий NAT-путь для bypass (§6.10, §6.8)

До этого захода `netstack.Config.Bypass` в продукте был `nil`, и `Stack.handle`
(`internal/netstack/netstack.go:259`, вердикт `Bypass`) молча дропал пакет —
единственная оставшаяся дыра, которая лгала о наблюдаемом поведении, а не просто
не реализовывала возможность.

**Решение.** Новый пакет `internal/bypass` — full-cone UDP NAT той же формы, что
`natTable` (`internal/netstack/udp.go`): сокет на исходный `addr:port` клиента,
горутина чтения ответов на каждый сокет, ленивый сметатель простоя на
собственных часах пакета (`clock.Clock`). Отличия от `natTable`, продиктованные
природой bypass: сокет всегда заводится через
`(&net.ListenConfig{Control: cfg.Control}).ListenPacket(ctx, "udp4", ":0")` —
`Control` привязывает его к физическому интерфейсу тем же `SO_BINDTODEVICE`
(§6.8), которым уже пользуются Xray, health-пробы и подписки, — и ключа с
адресом назначения нет вовсе: только `src`, всегда full-cone, потому что ответ
mDNS приходит с unicast-адреса респондера (`192.168.x.y:5353`), а не с адреса
`224.0.0.251:5353`, на который слал клиент. `Send` отказывает двумя разными
ошибками: пакет не IPv4/UDP — `ErrUnsupported`; политика `bypass_sink` выключена
— `ErrDisabled`. Разбор IPv4/UDP вынесен в `internal/packet.ParseUDP4`, отдельно
от `netstack.parse`, чтобы `internal/bypass` не зависел от `internal/netstack`.

Провод: `netstack.Stack.Deliver(pkt []byte)` — обратный путь в устройство через
тот же `s.write`, что и ответы `natTable`/gvisor-релеи (единственный писатель
остаётся один). `agent.Config.BypassControl bypass.ControlFunc` собирает
приёмник в `Up()` тем же отложенным замыканием, что уже стоит у
`InterruptConnections`/`Prober`: `Agent.deliverBypass` берёт `a.mu`, читает
`a.stack`, отпускает и зовёт `stack.Deliver`, если стек ещё жив. Жизненный цикл
`a.bypassNAT` зеркален `a.stack` — заводится в `Up`, закрывается в `Down` и
`watchService`; повторный `Up` после `Down` пересобирает NAT заново, старый
закрытый не переиспользуется. `cmd/hop/main.go` передаёт `physical.Control` (тот
же `*outbound.Selector`, что уже даёт `Interface` и `DialDirect`) третьим
параметром `run()`, симметричным уже существующему `dialDirect` — сам селектор
живёт только в `main()`, поэтому в `run()` идёт уже распакованная функция, а не
сам объект.

Политика `bypass_sink` (`internal/policy`) гасит настоящий приёмник, а не сам
вызов `Send` внутри `netstack.handle`: погасить вызов было бы неверно — тогда
`TestT17MDNSGoesToLocalNetwork` (вердикт-only, `fakenet.Bypass`,
`internal/netstack/netstack_test.go:196`) покраснел бы вместе с политикой, а он
обязан оставаться зелёным всегда, потому что проверяет только вердикт, а не
доставку. Guard-тесты — `TestBypassSendsDatagramFromBoundSocket` и
`TestBypassReplyReturnsToClient` (`internal/bypass`), красные под
`HOP_DISABLE=bypass_sink`.

**Проверка на уровне L3.** `internal/l3/bypass_test.go`,
`TestBypassMDNSReachesPhysicalInterfaceAndReturnsViaNAT` — весь путь
`agent → netstack (вердикт Bypass) → bypass.NAT → физический сокет → обратно`
против настоящего физического интерфейса (veth) в netns, симметрично тому, чем
`interrupt_test.go` стал для W8/W14. Тест форсирует ровно тот случай, который
§6.10 держит в уме как «правило не встало»: правило маршрутизации приоритетом
20000 (`ip rule add to 224.0.0.251/32 lookup <table> priority 20000`) уводит
группу mDNS в туннельную таблицу, и пакет всё равно обязан выйти в LAN — через
NAT-путь, а не через дыру в правилах маршрутизации. Пир (`peerMain`) поднимает
mDNS-респондер, вступающий в группу `224.0.0.251:5353`, и кладёт в ответ и
увиденный адрес источника, и эхо полученной нагрузки. Три независимых
утверждения, каждое своим `t.Fatalf`: пир получил запрос (доказано эхом
нагрузки); адрес источника, увиденный пиром, — адрес физического интерфейса
(`veth0`), а не адрес клиента в туннеле (положительная и отрицательная проверка
разом — это и ловит регресс «форвардит как есть» вместо настоящего NAT); клиент
получил ответ, и пришёл он с адреса респондера.
`HOP_L3=1 unshare -Urn /tmp/l3.test` — 0.17–0.64 с на прогон, три подряд повтора
и полный набор L3 зелёные, включая под `-race`.

**Замеры.**

- Форма правила маршрутизации для mDNS: `ip rule add to 224.0.0.251/32 lookup
  <table> priority N`, где `N` меньше `prioExclusions = 31000`
  (`internal/platform/linux.go:22`), забирает ровно эту группу в туннель, не
  трогая остальной multicast (проверено на SSDP, `239.255.255.250`) и не трогая
  правила, которые раскладывает `hopd` (`31000`/`31500`/`32000`). Проверено не
  только через `ip route get` (кэш маршрута можно спутать с намерением), но и
  счётчиками TX-пакетов на dummy-интерфейсе до/после `sendto` — решение
  маршрутизации действительно исполняется ядром, а не только видно в выводе
  команды.
- Отправка на multicast-адрес не требует членства в группе (IGMP-репорт нужен
  для приёма, не для передачи) — `bypass.NAT` шлёт `WriteTo` на
  `224.0.0.251:5353` без `IP_MULTICAST_IF` и без `IP_ADD_MEMBERSHIP`, и пакет
  всё равно уходит (подтверждено TX-счётчиками из измерения выше). Приём на
  стороне пира требует `IP_ADD_MEMBERSHIP` (`net.ListenMulticastUDP`) — без него
  ядро отбрасывает входящую датаграмму на IP-уровне даже при физическом приходе
  кадра на veth; это стандартное поведение хостового IGMP-членства, не специфика
  veth.
- `net.ListenPacket("udp4", ...)` на Linux отдаёт `*net.UDPConn`, чей `ReadFrom`
  возвращает `*net.UDPAddr` (не строку): прямое приведение типа в
  `bypass.socket` (`a.(*net.UDPAddr)`) обошлось без запасного пути через
  `netip.ParseAddrPort(a.String())`, который есть у `netstack.addrPort` для
  собственных нужд последнего. Проверено самими тестами
  (`TestBypassAcceptsReplyFromAnotherAddress`), на `go1.26.3`/linux — запасной
  путь не понадобился для сокетов, заведённых `ListenPacket` тем же способом.

#### Deviations

**Только UDP.** NAT-путь bypass несёт исключительно UDP; TCP в локальную сеть
(RFC1918, loopback, link-local — вердикт `Bypass` по `isBypass`,
`internal/netstack/verdict.go:119`) остаётся дропом: `bypass.NAT.Send`
отказывает `ErrUnsupported`, `netstack.handle` игнорирует ошибку так же, как и
раньше молчаливый дроп. Причина: §6.10 держит исключения ради обнаружения служб,
которое целиком UDP; §6.8 прямо называет обратным путём bypass ту же таблицу
трансляций, что UDP full-cone §5.3; честный TCP-путь означал бы терминацию
потока в gvisor, а его релей попал бы в реестр разрыва соединений §5.5 (этап 8,
выше), чья семантика «рвём соединения при смерти узла» для bypass-трафика,
никогда не ходившего через узел, неверна. Следующий заход, не забыто, а отложено
осознанно.

**DHCP через NAT-сокет честным быть не может.** Исходный порт клиента-DHCP (68)
переписывается на эфемерный, потому что `bypass.NAT` не сохраняет порт источника
отдельно от адреса, а бинд на порт ниже 1024 непривилегированному агенту
недоступен. DHCP числится в §6.10 среди исключений «мимо туннеля, в локальную
сеть», но настоящий DHCP-обмен через этот NAT-путь недостоверен — записано как
есть, а не умолчано. На практике DHCP самой машины это не задевает (интерфейс
адресуется системой до `hop up`, вне вердиктов netstack); незакрытый случай —
DHCP-relay или иной транзитный трафик на порт 67/68 изнутри туннеля.

**IPv6 mDNS-адрес спеки (`[ff02::fb]:5353`) в `isBypass` не реализован — и не
мог быть, в этом заходе.** §6.10 перечисляет его наравне с `224.0.0.251:5353`,
но `internal/netstack/verdict.go:119` (`isBypass`) сравнивает только с
`addrMDNS` — константой IPv4. Это не пропуск этого захода: IPv6-пакеты вообще не
доходят до `classify()`/`isBypass()` — они отбрасываются раньше, на ветке `!ok`
разбора пакета (`internal/netstack/netstack.go:245`, §6.9, «частично поднятый
IPv6 хуже отсутствующего»). Пока IPv6 в v1 блокируется целиком (до задачи
`ipv6_block` из очереди), IPv6 mDNS недостижим по построению, а не по недосмотру
— записано, чтобы следующая сессия, читая `HANDOFF.json`, не считала эту строку
спеки чем-то, что уже хардкожено в коде и ждёт переноса в конфигурацию.

**Смена интерфейса не инвалидирует уже открытые bypass-сокеты — дыра, а не
решение.** `Control` привязывает каждый сокет `bypass.NAT` к тому, что
`Selector.Interface()` вернул на момент его создания
(`internal/bypass/bypass.go:143`). «Следствие первое» §6.8 говорит прямо:
привязка сокета неизменна, и смена сети означает, что старые сокеты нужно
передозвонить. Ничего этого не происходит: время жизни NAT привязано к `a.stack`
(Up/Down), и переключение Wi-Fi → Ethernet не рвёт ни то, ни другое. Хуже того —
`sock.seen` обновляется на каждый `Send` (`internal/bypass/bypass.go:139`), а не
только на успешный ответ, поэтому клиент, который ретраит mDNS/SSDP каждые
несколько секунд (а служебное обнаружение делает именно так), держит мёртвый по
привязке сокет вечно живым: идлящая уборка (`Idle`, по умолчанию 60 с) до него
никогда не доберётся, потому что для неё сокет никогда не выглядит
простаивающим. Это хуже, чем «отъедет через 60 с простоя» — это «не отъедет
никогда, пока клиент продолжает спрашивать», а трафик тем временем либо уходит
через старый интерфейс, либо ошибается на `WriteTo`. До находки 1 финальной
волны ревью пользователь при этом не видел вообще ничего; после неё — растущий
`Stats.Blocked` без объяснения причины.

Код-фикс не вошёл в тот заход: обработка смены сети была отложенным пунктом
очереди, а расширять заход за пределы BypassSink автор не стал. Две формы,
которыми фикс мог бы стать, назывались там же: `NAT.Reset()`, которым
наблюдатель селектора зовёт при смене интерфейса, либо жёсткий TTL на возраст
сокета, независимый от `seen`.

**Закрыто** заходом «Этап 9 — перепривязка сокетов bypass» ниже, третьей
формой: NAT опрашивает `Selector.Interface()` на каждой отправке и закрывает
сокеты с устаревшей привязкой. Довод об объёме, которым откладывали, при
проверке не подтвердился — наблюдатель rtnetlink трогать не пришлось вовсе;
разбор там же.

**Full-cone bypass принимает ответ с любого адреса — известное и допустимое
свойство, не регрессия.** Потому что `bypass.NAT` full-cone (§5.3 требует этого
для UDP), любой, кто достанет до эфемерного bypass-порта агента по локальной
сети, может впрыснуть в туннель датаграмму с произвольным адресом источника,
включая адрес внутри туннеля, — `receive` (`internal/bypass/bypass.go:160`)
принимает `ReadFrom` с любого пира и переизлучает его адрес как есть. `natTable`
при `nat_key=src` (`internal/netstack/udp.go`) настолько же открыт — это
свойство модели, а не то, что внесла эта задача, и поведение не меняется.
Дешёвое усиление, названное ревью: отбрасывать ответы, чей адрес источника
совпадает с адресом самого клиента туннеля, — не сделано в этом заходе, записано
как принятое свойство, а не незамеченное.

Closes: `next_task` из `HANDOFF.json` (BypassSink, приоритет 1).

### Этап 8 — списки bypass/block §6.10 из конфигурации (`routing_lists`)

`isBypass` и `isBlocked` (`internal/netstack/verdict.go`) были кодом, а не
данными: диапазоны через `netip.Addr.IsPrivate` и соседей, порты через `switch`,
адреса mDNS и SSDP — константами пакета. Расширить набор (принтер в
CGNAT-диапазоне провайдера, корпоративная подсеть за пределами RFC1918) или
сузить его (в сети нет ни одного устройства Bonjour) было нельзя иначе как
правкой `verdict.go`.

**Решение.** `internal/netstack/routing.go`: `Rule` — правило «префикс +
протокол + порт», где ноль в поле значит «любой», и `Routing` — два списка,
`Bypass` и `Block`. `netstack.Config.Routing *Routing` (`nil` — умолчания
§6.10), `agent.Config.Routing` — тот же провод одним полем выше. Форма
подсмотрена у `Config.DNSUpstreams`: значение конфигурации, у которого пустота
означает умолчание, и до которого CLI и диск ещё не доросли. `classify`
принимает списки третьим параметром и остаётся чистой функцией; `flowTable`
держит разрешённые списки у себя, потому что вердикт принимается один раз на
поток (§3.4), и список, поменявшийся посреди жизни потока, нарушал бы контракт
незаметнее, чем сама смена списка.

**Что настраивается, а что нет.** Пол — исключения §5.6 «разрешённые всегда»
(локальные сети, DHCP, NTP): `resolveRouting` подмешивает их к любому непустому
списку, и убрать их конфигурацией нельзя. Довод: §5.6 обещает, что без них
fail-close ломает саму сеть, а не только выход в интернет, — и это обещание
относится и к неудачному конфигу, а не только к фазе. Ровно тот же довод стоит
за порядком в `classify`: `bypass` проверяется раньше `block`, поэтому список
блокировок из конфигурации не может перекрыть DHCP. Обнаружение служб §6.10
(mDNS, SSDP) — умолчание, а не пол: §5.6 их не перечисляет, они стоят в §6.10
рядом со словом «блокировать нельзя» ради Bonjour и AirPrint, и у того, у кого
в сети нет ни одного принтера, есть право не выпускать multicast мимо туннеля.
Объём взят из формулировки PLAN.md — «списки bypass/block §6.10 всё ещё
захардкожены… и должны приходить из конфигурации», то есть оба списка целиком, —
а не из одного набора адресов обнаружения служб.

Пользовательские split-префиксы сюда по-прежнему не относятся: PLAN.md говорит,
что они идут в правила маршрутизации, а не в вердикт `bypass`, потому что
`bypass` — это NAT через сокет агента, а не прозрачный форвардинг.

**Политика `routing_lists`** гасит чтение конфигурации целиком: с выключенной
политикой `resolveRouting` возвращает `DefaultRouting()` и стек ведёт себя ровно
как до этой задачи. Именно поэтому `TestT17MDNSGoesToLocalNetwork` и T31
(`internal/l3/bypass_test.go`) зелены при обоих её состояниях — они гоняют
умолчания, а умолчания совпадают с прежним жёстким набором один в один, — и
охраняют политику три новых теста: `TestRoutingBypassListComesFromConfig`,
`TestRoutingConfigCanDropServiceDiscovery` и `TestT32ConfiguredBypassLeavesTunnel`
(§8.3).

T32 стоит на стенде с fail-close (живых узлов нет) намеренно: утверждение
«конфигурация вывела поток в локальную сеть» проверяется в самой сильной форме —
вопреки закрытому §5.6 туннелю, — и заодно даёт ожидание с заведомым концом.
`fakenet.Bypass.WaitPackets` ждёт вечно, и охраняющий тест, построенный на нём,
при выключенной политике не краснел бы, а висел бы до таймаута `go test`;
`FakeDevice.WaitEmitted` (2 с) такого недостатка не имеет, поэтому синхронизация
идёт через второй пакет, ответ на который стек пишет в устройство. Тот же приём
уже стоит в `TestBypassSendErrorCountsAsBlocked`.

**Отклонение: блокируется `224.0.0.0/4`, а §6.10 пишет `224.0.0.0/3`.** Прежний
код блокировал multicast через `netip.Addr.IsMulticast`, то есть ровно
`224.0.0.0/4`; `/3` захватывает вдобавок зарезервированный `240.0.0.0/4`,
который не блокировался никогда. Выписывая список данными, легко было бы
«заодно» расширить блокировку до буквы спеки — и спрятать изменение поведения
внутри перевода кода в данные. Выбран консервативный вариант: умолчание
повторяет прежнее поведение один в один, расхождение с текстом §6.10 записано
здесь. Кому нужна буква — дописывает `240.0.0.0/4` в `Block` конфигурацией, и
это ровно то, ради чего список стал настраиваемым.

**Отклонение: пол §5.6 выписан префиксами IPv4 и для IPv6 не эквивалентен.**
`IsLoopback`, `IsPrivate` и `IsLinkLocalUnicast` знают и про `::1`, `fc00::/7`,
`fe80::/10`; список из `127.0.0.0/8`, RFC1918 и `169.254.0.0/16` — нет. Разницы
сегодня не существует: IPv6 до `classify` не доходит вовсе, он блокируется
раньше, на ветке `!ok` разбора (`netstack.go`, §6.9), и это расхождение спеки и
кода уже записано отдельно. Втягивать IPv6 в эту задачу молча было бы хуже, чем
оставить след: `Rule.matches` сравнивает через `netip.Prefix.Contains`, который
для чужого семейства всегда `false`, — то есть список IPv4 не может случайно
выпустить IPv6 мимо туннеля, когда IPv6 до вердикта доберётся
(`TestRoutingIPv4RuleDoesNotMatchIPv6` фиксирует это заранее).

**Отклонение: «конфигурация» пока кончается на `agent.Config`.** Ни CLI, ни диск
списки не задают — источник только программный, как и у `Config.DNSUpstreams`,
которое `cmd/hop/main.go` тоже не выставляет. Это половина провода, и названа
она половиной намеренно: вторая половина (формат на диске, команда CLI, валидация
пользовательского ввода) — вопрос §5.9 и стора, а не вердикта, и делать её вместе
с переводом списка в данные значило бы решать два вопроса одним заходом.

Closes: `next_task` из `HANDOFF.json` (списки §6.10 из конфигурации, приоритет 1).

### Этап 9 — RST для TCP в локальную сеть (`bypass_tcp_reject`)

Последнее место, где вердикт лгал о судьбе пакета. `classify` выдавала `Bypass`
для TCP-потока на RFC1918/loopback/link-local (правила `alwaysBypass` выписаны
без протокола и совпадают и с TCP), `handle` отдавала пакет в
`s.cfg.Bypass.Send`, а `internal/bypass` отвечал `ErrUnsupported` на всё, что не
IPv4/UDP. Итог — `Stats.Blocked` и молчаливый дроп: приложение висело до своего
`connect timeout`. Ровно тот отказ, про который §5.6 пишет «закрытие — отказ, а
не молчание», и ровно тот, который прошлый заход (BypassSink) отложил осознанно,
назвав `internal/reject` правильным ответом.

**`reject.Reply` здесь ответить не может — и это не деталь, а суть задачи.**
`Reply` первым делом спрашивает `Excluded`, а `Excluded` возвращает `true` для
любого локального адреса (`isLocal`: loopback, RFC1918, link-local, multicast,
broadcast). То есть на TCP SYN в `192.168.1.10:445` `Reply` возвращает `nil`.
Два списка отвечают на разные вопросы: `Excluded` — «на что респондер §5.6 не
имеет права отвечать» (там пакет не отвергнут, он просто не наше дело), вердикт
`Bypass` — «что выпустить в локальную сеть». В точке, где путь bypass отвергает
поток, второй вопрос уже решён, и первый список молчал бы там, где отказ и нужен.

**Решение.** `reject.RST(pkt)` — тот же `tcpRST`, что у `Reply`, без вопроса про
`Excluded`: строит RST для TCP-сегмента и `nil` для всего прочего (не TCP, мусор,
сам RST — иначе петля). Никакой политики внутри: кому отвечать, решает
вызывающий. Второй копии построителя RST в продукте по-прежнему нет.
`netstack.refuseBypassTCP` зовёт его под флагом `bypass_tcp_reject` и считает
ответ в `Stats.Rejected`; `nil` и выключенный флаг остаются дропом в
`Stats.Blocked` — молчание обязано быть наблюдаемым, а не бесследным. Шов между
двумя списками закреплён с обеих сторон: `TestBypassTCPNeedsRSTBecauseReplyStaysSilent`
(`internal/netstack`) и `TestRSTAnswersWhereReplyStaysSilent` (`internal/reject`)
утверждают разом, что `Reply` молчит, а `RST` отвечает, — «упрощение» обратно к
`Reply` вернёт молчаливый дроп и покраснеет не только T33, но и объяснение
причины.

**Проверка стоит до `Send`, а не после его `ErrUnsupported`.** Иначе отказ
зависел бы от того, есть ли приёмник вообще (в продукте до этапа 9 его не было,
в половине тестов его нет — `cfg.Bypass == nil`) и какой именно ошибкой он
ответил. «Bypass не несёт TCP» — утверждение уровня вердикта, вытекающее из
§6.8: обратный путь bypass есть та же таблица трансляций, что у UDP full-cone
§5.3, и TCP по ней не пройдёт ни при каком состоянии сокета. Поэтому оно и
живёт на уровне вердикта, а doc-комментарий интерфейса `BypassSink` теперь
говорит это прямо: реализации не нужно уметь отказывать по протоколу.

#### Решение: UDP, отвергнутый bypass, ICMP unreachable не получает

Вопрос был поставлен явно, ответ — **нет**, дроп со счётчиком `Stats.Blocked`
остаётся. `TestBypassSendErrorCountsAsBlocked` не меняет ожидания. Четыре довода,
от сильного к слабому.

**Первый: RFC 1122 §3.2.2 это запрещает.** ICMP-ошибку нельзя порождать в ответ
на датаграмму, адресованную broadcast- или multicast-адресу. А трафик, ради
которого путь bypass вообще существует, — это mDNS (`224.0.0.251`), SSDP
(`239.255.255.250`) и DHCP (`255.255.255.255`): весь он адресован ровно туда.
Отвечающий ICMP на mDNS-запрос нарушал бы стандарт в подавляющем большинстве
случаев, когда бы он срабатывал. Тот же инстинкт уже закодирован в
`reject.isLocal`, который заносит multicast и broadcast в исключения.

**Второй: это был бы неверный ответ, а не просто лишний.** `ICMPv4PortUnreachable`
означает «на том конце никто не слушает этот порт». Про принтер в локальной сети
мы этого не знаем и знать не можем: не слушает не он, а наш сокет не завёлся.
Отказ, сообщающий неправду о третьей стороне, хуже молчания — он уводит
диагностику в сторону, тогда как RST на TCP-в-LAN говорит правду о нашем
собственном пути.

**Третий: подвешивать здесь нечего.** §5.6 обосновывает «отказ вместо молчания»
именно тем, что молчаливый дроп подвешивает приложения до таймаута. TCP-в-LAN —
буквально этот случай: `connect` висит десятки секунд. Служебное обнаружение —
противоположный: mDNS и SSDP по построению без установления соединения,
периодические и ретраящиеся, никто их не ждёт с секундомером. Спасать от
таймаута нечего, потому что таймаута нет.

**Четвёртый: отказ здесь непостоянен, а RST для TCP — постоянен.** Причины, по
которым `Send` возвращает ошибку, — `ErrDisabled` (политика `bypass_sink`
выключена), `outbound.ErrNoInterface` (физического интерфейса сейчас нет),
ошибка `WriteTo`. Все три переменны во времени: интерфейс вернётся через
секунду. Ответить ICMP на такое значит превратить временную неготовность в
жёсткую ошибку у клиента (`net.UDPConn` на connected-сокете отдаёт ICMP наверх
как ошибку соединения). Отказ пути bypass для TCP, наоборот, не изменится
никогда: он следует из формы пути, а не из состояния сети.

Отдельно про `ErrDisabled`: политика `bypass_sink` существует, чтобы её
выключение воспроизводило поведение **до** её появления, то есть молчаливый
дроп. Ответ ICMP под выключенной политикой сломал бы этот контракт и вместе с
ним смысл `negcheck` для неё.

#### Решение: свой флаг `bypass_tcp_reject`, а не `reject_mode`

`reject_mode` не переиспользован. Довод, а не вкус:

- **Его doc-комментарий описывает fail-close** — «fail-close через RST/ICMP, а
  не дроп (§5.6, T12, T13)», — а T33 гоняется на стенде с **живым** узлом.
  Туннель открыт, выход есть, отказ означает «этим путём такой поток не
  пройдёт», а не «выхода нет». Свести их под один флаг — значит либо соврать в
  doc-комментарии, либо расширить его до «все отказы молчат», после чего строка
  T12/T13 «падает без чего» в §8.3 перестанет быть точной.
- **Прецедент рядом и он ровно про это.** `bypass_sink` — тоже флаг пути bypass,
  тоже с молчаливым дропом в выключенном состоянии, и он не стал частью
  `reject_mode`, хотя мог бы по тому же рассуждению. `bypass_tcp_reject`
  наследует ту же линию раздела: `reject_mode` про фазу (fail-close), флаги
  bypass — про путь.
- **`negcheck` теряет разрешающую способность при слиянии.** Guard-набор
  `reject_mode` стал бы объединением двух независимых утверждений, и «краснеет
  без `reject_mode`» перестало бы указывать на одну причину.

Контрдовод, который был взвешен и отвергнут: два флага допускают несогласованную
комбинацию (`reject_mode=drop` при включённом `bypass_tcp_reject` — hop молчит в
fail-close и отвечает в LAN). Он не весит: политики не пользовательская
настройка, а стенд фальсифицируемости, и гасятся они по одной именно затем,
чтобы каждая покраснила свою проверку. Несогласованные комбинации здесь —
инструмент, а не дефект.

Регистрация — `internal/policy/policies.go`, guard — `TestT33TCPToLocalNetworkGetsRST`
(`internal/netstack`), проверен красным под `HOP_DISABLE=bypass_tcp_reject`:
RST не строится вовсе, и тест ждёт полный `WaitTimeout`.

#### Deviations

**`packettest.ExpectRST` и `ExpectICMPUnreach` теперь ждут.** До этого захода они
смотрели только на уже записанное, и это делало их непригодными по назначению:
`Emitted()` осушает очередь, поэтому «сначала `WaitEmitted`, потом `ExpectRST`»
отдавало `nil` из пустоты, а «сразу `ExpectRST`» гонялось с насосом. Оба теперь
ждут до `WaitTimeout` тем же `Written()`-каналом и теми же часами
(`clock.System{}.After`), что и `WaitEmitted`. Поведение для уже записанных
пакетов не изменилось — единственный прежний вызывающий (`fake_test.go`) пишет
пакеты синхронно до вызова и проходит без правок. Изменение чужого пакета внутри
этой задачи — да; альтернатива была бы хуже: третий тест, повторяющий разбор
флагов TCP вручную вместо готового помощника.

**Отказ строится на каждый пакет потока, а не один раз.** Вердикт потока
запомнен (`flowTable`, §3.4), но ответ на нём не кэшируется: ретрансмит SYN,
пришедший до того, как RST дошёл до клиента, породит второй RST. Так же ведёт
себя ветка `Reject` (T12), и это правильнее, чем помнить «уже отвечено»: клиент,
не получивший первый ответ, обязан получить второй.

**TCP-в-LAN, названный bypass из конфигурации, отвергается так же.** Правило
`routing_lists` вида `{Prefix: <публичный префикс>, Proto: ProtoTCP}` даст
вердикт `Bypass`, и поток получит RST, а не выйдет в локальную сеть. Это не
регрессия конфигурируемости, а её честная граница: путь bypass — UDP-NAT (§6.8),
и конфигурация не может подарить ему TCP. До этого захода такое правило молча
дропало пакет, то есть врало ровно так же, только тише.

Closes: `next_task` из `HANDOFF.json` (RST для TCP в локальную сеть, приоритет 1).

### Этап 9 — перепривязка сокетов bypass при смене интерфейса (`bypass_rebind`)

Последняя дыра пути bypass, которая была дырой, а не отложенной возможностью.
`Control` привязывает сокет `bypass.NAT` к тому, что `Selector.Interface()`
вернул в момент его создания, и не перепривязывает никогда. Время жизни NAT
привязано к `a.stack` (Up/Down), а переключение Wi-Fi → Ethernet не рвёт ни то,
ни другое. Наблюдаемый симптом — растущий `Stats.Blocked` без объяснения либо,
что хуже, трафик, уходящий через интерфейс, который пользователь только что
покинул.

#### Выбранная форма и почему не две другие

`HANDOFF.json` предлагал выбрать из двух: `NAT.Reset()`, которым
rtnetlink-наблюдатель `outbound.Selector` толкает NAT при смене интерфейса,
либо жёсткий TTL на возраст сокета.

Взята **третья, и она же первая по существу**: тот же сигнал, но взятый
**опросом**, а не проталкиванием. NAT запоминает имя интерфейса, к которому
`Control` привязал сокет, и на каждом `Send` сверяет его с нынешним ответом
`Config.Interface` — в продукте это `outbound.Selector.Interface`. Разошлись —
сокет закрыт, следующий `Send` заводит новый. Несущий механизм ровно один;
TTL не добавлен.

**Почему это тот же сигнал, а не таймер.** `Selector.Interface()` — не
независимый опрос ОС, а публикуемый ответ того самого rtnetlink-наблюдателя:
`watch` получает `RouteUpdate`/`LinkUpdate`, зовёт `refresh`, и `set` кладёт имя
под `s.mu`. Читая это поле, NAT читает результат события, а не гадает по
времени. Разница с `Reset()` только в том, кто кого будит, и она в пользу
опроса: `Reset()` закрывает все сокеты на **любое** событие наблюдателя (а их
на активной сети много, и почти все — не смена интерфейса), а сравнение имён
срабатывает ровно тогда, когда интерфейс действительно другой.

**Почему не TTL.** TTL лечит симптом — заклинивший сокет, — а не причину, и
цену за это платит вслепую: слишком короткий рвёт исправные обмены, слишком
длинный оставляет окно утечки. Ни одно значение не выводится ни из чего.
Полом под сигналом он тоже не нужен: сигнал не может «не прийти», потому что
его не ждут — его читают на каждом `Send`, то есть ровно в тот момент, когда
устаревшая привязка впервые могла бы навредить.

#### Довод об объёме, которым откладывали, не подтвердился

Прошлый заход записал в `implementation-notes.md` и в `HANDOFF.json`, что
сделать это правильно значит трогать rtnetlink-наблюдатель `outbound.Selector`,
и сослался на «Global Constraint 9, `constraints.md`».

Проверено по существу: **трогать наблюдатель не нужно**. Всё, что дало бы
проталкивание, уже опубликовано — `Selector.Interface()` экспортирован, живёт
под `RWMutex`, обновляется наблюдателем и уже отдаётся связке как
`agent.Config.Physical` (`cmd/hop/main.go` передаёт туда `physical.Interface`).
Заходу понадобилось одно поле в `bypass.Config` и один проброс в
`agent/wire.go`; `internal/outbound` не изменён ни на строку. Иначе говоря,
основанием отложить служил объём, которого у задачи нет: правильная форма
дешевле той, ради дороговизны которой её отложили.

Отдельно: **`constraints.md` в репозитории не существует** — ни в рабочем
каталоге, ни в истории (`git log --all -- constraints.md` пуст на всех ветках).
Ссылка была на несуществующий документ, и именно ею обосновали перенос задачи в
очередь; следующий заход принял её на веру, потому что проверить ссылку дешевле,
чем она выглядит, только если её проверить. Ссылка убрана из `HANDOFF.json`
целиком, а правило, которое она изображала, названо своими словами как
договорённость проходов: **заход закрывает свой пункт очереди и не расширяется
на соседние модули; если правильная форма требует изменить чужой пакет — это
записывается в Deviations с доводом, а не служит основанием отложить задачу
молча**. Именно так поступали предыдущие заходы, меняя `internal/packettest` и
`internal/reject` ради своих задач. Всякую будущую ссылку на источник правила
следует проверять `ls` и `git log --all --` прежде, чем на неё опираться.

#### Решения

**Опрос — до захвата `n.mu`.** `Config.Interface` — чужой колбэк (в продукте
под своим `RWMutex`), звать его под своим замком незачем.

**Закрываются все сокеты с чужой привязкой, а не только тот, за которым
пришли.** Событие общее: интерфейс сменился для всей машины. Оставленный сокет
продолжал бы не только слать через прежний интерфейс, но и принимать на нём
ответы своей горутиной `receive`, отдавая их в туннель, — то есть путь внутрь
пережил бы путь наружу.

**Отсутствие маршрута по умолчанию сменой интерфейса не считается.** `Interface`
вернул ошибку или пустое имя — сравнивать не с чем, сокеты не трогаются. Это
законное переходное состояние ноутбука (§6.8, `outbound.New`: «Interface тогда
возвращает `ErrNoInterface`»), и разрыв живого сокета по нему превратил бы
мгновенную неготовность в жёсткий отказ — тот же довод, которым прошлый заход
оставил UDP-отказ молчаливым. Когда маршрут вернётся под другим именем, сличение
сработает тогда.

**`Config.Interface` не обязателен.** `Control` и `Reply` обязательны, а этот —
нет: `Config.Bypass` у связки старше, и тесты подставляют NAT без всякого
физического интерфейса. Пустое `sock.iface` означает «привязка неизвестна» и
никогда не считается устаревшей — это в точности прежнее поведение. Цена в том,
что забытый проброс молча выключил бы механизм в продукте; её платит W47.

**`Stats.Rebound`.** Счётчик закрытых по смене привязки сокетов, рядом с
`Sockets` и `Orphaned`. Растущее значение при стоящей сети означало бы, что
`Interface` отвечает неустойчиво. Как и весь `Stats()`, наружу пока не выведен —
это отдельный пункт очереди.

#### Флаг: свой, `bypass_sink` не переиспользован

Правдоподобным кандидатом на переиспользование был `bypass_sink`, и он не
годится **механически**, а не по вкусу: `bypass_sink=off` заставляет `Send`
вернуть `ErrDisabled` первой же строкой, до всякого сокета. Охраняющая проверка
покраснела бы под ним по чужой причине — не «сокет не сменился», а «наружу
вообще ничего не ушло», — и не отличала бы сломанную перепривязку от выключенного
пути. Охрана, краснеющая не от того, что охраняет, не охраняет ничего, и
`negcheck` потерял бы разрешение: «красное без `bypass_sink`» перестало бы
называть одну причину. Тот же довод, которым прошлый заход не слил
`bypass_tcp_reject` с `reject_mode`.

`bypass_rebind` зарегистрирован в `internal/policy/policies.go` рядом с
`BypassSink` и `BypassTCPReject`, с двумя охраняющими проверками. Обе написаны и
увидены красными **до** реализации, отдельным коммитом (`0dbf087`) — порядок,
которого держались три прошлых захода. Красными по существу, а не по
компиляции: проводка и поле `Config.Interface` вошли в тот же коммит именно
затем, чтобы падало утверждение, а не сборка.

#### Ловушка теста

`sock.seen` обновляется на **каждый** `Send`, а не на успешный обмен. Тест,
который замолчит на время смены интерфейса, пройдёт по неверной причине: сокет
соберёт обычная уборка простоя. Закрыто двумя приёмами разом.

Первый: в модульной проверке **часы стоят**. `sweepLocked` при неподвижных часах
не срабатывает вовсе (`now.Sub(n.swept) < n.idle/2`), поэтому уборке физически
некого собирать; проверка это ещё и утверждает явно, сверяя `clk.Now()` в конце.
Второй: клиент **шлёт непрерывно** — до смены, сразу после неё, — и проверка
требует, чтобы до смены порт не менялся, а после сменился. Один и тот же
механизм обязан и молчать без причины, и сработать по причине.

Отдельная проверка, `TestBypassIdleSweepNeverCollectsSocketUnderTraffic`,
закрепляет саму ловушку: при непрерывном трафике шагами в ¾ `Idle` уборка
запускается на каждом `Send` и не собирает сокет никогда — 7.5×`Idle`, и сокет
всё тот же. Она не охраняет флаг (зелена при любом его состоянии), она
объясняет, почему без `bypass_rebind` дыра не закрывается сама.

`fakenet.Bypass.WaitPackets` не используется нигде: он ждёт вечно и превратил бы
красный тест в зависание. Наблюдаемое — исходный порт, с которым датаграмма
приходит слушателю, и `listener.SetReadDeadline` с заведомым концом.

#### Новые проверки

- `TestBypassInterfaceChangeRebindsSocket` (`internal/bypass`) — охраняющая,
  сам механизм; проверена красной под `HOP_DISABLE=bypass_rebind`.
- `TestBypassSocketRebindsOnInterfaceChange` (`internal/agent`) — W47, охраняющая,
  шов `Config.Physical` → `bypass.Config.Interface`; тоже проверена красной.
- `TestBypassKeepsSocketWhenInterfaceUnknown` (`internal/bypass`) — консервативный
  край: пропавший default route за смену интерфейса не считается.
- `TestBypassIdleSweepNeverCollectsSocketUnderTraffic` (`internal/bypass`) —
  ловушка, не охрана.

Номерного T-теста заход не добавляет: утверждение модульное, как и у обоих
охранников `bypass_sink`, и §8.3 не трогается. L3-стенд со вторым veth (форма,
которую предлагал `HANDOFF.json`) не строился — он проверял бы `SO_BINDTODEVICE`
ядра, а не решение о переоткрытии сокета; ядро на этом пути уже покрыто T31.

#### Deviations

**Сигнал берётся опросом, а не проталкиванием — и это отход от формы, названной
в `HANDOFF.json` первой.** Форма из очереди (`NAT.Reset()` из наблюдателя)
отвергнута в пользу более дешёвой и более точной; довод выше. Консервативный
вариант по смыслу `CLAUDE.md`: он не добавляет ни нового источника событий, ни
новой горутины, ни изменений в платформенном пакете.

**Сверка идёт на `Send`, а не по таймеру, поэтому сокеты чужих клиентов
закрываются в момент первого `Send` любого из них.** Пока NAT молчит целиком,
устаревшие сокеты живут — но и вреда не наносят: наружу через них ничего не
уходит. Единственный остаток — горутина `receive`, способная принять ответ на
старом интерфейсе в этом промежутке; первый же `Send` закрывает все такие
сокеты разом, не только тот, за которым пришли, ровно ради этого.

**`Stats` вырос третьим полем.** `Rebound` добавлен в структуру, которую
сегодня в продукте никто не читает (`Stack.Stats` её не подмешивает — пункт
очереди). Поле заведено не «на будущее», а потому что охраняющая проверка
утверждает срабатывание механизма напрямую, а не только через смену порта.

Closes: `next_task` из `HANDOFF.json` (Invalidate bypass sockets on interface
change, приоритет 1).
