# Заметки реализации

Спека — `SPEC.md`. Сюда пишется то, что реализация вынудила решить иначе.

## Как снять замеры

```sh
# Граница ОС: B1a, B1b, двунаправленно, латентность.
go run ./cmd/b1 -mode boundary -duration 5s

# Linux: реальный TUN-fd + контрольный замер GSO. Нужен свой netns;
# unshare -Urn даёт CAP_NET_ADMIN внутри него, root не нужен.
go build -o b1 ./cmd/b1 && unshare -Urn ./b1 -mode tun -duration 5s

# Этап 3, поверх netstack. Прав не требует.
go run ./cmd/b3 -mode rtt        # RTT коротких TCP-обменов, без порога
go run ./cmd/b3 -mode fullcone   # B3: NAT-таблица под нагрузкой

# Оракул.
go run ./cmd/realtimelint .   # настоящее время только в internal/clock
go run ./cmd/negcheck         # каждая политика краснит свой тест
go test -run TestMetaCheck ./internal/negcheck   # негативная задача сама исправна
```

Гейт применяется автоматически и только на Windows (`-gate=false` снимает).

## Как гонять L3 (этап 2, Linux)

```sh
go test -c -o /tmp/l3.test ./internal/l3
HOP_L3=1 unshare -Urn /tmp/l3.test -test.v
```

`unshare -Urn` даёт `CAP_NET_ADMIN` в собственном netns — root не нужен. Без
`HOP_L3=1` тесты пропускаются: цена лишнего пропуска — строка в логе, цена
лишнего запуска в общем namespace — сеть машины.

В CI бинари собираются заранее и подсовываются через `HOP_L3_BIN_HOPD` и
`HOP_L3_BIN_HOP`: под `sudo` `go build` пошёл бы в чужой кеш и полез бы в сеть.

Проверить, что политика краснит свой тест:

```sh
HOP_L3=1 HOP_DISABLE=orphan_reject   unshare -Urn /tmp/l3.test -test.run 'T23'
HOP_L3=1 HOP_DISABLE=orphan_deadline unshare -Urn /tmp/l3.test -test.run 'T24'
HOP_L3=1 HOP_DISABLE=snapshot_restore unshare -Urn /tmp/l3.test -test.run 'T22'
```

## Как гонять L2 этапа 3

Прав не нужно, TUN не нужен, работает на трёх ОС:

```sh
go test ./internal/netstack        # T12, T13, T15, T16, T17
go test ./internal/bench           # TCP-путь насквозь через настоящую границу

HOP_DISABLE=verdict_order go test -run T16 ./internal/netstack
HOP_DISABLE=reject_mode   go test -run 'T12|T13' ./internal/netstack
HOP_DISABLE=nat_key       go test -run T15 ./internal/netstack
HOP_DISABLE=nat_key       go run ./cmd/b3 -mode fullcone   # рост таблицы втрое
```

## Как гонять L2 этапа 6 (резолвер, шаг 10 регистра)

Настоящие узлы (Xray за инжектором отказов), без TUN и без прав:

```sh
go test ./internal/l2 -run 'TestT14SwitchResolvesToNewIP|TestT16DNSToLocalRouterIsHijackedRealResolver|TestD33TruncatedAnswerRetriesOverTCPRealNode'

HOP_DISABLE=dns_cache_flush_on_switch go test ./internal/l2 -run TestT14SwitchResolvesToNewIP
HOP_DISABLE=verdict_order            go test ./internal/l2 -run TestT16DNSToLocalRouterIsHijackedRealResolver
HOP_DISABLE=dns_tcp_retry            go test ./internal/l2 -run TestD33TruncatedAnswerRetriesOverTCPRealNode
```

## Deviations

Разделы идут в том порядке, в каком записи появлялись, а не по номерам этапов:
сперва реализация этапов 0–5, затем заготовки этапов 6–9 со второй машины, затем
сверка регистра решений со спекой (пас 0), затем этапы, сделанные по принятым
решениям, — 7 и С.

Раздел «Этапы 6–9» со второй машины писался до паса 0 и местами противоречит
принятым там решениям; расхождения названы прямо внутри него. Он оставлен как
след, а не как руководство.

### Этапы 0–5 — оракул, граница, сервис, netstack, движок, живость

**B1 меряет транспорты, а не `PacketDevice`.** Прежняя редакция §8.6 говорила
«прогон синтетического потока через `PacketDevice`», но этап 1 по построению
идёт до того, как реализации `PacketDevice` появятся: их стоимость и есть
предмет замера. _Расхождением быть перестало: §8.6 переписан и говорит теперь
«через границу»._ Меряются транспорты напрямую — named pipe на Windows,
socketpair и TUN-fd на Unix — с тем же framing и батчингом, что понесёт
реализация. Консервативно: реализация добавит к этим числам, а не убавит.

**B1b на Windows моделирует кольцо Wintun, а не открывает адаптер.** Настоящий
`ReceivePacket` требует прав администратора и `wintun.dll` рядом с бинарём — это
открытый на тот момент вопрос §7 про `wintun.dll` и этап 8 (ныне закрыт, см.
C19). Модель: копия каждого пакета из 8-МиБ staging-буфера (порядок
receive-кольца Wintun) перед записью в трубу. Она воспроизводит то, что в замере
дорого, — лишний memcpy и давление на кэш, — но не стоимость самого вызова
драйвера. Число завышено на эту стоимость.

**Контрольный замер GSO сделан на UDP GSO, а не на TSO.** `UDP_SEGMENT` +
`TUN_F_USO4` дают многопакетный read() без TCP-рукопожатия; TSO потребовал бы
терминировать TCP-соединение прямо в харнессе. Форма разбора — как в
`handleVirtioRead` (wireguard-go, MIT): virtio-заголовок, затем нарезка на
сегменты с копированием заголовков и полезной нагрузки. Контрольная сумма UDP не
пересчитывается (для IPv4 нулевая сумма легальна), поэтому число слегка завышает
выигрыш GSO — ровно на ту работу, которую virtio-заголовок и договаривается
отдать железу.

**Замер пути «ядро → агент» на Linux считает и стоимость отправителя.** Пакеты
порождает UDP-сокет внутри netns, у него на пакет тоже приходится syscall.
Отправителей четыре, чтобы узким местом был читатель. Число — нижняя граница, не
верхняя.

**Поддельный `PacketDevice` живёт в `internal/packettest`, а не в
`internal/packet`.** `ExpectRST`/`ExpectICMPUnreach` принимают `testing.TB`;
импорт `testing` в продуктовый пакет протащил бы тестовые флаги в каждый бинарь,
который его слинкует.

**Реестр политик — центральный литеральный список, а не регистрация через
`init()`.** При регистрации из пакетов-владельцев полнота реестра зависела бы от
того, что слинковано в конкретный бинарь, и negcheck молча пропускал бы
политики. Список в `internal/policy/policies.go` полон по построению.

**Отказ в `orphaned` делает респондер сервиса, а не reject-маршруты ядра.** План
(раздел 0, D1) предполагал подмену маршрутов туннеля на `unreachable` /
`-reject`, и привилегированного кода на Linux и macOS не прибавлялось бы вовсе.
Замер `TestRouteReplaceOnEstablishedConnection` (`internal/l3`) показал, что
подмена закрывает только новые соединения: у уже установленного сокета `Write`
возвращает успех, а данные молча уходят в ретрансмиты — за 8 секунд наблюдения
ни одной ошибки. Это то самое молчание, против которого §5.6, только сдвинутое.
Совместить нельзя: с reject-маршрутом пакеты до устройства не доходят, и
отвечать не на что. Выбран консервативный вариант — сервис становится читателем
устройства и отвечает RST/ICMP; один механизм на трёх ОС, и на Windows он был
нужен в любом случае. §6.2 переписан по факту замера.

**Attach-token переживает `kill -9` агента, значит лежит на диске.** Задача
говорила «агент держит его только в памяти». Так нельзя: реаттач (T24) по
определению делает новый процесс, а память убитого ему недоступна, — токен
только в памяти означает, что T24 не проходит никогда. Токен лежит в
`$XDG_RUNTIME_DIR/hop/attach-token`, каталог 0700, файл 0600 (§6.14 это прямо
разрешает: «каталог агента 0700, файлы с ключами 0600»). Остальные требования
§6.14 соблюдены буквально: тип `tunnel.Token` форматируется заглушкой, поэтому в
лог он не попадает ни через один глагол `fmt`, включая `%#v` по объемлющей
структуре; в `status` его нет; сервису он уходит только в самом `Attach`.
Следствие, которое надо понимать: для процессов того же UID токен — не граница,
границей остаётся проверка UID/SID плюс права на сокет. Токен добавляет второй
рубеж против процесса, который до каталога агента не достаёт.

**`Detach(reason=restart)` не минует окно отказа, а сокращает его.** План писал
«чистый рестарт минует окно отказа целиком». Буквально это означало бы, что в
зазоре пакеты не отвергаются, — то есть молчаливое окно, ровно запрещённое §5.6.
Реализовано так: `Detach` даёт то же ребро и тот же отказ, но сервис знает
причину и показывает её в `status`, а окно схлопывается до времени respawn.

**Смерть сервиса переживает все разложенные им правила.** T29 первоначально
показал десять правил: `31000` исключения §5.6, прежнее `31500` с UID-диапазоном
§6.8 и `32000` туннельное. Новая сборка больше не создаёт `31500`, но переходный
`platform.Reclaim` всё ещё подбирает его после обновления. Уборка идёт **до**
снятия снапшота, иначе снапшот закрепил бы мусор как исходное состояние.

**Уровень L3 написан только для Linux.** macOS и Windows остались скелетами
рабочих процессов с `workflow_dispatch` (§8.4: они и так по расписанию). Причина
не в объёме: L3-Windows упирается в вопрос §7 про `wintun.dll` — без подписанной
библиотеки рядом с бинарём адаптер не поднимается, и план держит этот вопрос
блокером этапа 8. macOS-слой (utun через `AF_SYSTEM`, `SIOCAIFADDR`, `PF_ROUTE`)
писать вслепую, без раннера, значило бы получить непроверенный привилегированный
код. `platform.New()` на этих ОС отказывает явно, а не молча: молчаливая
заглушка дала бы зелёный L3 там, где ничего не проверено.

**gvisor поднял требование к Go до 1.26.3.** `gvisor.dev/gvisor` нужен ради
`pkg/tcpip/header` (§6.2, Apache-2.0) и понадобится целиком на этапе 3. Его
`go.mod` требует 1.26.3, поэтому столько же требует и наш; CI поставлен на
`1.26`. Версия берётся с ветки `go` (генерируемой), а не с `master`: на master в
дереве лежат шаблоны `*.tmpl.s`, которые ассемблер Go принимает за исходники и
не собирает.

**Исключения линта настоящего времени — построчные, `//hop:realtime`.** Файловых
исключений нет намеренно. Бенчмарк меряет время через `clock.System`, то есть
через тот же интерфейс, и исключений не требует; пометки стоят только внутри
`internal/clock`.

**`StopTunnel` сверяет владельца, хотя §3.1 этого не требует.** Спека задаёт
проверку личности только для `Attach`, а список операций даёт `StopTunnel()` без
условий. Но модель доверия §3.1 — «сокет доступен лишь владельцу, и внутри
одного пользователя случайный процесс не должен уметь перехватить чужой
дескриптор» — на снятие туннеля распространяется ровно так же: посторонний,
снявший чужой привилегированный туннель, наносит больше вреда, чем перехвативший
его. Консервативный вариант: `Machine.StopBy` требует совпадения UID/SID с
владельцем.

Сверяется именно личность, а не соединение, как у `Detach` и `Heartbeat`:
`hop -down` — отдельный процесс, он подключается заново, и владельцем соединения
не является по построению. Гейт по соединению сломал бы CLI.

**Право открыть канал даётся классу, а не конкретному пользователю.** §6.1 —
одна фраза: «Unix-сокет с правами владельца / named pipe с SDDL», и кто такой
владелец, спека не говорит. Стороны границы живут под разными пользователями:
сервис под root (нужны `/dev/net/tun` и `ip`), агент — под обычным. Сокет строго
владельцу означал бы EACCES у агента.

Выбрано: на Unix сокет 0660 с группой из `-group` (дефолт `hop`), на Windows ACE
для `IU` (интерактивные пользователи) вместо SID слушателя. Владение конкретным
туннелем при этом держит измеренная личность — SO_PEERCRED и
`ImpersonateNamedPipeClient`, — поэтому широкий ACE не даёт перехватить или
снять чужой туннель.

Несуществующая группа валит старт, а не понижает права молча до 0600: сервис,
поднявший сокет, к которому агент не достучится, выглядит рабочим и не работает.
L3 передаёт `-group ""` — там обе стороны идут под root в своём netns.

**UDP не проходит через gvisor вовсе. Это материал для §5.1.** План этапа 3
говорит «gvisor `tcpip` поверх `PacketDevice`»; по факту gvisor обслуживает
только TCP. Причина в устройстве его UDP-форвардера: `CreateEndpoint`
(`pkg/tcpip/transport/udp/forwarder.go`) делает `net.Bind` на адрес назначения и
`net.Connect` на адрес источника, то есть отдаёт **connected**-эндпоинт на пару
(src, dst). Это ровно NAT по паре — то, что §5.3 запрещает и что T15 обязан
ронять. Full-cone на этом API выражается только так: заводить отдельный эндпоинт
на каждого нового отвечающего и писать ответ в него, то есть держать в gvisor
структуру, которая живёт не по правилам gvisor.

Выбран консервативный вариант: UDP разбирается и собирается своими руками
(`internal/packet.BuildUDP` на заголовках gvisor, Apache-2.0), NAT — своя
таблица по source addr:port, исходящее — один `net.PacketConn` на исходный порт,
ровно как отдаёт `core.DialUDP`. Это то же, что делает собственный TUN Xray
(`proxy/tun/udp_fullcone.go`), на который §5.3 и ссылается. UDP не нуждается ни
в машине состояний, ни в окнах, ни в сборке потока — всё, ради чего берут
netstack; за вычетом NAT он состоит из разбора заголовка.

Чего это стоит §5.1. **Форка не потребовалось, костыля через `PacketEndpoint`
тоже, и перехвата ниже заявленного уровня нет.** Но утверждение §5.1 «свой
TUN-слой убирает второй netstack в горячем пути» держится теперь на меньшем:
netstack в горячем пути — это TCP, а UDP идёт мимо него. Выбор gvisor этим не
опровергнут — для TCP он даёт именно то, что нужно, — но его доля в продукте
меньше, чем читается из §5.1.

**Вердикт принимается до gvisor, а не внутри него.** §3.4 требует решения по
первому пакету потока. Из четырёх вердиктов три обязаны сработать раньше, чем
пакет попадёт в стек: bypass-пакет в стек заходить не должен вовсе, reject
отвечает `internal/reject` (тот же код, что обслуживает `orphaned`), hijack-dns
над UDP до стека и не доходит. Поэтому вердикт живёт в насосе, на сырых пакетах,
и в gvisor попадает только то, что признано proxy или DNS-над-TCP.

Что при этом даёт gvisor и чего пришлось бы городить без него: `tcp.Forwarder`
вызывает обработчик на SYN и **откладывает рукопожатие до `CreateEndpoint`**.
Поэтому исходящее соединение устанавливается раньше SYN-ACK, а его неудача
превращается в RST, а не в «соединение установлено, но мертво». Это свойство
проверяется `TestRefusedUpstreamNeverCompletesHandshake`. Своими руками оно
означало бы собственную реализацию TCP-рукопожатия — то, ради чего netstack и
берут.

**Вердикт кэшируется в таблице потоков; таблицы в спеке нет.** «Вердикт на
первом пакете» буквально означает, что он не пересматривается. Без таблицы
вердикт считался бы заново на каждом пакете, и смерть последнего узла посреди
установленного соединения превращала бы его следующий пакет в RST **в обход
gvisor**, который этим соединением в этот момент владеет. Таблица —
`internal/netstack/flow.go`, ключ 5-кортеж, уборка по простою на фейковых часах.
Новые потоки при этом отвергаются немедленно: fail-close закрывает новое, а не
чужое.

**Пятый вердикт — `block`, молчаливый дроп.** §3.4 перечисляет четыре, но §6.10
велит блокировать широковещательный NetBIOS и прочий multicast и broadcast, а
§6.9 — IPv6. Отвечать на них нечем: RST в multicast бессмысленен, а ICMP на
broadcast — это ответ самому себе. Дроп здесь не нарушает §5.6: тот запрещает
молчание там, где приложение ждёт ответа от конкретного собеседника, а не в
обнаружении служб. Сюда же уходит всё, что не TCP и не UDP, включая ICMP от
клиента: исходящего для него на этапе 3 нет.

**Список bypass §6.10 не переиспользует `reject.Excluded`, хотя они похожи.**
Вопросы разные: `Excluded` отвечает «на что респондер не имеет права отвечать» и
консервативно относит туда весь multicast; bypass отвечает «что выпустить в
локальную сеть», а §6.10 делит multicast на разрешённое обнаружение служб (mDNS,
SSDP) и блокируемое остальное. Шов между двумя списками закрыт тестом
`TestRejectVerdictNeverEndsInSilence`: ничто, получившее вердикт reject, не
должно оказаться исключением `internal/reject` — иначе fail-close стал бы
молчаливым дропом, ровно тем, что запрещает §5.6.

**T15 в том виде, как он записан в §8.3, краснеет не по заявленной причине.**
§8.3 обещает, что при NAT по паре src+dst «ответы потеряются». Три ответа от
трёх контактированных адресов доходят при любом ключе: запись под них есть.
Теряется ответ с адреса, на который клиент **не** слал, — а это и есть
определение full-cone. Тест проверяет обе половины: одна NAT-запись на исходный
порт (при `nat_key=src+dst` их становится три) и ответ от четвёртого, никогда не
контактированного адреса. Первая половина краснеет по счёту, вторая — по
существу.

**Bypass — приёмник за интерфейсом, а не настоящая локальная сеть.** В продукте
таких пакетов на устройстве нет вовсе: исключения выражены правилами
маршрутизации выше туннельного и в таблицу туннеля не заходят (§6.2). Вердикт
bypass в netstack — второй рубеж на случай, если правило не встало, по образцу
`reject.Excluded`. Куда он отдаёт пакет, решает вызывающий; на этапе 3 это
запись в памяти, на этапе 8 — сокет, привязанный к дефолтному интерфейсу.

**hijack-dns над TCP терминируется уже сейчас, хотя резолвер — заглушка.** §3.4
говорит «dst-порт 53 (UDP или TCP)», а до запроса в TCP не добраться, не
терминировав поток. Поэтому DNS-над-TCP идёт в gvisor и разбирается по RFC 1035
§4.2.2 (двухбайтовый префикс длины), после чего попадает в тот же `Resolver`,
что и UDP. Этап 6 меняет только реализацию `Resolver`.

**Строители IPv4-пакетов переехали в `internal/packet`.** `BuildUDP` нужен
netstack (ответ NAT и ответ резолвера), оракулу и замеру B3 — трём разным
пакетам, из которых один компилируется в бинарь, а значит не может тянуть
`testing`. Три копии арифметики контрольных сумм разошлись бы молча;
`internal/packettest` теперь на них делегирует.

**Замер RTT ставит по обе стороны границы по стеку gvisor.** Настоящим ядром на
дальней стороне был бы TUN, то есть права и платформенный код, то есть уровень
L3. Замер остаётся L2 ценой того, что «приложение и ядро» — тоже gvisor, и его
стоимость входит в число. Абсолютные значения поэтому завышены; переносимо здесь
сравнение Linux с Windows, где меняется только граница. Та же логика, что в
B1-строке про загруженный прогон 3.

### Этап 6 — резолвер

**Р27. Сброс кэша: резолвер подписан сам, связка дожидается подтверждения.**
§5.7 требует, чтобы кэш сбрасывал сам резолвер по подписке, и связка «не
участвовала в самом сбросе». Но `health.Manager.Events()` — одноконсьюмерный
канал, который уже читает `agent.pumpEvents`, а Р33 (`switch_order`, W11, W13)
требует, чтобы кэш был выкинут **раньше**, чем событие ушло наружу: иначе
приложение, разбуженное событием, успевает перерезолвить имя и получить адрес,
добытый через мёртвый узел, — и §5.7(в) оказывается выполнен формально.

Совместить два требования буквально нельзя: подписчик живёт в своей горутине.
Решение: резолвер получает `Config.Events` и флашит сам, а связка после отправки
ждёт `Config.Acked`. Подтверждение приходит и тогда, когда сброса не было
(политика выключена), — иначе выключенный флаг подвешивал бы связку вместо того,
чтобы покраснить проверку. Цена: точка синхронизации между двумя горутинами на
каждом переключении узла.

**Р28. Транспорт клиента приезжает вторым интерфейсом, а не параметром.**
D33–D36 требуют разного поведения для клиента по UDP (флаг TC плюс потолок его
буфера EDNS0) и по TCP (полный RRset), а `netstack.Resolver.Query`, замороженный
с этапа 3, транспорта не несёт. Рядом объявлен `netstack.StreamResolver` с
`QueryStream`, и `tcp.go` делает type assertion — тот же приём, каким сделан
`FlushableResolver` в связке. Замороженный интерфейс не тронут, все прежние
call-site и фейки работают как были, а счётчик `TruncToClient` остался в
резолвере, как требует §2 регистра.

**Р29. Разбор DNS свой, по смещениям, а не `x/net/dns/dnsmessage`.** У6 требует,
чтобы ответ собирался копированием байт: секция вопроса из запроса как есть, всё
остальное от апстрима байт в байт, включая TTL (C4). Значит нужны не разобранные
структуры, а точные смещения — где начинается и кончается каждый RR, где лежит
OPT, где внутри него ECS. `dnsmessage` смещений не отдаёт, и для ECS и EDNS0
пришлось бы считать байты руками поверх него, то есть держать два разбора вместо
одного. `internal/dnsmsg` — свой, без новых зависимостей.

**Р30. Состояние DNS видно в логе агента, а не в `hop status`.** Р15 отдаёт
клиенту `SERVFAIL`, когда живых узлов нет, и прямо называет цену: приложение не
отличает «VPN закрылся» от «DNS сломался», а внятная причина «видна в
`hop status`». Но `hop -status` спрашивает по IPC **сервис** и получает
`tunnel.State`; резолвер живёт в процессе агента, и канала от второго процесса
`hop` к работающему агенту нет вовсе — по C9 это разделено сознательно. Строить
его сейчас значило бы втащить в этап 6 работу этапа 9. DNS печатается там же,
где уже печатается фаза трафика, — в `cmd/hop/watch.go`.

**Р31. Фаза `bypass` в продукте до резолвера не доходит.** Р25 и D20 описывают
поведение резолвера в `bypass`, а C8 — что перехваченный DNS идёт там мимо
узлов. Но `agent.Bypass(true)` по Р35 (`bypass_teardown`) снимает туннель
целиком, вместе с ним уходит стек, и запросов на :53 больше не приходит: система
резолвит своим резолвером напрямую. Ветка прямого апстрима остаётся живой ровно
при выключенной `bypass_teardown` и потому реализована. Сброс кэша на краях
`bypass` (D20) от этого не зависит и нужен всегда: резолвер переживает
`Down`/`Up`, а адреса, добытые напрямую, указывают на CDN настоящего региона.

**Р32. Край `bypass` резолверу показывает связка, но решает он сам.** Фаза
приходит функцией, то есть опрашивается; заметить край опросом можно было бы
только по таймеру, а это либо задержка в размер шага, либо сотни тиков на каждое
удержание в `waiting`. Связка зовёт `Resolver.PhaseChanged()` из `refreshPhase`,
который и так вызывается на каждом переходе. Что считать краем и что при этом
сбросить, решает резолвер: связка говорит «посмотри», а не «сбрось».

**Р33. Имена узлов резолвит связка до Xray, а не Xray сам.** §5.7(а) называет
петлю, но не место, где она разрывается. Xray резолвит адрес узла своим сокетом,
который через перехваченный :53 уходит в туннель — то есть в резолвер, которому
нужен живой узел, которого нет, пока имя не разрешилось. Поэтому
`agent.reloadNodes` резолвит имя через `Bootstrap` и подставляет адрес в
`engine.Node.Server` до сборки конфига. Подстановка сохраняет рукопожатие:
`engine.tlsSettings` берёт `serverName` из `sni`, иначе из `host`, иначе
оставляет Xray взять адрес — и последнее после подстановки упёрлось бы в чужой
сертификат, поэтому при непустом `security` и пустых обоих параметрах `sni`
выставляется исходным именем. Отказ bootstrap узел не выбрасывает: иначе один
недоступный апстрим сокращал бы подписку молча.

### Этапы 6–9 — стор, подписки, резолвер, связка, CLI, поставка

Записи ниже приехали со второй машины и описывают код, которого **в этом
репозитории пока нет**: `internal/store`, `internal/subscription`,
`internal/resolver`, `internal/supervisor`, `packaging/`, `docs/wintun.md`.
Держим их здесь, потому что это уже принятые решения с обоснованием, а не
намерения, — но пока код не приехал, читать их надо как «что выяснилось там», а
не «как устроено здесь». Нумерация C1–C21 сквозная: в исходном файле номера
C11–C14 стояли дважды.

**C1. `store` импортирует `health` ради типа `NodeHealth`.** §3.4 говорит «store
не знает ни про кого», но §3.4 же вменяет ему персистентность `NodeHealth`, а
сама модель принадлежит `health`: окно, состояние и счётчик ошибок трафика
меняет только он. Варианты были — продублировать структуру в `store` или вынести
её в `node`. Дубль означал бы две модели одного состояния и ручную конверсию на
каждой пробе; `node` — модель узла, и живость в неё не входит по прямому
указанию §2. Выбран импорт: `store` берёт из `health` **только тип данных**, ни
одной функции; обратного импорта нет и быть не должно.

**C2. Решение «рвать ли соединения» выражено в `health`, а не у потребителя
события.** §5.5 формулирует его как свойство сигнала: событие несёт `reason`, а
что с ним делать — дело того, кто событие получил. Реализовано методом
`health.Switch.Interrupts()`. Причина: §8 требует, чтобы у политики
`switch_reason` был охраняющий тест, а он по контракту фазы живёт в
`./internal/health` — значит и развилка обязана быть там же. Потребитель события
(супервизор, netstack) вызывает метод и не воспроизводит его логику у себя;
второе место означало бы второй ответ на тот же вопрос.

**C3. Апстрим-DNS ходит сначала по UDP и только на флаг TC — по TCP.** Контракт
фазы предполагал один путь наверх — поток с префиксом длины (RFC 7766), потому
что `Engine.DialUDP` отдаёт `PacketConn` на исходный порт клиента и второй
модели full-cone под резолвер не хотелось. Но TCP-сессия на каждый запрос — это
рукопожатие узла на каждый резолв, то есть лишний RTT там, где его считает
пользователь. Добавлено **необязательное** поле `Config.DialUDP` того же вида,
что `Dial`: датаграмма пишется и читается целиком, без префикса. `nil` оставляет
прежнее поведение — весь апстрим по TCP, — поэтому проводка, собранная по
контракту, продолжает компилироваться и работать. Усечённый ответ (TC) в обоих
случаях перезапрашивается потоком: RFC 1035 §4.2.1.

**C4. TTL в отданном из кэша ответе не уменьшается.** §5.7в требует, чтобы кэш
уважал TTL, — он и уважает: запись живёт ровно столько, сколько назвал апстрим
(в рамках `MinTTL`/`MaxTTL`), и по истечении перезапрашивается. Но само
сообщение отдаётся клиенту байт в байт, с исходным TTL и подменённым
идентификатором. Честный вариант — разобрать ответ на записи и пересобрать его
на каждом попадании в кэш; `dnsmessage.Builder` требует для этого типизованного
метода на каждый тип записи, то есть switch по всему перечислению RR ради
вычитания секунд. Цена ошибки мала и ограничена сверху: клиент держит запись
дольше нас не более чем на `MaxTTL`, а при смене узла кэш всё равно сбрасывается
целиком.

**C5. Clash YAML из каскада §6.12 распознаётся, но не разбирается.** §6.12
ставит его второй ступенью каскада
(`base64 → Clash YAML → построчно → по схеме`). Ступень на месте — тело с ключом
`proxies:` определяется и отвергается одной внятной ошибкой, — но конвертации
YAML в узлы нет: она тянет за собой YAML-зависимость и вторую, независимую от
ссылок, модель разбора. Выбран консервативный вариант: явный отказ вместо
разбора YAML построчно, при котором на каждую строку приходит своя бессмысленная
ошибка, а настоящая причина тонет. Первая, третья и четвёртая ступени каскада
работают полностью.

**C6. `security=reality` остаётся отдельным значением, а не сводится к `tls`.**
§6.12 пересказывает nekoray («reality → tls плюс pbk/sid/spx»), но §2
перечисляет `security` как `none | tls | reality`, и `engine.buildConfig`
разбирает `reality` отдельной веткой (`realitySettings` — не то же самое, что
`tlsSettings`). Сведение к `tls` на разборе означало бы, что различать их
придётся по наличию `pbk` в params, то есть восстанавливать выброшенное знание.
Нормализации §6.12 по значениям (`none/0/false`, `1/true`) сохранены полностью.

**C7. Классификация §6.15 видит только те отказы, о которых Xray сообщил явно.**
`core.Dial` возвращает трубу немедленно, а исход соединения приезжает позже и в
другое место — через `session.SubmitOutboundErrorToOriginator`
(`common/session/context.go:119`). Движок ставит в контекст приёмник этих
ошибок, и `classify` считает смертью узла только то, что в него пришло. Всё
остальное — обрыв, устроенный целевым хостом, и узел за него не отвечает.

Цена решения найдена измерением, а не рассуждением: если узел рвёт соединение
**корректным закрытием** посреди рукопожатия VLESS (режим стенда
`cut-after-handshake` из §8.1), Xray сводит ошибку к `io.EOF`
(`app/proxyman/outbound/handler.go:246` фильтрует EOF, `io.ErrClosedPipe` и
`context.Canceled`), ничего не сообщает, и для нас это неотличимо от сайта,
закрывшего соединение первым. Такой узел классификацией трафика **не
убивается**. Разрыв через RST — убивается, тест `TestNodeTornByInjectorIsDeath`.

Выбран консервативный вариант. Альтернатива — считать смертью всякое соединение,
закрывшееся без единого байта от узла, — ловит `cut-after-handshake` и вместе с
ним всякий сайт, который принимает соединение и закрывается молча. Это ровно тот
отказ, против которого написан §6.15 и стоит T20. Дыра закрыта не здесь, а §6.7:
проба идёт тем же outbound, ничего не получает и уходит в окно k-из-n (§6.3).
Классификация трафика остаётся вторым сигналом, а не первым.

**C8. В фазе bypass наружу выпускается TCP, но не UDP.** §5.6 обещает, что
`hop bypass --on` осознанно выпускает трафик напрямую. Прямой путь у агента
ровно один — outbound `direct` движка (`Engine.DialDirect`, §6.8 биндит его к
дефолтному интерфейсу), и он отдаёт только `net.Conn`. Датаграммного прямого
исходящего у движка нет: `Engine.DialUDP` ключуется тегом узла, потому что
full-cone §5.3 держится на `core.DialUDP` с инбаунд-тегом. Поэтому в фазе bypass
TCP и перехваченный DNS идут мимо узлов, а UDP-поток исходящего не находит и
датаграмма не выпускается.

Выбран консервативный вариант: обычный `net.Dial` из процесса агента выпустил бы
UDP на Linux (правило §6.8 по UID-диапазону), но на macOS и Windows петля
закрывается `sockopt.interface`, который ставит Xray, — сокет мимо движка ушёл
бы обратно в туннель. Один механизм на трёх ОС дороже, чем недостающий UDP в
режиме, который сам по себе аварийный: §С6 описывает его как «починить подписку
либо осознанно выпустить трафик», и веб с DNS для этого работают.

**C9. `supervisor.Status` не содержит `device` и не умеет `orphaned`.** §2
перечисляет `TunnelState` как один объект с полями `phase`, `active_node`,
`last_switch`, `device`. Разделено по владельцу: `device` и фаза `orphaned`
известны только сервису (§6.2), активный узел и причина последнего переключения
— только агенту. `hop status` показывает то и другое, склеивая
`ipc.Client.Status()` с `supervisor.Status()`. Общий объект означал бы, что одно
и то же поле заполняют двое, и расхождение (агент считает себя `up`, сервис уже
в `orphaned`) осталось бы незамеченным.

**C10. Форс-проверка §6.6 приходит сигналом, а не от наблюдателя за сетью.**
§6.6 перечисляет смену интерфейса, пробуждение из сна и правку таблицы
маршрутизации. Наблюдатели за всеми тремя — платформенный код (netlink,
SCDynamicStore, WMI), то есть этап 8. До него ребро выражено `SIGHUP`:
`supervisor.Force(health.Trigger)` уже на месте и проверен T6, меняется только
источник события. Юнит systemd и тест умеют дать его руками.

**C11. При отсутствующем агенте `hop status` и `hop down` говорят с сервисом
напрямую.** §3.3 требует, чтобы клиенты ходили к сервису только через агент —
одна привилегированная граница, одна точка аудита. Но оба состояния, ради
которых эта пара команд существует, наступают именно тогда, когда агента нет:
`orphaned` по определению означает «агента не стало» (§6.2), а §2 обязывает
`status` его показывать; `hop down` (§С7) обязан снять туннель и в этом случае,
иначе интерфейс держится до истечения `orphan_deadline`, и пользователю нечем
вмешаться. Пока агент жив, оба ходят через него, и склейка состояний остаётся в
одном месте (C9). Прав это не расширяет: `StopTunnel` сверяет владельца сам
(`Machine.StopBy`), а `Status` не отдаёт ни узлов, ни ключей.

**C12. Подписки и узлы правит процесс CLI, а не агент.** §3.3 говорит «вся
логика в агенте», но §С2 (`hop sub add`) идёт раньше §С3 (`hop up`): требовать
живого агента для добавления подписки значило бы требовать туннеля до того, как
появился хоть один узел. Поэтому `sub add/update/rm/list` и `node add/rm` — это
прямая работа со стором из процесса команды.

Следствие, о котором CLI предупреждает вслух: живой агент состава узлов не
перечитывает — список кандидатов он собрал в `supervisor.New`, и новые узлы
вступают в силу после `hop down` и `hop up`. Второе следствие — две записи в
один стор из разных процессов: файлы пишутся целиком, поэтому одновременные
правки состава агентом и CLI теряют одну из них. Сейчас агент в стор не пишет
вовсе, так что окна нет; появится запись здоровья на диск — понадобится либо
блокировка файла, либо перенос этих команд в агент.

**C13. `hop up` не демонизируется: это и есть агент.** §С3 описывает `hop up`
как «поднимает туннель», из чего читается фоновый запуск. Реализовано иначе: без
команды и по `hop up` бинарь работает агентом в переднем плане, пока туннель
жив, — так его и запускает менеджер служб при логине (§6.13), и так же его
запускает стенд L3. Своей демонизации (fork, pid-файл, перезапуск) нет
намеренно: §5.2 отдал жизненный цикл процессов сервису и менеджеру служб, и
второй такой механизм внутри агента дублировал бы их с худшим качеством. Если
агент уже работает, `hop up` не поднимает второй туннель, а делает то
единственное, чего от него в этом случае ждут: `--node` фиксирует узел.

**C14. `hop node rm` и `hop node ping` выражены имеющимися API.** Удаления узла
поштучно в сторе нет — есть слияние состава группы (§5.8), и `node rm`
выражается через него: применяется остаток группы, узлы-соседи сохраняют id и
историю проб, удалённый уходит вместе со своей. Цена — два ручных узла с
совпавшим ключом слияния (§6.16) в группе `manual` неразличимы, и после удаления
третьего один из них получит новый id.

Пробы поштучно не умеет расписание: `Scheduler.Force` гоняет горячий ярус
целиком (§6.5), и залп по всей подписке ради одной команды запрещён тем же §6.5.
Поэтому `hop node ping <id>` — это форс-проверка (§6.6) и состояние узла после
неё; узел из редкого яруса может ответить прежним состоянием.

**C15. Сценарий С1 закрывается поставкой, а не командой.** §1/С1 («ставит пакет,
инсталлятор регистрирует сервис, агент стартует при логине») — это `packaging/`
и I1–I4 (§8.5), и от CLI ему нужно ровно одно свойство: агент запускается как
`hop up` в переднем плане, а глобальные флаги идут **до** команды
(`hop -socket … up`), потому что разбор аргументов останавливается на первом
не-флаге. Юниты systemd и LaunchAgent написаны именно так. Остальные сценарии —
С2–С8 — выполнимы командами §5.9 целиком.

**C16. Сокет на macOS — `/var/run/hop.sock`, а не умолчание `ipc.DefaultPath`.**
§3.1 не называет пути, но код называет: `defaultPath()` отдаёт `/run/hop.sock`
на всём, что не Windows. На macOS каталога `/run` нет, а корневая файловая
система только для чтения — создать его нечем, и сервис с умолчанием не
поднимется вовсе. Инсталлятор macOS передаёт `-socket /var/run/hop.sock` в обоих
plist (`packaging/macos/*.plist`). Правка самого умолчания была бы честнее, но
это чужой пакет и чужой этап; путь задан там, где он всё равно обязан быть
записан дважды — в plist демона и агента.

Побочное следствие для порядка аргументов агента: разбор флагов останавливается
на первом не-флаге, поэтому в plist стоит `hop -socket … up`, а не
`hop up -socket …`. Во втором виде флаг остался бы неразобранным и агент искал
бы несуществующий `/run/hop.sock`.

**C17. L4 не поднимает туннель и не перезагружает машину.** §8.5 требует от I1
«агент стартует при логине», от I2 — перезагрузку. Ни того, ни другого на
hosted-раннере нет: сессии логина не существует, перезагрузка убивает задачу, а
поднятый туннель отобрал бы у раннера сеть — ровно поэтому L3 живёт в netns.
Заменено на проверяемое: I1 — сервис активен и включён в автозапуск, автозапуск
агента зарегистрирован, а член группы `hop` действительно открывает сокет, тогда
как посторонний получает `EACCES` (§6.1); I2 — юнит включён в
`multi-user.target`, и убитый `SIGKILL` сервис возвращается сам. Настоящая
перезагрузка и настоящий логин остаются ручной проверкой перед релизом.
Инсталлятор при этом намеренно **не** запускает агента: установка, меняющая
маршруты машины, не может быть прогнана в CI ни разу.

**C18. §6.14 на Windows выражается не режимом каталога.** «Каталог агента
`0700`, файлы `0600`» — это POSIX-режимы, которых на Windows нет:
`os.MkdirAll(0700)` там не значит ничего. Гарантия держится профилем
пользователя — `%USERPROFILE%` уже закрыт для других непривилегированных учётных
записей, и стор наследует его ACL. Инсталлятор Windows каталог стора не создаёт:
он работает с повышением и, будучи запущен под другой учётной записью, создал бы
каталог не тому человеку. На Linux и macOS `0700` с владельцем-человеком
выставляется установкой явно, в том числе при обновлении.

**C19. §6.13 на Windows не выполняется до обработчика SCM в `hopd`.**
Инсталлятор регистрирует службу правильно (автозапуск, LocalSystem) и
регистрирует автозапуск агента задачей планировщика, но запуск службы падает с
1053: `cmd/hopd` — обычная консольная программа, диспетчеру служб она не
отвечает (`golang.org/x/sys/windows/svc` не подключён). Скрипт говорит это
прямым текстом в ошибке, а L4-Windows гоняет только то, что уже работает —
закреплённую версию и подпись `wintun.dll`. Вопрос §7 про `wintun.dll` при этом
закрыт решением, а не кодом: `docs/wintun.md` — версия и sha256 закреплены,
библиотека скачивается при сборке и в репозиторий не кладётся.

**C20. Режим `rst` инжектора рвёт соединение после первых байт клиента, а не
мгновенно по accept.** §8.1 называет `rst` «немедленным RST». Буквальная
реализация — `SetLinger(0)` и `Close` сразу после `accept` — оказалась
недетерминированной: когда данные клиента ещё в полёте, ядро завершает такое
закрытие штатным FIN, и клиент получает `EOF` вместо `ECONNRESET`. На стенде это
давало ~14% ложных падений `TestRSTGivesConnectionReset`, а хуже того —
подрывало сам смысл §8.1, где `rst` и `blackhole` обязаны быть **разными**
наблюдаемыми: `EOF` неотличим от «сервер ответил и попрощался». Замерено на 500
прогонах: чтение перед разрывом убирает гонку полностью (0 из 500 против 13 из
500). Выбран консервативный вариант — дождаться первого байта и только потом
рвать. Наблюдаемое клиента не изменилось (первое, что он получает, — RST, и
никогда не данные), а молчащего клиента разблокирует `Close` стенда, ровно как в
`blackhole`. Реальный потребитель — VLESS-клиент Xray — всегда говорит первым,
поэтому «немедленность» на нём неотличима.

**C21. Бюджет T9/T11 берётся подтверждающей пробой, а не таймаутом трафика.**
§8.3 даёт пять секунд от отказа узла до переключения, а §6.3 требует двух неудач
из трёх. По периодам ярусов §6.5 это две пробы активного узла, то есть минута.
Закрыто двумя вещами: `ScheduleConfig.ConfirmDelay` подтягивает срок отказавшего
узла горячего яруса к 500 мс вместо периода яруса, а `ProbeTimeout` (2 с)
снимает зависшую пробу — без него `blackhole` держал бы ярус вечно. Смерть,
увиденную трафиком (§6.15), выбор замечает через `Monitor.SetOnDeath`: трафик
идёт вне расписания. Политика `confirm_probe`, охранники — T9 и T11 в
`internal/supervisor`.

Что здесь осталось нечестным: отсчёт пяти секунд идёт от первой неудачной пробы,
а не от самого отказа узла. Между отказом и первой пробой лежит период активного
яруса — до 30 секунд, если в этот момент через узел не идёт трафика. Трафик этот
разрыв закрывает (его ошибки идут в то же окно), но молчащий клиент за
blackhole-узлом узнает о переключении позже бюджета. Закрыть до конца можно
только детектором зависшего потока на датаплейне; в v1 не делаем — §4 не просит,
а цена — состояние на каждый поток.

### Найдено при сверке регистра решений со спекой (пас 0)

**Пакеты v1 неподписанные, и двойным кликом они не ставятся.** Решение
«настоящие пакеты под три ОС» столкнулось с §4, который выносит Developer ID и
нотаризацию за v1. Совместить буквально нельзя: скачанный `.pkg` без нотаризации
Gatekeeper не пропустит, неподписанный MSI ловит SmartScreen. Консервативный
вариант — оставить исключение §4 в силе, а пакеты собирать настоящими и ставить
из командной строки: `sudo installer -pkg` и `msiexec /i` идут мимо обеих
проверок. Цена записана в §4 прямо: строка установки — часть инструкции, а не
удобство. Отказываться от `.pkg` в пользу tarball было бы хуже — `postinstall`
даёт регистрацию демона (§5.10) и автозапуск (§6.13), которые иначе пришлось бы
писать скриптом трижды. Проверяется I1 на чистой машине; если ОС всё же упрутся,
выбор возвращается (записано в этапе 9 плана).

**Bypass через сокет агента — это NAT.** Решение «сокет, привязанный к
дефолтному интерфейсу» на Linux не реализуемо в заявленном виде:
`SO_BINDTODEVICE` требует `CAP_NET_RAW`, а §6.8 уже отказался на это полагаться.
Находка в том, что привязка там и не нужна — правило с UID-диапазоном уводит
мимо TUN-таблицы весь трафик агента. Но ОС подставляет в исходящий пакет свой
адрес, а сохранить адрес клиента можно было бы только raw-сокетом, то есть снова
`CAP_NET_RAW`. Значит обратный путь идёт через таблицу трансляций — ту же, что
UDP full-cone. Для обнаружения служб (§6.10) этого достаточно; прозрачным
форвардом bypass не является, и §6.8 теперь это говорит.

**Стартовый бюджет §5.6 не имел своего значения в `TunnelState.phase`.** Всплыло
при разделении фазы на две. Спека описывает состояние «ни один узел не проверен,
трафик ждёт» и отводит ему 30 секунд, но перечисление §2 его не содержало:
`status` в эти секунды показывал бы либо `up`, либо `failing`, и оба ответа
неверны. Добавлено значение `waiting`. Не отклонение от спеки, а её внутреннее
противоречие, найденное при правке.

**Нумерация §7 содержала два пункта «3», и `PLAN.md` ссылался на неё со
сдвигом.** Список открытых вопросов получил пункт про лицензию первым уже после
того, как таблица привязки к этапам в плане была написана, — с тех пор её номера
указывали не на те вопросы. Оба файла приведены к нумерации §7 в нынешней
редакции; в таблице плана закрытые вопросы помечены прочерком вместо номера,
чтобы сдвиг не повторился.

### Этап 7 — стор и подписки

**Таблица `user_id` §6.16 заполняется только для четырёх протоколов из шести.**
Ключ слияния читает `user_id` из `params` по таблице §6.16, но разбор ссылок
кладёт туда `uuid`, `password` и `method` только для vless, vmess, trojan и
shadowsocks — ровно для тех, что умеет наша сборка Xray. У hysteria2 `auth`
лежит в userinfo ссылки, у wireguard публичный ключ пира — в своём поле, и
построчный разбор их не достаёт: эти протоколы всё равно уходят в узлы с
`supported: false`. Следствие — два узла hysteria2 на одном `host:port` с
разными учётными данными сливаются в один, потому что ключ вырождается в
`protocol + server + port`. Вырождение само по себе законно (§6.16 называет его
прямо), но здесь его причина не «поля нет у протокола», а «мы его не разбираем».

Консервативный вариант — оставить как есть: неподдержанный узел не пробуется и
не выбирается (§6.11), истории проб у него нет, и терять слиянию нечего. Цена
ограничена списком узлов: провайдер отдал два, показали один. Чинится в тот же
день, когда hysteria2 или wireguard попадут в сборку Xray, — тогда их разбор
станет обязательным по другой причине, и таблица §6.16 заработает целиком.
Отдельная проверка на это не написана намеренно: она закрепила бы нынешний
пробел разбора как ожидаемое поведение.

**Два узла с одним `merge_key` в одной группе переживает только первый.** §6.16
задаёт ключ и молчит о том, что делать, если он совпал у двух узлов уже лежащих
в сторе. Такое возможно как след прежней ошибки или правки самого правила.
Решение: карта ключей хранит первый, второй неотличим от него и уходит в
`Removed`. Причина — карта иначе не строится, а выбирать между двумя
неразличимыми узлами всё равно не по чему. В группе `manual` случай невозможен
по Р10: ключа там нет вовсе.

**S37 проверен с одной стороны шва, и это не обойти внутри этапа 7.** Регистр
требует, чтобы восстановленный из файла узел в состоянии `alive` не считался
проверенным: иначе fail-close §5.6 не наступит там, где обязан. Проверка
отнесена к `internal/store`, но само утверждение — про `health.Manager`, а у
него нет никакого API засева состояния: `Config.Nodes` принимает только
`{ID, Supported}`, а `probed` выставляется исключительно внутри
`nodeState.record()`. Сквозная проверка потребовала бы функции восстановления в
`internal/health`, то есть правки зелёного этапа 5 ради теста этапа 7.

Сделано: стор доказывает свою половину — восстановленный срез приходит с пустым
окном и нулевым `traffic_failures`, и в `health.json` нет поля, которым «узел
уже пробовали» дошло бы до живости вообще. Отсюда `probed == false` по
собственному правилу `health`. Вторая половина — что живость действительно не
считает такой узел проверенным — остаётся за этапом С, где связка соединит стор
с менеджером; там же ей место и по §3.4, потому что соединяет их `agent`, а не
любой из них сам. Не за этапом 8: тот про L3 и защиту от петли.

Цена записана честно: пока связки нет, между «стор отдаёт пустое окно» и
«fail-close наступает» лежит непроверенный стык. Он единственный в этапе, где
восстановленное состояние может соврать, и потому вынесен сюда, а не оставлен в
списке §9 регистра.

### Этап С — связка

**`health` не умел менять набор узлов, и §5.8 из-за этого не выполнялся.**
`Manager` принимал узлы только в `New`. Обновление подписки означало бы
пересоздание менеджера, то есть обнуление окна, `rtt` и состояния всех узлов —
той самой истории, ради сохранения которой §5.8 отказывается от полной замены.
Стор при этом честно сохранял бы `id` на диске, а живость начинала бы с нуля
каждые несколько часов, и снаружи это выглядело бы как работающий diff.

Добавлен `Manager.SetNodes`: оставшийся узел сохраняет `nodeState` целиком,
исчезнувшие уходят, порядок берётся из нового набора (Р8). Единственная правка
зелёного этапа 5 за весь этап С, и она чистое дополнение — ни одна из 43
проверок этапа 5 не менялась.

**Первая редакция `SetNodes` внесла гонку данных.** Она мутировала
`nodeState.node` под замком менеджера, но `Manager.probe` читает `s.node.ID`
**вне** замка — по построению: проба идёт в сеть, и держать на ней замок нельзя.
Нашёл `go test -race`, не чтение. Консервативная починка: живой объект не
мутируется вовсе, заводится копия с той же историей и склонированным окном.
Проба, оставшаяся в полёте, допишет результат в осиротевший объект и потеряет
его. Цена — одна потерянная проба на изменившийся узел при обновлении подписки,
то есть один раунд; альтернатива — гонка в модуле, на котором держится
автопереключение.

**Таймер дренажа заводился внутри горутины.** Потолок §5.8 отсчитывался поэтому
не от смены набора узлов, а от того момента, когда планировщик доберётся до
горутины. На настоящих часах это незаметная неточность, которая не нашлась бы
никогда; на фейковых — прямой отказ проверки W21. Таймер заведён синхронно в
`swap`.

**Охраняющие проверки в первой редакции были зелены при обоих состояниях
флага.** Написаны ветвлением: «политика включена — проверяем хорошее, выключена
— проверяем плохое». Это ровно тот дефект, ради которого существует `negcheck`,
и он назвал семь проверок из восьми. Правило §8 требует не «тест знает про
флаг», а «тест краснеет без политики». Переписаны безусловными утверждениями.

Следствие, которое пришлось внести в продукт: с выключенным `xray_drain` прежний
инстанс Xray закрывается **синхронно** в `swap`, а не горутиной. Иначе
охраняющая проверка зеленела по расписанию планировщика, а не по существу. И W18
смотрит на само соединение, а не на флаг `closed`: §5.5 обещает соединение.

**`hop bypass --on` снимает туннель, а не разворачивает трафик внутри него.**
§5.6 говорит «осознанно выпускает трафик напрямую» и не говорит как. Второй
вариант — оставить интерфейс и гнать весь трафик в bypass-сокет — означал бы,
что весь трафик машины идёт через NAT пользовательского процесса (§6.8), который
для этого не строился. Цена выбранного варианта заметная и записана в регистре:
в состоянии `bypass` фаза туннеля равна `down`, и снаружи это выглядит как «VPN
выключен», поэтому `status` обязан объяснять разницу словами.

**Резолвер этапа С отвечает SERVFAIL, а не молчит.** Настоящий резолвер — этап
6, но связке надо что-то подставить уже сейчас. Молчание подвесило бы приложение
до таймаута — то, что запрещает §5.6. Пустой `NOERROR` хуже: он означает «имени
нет», приложение кэширует отрицательный ответ и не повторит запрос, когда этап 6
приедет. Следствие: до этапа 6 связка не резолвит имён, и её датаплейн
проверяется по адресам.

**`PacketDevice` не закрывается агентом.** §3.2 даёт ему чтение, запись и MTU —
закрывать нечем, и это правильно: устройством владеет тот, кто его выдал.
`Transport.Release` снимает туннель и закрывает устройство одним вызовом.

**§2 иллюстрировал разделение фаз невозможной комбинацией.** Пас 0 обосновал две
фазы примером «туннель `orphaned`, а трафик `bypass`». Такой не бывает:
`orphaned` означает отсутствие агента, а `bypass` держит агент и на диск не
пишет (§5.6) — реаттачившийся агент приходит без обхода. Довод от замены примера
не меняется, он в разных владельцах и в §5.2. Пример заменён на «`up` +
`failing`» — туннель поднят, живых узлов нет; истинны обе половины.

**Номер решения `Рn` сам по себе двусмыслен — всегда указывать регистр.**
Обнаружено при сверке этапа С. Серий две, и они пересекаются:

- регистр решений паса 0 (тот, что закрывался выбором в артефакте) — `Р1–Р26`;
- регистры верификации, где нумерация задумывалась сквозной, — `Р1–Р6`
  автопереключение, `Р7–Р14` стор, `Р15–Р26` DNS, `Р30+` связка.

Отсюда `Р15`–`Р26` означают разное в зависимости от того, какой документ имелся
в виду: `Р22` — это и «насколько живуч `hop bypass --on`» (пас 0), и «bootstrap
ходит на настроенные апстримы, а не на системные» (DNS). Один такой промах уже
случился в этих заметках и был исправлен.

Переименовывать серии задним числом дороже, чем ссылаться полностью: ссылка вида
«Р22 регистра решений» или «Р22 регистра DNS» однозначна и ничего не ломает.
Правило — всегда с названием регистра; голый номер считать опечаткой.

**Стартовое окно §5.6 отвечало RST вместо ожидания.** Нашлось рецензией со
стороны, а не проверкой: первая редакция регистра связки отнесла W33 к свойствам
`netstack` и не написала её. Шов лежал ровно в связке: `Healthy()` возвращает
`true` в стартовом окне, поэтому вердикт — `Proxy`, диалер идёт за активным
узлом, не находит его и отдаёт ошибку, а `netstack` превращает любую ошибку
дозвона в RST. То есть §5.6 нарушался ровно тем способом, который он сам и
называет: «иначе первое же приложение получает RST в те секунды, пока идёт
стартовый обход подписки».

Починка не могла быть ожиданием в диалере: он вызывается из обработчика
форвардера, то есть с цикла чтения устройства, и ожидание в нём остановило бы
весь туннель. Введена `netstack.ErrNotReady`: в стартовом окне диалер отдаёт её,
а `netstack` не отвечает на SYN вовсе — `Complete(false)` вместо
`Complete(true)`. Ожидание держит TCP клиента, а не наша горутина, и повтор SYN
приходит сам. Молчание здесь §5.6 не нарушает: тот запрещает молчание там, где
решение принято, а в стартовом окне оно ещё не принято. Проверка — W33.

### Этап С — шов с ОС (`cmd/hop`)

**`cmd/hop` оставался заглушкой этапа 2 и после того, как связка была
написана.** Коммит связки добавил три тысячи строк в `internal/agent` и ни одной
в `cmd/hop`. «Первый настоящий `hop up`» произошёл в `harness_test.go`, а не в
бинаре: собранный `hop` не содержал ни одного символа Xray, netstack, `agent`
или `store` — проверяется `go tool nm`. Датаплейном оставался `drain`, читавший
устройство и выбрасывавший прочитанное, при том что `hopd` заворачивал в туннель
весь трафик машины. То есть `hop up` означал не «трафик мимо прокси», а чёрную
дыру.

Нашлось не проверкой и не рецензией, а жалобой на рабочие конфиги, которые «не
идут через прокси». Ни один уровень регистра этого поймать не мог: L1 и L2
проверяют `internal/agent` на фейках, L3 этапа 8 ещё не написан, а связь «пакеты
модулей зелены» → «продукт работает» не проверял никто. Вывод для регистра: у
каждого этапа, кончающегося бинарём, обязана быть проверка на самом бинаре, и
она не бывает L1.

**`AgentUID` уходил нулём.** `cmd/hop` собирал `tunnel.Params` без этого поля, и
правило §6.8 раскладывалось как `uidrange 0-0` — то есть выводило мимо туннеля
трафик root, а не агента. При заглушке это было незаметно: агент никуда не
ходил. При живом датаплейне трафик Xray к узлу возвращался бы в туннель петлёй.
Правило §6.8 при этом выглядело выполненным — оно стояло в `ip rule`. Проверка —
W36, и она смотрит на число, потому что поведение здесь наблюдаемо только с
поднятым TUN.

**Проба засчитывалась дважды.** §6.7 требует, чтобы проба шла через outbound
проверяемого узла, а отказ дозвона на уровне системного диалера Xray уже уходит
в `ReportFailure` (`internal/engine/dialer.go`). Значит один провал пробы
попадал бы и в окно проб, и в счётчик ошибок трафика, а §5.4 требует **двух
разных** счётчиков: узел умирал бы вдвое быстрее порога §6.3 — в ту сторону,
которую `classify.go` сам называет худшей. Решение Р38: контекст пробы
помечается (`engine.WithProbe`), и `nodeDialer` по метке молчит. Отменяется
рассылка, а не классификация: вердикт по-прежнему возвращается вызывающему,
иначе проба не отличила бы смерть узла от отказа целевого хоста. Проверки — W37
в `engine` (близнец `TestDeadNodeGivesFatalVerdict`, разница ровно в метке) и
W37 в `agent`.

#### Deviations

**§5.5 в части разрыва соединений не выполняется в продукте.**
`health.Config.Interrupt` оставлен пустым: разрыв активных соединений при смерти
узла требует от `netstack` учёта живых потоков, а `flowTable` хранит вердикты,
не соединения, и `tcpStack` не ведёт реестра релеев. Это не новая дыра — W8 и
W14 красны в регистре с самого этапа С, — но до сих пор она была теоретической,
а теперь наблюдаема: при смерти узла установленные соединения повиснут до
таймаута вместо RST. Консервативный выбор здесь — оставить поле пустым, а не
подсунуть заглушку, возвращающую ноль: ноль означал бы «рвать было нечего», и
`interrupted_connections` в событии переключения врал бы вместо того, чтобы
отсутствовать. Закрывается вместе с W8/W14, реестр релеев — работа этапа 8, где
`netstack` и так переписывается под настоящий TUN.

**Закрыто.** См. ниже, «Этап 8 — реестр релеев netstack и разрыв соединений».

**Датаплейна на Windows нет.** Устройство там приезжает именованной трубой, а не
дескриптором (`ipc.Result.FD` всегда -1), и труба — работа этапа 8 вместе с
`wintun.dll`. `openDevice` на Windows отказывает named-ошибкой, а не отдаёт
заглушку: молчаливая заглушка означала бы ровно тот дефект, ради которого этот
этап делался, — «`hop up` прошёл, трафика нет».

### Этап 8 — реестр релеев netstack и разрыв соединений (§5.5, W8/W14)

Контракт снаружи был закрыт с этапа С и ждал только вызывающей стороны:
`health.Config.Interrupt` — `func() int`, и `emitLocked`
(`internal/health/manager.go:687`) зовёт его ровно при `reason: dead`, уже после
того, как `m.active` под тем же локом переехал на новый узел. Внутри `Interrupt`
поэтому не нужно решать, «чьи» соединения рвать: к моменту вызова `Active()` уже
отдаёт новый узел, а узел соединения фиксирован на дозвоне и не меняется (Р30,
`internal/agent/dialer.go:32`). Не хватало только того, что рвать:
`tcpStack.pipe` (`internal/netstack/tcp.go`) заводило на каждое TCP-соединение
два `io.Copy` и `stop()`, но не сохраняло ни то, ни другое.

**Решение.** Реестр открытых релеев в `tcpStack` — карта `*tcpRelay` под своим
мьютексом. Запись встаёт в `pipe` до старта горутин-насосов и снимается изнутри
того же `stop()`, которым релей закрывается и естественным концом потока (любая
сторона умолкла). `tcpStack.closeAll()` берёт снимок карты под локом и зовёт
`stop()` по снимку уже вне лока — иначе `removeRelay` внутри `stop()` дал бы
взаимную блокировку самим собой. `Stack.InterruptTCP()`
(`internal/netstack/netstack.go`) — тонкая обёртка наружу.
`Agent.InterruptConnections()` (`internal/agent/wire.go`) отдаёт 0, если стек не
поднят (агент в `Down`), и делегирует в `InterruptTCP` иначе; `cmd/hop/main.go`
подключает его в `health.Config.Interrupt` тем же приёмом отложенного замыкания,
что уже стоял у `Prober` (`var a *agent.Agent` объявлена до сборки живости,
потому что оба поля зовут метод ещё не собранного агента).

UDP в реестр не входит: SPEC и регистр (T9, T10, W8) говорят конкретно про TCP,
и `natTable` (`internal/netstack/udp.go`) им не тронут — то же расширение тем же
приёмом осталось следующим шагом, не этим.

**Чего не хватало для проверки и что построено.** Ни A18 (`internal/health`), ни
T9/T10 (`internal/l2`, `TestT9BlackholeBreaksLiveConnection` и сосед) не
проходят через настоящий `tcpStack.pipe` — оба рвут через стенд
(`harness.interrupt()` в `internal/l2/harness_test.go`, чей комментарий прямо
говорит: «в продукте это делает netstack; здесь — стенд»), и это остаётся верно:
они проверяют контракт вызова (сколько раз, с какой причиной), а не сам реестр.
Недостающая проверка — новый `internal/netstack/interrupt_test.go`: второй,
настоящий `gvisor`-стек (`gstack.Stack` с собственным `LinkEndpoint`) по другую
сторону того же `packettest.FakeDevice`, что и остальные тесты пакета — мост не
граница ОС (`internal/bench`), потому что важно настоящее TCP-рукопожатие через
`tcp.Forwarder`, а не сама труба. `fakenet.Dialer.DialTCP` отдаёт эхо-соединение
— им и доказывается, что реле живо (данные ходят) до `InterruptTCP`, а не только
«дозвон случился». Три теста: `TestInterruptTCPClosesLiveConnection` (одно
соединение, эхо, разрыв, клиент видит закрытие),
`TestInterruptTCPCountsAllOpenRelays` (три соединения, счёт и разрыв всех, не
первого попавшегося) и `TestInterruptTCPWithNoConnectionsReturnsZero` (рвать
нечего — не ошибка). `FakeDevice` получил маленький публичный метод `Written()`
— тот же канал, которым уже жил `WaitEmitted`, но для стенда, которому нужен
непрерывный насос, а не разовое ожидание известного числа пакетов.

Закрывает W8 и W14 (`docs/verification-agent.md:310,321`).

### §6.8 переписан по замеру, а не по рассуждению

**Спека утверждала неверный факт, и на нём стоял выбор механизма.** §6.8
говорил, что `SO_BINDTODEVICE` требует `CAP_NET_RAW` и потому непригоден
непривилегированному агенту, а значит на Linux нужен `ip rule` с UID-диапазоном.
Оба утверждения не выдержали замера.

Замерено под uid 1000 без capabilities (ядро 7.1.5), дважды и независимо:

| операция                                     | результат |
| -------------------------------------------- | --------- |
| `SO_MARK`                                    | `EPERM`   |
| `SO_BINDTODEVICE`, свежий сокет              | работает  |
| `SO_BINDTODEVICE`, повторно на том же сокете | `EPERM`   |
| `SO_BINDTODEVICE`, отвязка                   | `EPERM`   |

Ядро проверяет `CAP_NET_RAW` только когда `sk->sk_bound_dev_if` уже ненулевой.
Первая привязка разрешена всем — а это ровно тот режим, в котором привязку
применяют все изученные реализации: в `Control`-колбэке диалера, один раз, до
`connect`.

**Замер при поднятом туннеле** (решающий, делался последним):

```
uid 1000: без привязки → 192.168.0.125    с привязкой → 192.168.0.125
uid 0   : без привязки → 10.255.0.1       с привязкой → 192.168.0.125
```

Читается так. Под root непривязанный сокет уходит через `hop0` — **датаплейн
работает сквозняком**, соединение до внешнего адреса устанавливается через
netstack, диалер, Xray и узел. Привязанный уходит мимо туннеля при активных
туннельных правилах — **привязка годится как защита от петли**. Под uid 1000 в
туннель не попадает ничего: uid-правило §6.8 выводит мимо туннеля весь трафик
пользователя, потому что агент делит uid с рабочим столом.

Последнее и есть та поломка, с которой начался этот заход: «конфиги рабочие, а
трафик не идёт через proxy». Правило §6.8 при этом выглядело выполненным — оно
стояло в `ip rule` и делало ровно то, что написано.

**Ссылка на `sing-tun/tun_linux.go:791` была прочитана неверно.**
`NewRuleUIDRange` служит там пользовательскому split-tunneling'у по приложениям
(на Android uid = приложение). Защитой от петли uid-правило не пользуется ни
один из изученных проектов. У sing-box проксирующий процесс — root, поэтому
uid-правило у них по построению не может быть защитой от петли; nekoray и
hiddify-core, у которых расстановка процессов такая же, как здесь, опознают
трафик своего движка и выпускают его привязанным к интерфейсу аутбаундом.

**Урок для метода, а не только для §6.8.** Раздел был написан связно и
обоснованно, ссылался на настоящий механизм в настоящем чужом коде — и был
неверен в факте, который проверяется двадцатью строками на C. Утверждение вида
«системный вызов требует привилегий» обязано быть замерено до того, как из него
выведен выбор архитектуры.

#### Deviations

**Привязка не накрывает сокеты мимо Xray.** uid-правило выводило мимо туннеля
весь трафик процесса; привязка — только те сокеты, на которых поставлена.
Резолвер bootstrap (§5.7) и скачивание подписок (§5.8) обязаны биндиться своим
`Control`-колбэком. Пропущенный сокет образует петлю молча, и никакая проверка
уровня L1 этого не увидит.

**Перепривязка невозможна.** При смене дефолтного интерфейса установленные
соединения не переносятся — их надо рвать и передозваниваться. Записано в §6.8
следствием первым.

**Нижняя граница по версии ядра не установлена.** Замер сделан на 7.1.5. С какой
версии первая `SO_BINDTODEVICE` непривилегированна — не проверено; на старых
ядрах привязка может отказать, и тогда нужен либо отказ дозвона, либо
capability. Проверять до объявления поддержки дистрибутивов.

### Этап 9 — BypassSink: настоящий NAT-путь для bypass (§6.10, §6.8)

До этого захода `netstack.Config.Bypass` в продукте был `nil`, и `Stack.handle`
(`internal/netstack/netstack.go:259`, вердикт `Bypass`) молча дропал пакет —
единственная оставшаяся дыра, которая лгала о наблюдаемом поведении, а не просто
не реализовывала возможность.

**Решение.** Новый пакет `internal/bypass` — full-cone UDP NAT той же формы, что
`natTable` (`internal/netstack/udp.go`): сокет на исходный `addr:port` клиента,
горутина чтения ответов на каждый сокет, ленивый сметатель простоя на
собственных часах пакета (`clock.Clock`). Отличия от `natTable`, продиктованные
природой bypass: сокет всегда заводится через
`(&net.ListenConfig{Control: cfg.Control}).ListenPacket(ctx, "udp4", ":0")` —
`Control` привязывает его к физическому интерфейсу тем же `SO_BINDTODEVICE`
(§6.8), которым уже пользуются Xray, health-пробы и подписки, — и ключа с
адресом назначения нет вовсе: только `src`, всегда full-cone, потому что ответ
mDNS приходит с unicast-адреса респондера (`192.168.x.y:5353`), а не с адреса
`224.0.0.251:5353`, на который слал клиент. `Send` отказывает двумя разными
ошибками: пакет не IPv4/UDP — `ErrUnsupported`; политика `bypass_sink` выключена
— `ErrDisabled`. Разбор IPv4/UDP вынесен в `internal/packet.ParseUDP4`, отдельно
от `netstack.parse`, чтобы `internal/bypass` не зависел от `internal/netstack`.

Провод: `netstack.Stack.Deliver(pkt []byte)` — обратный путь в устройство через
тот же `s.write`, что и ответы `natTable`/gvisor-релеи (единственный писатель
остаётся один). `agent.Config.BypassControl bypass.ControlFunc` собирает
приёмник в `Up()` тем же отложенным замыканием, что уже стоит у
`InterruptConnections`/`Prober`: `Agent.deliverBypass` берёт `a.mu`, читает
`a.stack`, отпускает и зовёт `stack.Deliver`, если стек ещё жив. Жизненный цикл
`a.bypassNAT` зеркален `a.stack` — заводится в `Up`, закрывается в `Down` и
`watchService`; повторный `Up` после `Down` пересобирает NAT заново, старый
закрытый не переиспользуется. `cmd/hop/main.go` передаёт `physical.Control` (тот
же `*outbound.Selector`, что уже даёт `Interface` и `DialDirect`) третьим
параметром `run()`, симметричным уже существующему `dialDirect` — сам селектор
живёт только в `main()`, поэтому в `run()` идёт уже распакованная функция, а не
сам объект.

Политика `bypass_sink` (`internal/policy`) гасит настоящий приёмник, а не сам
вызов `Send` внутри `netstack.handle`: погасить вызов было бы неверно — тогда
`TestT17MDNSGoesToLocalNetwork` (вердикт-only, `fakenet.Bypass`,
`internal/netstack/netstack_test.go:196`) покраснел бы вместе с политикой, а он
обязан оставаться зелёным всегда, потому что проверяет только вердикт, а не
доставку. Guard-тесты — `TestBypassSendsDatagramFromBoundSocket` и
`TestBypassReplyReturnsToClient` (`internal/bypass`), красные под
`HOP_DISABLE=bypass_sink`.

**Проверка на уровне L3.** `internal/l3/bypass_test.go`,
`TestBypassMDNSReachesPhysicalInterfaceAndReturnsViaNAT` — весь путь
`agent → netstack (вердикт Bypass) → bypass.NAT → физический сокет → обратно`
против настоящего физического интерфейса (veth) в netns, симметрично тому, чем
`interrupt_test.go` стал для W8/W14. Тест форсирует ровно тот случай, который
§6.10 держит в уме как «правило не встало»: правило маршрутизации приоритетом
20000 (`ip rule add to 224.0.0.251/32 lookup <table> priority 20000`) уводит
группу mDNS в туннельную таблицу, и пакет всё равно обязан выйти в LAN — через
NAT-путь, а не через дыру в правилах маршрутизации. Пир (`peerMain`) поднимает
mDNS-респондер, вступающий в группу `224.0.0.251:5353`, и кладёт в ответ и
увиденный адрес источника, и эхо полученной нагрузки. Три независимых
утверждения, каждое своим `t.Fatalf`: пир получил запрос (доказано эхом
нагрузки); адрес источника, увиденный пиром, — адрес физического интерфейса
(`veth0`), а не адрес клиента в туннеле (положительная и отрицательная проверка
разом — это и ловит регресс «форвардит как есть» вместо настоящего NAT); клиент
получил ответ, и пришёл он с адреса респондера.
`HOP_L3=1 unshare -Urn /tmp/l3.test` — 0.17–0.64 с на прогон, три подряд повтора
и полный набор L3 зелёные, включая под `-race`.

**Замеры.**

- Форма правила маршрутизации для mDNS: `ip rule add to 224.0.0.251/32 lookup
  <table> priority N`, где `N` меньше `prioExclusions = 31000`
  (`internal/platform/linux.go:22`), забирает ровно эту группу в туннель, не
  трогая остальной multicast (проверено на SSDP, `239.255.255.250`) и не трогая
  правила, которые раскладывает `hopd` (`31000`/`31500`/`32000`). Проверено не
  только через `ip route get` (кэш маршрута можно спутать с намерением), но и
  счётчиками TX-пакетов на dummy-интерфейсе до/после `sendto` — решение
  маршрутизации действительно исполняется ядром, а не только видно в выводе
  команды.
- Отправка на multicast-адрес не требует членства в группе (IGMP-репорт нужен
  для приёма, не для передачи) — `bypass.NAT` шлёт `WriteTo` на
  `224.0.0.251:5353` без `IP_MULTICAST_IF` и без `IP_ADD_MEMBERSHIP`, и пакет
  всё равно уходит (подтверждено TX-счётчиками из измерения выше). Приём на
  стороне пира требует `IP_ADD_MEMBERSHIP` (`net.ListenMulticastUDP`) — без него
  ядро отбрасывает входящую датаграмму на IP-уровне даже при физическом приходе
  кадра на veth; это стандартное поведение хостового IGMP-членства, не специфика
  veth.
- `net.ListenPacket("udp4", ...)` на Linux отдаёт `*net.UDPConn`, чей `ReadFrom`
  возвращает `*net.UDPAddr` (не строку): прямое приведение типа в
  `bypass.socket` (`a.(*net.UDPAddr)`) обошлось без запасного пути через
  `netip.ParseAddrPort(a.String())`, который есть у `netstack.addrPort` для
  собственных нужд последнего. Проверено самими тестами
  (`TestBypassAcceptsReplyFromAnotherAddress`), на `go1.26.3`/linux — запасной
  путь не понадобился для сокетов, заведённых `ListenPacket` тем же способом.

#### Deviations

**Только UDP.** NAT-путь bypass несёт исключительно UDP; TCP в локальную сеть
(RFC1918, loopback, link-local — вердикт `Bypass` по `isBypass`,
`internal/netstack/verdict.go:119`) остаётся дропом: `bypass.NAT.Send`
отказывает `ErrUnsupported`, `netstack.handle` игнорирует ошибку так же, как и
раньше молчаливый дроп. Причина: §6.10 держит исключения ради обнаружения служб,
которое целиком UDP; §6.8 прямо называет обратным путём bypass ту же таблицу
трансляций, что UDP full-cone §5.3; честный TCP-путь означал бы терминацию
потока в gvisor, а его релей попал бы в реестр разрыва соединений §5.5 (этап 8,
выше), чья семантика «рвём соединения при смерти узла» для bypass-трафика,
никогда не ходившего через узел, неверна. Следующий заход, не забыто, а отложено
осознанно.

**DHCP через NAT-сокет честным быть не может.** Исходный порт клиента-DHCP (68)
переписывается на эфемерный, потому что `bypass.NAT` не сохраняет порт источника
отдельно от адреса, а бинд на порт ниже 1024 непривилегированному агенту
недоступен. DHCP числится в §6.10 среди исключений «мимо туннеля, в локальную
сеть», но настоящий DHCP-обмен через этот NAT-путь недостоверен — записано как
есть, а не умолчано. На практике DHCP самой машины это не задевает (интерфейс
адресуется системой до `hop up`, вне вердиктов netstack); незакрытый случай —
DHCP-relay или иной транзитный трафик на порт 67/68 изнутри туннеля.

**IPv6 mDNS-адрес спеки (`[ff02::fb]:5353`) в `isBypass` не реализован — и не
мог быть, в этом заходе.** §6.10 перечисляет его наравне с `224.0.0.251:5353`,
но `internal/netstack/verdict.go:119` (`isBypass`) сравнивает только с
`addrMDNS` — константой IPv4. Это не пропуск этого захода: IPv6-пакеты вообще не
доходят до `classify()`/`isBypass()` — они отбрасываются раньше, на ветке `!ok`
разбора пакета (`internal/netstack/netstack.go`, `handle`). IPv6 mDNS недостижим
по построению, а не по недосмотру — записано, чтобы следующая сессия, читая
`HANDOFF.json`, не считала эту строку спеки чем-то, что уже хардкожено в коде и
ждёт переноса в конфигурацию.

**Дописано заходом `ipv6_block`:** причина оказалась не та, которую называл этот
абзац. `[ff02::fb]:5353` правилом блокировки IPv6 **не** закрыт — замер: весь
link-local multicast забирает таблица `local` приоритетом 0, выше правила, — и
§6.10 этого и требует. Недостижим он ровно потому, что в туннель не попадает:
у `hopt0` нет ни одного адреса IPv6. Строка «IPv6 в v1 блокируется целиком»
из прежней редакции этого абзаца была неверна и убрана.

**Смена интерфейса не инвалидирует уже открытые bypass-сокеты — дыра, а не
решение.** `Control` привязывает каждый сокет `bypass.NAT` к тому, что
`Selector.Interface()` вернул на момент его создания
(`internal/bypass/bypass.go:143`). «Следствие первое» §6.8 говорит прямо:
привязка сокета неизменна, и смена сети означает, что старые сокеты нужно
передозвонить. Ничего этого не происходит: время жизни NAT привязано к `a.stack`
(Up/Down), и переключение Wi-Fi → Ethernet не рвёт ни то, ни другое. Хуже того —
`sock.seen` обновляется на каждый `Send` (`internal/bypass/bypass.go:139`), а не
только на успешный ответ, поэтому клиент, который ретраит mDNS/SSDP каждые
несколько секунд (а служебное обнаружение делает именно так), держит мёртвый по
привязке сокет вечно живым: идлящая уборка (`Idle`, по умолчанию 60 с) до него
никогда не доберётся, потому что для неё сокет никогда не выглядит
простаивающим. Это хуже, чем «отъедет через 60 с простоя» — это «не отъедет
никогда, пока клиент продолжает спрашивать», а трафик тем временем либо уходит
через старый интерфейс, либо ошибается на `WriteTo`. До находки 1 финальной
волны ревью пользователь при этом не видел вообще ничего; после неё — растущий
`Stats.Blocked` без объяснения причины.

Код-фикс не вошёл в тот заход: обработка смены сети была отложенным пунктом
очереди, а расширять заход за пределы BypassSink автор не стал. Две формы,
которыми фикс мог бы стать, назывались там же: `NAT.Reset()`, которым
наблюдатель селектора зовёт при смене интерфейса, либо жёсткий TTL на возраст
сокета, независимый от `seen`.

**Закрыто** заходом «Этап 9 — перепривязка сокетов bypass» ниже, третьей
формой: NAT опрашивает `Selector.Interface()` на каждой отправке и закрывает
сокеты с устаревшей привязкой. Довод об объёме, которым откладывали, при
проверке не подтвердился — наблюдатель rtnetlink трогать не пришлось вовсе;
разбор там же.

**Full-cone bypass принимает ответ с любого адреса — известное и допустимое
свойство, не регрессия.** Потому что `bypass.NAT` full-cone (§5.3 требует этого
для UDP), любой, кто достанет до эфемерного bypass-порта агента по локальной
сети, может впрыснуть в туннель датаграмму с произвольным адресом источника,
включая адрес внутри туннеля, — `receive` (`internal/bypass/bypass.go:160`)
принимает `ReadFrom` с любого пира и переизлучает его адрес как есть. `natTable`
при `nat_key=src` (`internal/netstack/udp.go`) настолько же открыт — это
свойство модели, а не то, что внесла эта задача, и поведение не меняется.
Дешёвое усиление, названное ревью: отбрасывать ответы, чей адрес источника
совпадает с адресом самого клиента туннеля, — не сделано в этом заходе, записано
как принятое свойство, а не незамеченное.

Closes: `next_task` из `HANDOFF.json` (BypassSink, приоритет 1).

### Этап 8 — списки bypass/block §6.10 из конфигурации (`routing_lists`)

`isBypass` и `isBlocked` (`internal/netstack/verdict.go`) были кодом, а не
данными: диапазоны через `netip.Addr.IsPrivate` и соседей, порты через `switch`,
адреса mDNS и SSDP — константами пакета. Расширить набор (принтер в
CGNAT-диапазоне провайдера, корпоративная подсеть за пределами RFC1918) или
сузить его (в сети нет ни одного устройства Bonjour) было нельзя иначе как
правкой `verdict.go`.

**Решение.** `internal/netstack/routing.go`: `Rule` — правило «префикс +
протокол + порт», где ноль в поле значит «любой», и `Routing` — два списка,
`Bypass` и `Block`. `netstack.Config.Routing *Routing` (`nil` — умолчания
§6.10), `agent.Config.Routing` — тот же провод одним полем выше. Форма
подсмотрена у `Config.DNSUpstreams`: значение конфигурации, у которого пустота
означает умолчание, и до которого CLI и диск ещё не доросли. `classify`
принимает списки третьим параметром и остаётся чистой функцией; `flowTable`
держит разрешённые списки у себя, потому что вердикт принимается один раз на
поток (§3.4), и список, поменявшийся посреди жизни потока, нарушал бы контракт
незаметнее, чем сама смена списка.

**Что настраивается, а что нет.** Пол — исключения §5.6 «разрешённые всегда»
(локальные сети, DHCP, NTP): `resolveRouting` подмешивает их к любому непустому
списку, и убрать их конфигурацией нельзя. Довод: §5.6 обещает, что без них
fail-close ломает саму сеть, а не только выход в интернет, — и это обещание
относится и к неудачному конфигу, а не только к фазе. Ровно тот же довод стоит
за порядком в `classify`: `bypass` проверяется раньше `block`, поэтому список
блокировок из конфигурации не может перекрыть DHCP. Обнаружение служб §6.10
(mDNS, SSDP) — умолчание, а не пол: §5.6 их не перечисляет, они стоят в §6.10
рядом со словом «блокировать нельзя» ради Bonjour и AirPrint, и у того, у кого
в сети нет ни одного принтера, есть право не выпускать multicast мимо туннеля.
Объём взят из формулировки PLAN.md — «списки bypass/block §6.10 всё ещё
захардкожены… и должны приходить из конфигурации», то есть оба списка целиком, —
а не из одного набора адресов обнаружения служб.

Пользовательские split-префиксы сюда по-прежнему не относятся: PLAN.md говорит,
что они идут в правила маршрутизации, а не в вердикт `bypass`, потому что
`bypass` — это NAT через сокет агента, а не прозрачный форвардинг.

**Политика `routing_lists`** гасит чтение конфигурации целиком: с выключенной
политикой `resolveRouting` возвращает `DefaultRouting()` и стек ведёт себя ровно
как до этой задачи. Именно поэтому `TestT17MDNSGoesToLocalNetwork` и T31
(`internal/l3/bypass_test.go`) зелены при обоих её состояниях — они гоняют
умолчания, а умолчания совпадают с прежним жёстким набором один в один, — и
охраняют политику три новых теста: `TestRoutingBypassListComesFromConfig`,
`TestRoutingConfigCanDropServiceDiscovery` и `TestT32ConfiguredBypassLeavesTunnel`
(§8.3).

T32 стоит на стенде с fail-close (живых узлов нет) намеренно: утверждение
«конфигурация вывела поток в локальную сеть» проверяется в самой сильной форме —
вопреки закрытому §5.6 туннелю, — и заодно даёт ожидание с заведомым концом.
`fakenet.Bypass.WaitPackets` ждёт вечно, и охраняющий тест, построенный на нём,
при выключенной политике не краснел бы, а висел бы до таймаута `go test`;
`FakeDevice.WaitEmitted` (2 с) такого недостатка не имеет, поэтому синхронизация
идёт через второй пакет, ответ на который стек пишет в устройство. Тот же приём
уже стоит в `TestBypassSendErrorCountsAsBlocked`.

**Отклонение: блокируется `224.0.0.0/4`, а §6.10 пишет `224.0.0.0/3`.** Прежний
код блокировал multicast через `netip.Addr.IsMulticast`, то есть ровно
`224.0.0.0/4`; `/3` захватывает вдобавок зарезервированный `240.0.0.0/4`,
который не блокировался никогда. Выписывая список данными, легко было бы
«заодно» расширить блокировку до буквы спеки — и спрятать изменение поведения
внутри перевода кода в данные. Выбран консервативный вариант: умолчание
повторяет прежнее поведение один в один, расхождение с текстом §6.10 записано
здесь. Кому нужна буква — дописывает `240.0.0.0/4` в `Block` конфигурацией, и
это ровно то, ради чего список стал настраиваемым.

**Отклонение: пол §5.6 выписан префиксами IPv4 и для IPv6 не эквивалентен.**
`IsLoopback`, `IsPrivate` и `IsLinkLocalUnicast` знают и про `::1`, `fc00::/7`,
`fe80::/10`; список из `127.0.0.0/8`, RFC1918 и `169.254.0.0/16` — нет. Разницы
сегодня не существует: IPv6 до `classify` не доходит вовсе, он блокируется
раньше, на ветке `!ok` разбора (`netstack.go`, §6.9), и это расхождение спеки и
кода уже записано отдельно. Втягивать IPv6 в эту задачу молча было бы хуже, чем
оставить след: `Rule.matches` сравнивает через `netip.Prefix.Contains`, который
для чужого семейства всегда `false`, — то есть список IPv4 не может случайно
выпустить IPv6 мимо туннеля, когда IPv6 до вердикта доберётся
(`TestRoutingIPv4RuleDoesNotMatchIPv6` фиксирует это заранее).

**Отклонение: «конфигурация» пока кончается на `agent.Config`.** Ни CLI, ни диск
списки не задают — источник только программный, как и у `Config.DNSUpstreams`,
которое `cmd/hop/main.go` тоже не выставляет. Это половина провода, и названа
она половиной намеренно: вторая половина (формат на диске, команда CLI, валидация
пользовательского ввода) — вопрос §5.9 и стора, а не вердикта, и делать её вместе
с переводом списка в данные значило бы решать два вопроса одним заходом.

Closes: `next_task` из `HANDOFF.json` (списки §6.10 из конфигурации, приоритет 1).

### Этап 9 — RST для TCP в локальную сеть (`bypass_tcp_reject`)

Последнее место, где вердикт лгал о судьбе пакета. `classify` выдавала `Bypass`
для TCP-потока на RFC1918/loopback/link-local (правила `alwaysBypass` выписаны
без протокола и совпадают и с TCP), `handle` отдавала пакет в
`s.cfg.Bypass.Send`, а `internal/bypass` отвечал `ErrUnsupported` на всё, что не
IPv4/UDP. Итог — `Stats.Blocked` и молчаливый дроп: приложение висело до своего
`connect timeout`. Ровно тот отказ, про который §5.6 пишет «закрытие — отказ, а
не молчание», и ровно тот, который прошлый заход (BypassSink) отложил осознанно,
назвав `internal/reject` правильным ответом.

**`reject.Reply` здесь ответить не может — и это не деталь, а суть задачи.**
`Reply` первым делом спрашивает `Excluded`, а `Excluded` возвращает `true` для
любого локального адреса (`isLocal`: loopback, RFC1918, link-local, multicast,
broadcast). То есть на TCP SYN в `192.168.1.10:445` `Reply` возвращает `nil`.
Два списка отвечают на разные вопросы: `Excluded` — «на что респондер §5.6 не
имеет права отвечать» (там пакет не отвергнут, он просто не наше дело), вердикт
`Bypass` — «что выпустить в локальную сеть». В точке, где путь bypass отвергает
поток, второй вопрос уже решён, и первый список молчал бы там, где отказ и нужен.

**Решение.** `reject.RST(pkt)` — тот же `tcpRST`, что у `Reply`, без вопроса про
`Excluded`: строит RST для TCP-сегмента и `nil` для всего прочего (не TCP, мусор,
сам RST — иначе петля). Никакой политики внутри: кому отвечать, решает
вызывающий. Второй копии построителя RST в продукте по-прежнему нет.
`netstack.refuseBypassTCP` зовёт его под флагом `bypass_tcp_reject` и считает
ответ в `Stats.Rejected`; `nil` и выключенный флаг остаются дропом в
`Stats.Blocked` — молчание обязано быть наблюдаемым, а не бесследным. Шов между
двумя списками закреплён с обеих сторон: `TestBypassTCPNeedsRSTBecauseReplyStaysSilent`
(`internal/netstack`) и `TestRSTAnswersWhereReplyStaysSilent` (`internal/reject`)
утверждают разом, что `Reply` молчит, а `RST` отвечает, — «упрощение» обратно к
`Reply` вернёт молчаливый дроп и покраснеет не только T33, но и объяснение
причины.

**Проверка стоит до `Send`, а не после его `ErrUnsupported`.** Иначе отказ
зависел бы от того, есть ли приёмник вообще (в продукте до этапа 9 его не было,
в половине тестов его нет — `cfg.Bypass == nil`) и какой именно ошибкой он
ответил. «Bypass не несёт TCP» — утверждение уровня вердикта, вытекающее из
§6.8: обратный путь bypass есть та же таблица трансляций, что у UDP full-cone
§5.3, и TCP по ней не пройдёт ни при каком состоянии сокета. Поэтому оно и
живёт на уровне вердикта, а doc-комментарий интерфейса `BypassSink` теперь
говорит это прямо: реализации не нужно уметь отказывать по протоколу.

#### Решение: UDP, отвергнутый bypass, ICMP unreachable не получает

Вопрос был поставлен явно, ответ — **нет**, дроп со счётчиком `Stats.Blocked`
остаётся. `TestBypassSendErrorCountsAsBlocked` не меняет ожидания. Четыре довода,
от сильного к слабому.

**Первый: RFC 1122 §3.2.2 это запрещает.** ICMP-ошибку нельзя порождать в ответ
на датаграмму, адресованную broadcast- или multicast-адресу. А трафик, ради
которого путь bypass вообще существует, — это mDNS (`224.0.0.251`), SSDP
(`239.255.255.250`) и DHCP (`255.255.255.255`): весь он адресован ровно туда.
Отвечающий ICMP на mDNS-запрос нарушал бы стандарт в подавляющем большинстве
случаев, когда бы он срабатывал. Тот же инстинкт уже закодирован в
`reject.isLocal`, который заносит multicast и broadcast в исключения.

**Второй: это был бы неверный ответ, а не просто лишний.** `ICMPv4PortUnreachable`
означает «на том конце никто не слушает этот порт». Про принтер в локальной сети
мы этого не знаем и знать не можем: не слушает не он, а наш сокет не завёлся.
Отказ, сообщающий неправду о третьей стороне, хуже молчания — он уводит
диагностику в сторону, тогда как RST на TCP-в-LAN говорит правду о нашем
собственном пути.

**Третий: подвешивать здесь нечего.** §5.6 обосновывает «отказ вместо молчания»
именно тем, что молчаливый дроп подвешивает приложения до таймаута. TCP-в-LAN —
буквально этот случай: `connect` висит десятки секунд. Служебное обнаружение —
противоположный: mDNS и SSDP по построению без установления соединения,
периодические и ретраящиеся, никто их не ждёт с секундомером. Спасать от
таймаута нечего, потому что таймаута нет.

**Четвёртый: отказ здесь непостоянен, а RST для TCP — постоянен.** Причины, по
которым `Send` возвращает ошибку, — `ErrDisabled` (политика `bypass_sink`
выключена), `outbound.ErrNoInterface` (физического интерфейса сейчас нет),
ошибка `WriteTo`. Все три переменны во времени: интерфейс вернётся через
секунду. Ответить ICMP на такое значит превратить временную неготовность в
жёсткую ошибку у клиента (`net.UDPConn` на connected-сокете отдаёт ICMP наверх
как ошибку соединения). Отказ пути bypass для TCP, наоборот, не изменится
никогда: он следует из формы пути, а не из состояния сети.

Отдельно про `ErrDisabled`: политика `bypass_sink` существует, чтобы её
выключение воспроизводило поведение **до** её появления, то есть молчаливый
дроп. Ответ ICMP под выключенной политикой сломал бы этот контракт и вместе с
ним смысл `negcheck` для неё.

#### Решение: свой флаг `bypass_tcp_reject`, а не `reject_mode`

`reject_mode` не переиспользован. Довод, а не вкус:

- **Его doc-комментарий описывает fail-close** — «fail-close через RST/ICMP, а
  не дроп (§5.6, T12, T13)», — а T33 гоняется на стенде с **живым** узлом.
  Туннель открыт, выход есть, отказ означает «этим путём такой поток не
  пройдёт», а не «выхода нет». Свести их под один флаг — значит либо соврать в
  doc-комментарии, либо расширить его до «все отказы молчат», после чего строка
  T12/T13 «падает без чего» в §8.3 перестанет быть точной.
- **Прецедент рядом и он ровно про это.** `bypass_sink` — тоже флаг пути bypass,
  тоже с молчаливым дропом в выключенном состоянии, и он не стал частью
  `reject_mode`, хотя мог бы по тому же рассуждению. `bypass_tcp_reject`
  наследует ту же линию раздела: `reject_mode` про фазу (fail-close), флаги
  bypass — про путь.
- **`negcheck` теряет разрешающую способность при слиянии.** Guard-набор
  `reject_mode` стал бы объединением двух независимых утверждений, и «краснеет
  без `reject_mode`» перестало бы указывать на одну причину.

Контрдовод, который был взвешен и отвергнут: два флага допускают несогласованную
комбинацию (`reject_mode=drop` при включённом `bypass_tcp_reject` — hop молчит в
fail-close и отвечает в LAN). Он не весит: политики не пользовательская
настройка, а стенд фальсифицируемости, и гасятся они по одной именно затем,
чтобы каждая покраснила свою проверку. Несогласованные комбинации здесь —
инструмент, а не дефект.

Регистрация — `internal/policy/policies.go`, guard — `TestT33TCPToLocalNetworkGetsRST`
(`internal/netstack`), проверен красным под `HOP_DISABLE=bypass_tcp_reject`:
RST не строится вовсе, и тест ждёт полный `WaitTimeout`.

#### Deviations

**`packettest.ExpectRST` и `ExpectICMPUnreach` теперь ждут.** До этого захода они
смотрели только на уже записанное, и это делало их непригодными по назначению:
`Emitted()` осушает очередь, поэтому «сначала `WaitEmitted`, потом `ExpectRST`»
отдавало `nil` из пустоты, а «сразу `ExpectRST`» гонялось с насосом. Оба теперь
ждут до `WaitTimeout` тем же `Written()`-каналом и теми же часами
(`clock.System{}.After`), что и `WaitEmitted`. Поведение для уже записанных
пакетов не изменилось — единственный прежний вызывающий (`fake_test.go`) пишет
пакеты синхронно до вызова и проходит без правок. Изменение чужого пакета внутри
этой задачи — да; альтернатива была бы хуже: третий тест, повторяющий разбор
флагов TCP вручную вместо готового помощника.

**Отказ строится на каждый пакет потока, а не один раз.** Вердикт потока
запомнен (`flowTable`, §3.4), но ответ на нём не кэшируется: ретрансмит SYN,
пришедший до того, как RST дошёл до клиента, породит второй RST. Так же ведёт
себя ветка `Reject` (T12), и это правильнее, чем помнить «уже отвечено»: клиент,
не получивший первый ответ, обязан получить второй.

**TCP-в-LAN, названный bypass из конфигурации, отвергается так же.** Правило
`routing_lists` вида `{Prefix: <публичный префикс>, Proto: ProtoTCP}` даст
вердикт `Bypass`, и поток получит RST, а не выйдет в локальную сеть. Это не
регрессия конфигурируемости, а её честная граница: путь bypass — UDP-NAT (§6.8),
и конфигурация не может подарить ему TCP. До этого захода такое правило молча
дропало пакет, то есть врало ровно так же, только тише.

Closes: `next_task` из `HANDOFF.json` (RST для TCP в локальную сеть, приоритет 1).

### Этап 9 — перепривязка сокетов bypass при смене интерфейса (`bypass_rebind`)

Последняя дыра пути bypass, которая была дырой, а не отложенной возможностью.
`Control` привязывает сокет `bypass.NAT` к тому, что `Selector.Interface()`
вернул в момент его создания, и не перепривязывает никогда. Время жизни NAT
привязано к `a.stack` (Up/Down), а переключение Wi-Fi → Ethernet не рвёт ни то,
ни другое. Наблюдаемый симптом — растущий `Stats.Blocked` без объяснения либо,
что хуже, трафик, уходящий через интерфейс, который пользователь только что
покинул.

#### Выбранная форма и почему не две другие

`HANDOFF.json` предлагал выбрать из двух: `NAT.Reset()`, которым
rtnetlink-наблюдатель `outbound.Selector` толкает NAT при смене интерфейса,
либо жёсткий TTL на возраст сокета.

Взята **третья, и она же первая по существу**: тот же сигнал, но взятый
**опросом**, а не проталкиванием. NAT запоминает имя интерфейса, к которому
`Control` привязал сокет, и на каждом `Send` сверяет его с нынешним ответом
`Config.Interface` — в продукте это `outbound.Selector.Interface`. Разошлись —
сокет закрыт, следующий `Send` заводит новый. Несущий механизм ровно один;
TTL не добавлен.

**Почему это тот же сигнал, а не таймер.** `Selector.Interface()` — не
независимый опрос ОС, а публикуемый ответ того самого rtnetlink-наблюдателя:
`watch` получает `RouteUpdate`/`LinkUpdate`, зовёт `refresh`, и `set` кладёт имя
под `s.mu`. Читая это поле, NAT читает результат события, а не гадает по
времени. Разница с `Reset()` только в том, кто кого будит, и она в пользу
опроса: `Reset()` закрывает все сокеты на **любое** событие наблюдателя (а их
на активной сети много, и почти все — не смена интерфейса), а сравнение имён
срабатывает ровно тогда, когда интерфейс действительно другой.

**Почему не TTL.** TTL лечит симптом — заклинивший сокет, — а не причину, и
цену за это платит вслепую: слишком короткий рвёт исправные обмены, слишком
длинный оставляет окно утечки. Ни одно значение не выводится ни из чего.
Полом под сигналом он тоже не нужен: сигнал не может «не прийти», потому что
его не ждут — его читают на каждом `Send`, то есть ровно в тот момент, когда
устаревшая привязка впервые могла бы навредить.

#### Довод об объёме, которым откладывали, не подтвердился

Прошлый заход записал в `implementation-notes.md` и в `HANDOFF.json`, что
сделать это правильно значит трогать rtnetlink-наблюдатель `outbound.Selector`,
и сослался на «Global Constraint 9, `constraints.md`».

Проверено по существу: **трогать наблюдатель не нужно**. Всё, что дало бы
проталкивание, уже опубликовано — `Selector.Interface()` экспортирован, живёт
под `RWMutex`, обновляется наблюдателем и уже отдаётся связке как
`agent.Config.Physical` (`cmd/hop/main.go` передаёт туда `physical.Interface`).
Заходу понадобилось одно поле в `bypass.Config` и один проброс в
`agent/wire.go`; `internal/outbound` не изменён ни на строку. Иначе говоря,
основанием отложить служил объём, которого у задачи нет: правильная форма
дешевле той, ради дороговизны которой её отложили.

Отдельно: **`constraints.md` в репозитории не существует** — ни в рабочем
каталоге, ни в истории (`git log --all -- constraints.md` пуст на всех ветках).
Ссылка была на несуществующий документ, и именно ею обосновали перенос задачи в
очередь; следующий заход принял её на веру, потому что проверить ссылку дешевле,
чем она выглядит, только если её проверить. Ссылка убрана из `HANDOFF.json`
целиком, а правило, которое она изображала, названо своими словами как
договорённость проходов: **заход закрывает свой пункт очереди и не расширяется
на соседние модули; если правильная форма требует изменить чужой пакет — это
записывается в Deviations с доводом, а не служит основанием отложить задачу
молча**. Именно так поступали предыдущие заходы, меняя `internal/packettest` и
`internal/reject` ради своих задач. Всякую будущую ссылку на источник правила
следует проверять `ls` и `git log --all --` прежде, чем на неё опираться.

#### Решения

**Опрос — до захвата `n.mu`.** `Config.Interface` — чужой колбэк (в продукте
под своим `RWMutex`), звать его под своим замком незачем.

**Закрываются все сокеты с чужой привязкой, а не только тот, за которым
пришли.** Событие общее: интерфейс сменился для всей машины. Оставленный сокет
продолжал бы не только слать через прежний интерфейс, но и принимать на нём
ответы своей горутиной `receive`, отдавая их в туннель, — то есть путь внутрь
пережил бы путь наружу.

**Отсутствие маршрута по умолчанию сменой интерфейса не считается.** `Interface`
вернул ошибку или пустое имя — сравнивать не с чем, сокеты не трогаются. Это
законное переходное состояние ноутбука (§6.8, `outbound.New`: «Interface тогда
возвращает `ErrNoInterface`»), и разрыв живого сокета по нему превратил бы
мгновенную неготовность в жёсткий отказ — тот же довод, которым прошлый заход
оставил UDP-отказ молчаливым. Когда маршрут вернётся под другим именем, сличение
сработает тогда.

**`Config.Interface` не обязателен.** `Control` и `Reply` обязательны, а этот —
нет: `Config.Bypass` у связки старше, и тесты подставляют NAT без всякого
физического интерфейса. Пустое `sock.iface` означает «привязка неизвестна» и
никогда не считается устаревшей — это в точности прежнее поведение. Цена в том,
что забытый проброс молча выключил бы механизм в продукте; её платит W47.

**`Stats.Rebound`.** Счётчик закрытых по смене привязки сокетов, рядом с
`Sockets` и `Orphaned`. Растущее значение при стоящей сети означало бы, что
`Interface` отвечает неустойчиво. Наружу выведен следующим заходом — см.
«Этап 9 — счётчики bypass в снимке стека».

#### Флаг: свой, `bypass_sink` не переиспользован

Правдоподобным кандидатом на переиспользование был `bypass_sink`, и он не
годится **механически**, а не по вкусу: `bypass_sink=off` заставляет `Send`
вернуть `ErrDisabled` первой же строкой, до всякого сокета. Охраняющая проверка
покраснела бы под ним по чужой причине — не «сокет не сменился», а «наружу
вообще ничего не ушло», — и не отличала бы сломанную перепривязку от выключенного
пути. Охрана, краснеющая не от того, что охраняет, не охраняет ничего, и
`negcheck` потерял бы разрешение: «красное без `bypass_sink`» перестало бы
называть одну причину. Тот же довод, которым прошлый заход не слил
`bypass_tcp_reject` с `reject_mode`.

`bypass_rebind` зарегистрирован в `internal/policy/policies.go` рядом с
`BypassSink` и `BypassTCPReject`, с двумя охраняющими проверками. Обе написаны и
увидены красными **до** реализации, отдельным коммитом (`0dbf087`) — порядок,
которого держались три прошлых захода. Красными по существу, а не по
компиляции: проводка и поле `Config.Interface` вошли в тот же коммит именно
затем, чтобы падало утверждение, а не сборка.

#### Ловушка теста

`sock.seen` обновляется на **каждый** `Send`, а не на успешный обмен. Тест,
который замолчит на время смены интерфейса, пройдёт по неверной причине: сокет
соберёт обычная уборка простоя. Закрыто двумя приёмами разом.

Первый: в модульной проверке **часы стоят**. `sweepLocked` при неподвижных часах
не срабатывает вовсе (`now.Sub(n.swept) < n.idle/2`), поэтому уборке физически
некого собирать; проверка это ещё и утверждает явно, сверяя `clk.Now()` в конце.
Второй: клиент **шлёт непрерывно** — до смены, сразу после неё, — и проверка
требует, чтобы до смены порт не менялся, а после сменился. Один и тот же
механизм обязан и молчать без причины, и сработать по причине.

Отдельная проверка, `TestBypassIdleSweepNeverCollectsSocketUnderTraffic`,
закрепляет саму ловушку: при непрерывном трафике шагами в ¾ `Idle` уборка
запускается на каждом `Send` и не собирает сокет никогда — 7.5×`Idle`, и сокет
всё тот же. Она не охраняет флаг (зелена при любом его состоянии), она
объясняет, почему без `bypass_rebind` дыра не закрывается сама.

`fakenet.Bypass.WaitPackets` не используется нигде: он ждёт вечно и превратил бы
красный тест в зависание. Наблюдаемое — исходный порт, с которым датаграмма
приходит слушателю, и `listener.SetReadDeadline` с заведомым концом.

#### Новые проверки

- `TestBypassInterfaceChangeRebindsSocket` (`internal/bypass`) — охраняющая,
  сам механизм; проверена красной под `HOP_DISABLE=bypass_rebind`.
- `TestBypassSocketRebindsOnInterfaceChange` (`internal/agent`) — W47, охраняющая,
  шов `Config.Physical` → `bypass.Config.Interface`; тоже проверена красной.
- `TestBypassKeepsSocketWhenInterfaceUnknown` (`internal/bypass`) — консервативный
  край: пропавший default route за смену интерфейса не считается.
- `TestBypassIdleSweepNeverCollectsSocketUnderTraffic` (`internal/bypass`) —
  ловушка, не охрана.

Номерного T-теста заход не добавляет: утверждение модульное, как и у обоих
охранников `bypass_sink`, и §8.3 не трогается. L3-стенд со вторым veth (форма,
которую предлагал `HANDOFF.json`) не строился — он проверял бы `SO_BINDTODEVICE`
ядра, а не решение о переоткрытии сокета; ядро на этом пути уже покрыто T31.

#### Deviations

**Сигнал берётся опросом, а не проталкиванием — и это отход от формы, названной
в `HANDOFF.json` первой.** Форма из очереди (`NAT.Reset()` из наблюдателя)
отвергнута в пользу более дешёвой и более точной; довод выше. Консервативный
вариант по смыслу `CLAUDE.md`: он не добавляет ни нового источника событий, ни
новой горутины, ни изменений в платформенном пакете.

**Сверка идёт на `Send`, а не по таймеру, поэтому сокеты чужих клиентов
закрываются в момент первого `Send` любого из них.** Пока NAT молчит целиком,
устаревшие сокеты живут — но и вреда не наносят: наружу через них ничего не
уходит. Единственный остаток — горутина `receive`, способная принять ответ на
старом интерфейсе в этом промежутке; первый же `Send` закрывает все такие
сокеты разом, не только тот, за которым пришли, ровно ради этого.

**`Stats` вырос третьим полем.** `Rebound` добавлен в структуру, которую на
момент этого захода в продукте никто не читал (`Stack.Stats` её не подмешивала;
следующий заход это закрыл). Поле заведено не «на будущее», а потому что охраняющая проверка
утверждает срабатывание механизма напрямую, а не только через смену порта.

Closes: `next_task` из `HANDOFF.json` (Invalidate bypass sockets on interface
change, приоритет 1).

### Этап 9 — счётчики bypass в снимке стека (`Stack.Stats`)

`bypass.NAT.Stats()` считал три числа (`Sockets`, `Orphaned`, `Rebound`) для
одних только тестов: в продукте его не звал никто, и `Stack.Stats()`
подмешивала `natTable`, но не приёмник bypass, хотя стек держит его в
`Config.Bypass`. Дороже всего обходился `Rebound`: «сеть в порядке» от
«интерфейс мигает» отличимо только по нему, а прочитать его было неоткуда.

#### Форма: приёмник остался `Send`-only

Выбор был из двух: расширить `netstack.BypassSink` вторым методом либо оставить
его односложным и спрашивать счётчики проверкой типа на необязательном
интерфейсе. Взят второй вариант — `BypassStatSource`.

**Несущий довод — способность есть не у всякой реализации, а обязанность
досталась бы всем.** `BypassSink` описывает ровно одну обязанность: выпустить
пакет мимо туннеля. Счётчики сокетов есть у того, у кого есть сокеты; у
`fakenet.Bypass` их нет и не будет, а этот пакет намеренно не зависит ни от
`testing`, ни от продуктовых пакетов (его doc об этом и написан — им пользуется
бенчмарк). Расширение интерфейса заставило бы его импортировать
`internal/bypass` ради типа возвращаемого значения, а всякого будущего приёмника
на macOS и Windows — возвращать нули по обязанности. Отказ от расширения ничего
не отнимает: приёмник, который считать умеет, подмешивается; который не умеет —
даёт нули, и это честное «неизвестно», а не подделанный ответ.

Второй довод — в этом же файле уже дважды принято ровно это решение:
`StreamResolver` (знание о транспорте к замороженному `Resolver`) и
`FlushableResolver` в связке. Формулировка из doc `StreamResolver` подходит
дословно: объявил метод — зовём его, не объявил — прежнее поведение. Заводить
третьим случаем другой приём значило бы разводить два способа делать одно.

**Что за это заплачено.** Несовпавшая проверка типа промахивается **молча**,
нулями — тот же класс отказа, ради которого написан W47. Поэтому охраняющих
проверок две, и вторая (`TestStackStatsSeesRealBypassNAT`) ставит за стек
настоящий `bypass.NAT`, а не подставной приёмник: разъехавшаяся сигнатура
`Stats()` даст зелень на подставном и красноту на настоящем.

#### Уборка простоя из `Stats()` убрана

`bypass.NAT.Stats()` попутно прокручивала уборку простаивающих сокетов, и её
doc объяснял это паритетом с `natTable.Stats()`. **Паритета нет:**
`natTable.stats()` (`internal/netstack/udp.go`) — чистое чтение под замком, а
принудительная прокрутка вынесена в отдельный `natTable.Sweep()`; замер B3
(`internal/bench/netstack.go`) так и делает — двигает часы и шлёт ещё один
пакет, вместо того чтобы надеяться на снимок. Утверждение в doc было о
механизме, и оно не выдержало сверки с механизмом.

Пока `Stats()` никто не звал, совмещение было безвредным. С подмешиванием оно
становится продуктовым поведением, и плохим сразу по трём причинам.

- **Наблюдение меняет наблюдаемое.** Время жизни сокета начало бы зависеть от
  того, открыт ли у пользователя экран состояния и как часто он опрашивается.
- **Снимок стал бы внутренне разноголосым.** Числа `natTable` означают «на
  момент последнего пакета», числа bypass означали бы «на сейчас», а лежат они
  в одной структуре и читаются как одно измерение.
- **Это поведение, а не наблюдаемость.** Правило репозитория — новое поведение
  едет со своим флагом и краснеющей проверкой. Заход об наблюдаемости, который
  протаскивает изменение уборки побочным эффектом геттера, ровно это правило и
  обходит.

Цена решения названа вслух и остаётся дырой: после того как трафик прекратился,
сокеты bypass доживают до `Close`. Закрывается она фоновым тикером — то есть
поведением, которому полагается флаг и охрана, — и это кандидат в следующий
заход, а не побочный эффект этого.

`TestBypassIdleClosesSocket` опирался на уборку внутри `Stats()` и переписан:
уборку прокручивает второй клиент, как в B3. Проверено мутацией — с отключённым
`sweepLocked` тест краснеет (`Sockets = 2`).

#### Сосед: `Rejected` больше не складывает два разных отказа

Заход `bypass_tcp_reject` оставил `Stats.Rejected` суммой двух причин:
fail-close («живого узла нет») и отказ TCP с вердиктом bypass («узлы живы, но
этим путём поток не пройдёт»). Числа складывались, а лечатся эти неисправности
по-разному. Сосед закрыт здесь, а не отложен: это то же самое утверждение, что
и весь заход, — путь bypass неразличим в снимке, — и стоит оно одного поля,
одного `s.count` и одной проверки. `Rejected` осталось суммой (существующие
утверждения T33 и T12/T13 не сдвинуты), а `BypassTCPRejected` выделяет из неё
свою половину.

#### Новые проверки

- `TestStackStatsFoldsBypassSinkCounters` (`internal/netstack`) — подставной
  приёмник отдаёт 7/9/11; числа заведомо разные, чтобы перепутанные местами
  поля были видны.
- `TestStackStatsSeesRealBypassNAT` (`internal/netstack`) — W49, шов между
  необязательным интерфейсом и настоящим `bypass.NAT`; заодно проверяет
  `Rebound`, ради которого счётчики и выводятся.
- `TestStackStatsSeparatesBypassTCPRejectFromFailClose` (`internal/netstack`) —
  два стенда, живой и мёртвый, и утверждение, что снимок их различает.

Все три увидены красными до реализации, отдельным коммитом, и красными по
утверждению, а не по сборке: поля в `netstack.Stats` заведены в том же коммите
пустыми, чтобы падал `assert`.

Проверки на приёмник **без** `Stats()` заход не завёл намеренно: такую зелень
даёт и полное отсутствие реализации, а настоящую охрану этого края несёт весь
остальной пакет — во всех прочих тестах `internal/netstack` в `Config.Bypass`
стоит `fakenet.Bypass`, который `Stats()` не объявляет, и паника или отказ на
проверке типа покраснила бы их скопом.

Флаг заход не заводит: наблюдаемость, на которой ничто не ветвится, — не
политика. Выключать в ней нечего, и охраняющая проверка краснела бы не от
выключения, а от отсутствия кода.

#### Deviations

**`internal/netstack` начал импортировать `internal/bypass`.** Импортируется
только тип возвращаемого значения (`bypass.Stats`); стек по-прежнему нигде не
создаёт `bypass.NAT` и работает с любым `Send`-only приёмником, так что
инверсия зависимости, ради которой `BypassSink` объявлен на стороне
потребителя, не нарушена. Отвергнута альтернатива — объявить структуру
счётчиков ещё раз в `netstack` и переходник в `agent/wire.go`: это вторая копия
одной правды в месте, где поля меняются (за два захода их стало три), а вторая
копия расходится с первой. Цикла нет: `internal/bypass` зависит от `clock`,
`packet` и `policy`, а его тесты — от `packettest`.

**Уборка простоя из `Stats()` убрана, то есть заход про наблюдаемость изменил
поведение.** Изменение — в сторону «геттер ничего не делает», и в продукте оно
не меняет ничего вовсе: до этого захода `Stats()` в продукте не звали. Довод
выше.

**`Stats.Rejected` разделено, хотя это пункт соседнего захода.** Разделение
описано выше; сумма сохранена, ни одно существующее утверждение не сдвинуто.

Closes: `next_task` из `HANDOFF.json` (Surface `bypass.NAT.Stats()` through
`netstack.Stack.Stats()`, приоритет 1).

### doclint — утверждение документа о состоянии обязано опираться на исполнимое

Заход параллельный: он ничего не добавляет продукту и целиком лежит в
документах и в третьем линтере семьи `cmd/negcheck` / `cmd/realtimelint`.

**Почему вообще.** За один день нашлись две гнили одного вида. Первая —
ссылка на «Global Constraint 9, `constraints.md`», которой два прохода подряд
обосновывали перенос задачи в очередь; файла нет ни в одной ветке, а задача,
когда её наконец проверили по существу, стоила одного поля и одного проброса.
Вторая — «T21–T29 проходят в netns» в `PLAN.md` при том, что четырёх из этих
номеров не существует как тестов вовсе. Ни то, ни другое не ловилось ничем.
Уцелело ровно то, за чем стояла исполнимая проверка: `negcheck`,
`realtimelint` и нумерованный индекс тестов. Отсюда правило, которое линтер и
проверяет: **утверждение документа о состоянии обязано опираться на что-то
исполнимое** — тест с этим номером, запись в реестре политик, файл на диске,
ссылку git.

**Форма проверки — как у `negcheck`, а не как у `realtimelint`.** У
`realtimelint` собственного теста нет вовсе: его оракул — само дерево
продукта. Для линтера документов это не годится: он краснеет на живых
документах, и «зелено на репозитории» ничего не говорит о том, краснеет ли он
там, где должен. Поэтому взята форма `TestMetaCheck`: два поддельных
репозитория в `internal/doclint/testdata` — «грязный» с одной гнилью каждого
вида и «честный», где те же обороты употреблены правильно. Проверяются оба
направления, и второе здесь важнее первого: линтер, который кричит на каждое
второе слово, выключат, и тогда он не проверяет ничего. `testdata` выбран
вместо каталога `fixture` (как у `negcheck`) намеренно: поддельные тестовые
файлы фикстур не должны попадать в `go test ./...`, а `testdata`
инструментарий Go игнорирует по построению.

**Флага политики заход не заводит.** Правило реестра — про новые политики
продукта, а линтер политикой не является: выключать в нём нечего, ветвления в
продукте он не создаёт, и охраняющий тест, который краснел бы «без политики»,
пришлось бы придумывать вокруг пустоты. У `realtimelint` флага нет по той же
причине. Довод `HANDOFF.json` («probably none») принят как есть.

#### Где проведена граница распознавания

Главный риск такого линтера — ложные срабатывания: проза называет пути и имена
в десятке обёрток. Граница везде выбрана в сторону «пропустить сомнительное».

**Номера T\*/W\*.** Читаются из `PLAN.md`, `docs/verification-agent.md`
целиком и из `SPEC.md` — только внутри таблиц §8. В остальном тексте спеки
номер стоит ссылкой на соседний раздел, а не утверждением «это проверено».
Диапазоны раскрываются: «W6–W10» — утверждение про пять номеров, и ложный
тезис «T21–T29 проходят в netns» был ложным именно как диапазон. Раскрытие
требует одинаковой буквы и роста, поэтому `T23-fast` и `T12/T13` диапазонами
не считаются. Подтверждением служит только Go-тест: номер в имени функции
`Test*` или в её doc-комментарии. Номер в комментарии рабочего файла не
годится — комментарий не краснеет.

**Имена политик.** Не всякий `snake_case` в обратных кавычках: в `PLAN.md`
так же записаны `heartbeat_miss = 3`, `last_switch`, `tunnel_phase`,
`interrupted_connections`, и ни один из них политикой не является. Политикой
считаются ровно две формы: имя, за которым сразу стоит `=` (`ipv6_block=off` —
так написаны разделы «что должно сломаться при выключении»), и ячейка таблицы,
в которой нет ничего, кроме имени в кавычках, — так устроена колонка политики
в регистрах. Обе формы на сегодняшних документах дают только настоящие имена;
проза вида «политика `bypass_rebind`» пропускается сознательно.

**Пути.** Из разметки берутся только обратные кавычки (в `HANDOFF.json` —
строковые значения JSON), и дальше кандидат обязан пройти узкое горло.
Отбрасываются: всё с пробелом (`go build ./...`, `ip rule add …`), шаблоны и
многоточия (`packaging/macos/*.plist`), абсолютные пути и URL (`/run/hop.sock`,
`gvisor.dev/gvisor`), адресация (`0.0.0.0/0`, `fe80::/10`), притяжательные
формы (`cmd/realtimelint's`). Путь с косой чертой проверяется, только если его
первый сегмент — существующая запись верхнего уровня репозитория: это одним
условием убирает все цитаты в `refs/` (`proxy/tun/udp_fullcone.go`,
`transport/internet/sockopt_linux.go:24`) и импорты. Хвост вида `pkg.Symbol`
(`internal/outbound.Selector`) срезается до каталога. **Голое имя файла со
ссылкой на строку не проверяется вовсе** — в этом репозитории так цитируют
чужие исходники (`tun_linux.go:451`, `sockopt_darwin.go:136`), а свои файлы
цитируют полным путём; без этого правила линтер шумел бы шестью строками.
Голое имя без ссылки на строку ищется по всему дереву как basename, а не по
корню: `verdict.go` и `classify.go` в прозе означают файл, а не путь. Из
расширений признаются только `.go`, `.md`, `.yml`/`.yaml` — `.json` намеренно
исключён, потому что `nodes.json`, `groups.json` и `health.json` появляются на
диске пользователя, а не в репозитории.

**Ветки и хеши.** Только `HANDOFF.json` и только целым токеном: `worktree-*`
или 7–40 шестнадцатеричных знаков, где есть и цифра, и буква (иначе «defaced»
стало бы хешем). Проверка выключается флагом `-git=false`, и в CI стоит именно
он: у чекаута нет ни локальных веток проходов, ни, вообще говоря, полной
истории. Это единственная из четырёх проверок, которая живёт на машине
разработчика, — и живёт она там правомерно: `HANDOFF.json` пишут и читают
только проходы, в CI его никто не трогает.

#### Список исключений и его обратная сторона

`docs/not-yet-written.md` — единственный список, который линтер читает сам.
Строка в нём — это признание «за этим именем пока ничего не стоит, и вот
почему». Список работает и в обратную сторону: строка, ставшая ненужной (тест
написан, политика зарегистрирована, файл появился), краснит линтер так же, как
утверждение без подтверждения. Без этого список за три прохода превратился бы
в свалку и линтер перестал бы что-либо утверждать. Сам список тоже проверяется
на пути: причина, ссылающаяся на несуществующий документ, — ровно та гниль,
против которой всё это писалось.

Отдельный раздел «Названы мёртвыми» — обратная сторона списка: имена, которые
обязаны **не** существовать. Туда попал `constraints.md`. Точечная пометка
`doclint:ignore` в строке для него не годится: имя названо в том числе внутри
записи закрытого прохода в `HANDOFF.json`, а её этот проход править не имеет
права. Пометка остаётся способом по умолчанию — она уже, — а строка списка
применяется, когда строку документа тронуть нельзя.

#### Что линтер нашёл сверх трёх известных

Кроме `ipv6_block`, T25–T28 и устаревшего блока `branch` — ещё четыре вещи.
`PLAN.md` называл `HANDOFF.md` <!-- doclint:ignore --> — такого файла нет и не
было, документ зовётся `HANDOFF.json` (исправлено). `event_broadcast`,
`exit_codes` и `json_schema` названы флагами этапа 9, которого нет в коде
(внесены в список). T31 назван
и в §8.4, и в `PLAN.md` как проходящий в netns — тест существует
(`internal/l3/bypass_test.go`), но номера не носил, и с точки зрения любого
читателя утверждение было непроверяемым; номер вписан в doc-комментарий.
`docs/wintun.md` и `internal/supervisor` — записи «со второй машины», внесены
в список.

Одну находку линтер сделать не может, и её стоит назвать вслух:
`docs/verification-agent.md` §6.1 числит W14 и W33 в «не написаны намеренно»,
а тесты с этими номерами с тех пор появились. Утверждение об **отсутствии**
проверяемо только против списка, а список этот пока прозаический; поэтому §6.1
получил указатель на машинную половину, а не переписан.

#### Deviations

**Проверок четыре, а не три.** `HANDOFF.json` называет не только пути, но и
ветки с хешами, и устаревший блок `branch`/`branch_note` — известное истинное
срабатывание — иначе не краснел бы ничем: имя ветки не путь. Проверка
добавлена как четвёртая и как единственная выключаемая, довод выше.

**Область проверки путей шире названной в задаче на один файл.** К
`HANDOFF.json`, `PLAN.md`, `SPEC.md` и `implementation-notes.md` добавлен сам
`docs/not-yet-written.md`.

**Номера ищутся в имени теста без границы слова слева.** `TestW41SubReachesDisk`
— номер слипается с `Test`, и требование границы слева потеряло бы половину
регистра. В документах граница слева требуется: иначе `W` из середины слова
становилась бы номером.

#### Договорённость проходов: `HANDOFF.json` — указатели, а не пересказ

Записывается сюда же, где записана предыдущая договорённость (про то, что
заход закрывает свой пункт очереди и не расширяется молча): `implementation-notes.md`
— журнал решений, переживающий проходы, а `HANDOFF.json` каждый проход
переписывается заново и хранить в нём правило значит терять его.

**`HANDOFF.json` несёт указатели и ловушки, а не пересказ `PLAN.md`.**
Полезнее всего за четыре прохода в нём оказались ссылки вида `файл:строка` и
названные грабли («`seen` обновляется на каждом `Send`»): то, чего в документах
нет и что стоило прошлому проходу времени. Хуже всего — пересказ области
задачи `routing_lists`, который противоречил `PLAN.md` и был отменён вручную.
Пересказ есть вторая копия правды, и она расходится: у копии нет причины
меняться вместе с оригиналом. Поэтому вместо изложения задачи — ссылка на
раздел `PLAN.md` или `SPEC.md`, где она изложена, плюс то, чего там нет:
ловушки, замеры, отвергнутые формы и их доводы. Проверять это машиной нечем —
разница между указателем и пересказом не выражается регуляркой, — но
`cmd/doclint` закрывает соседнюю половину: всякий путь, номер, флаг и ветка,
названные в `HANDOFF.json` и документах, теперь обязаны существовать.

### Этап 8 — блокировка IPv6 (`ipv6_block`, T28, W48)

Задача из очереди: «IPv6 blocking under `ipv6_block`, red_without_it: T28».
Исходное состояние — IPv6 умирал в ветке `!ok` разбора `internal/netstack`, то
есть как побочный эффект «пакет не разобрался», и `TestIPv6IsBlocked`
(`internal/netstack`) это фиксировал. Политики `ipv6_block` не было, T28 не
существовал.

#### Что замерено (и что из замера вышло)

Стенд: `unshare -Urn`, veth-пара, дальний конец в своём netns с
TCP-эхосервером на `fd00:9:9::2`, и разложенные руками ровно те правила и
маршруты, что кладёт `platform.Up`.

**1. Куда на самом деле идёт IPv6 при поднятом туннеле.** На физический
интерфейс. `ip -6 route get 2001:db8::1` → `dev veth0 src fd00:99::1`;
соединение с внешним пиром **устанавливается**, эхо возвращается. Таблица
туннеля в IPv6 пуста и в поиске маршрута не участвует вовсе, потому что
`platform.Up` кладёт в неё только `ip route add default` — команду семейства
IPv4. То есть утечка идёт **мимо** TUN, и ветка `!ok` в `netstack` к ней
отношения не имеет и иметь не может: пакет, не дошедший до устройства, стек не
видит. Отсюда же вывод, что уровень netstack — не «половина» задачи, а другой
вопрос: он про IPv6, который в туннель попал, а таких пакетов нет (замер: у
`hopt0` нет ни одного адреса IPv6 — у TUN нет MAC, и link-local ядром не
генерируется).

**2. Чем закрывать.** Замерены три типа правила `ip -6 rule`:

| правило      | что видит приложение | срок      |
| ------------ | -------------------- | --------- |
| `unreachable` | `ENETUNREACH`        | мгновенно |
| `prohibit`    | `EACCES`             | мгновенно |
| `blackhole`   | `EINVAL`             | мгновенно |

Выбран `unreachable`. `blackhole` отпадает по §5.6 (отказ, а не молчание — и
`EINVAL` вдобавок не отказ маршрутизации, а «неверный аргумент», по которому
приложение не догадается о причине). Между `unreachable` и `prohibit` довод
механический, а не эстетический: `ENETUNREACH` — ровно тот сигнал «на этой
машине IPv6 нет», по которому Happy Eyeballs (RFC 8305) и обычный
`getaddrinfo`-код переходят на IPv4 без задержки, а `EACCES` большинство
клиентов трактует как жёсткую ошибку.

**3. Что правило НЕ трогает.** `::1` и всё локальное живо: их забирает таблица
`local` приоритетом 0, то есть выше нашего правила (замер: `connect` на `::1`
даёт `ECONNREFUSED`, а не `ENETUNREACH`). Link-local multicast — `ff02::fb`
(mDNS), `ff02::1` — тоже уходит в `local` и остаётся работать; это совпадает с
§6.10, который обнаружение служб блокировать запрещает, и закрывает вопрос,
оставленный разделом про `addrMDNS`: IPv6-mDNS недостижим не потому, что его
запретили, а потому что в туннель он не попадает. Закрыт, таким образом,
маршрутизируемый и unicast-IPv6, включая `fe80::` unicast (он в `main`, ниже
правила).

**4. Собственные сокеты агента правило не обходят.** `SO_BINDTODEVICE` (§6.8)
от него не спасает — замер: сокет, привязанный к `veth0`, получает тот же
`ENETUNREACH`. Следствие записано в §6.9: узел, доступный только по IPv6, в v1
недостижим. Это цена §6.9, а не недосмотр.

**5. Видит ли снапшот §8.4 правило IPv6.** Нет. `netstate.Capture` снимал
`ip -o rule show`, а это только IPv4: замер вокруг `ip -6 rule add` показал
снапшот, не изменившийся ни одной строкой. Значит правило, пережившее `down`,
оставило бы T22 и T29 зелёными. Добавлен раздел `rules6`. Маршруты добирать не
пришлось — `ip -o route show table all` печатает оба семейства сразу.

**6. `sysctl disable_ipv6` как альтернатива — отвергнут замером.** Он уничтожает
статически настроенные глобальные адреса интерфейса и обратным `=0` их **не
возвращает**: снапшот вокруг цикла disable/enable разошёлся на три строки
(адрес, connected-маршрут, запись в `local`). То есть механизм ломает §8.4 по
построению, и чтобы его починить, пришлось бы записывать и восстанавливать всю
адресацию IPv6 руками — то есть написать второй `netstate` внутри платформенного
слоя.

#### Решение

Один шаг в `upSteps`, под `policy.IPv6Block`:
`ip -6 rule add unreachable priority 32000`, откат — `ip -6 rule del` той же
формы. Приоритет тот же, что у туннельного правила IPv4, потому что утверждение
то же самое: «всё остальное» — в туннель для IPv4, в отказ для IPv6. 31000
оставлен свободным под исключения §5.6 для IPv6, которых в v1 нет.

Шаг стоит **первым** в списке. Журнал откатывает LIFO
(`netstate.Journal.Rollback` идёт с конца), поэтому первый поставленный
снимается последним — и нет ни одного момента, ни при подъёме, ни при откате,
ни при срыве `Up` на середине, когда интерфейс уже или ещё существует, а IPv6
открыт.

`Reclaim` снимает правила обоих семейств и делает это при любом состоянии
флага: убирать за предыдущим воплощением — не политика, а обязанность старта
(§6.2), и прошлая сборка могла разложить правило при включённой политике.
Обратный опыт это подтвердил: `Reclaim` без половины `-6` роняет T29 строкой
`rules6: +32000: from all unreachable` — то есть новый раздел снапшота работает
не на бумаге.

#### Где проходит граница `ipv6_block`

Выключается ровно один шаг `Up`. Не выключается ни раздел `rules6` в
`netstate`, ни уборка `-6` в `Reclaim`: первое — контракт §8.4, второе —
обязанность старта; ни то ни другое не ветвит поведение продукта и краснеть без
флага не может, а значит политикой не является.

Флаг свой, а не чужой:

- **не `snapshot_restore`**: он гасит откат, а не раскладку. Под ним `Up`
  поставит правило IPv6 как ни в чём не бывало, и T28 останется зелёным —
  охраной он не работает вовсе.
- **не `routing_lists`**: тот живёт в вердикте `netstack`, куда IPv6-пакет не
  доходит и не может дойти (пункт 1 замера). Красноты по своей причине он бы не
  дал.
- **не `orphan_reject`**: он про состояние `orphaned`, а T28 гоняется в `up`.

Краснеющих проверок две, разного рода, и это сознательно:

- **W48** (`TestW48UpBlocksIPv6`, `TestW48IPv6BlockIsFirstStepAndSoLastUndone`,
  `internal/platform`) — без прав, про решение: правило в списке шагов есть, оно
  `unreachable`, оно стоит первым, у него есть откат. Список шагов ради этого
  вынесен из `Up` в чистую функцию `upSteps` — тем же приёмом, которым §6.2
  вынес респондер отдельно от привилегированного ввода-вывода.
- **T28** (`TestT28IPv6IsBlocked`, `TestT28IPv6ReturnsAfterDown`,
  `internal/l3`) — в netns, про ядро: до пира не дошло, приложение получило
  отказ мгновенно, IPv4 остался в туннеле, а после `down` IPv6 вернулся и
  снапшот совпал.

В реестре политик (`internal/policy/policies.go`) назван только W48: `negcheck`
исполняет Guards через `go test`, а `internal/l3` без `HOP_L3` и своего netns
пропускается — L3-строка была бы зелёной при любом состоянии флага, то есть
ровно фикстурой `fixture_bad`.

T28 содержит контроль стенда: **до** поднятия туннеля соединение с пиром по
IPv6 устанавливается и обменивается данными. Без него краснота теста ничего не
значила бы — netns без IPv6 дал бы «заблокирован» даром.

#### Deviations

**§6.9 переписан: «блокируется на уровне маршрутов TUN» замером опровергнуто.**
Маршрут в таблице туннеля утечки не касается, потому что утечка идёт мимо
туннеля. Спека правится в пользу замера — это третий такой случай в проекте.

**Соединение по IPv6, установленное до `up`, замолкает, а не отказывает.**
После установки правила наружу оно больше ничего не отправляет — замерено на
стороне пира: пакет до него не доходит, — но `send` возвращает успех, и сокет
висит до собственного таймаута TCP. Утечки нет, есть молчание, которого §5.6 не
любит. Это **другое** утверждение, чем то, которое несёт T28 (§6.9, «не ушло
мимо туннеля»), и закрывается оно другим механизмом: разрушением сокетов через
`SOCK_DESTROY`. Замерено, что механизм работает и доступен: `ss --kill -6 -t
dst [fd00:99::2]` под `unshare -Urn` возвращает 0 и переводит соединение в
`ECONNABORTED` — то есть `CAP_NET_ADMIN` хватает, root не нужен, а `ss` едет в
том же `iproute2`, что и `ip`, так что новой зависимости нет. Не сделано в этом
заходе: это своя привилегированная поверхность (`CONFIG_INET_DIAG_DESTROY` есть
не везде), своё утверждение и свой флаг со своей краснеющей проверкой — а
«один флаг, одно утверждение» этот кодовой базой уже дважды защищено. Отложено
названным пунктом, а не умолчанием.

**Тронут `internal/netstate`, соседний пакет.** Раздел `rules6` добавлен туда,
потому что без него правило IPv6 невидимо для §8.4 и «восстановление до
снапшота» стало бы враньём ровно в той части, которую этот заход и добавляет.
Записано здесь по конвенции между заходами: правка соседнего пакета допустима с
доводом, но не молча.

**Тронут стенд `internal/l3` шире одного файла.** Пир получил адрес IPv6 и
второй слушатель (`routecache_test.go`), `dropHopRules` — уборку обоих семейств,
и появился `waitAddrsSettled` (`harness_test.go`). Последнее — не украшение: DAD
меняет вывод `ip addr` асинхронно уже после успешного возврата команды, а §8.4
сравнивает снапшоты побайтово, так что снапшот, снятый внутри этого окна, не
совпал бы сам с собой через секунду и уронил бы T28 чужой краснотой.

Closes: пункт очереди «IPv6 blocking under `ipv6_block`» (`HANDOFF.json`,
`queue_after_bypass_rebind`).

### Этап 8 — отказ соединениям IPv6 старше туннеля (`ipv6_kill_established`, W50)

Задача из очереди: единственная дыра §5.6, которую замерил и намеренно оставил
открытой проход `ipv6_block`. После того как встало правило
`ip -6 rule add unreachable priority 32000`, уже установленный сокет IPv6
наружу ничего не выпускает, но и не отказывает: он висит до собственного
таймаута TCP, а `send` всё это время возвращает успех. На двухстековой машине
это каждое открытое соединение браузера в момент `up`.

#### Что замерено (и что из замера вышло)

Стенд — тот, что построил прошлый заход: `unshare -Urn`, veth-пара, дальний
конец в своём netns с TCP-эхосервером на `fd00:9:9::2`.

**1. Дыра воспроизведена.** После правила `write` в установленный сокет
возвращает `n=26, err=nil`, а `read` с дедлайном 700 мс возвращает
`i/o timeout`. Это молчание, а не отказ. Новое соединение при этом отказывает
за 45 мкс (`ENETUNREACH`) — то есть правило работает, и открытым остаётся ровно
то, что старше правила.

**2. UDP в зачистке не нуждается — замер, а не рассуждение.** Связанный сокет
UDP, успешно отправлявший до правила, сразу после него получает на `write`
`network is unreachable`. UDP перепроверяет маршрут, TCP на установленном
соединении — нет. Значит зачистка касается только TCP, и вопрос «а как же QUIC»
закрыт замером, а не объёмом.

**3. `ss --kill` возвращает 0, даже когда не убил ничего.** Замер без
`CAP_NET_ADMIN`: `ss --kill -6 -t dport = :N` печатает
`SOCK_DESTROY answers: Operation not permitted`, ничего не разрушает и выходит
с кодом **0**. Это несущий довод против формы «звать `ss`»: вопрос этого
захода — падать или деградировать — решается по коду возврата, а его нет.
Различать исходы по английской строке диагностики iproute2 значит объявить
интерфейсом то, что им никто не объявлял.

**4. `ss --kill -6 -t dst [...]` пропускает `SYN_SENT`.** Замер: до правила
поднят сокет в `SYN_SENT` (адрес on-link, никто не отвечает); `ss --kill` по
адресу пира разрушил `ESTABLISHED` и оставил `SYN_SENT` на месте — фильтр
состояний по умолчанию у `ss -t` это `ESTABLISHED`. Между тем `SYN_SENT`
переживает правило ровно так же (маршрут разрешён при `connect`) и без
зачистки висит до таймаута. То есть предложенная прошлым заходом точка входа не
закрывает дыру, которую сама называет.

**5. `netlink.SocketDestroy` из библиотеки умеет только IPv4.** Замер: на паре
адресов IPv6 возвращает `not implemented`; в исходнике семейство запроса зашито
как `AF_INET`, а адреса приводятся `To4()`. Дамп (`SocketDiagTCP`) при этом
IPv6 разбирает правильно и отдаёт `cookie`. Значит netlink-форма стоит примерно
тридцати строк сериализации `inet_diag_req_v2` — и ни одной новой зависимости:
`vishvananda/netlink` уже прямая зависимость модуля (`internal/outbound`).

**6. Ручной `SOCK_DESTROY` закрывает оба случая.** Разрушение установленного
сокета: `read` → `ECONNABORTED`, `write` → `EPIPE`, немедленно. Разрушение
`SYN_SENT`: висевший `connect` возвращает `ECONNABORTED` вместо того, чтобы
досидеть свои 20 секунд.

**7. Ошибки ядра различимы.** Разрушение несуществующего сокета даёт `ENOENT`.
Разрушение по протоколу, у которого обработчика diag нет вовсе (`IPPROTO_DCCP`),
даёт тот же `ENOENT`. То есть `EOPNOTSUPP` ни одним из этих путей не приходит и
свободен под «ядро собрано без `CONFIG_INET_DIAG_DESTROY`».

**8. Слушателя ядро разрушать отказывается.** `SOCK_DESTROY` на `LISTEN` даёт
`EINVAL`, слушатель остаётся жив. Значит исключать `LISTEN` нужно не ради
безопасности, а чтобы не сочинять себе ошибки на ровном месте.

**9. Соединение к СВОЕМУ адресу правило не закрывает.** Замер: адрес
`fd00:9:9::1` на `dummy`, соединение с него же на него же; после правила и
установленное соединение работает, и новое устанавливается — `ip -6 route get`
показывает `table local`, приоритет 0, выше нашего правила. Отсюда граница
отбора: разрушать нельзя не только `::1`, но и любой собственный адрес машины.

**10. Соединение IPv4 приезжает в дампе `AF_INET6`.** Замер: dual-stack
слушатель на `[::]`, дозвон по `tcp4` — соединение видно в
`SocketDiagTCP(AF_INET6)` с адресом `::ffff:127.0.0.1` и `To4() != nil`. На
настоящем рабочем столе таких сокетов много, и зачистка «всё, что IPv6»
разрушила бы работающие соединения IPv4.

#### Решение

Один шаг `Up`, `stepKillIPv6`, сразу за шагом `ipv6 block`. Раньше правила
зачистка бессмысленна — разрушенное тут же переустановится; позже — окно
молчания длиннее без нужды.

**Форма: netlink, не `ss`.** Несущий довод — пункт 3 замера: вопрос «падать или
деградировать» решается по коду возврата, а `ss --kill` возвращает ноль в любом
случае. Пункт 4 — второй довод того же рода: маска состояний в netlink задаётся
явно (`1 << state` по сокету из дампа), а у `ss` она подразумевается и
подразумевается неверно для этой задачи. Цена формы — тридцать строк
сериализации `inet_diag_req_v2` (пункт 5), и на этом всё: дамп библиотечный,
зависимость уже есть, `ss` из `iproute2` больше не нужен вовсе.

**Ядро без `CONFIG_INET_DIAG_DESTROY`: `Up` продолжается, изъян уходит в
журнал.** Обоснование — сам §5.6. К моменту зачистки правило уже стоит, наружу
не утекает ничего ни при каком исходе; без зачистки теряется только **срок**
отказа. Уронить `Up` значило бы обменять ограниченный изъян (сокеты IPv6 старше
туннеля висят до своего таймаута TCP) на неограниченный: туннеля нет вовсе, и
наружу в открытую идёт всё, включая IPv4 — ровно то, ради чего §5.6 написан.
Третий вариант, предварительная проверка ядра с отказом стартовать, отвергнут
тем же доводом и вдобавок стоил бы своей привилегированной поверхности. Но
деградация молчаливой не становится: тот же §5.6, обращённый на сам инструмент,
требует сказать, чего сделать не удалось, — поэтому `platform.New` получил
логгер, а неудача пишется `Warn` с причиной и с числом неразрушенных сокетов.

Про сам `EOPNOTSUPP` честно: что именно возвращает ядро, собранное **без**
этого параметра, здесь не замерено — для этого нужно другое ядро. Замерено
другое (пункт 7): ни исчезнувший сокет, ни отсутствующий обработчик протокола
этого кода не дают, так что занять его под «ядро не умеет» безопасно. И решение
от догадки не зависит: ни одна ветка `Up` не роняет, различается только текст в
журнале.

**Отбор целей — по границе самого правила.** Разрушается то и только то, что
правило §6.9 обрекло на молчание: маршрутизируемый unicast, ULA и `fe80::`
unicast (все в `main`, ниже правила). Не трогаются `::1` и собственные адреса
машины (таблица `local`, приоритет 0 — пункт 9), соединения IPv4 из дампа
`AF_INET6` (пункт 10) и слушатели (пункт 8).

**Однократность: почти, и «почти» названо.** Довод прошлого захода — «после
правила новое соединение IPv6 не установится, значит хватит одного прохода» —
верен наполовину. Он не покрывает сокеты, которые к моменту правила уже были в
`SYN_SENT`: пункт 4 показывает, что они переживают правило и что зачистка,
смотрящая только на `ESTABLISHED`, их пропускает. Это чинится маской состояний,
а не вторым проходом. Остаётся вторая, настоящая дырка: `connect()` разрешает
маршрут **до** того, как вставит сокет в хэш-таблицу, и дамп, попавший ровно в
этот зазор, сокета не увидит. Закрыть её совсем нельзя ничем из пространства
пользователя — можно только сузить: дамп повторяется, пока раунд что-то
разрушает, но не больше четырёх раз, и к следующему дампу такой сокет уже в
`SYN_SENT`. Цикл кончается, потому что множество целей не пополняется (пункт 1,
`ENETUNREACH` на новом соединении), а предел стоит на случай ошибки, которая
повторяется бесконечно.

**Откат: его нет, и это утверждение.** Разрушенный сокет обратно не собрать,
поэтому у шага пустой `del`, и `TestW50UpSweepsSilencedIPv6` это проверяет
явно, чтобы однажды кто-нибудь не дописал туда «откат». §6.2 и §8.4 это не
задевает: снапшот `netstate` состоит из ссылок, адресов, маршрутов и правил —
сокетов в нём нет вовсе, и `Verify` после `down` сравнивает ровно то же, что
сравнивал. T22 и T29 прогнаны и зелены. Прецедент в журнале уже был: шаг `mtu`
тоже без отката. И прецедент по существу тоже: `Reject` (§6.2) необратимо рвёт
соединения на другом ребре и в журнал не попадает вовсе.

Почему тогда шаг всё-таки в списке, а не сбоку от него: список шагов `Up` —
единственное место, где решение видно без прав, и W50 существует ровно потому,
что `upSteps` осталась чистой функцией. Шаг сбоку пришлось бы проверять
привилегированным прогоном в netns, то есть той самой `fixture_bad`, которой
здесь избегают.

#### Где проходит граница `ipv6_kill_established`

Выключается ровно один шаг `Up`. Флаг свой, а не `ipv6_block`, по доводу,
которым `bypass_rebind` не стал частью `bypass_sink`: при `ipv6_block=off`
правила нет вовсе, значит и молчащего сокета не возникнет, и охрана краснела бы
по отсутствию правила, а не по отсутствию зачистки.

Зависимость между флагами при этом есть, она односторонняя и выражена в коде:
без правила зачистка не бесполезна, а **вредна** — она рвала бы работающие
соединения IPv6. Поэтому шаг стоит в `Up` только при обоих включённых флагах, а
W50 при `HOP_DISABLE=ipv6_block` пропускается: его утверждение в такой сборке
невыразимо, и краснеть ему полагается по своему флагу, а не по чужому. Первая
редакция охраны пропуска не делала, и охрана краснела на чужом флаге — ровно
та ловушка, ради которой флаг и отделяли. Обратную сторону — что шага там
действительно нет — держит `TestIPv6KillIsAbsentWithoutTheRule`; охраной он не
служит и служить не может.

Краснеющих проверок две, разного рода, как у `ipv6_block`:

- **W50** (`TestW50UpSweepsSilencedIPv6`, `internal/platform`) — без прав, про
  решение: шаг есть, стоит сразу за правилом, отката не имеет, командой `ip` не
  выражен.
- **`TestW50IPv6EstablishedIsAbortedNotSilenced`** (`internal/l3`) — в netns,
  про ядро: установленное соединение получает отказ за микросекунды, а не
  `i/o timeout`, и сокет в `SYN_SENT` — тоже. В реестре политик не назван по
  общему правилу: `negcheck` гоняет `go test`, а L3 без `HOP_L3` пропускается.

L3-половина содержит контроль стенда — до туннеля соединение с пиром по IPv6
устанавливается и обменивается данными, — и проверяет **два** сокета, а не
один. Второй, в `SYN_SENT`, не украшение: без него тест был бы зелен и с
зачисткой по одному `ESTABLISHED`, то есть не заметил бы пункт 4 замера.

#### Deviations

**§6.9 переписан: «в v1 не делается» больше не так.** Раздел «Чего блокировка
не делает» заменён на описание механизма, границ отбора и поведения на ядре без
`CONFIG_INET_DIAG_DESTROY`. Прошлый заход оставил там точный список того, что
предстоит решить, — решено и записано.

**`platform.New` получил логгер, задет `cmd/hopd`.** Шаг зачистки умеет
деградировать, и деградация обязана быть слышна: молчаливая деградация — это то
же молчание, против которого §5.6, только обращённое к человеку. Другого канала
у платформенного слоя нет — `Up` возвращает только ошибку, а ошибка здесь
запрещена по решению выше. Правка соседнего пакета — одна строка в
`cmd/hopd/main.go` и подпись `New` в `other.go`; записано по конвенции между
заходами.

**`step` получил поле `do`, литералы переведены на именованные поля.**
`SOCK_DESTROY` командой `ip` не выражается, а весь список шагов до сих пор был
списком командных строк. Позиционные литералы `step{...}` после добавления поля
перестали компилироваться, поэтому переписаны на именованные — правка
механическая, поведение шагов не изменилось.

**Замер про IPv4-близнеца не удался и потому ничего не утверждает.** Проверялось,
не течёт ли мимо туннеля установленное соединение **IPv4** — механизм тот же
(закэшированный маршрут переживает подъём). Соединение действительно осталось
живым, но замер ничего не доказывает: адрес пира на стенде `10.9.9.2` лежит в
`10.0.0.0/8`, то есть в `LocalPrefixes` — это исключение §5.6, и мимо туннеля
оно уходит по решению, а не по дефекту. Записано как несостоявшийся замер, а не
как находка; переставить его на адрес вне RFC1918 — работа следующего захода.

Closes: пункт очереди «Refuse, don't silence, IPv6 connections that predate
`up`» (`HANDOFF.json`, `next_task`).

### Этап 9 — счётчики стека доходят до пользователя (`StackStats`, W54)

Прошлый заход довёл счётчики приёмника bypass до `netstack.Stack.Stats()` и там
остановился. Дальше пути не было: связка отдавала наружу только `DNSStats`, ни
`cmd/hop`, ни `internal/ipc` про счётчики стека не знали, и переоткрытие сокета
по смене интерфейса (`BypassRebound`) наблюдалось исключительно тестом. Счётчик,
которого никто не читает, — не наблюдаемость, а мёртвый код с хорошим именем.

**Отдельный вызов, а не поле `Snapshot`.** §2 регистра говорит: «снимок по
частям не годится», и это был довод в пользу того, чтобы вложить счётчики в
`Snapshot`. Он отвергнут двумя фактами. Первый: слой 1 сборки (§7 регистра,
«Типы и снимок») объявлен **без зависимостей**, а `Snapshot` живёт в
`agent.go` — поле типа `netstack.Stats` втащило бы туда датаплейн, а
собственная копия структуры счётчиков в `agent` была бы вторым экземпляром
правды, то есть ровно тем, против чего написана конвенция `HANDOFF.json`.
Второй: довод §2 — про состояние, которое тест собирает из нескольких геттеров
и получает то, чего никогда не было. Счётчики накопительны и монотонны в
пределах жизни стека; «фаза трафика с чуть более поздними числами» — не
состояние, которого не было. Образец взят готовый: `DNSStats` отдаёт
`resolver.Stats` вторым значением из `wire.go`, где зависимость на резолвер уже
есть.

**Второе значение — не украшение.** `StackStats` отвечает `false` до `Up` и
после `Down`. Нули за неподнятый датаплейн читались бы как «туннель работает, и
через него ничего не прошло» — та же ложь, ради которой второе значение
появилось у `DNSStats`. Отсюда же и семантика сброса, которую `HANDOFF`
требовал назвать вслух: счётчики живут ровно столько, сколько стек, `Up`
собирает новый и начинает счёт заново. Сброса «на месте» нет — обнуление по
чтению означало бы, что снимок меняет наблюдаемое, а этот довод в репозитории
уже стоил уборки простоя в `bypass.NAT.Stats`.

**Замок отпускается до `Stats()`.** `a.mu` берётся только чтобы прочитать
указатель на стек. Держать его поверх `stack.Stats()` было бы связыванием
порядков замков: приёмник bypass зовёт `a.deliverBypass` из своей горутины
чтения, а тот берёт `a.mu`; сегодня `Reply` вызывается уже вне `n.mu`
(`internal/bypass/bypass.go`), то есть цикла нет, но он оказался бы в одной
правке от нас, и цена — не покраснение теста, а взаимная блокировка.

**Что напечатано и на каком уровне.** `watch` печатает счётчики на DEBUG одной
строкой «стек». Края на INFO, как у фазы трафика и DNS, нет намеренно: край у
накопительного счётчика пришлось бы назначить порогом, а порога никто не мерил
— назначенный на глаз, он давал бы либо молчание, либо шум. Подписи держит
таблица `stackCounters`, значения берутся по имени поля через `reflect`: так
подпись и счётчик связаны в одном месте, и W54 сверяет таблицу с типом. Ровно
эта половина и краснеет, если завести новое поле в `netstack.Stats` — проверено
подстановкой лишнего поля, проверка назвала его по имени.

**Чего сюда не вошло и почему.** Число сокетов, разрушенных зачисткой IPv6, и
деградация на ядре без `INET_DIAG_DESTROY` (W50) остались логом `hopd`, как и
были. Владелец у них другой — платформенный слой в **сервисе**, а не стек в
связке; событие однократно (шаг `Up`), и превращать его в накопительное число
пришлось бы через `internal/ipc` с отдельно назначенной семантикой сброса. По
требованию `HANDOFF` («не превращать событие журнала в счётчик молча») это
записано как решение не делать, а не как забытая половина.

Closes: пункт `next_task` «Довести `Stack.Stats()` до пользователя»
(`HANDOFF.json`).

### Этап 9 — уборка простоя сокетов bypass без трафика (`bypass_idle_sweep`, W51)

Пункт очереди, заведённый прошлым проходом, когда прокрутку уборки вынесли из
`bypass.NAT.Stats()` («геттер, меняющий наблюдаемое, — это поведение, а
поведение обязано иметь флаг»). Цена того решения была названа вслух и осталась
неоплаченной: после того как трафик прекратился, сокет bypass доживал до
`Close`.

#### Что замерено (и что из замера вышло)

1. **«Сокет живёт до `Close`» — не предположение, а падение теста.**
   `TestW51IdleSocketIsCollectedWithoutTraffic` на исходном коде даёт
   `Sockets = 1, ожидался 0` через 3×`Idle` полного молчания клиента. Ни `Send`,
   ни `Stats`, ни `Close` после первой датаграммы не зовутся — идут только часы.
   Это тот же замер, что и краснота охраны под `HOP_DISABLE=bypass_idle_sweep`:
   утверждение и его цена проверяются одной и той же строкой.

2. **Тикер, заведённый внутри горутины, теряет тики инъектируемых часов.**
   Первая редакция звала `clk.NewTicker` в теле `sweepLoop`. Проверка была
   зелена на одиночном прогоне и покраснела на `go test -count=20 -race` тем же
   `Sockets = 1`. Причина не в гонке данных (детектор молчит), а в сроках:
   `clock.Fake` назначает первый тик от момента `NewTicker`, и `Advance`,
   обогнавший планировщик, двигает время до того, как тикеру назначен срок, —
   ни один тик не доставляется вовсе. Тикер переехал в `New`: после возврата из
   `New` он заведён, чем бы ни был занят планировщик. На системных часах дефект
   был бы невидим и стоил бы задержки уборки на первый период, а не отказа.

3. **Ловушка соседнего прохода жива и не задета.**
   `TestBypassIdleSweepNeverCollectsSocketUnderTraffic` зелен и под фоновой
   уборкой, 20 прогонов под `-race`. Так и должно быть: `sock.seen`
   обновляется на каждый `Send`, и ретраящий клиент держит сокет вечно молодым
   независимо от того, кто прокрутку позвал. Проверка по-прежнему доказывает,
   что уборка простоя не годится на роль перепривязки.

4. **Утечка самого механизма измерена, а не обещана.**
   `TestW51IdleSweepDoesNotOutliveClose` заводит NAT, не отправив ни одной
   датаграммы: горутин чтения нет вовсе, поэтому счётчику видно ровно уборщика.
   Он обязан появиться после `New` и исчезнуть после `Close`.

#### Решение

Фоновый тикер на `clock.Clock`, а не внешний `Sweep()`. Внешний потребовал бы
второй половины — того, кто его зовёт, — а звать некому: у `bypass.NAT` нет
владельца с собственным циклом. `netstack.Stack` им не является (он реагирует
на пакеты), и заводить цикл там значило бы вносить поведение в соседний модуль
ради механизма, который целиком принадлежит `bypass`. Сам `natTable.Sweep()`
подтверждает: он существует с прошлого этапа и в продукте не зовётся ни разу,
только в замере B3.

Новой уборки не заведено — заведён второй повод позвать ту же `sweepLocked`.
Период — `Idle/2`, тот же шаг, которым `sweepLocked` сам себя ограничивает:
чаще он всё равно ничего не сделает, реже — растянул бы срок жизни
простоявшего сокета сверх `Idle`+`Idle/2` без пользы. На тике прокрутка
принудительная (`sweepNow`, приём `natTable.Sweep`): собственный ограничитель
снимается, потому что частоту уже ограничил тикер снаружи, а совпасть с
недавним `Send` тик может в любой момент.

Останов — по `done`, закрываемому в `Close`, и по той же `sync.WaitGroup`, что
ждёт горутин чтения: уборщик обязан кончиться раньше, чем `Close` вернётся.

#### Где проходит граница `bypass_idle_sweep`

Флаг гасит **только фоновую половину**. Прокрутка внутри `Send` остаётся при
любом его состоянии: она старше этого прохода, у неё своя зелёная проверка
(`TestBypassIdleClosesSocket`), и увести её под новый флаг значило бы выключать
заодно проверенное поведение — охрана краснела бы за двоих, и что именно из
двух сломано, по её красноте было бы не сказать.

Выключенный флаг не оставляет ни горутины, ни тикера: механизма нет целиком, а
не «есть, но ничего не делает». Иначе выключение меняло бы исход, оставляя цену
— горутину и тикер на каждый NAT.

Флаг свой, а не `bypass_sink`: под тем `Send` отдаёт `ErrDisabled`, сокета не
заводится вовсе, и охрана краснела бы по чужой причине — «нечего убирать»
вместо «не убрано». Тот же довод, которым `bypass_rebind` не стал частью
`bypass_sink`. И не `bypass_rebind`: тот закрывает сокет по событию смены
интерфейса, а этот — по молчанию. Разница видна прямо в проверках: охрана
перепривязки нарочно держит часы стоящими, чтобы уборка простоя не дала ей
ложной зелени, а охрана W51 нарочно двигает часы при молчащем клиенте.

#### Deviations

**§6.1 регистра расширен до W51, а не до «W34–W49, W51».** Абзац «Реализовано и
зелено» не был обновлён проходом `ipv6_kill_established` и остановился на W49,
хотя W50 зелен. Дописать свой номер, оставив дыру на чужом, значило бы
утверждать документом, что W50 не зелен, — то есть заменить пропуск на ошибку.
Диапазон сомкнут. Это ровно то расхождение, на которое указывает пункт очереди
«Свести §6.1 регистра и `docs/not-yet-written.md` в один источник».

**`natTable` (`internal/netstack/udp.go`) той же участи не лишена.** У неё
прокрутка по-прежнему едет на `mapping()` и на внешний `Sweep()`, который в
продукте никто не зовёт, — значит при остановленном трафике её сокеты живут до
`close()` стека. Тот же дефект, то же лечение. Не сделано намеренно: пункт
очереди назван про `bypass`, а перенос механизма в `netstack` — это второе
поведение, второй флаг и вторая охраняющая проверка в чужом пакете. Записано
здесь и в doc-комментарии `Stats`, чтобы не потерялось.

Closes: пункт очереди «Уборка простоя сокетов bypass без трафика»
(`HANDOFF.json`, `queue`).

### doclint — второе направление: проза, объявившая номер ненаписанным

Заход тоже параллельный и тоже целиком в документах и линтере. Он закрывает два
пункта очереди `HANDOFF.json` — «Дать номера регистра тестам, закрывающим
W29–W31» и «Свести §6.1 регистра и `docs/not-yet-written.md` в один источник», —
и оба оказались одной задачей: документ не должен утверждать состояние, которого
никто не проверяет, и утверждение «не сделано» здесь ничем не лучше утверждения
«сделано».

**Что оказалось правдой, а что унаследованной верой.** §6.1 закрывала тройку
W29–W31 одним `TestReportFailureHasOneCallSite`. Проверено по существу, а не по
доверию к абзацу:

- **W29 — правда.** Строка регистра дословно требует, чтобы этот тест «оставался
  зелёным после появления `agent`». Тест обходит дерево от корня модуля, значит
  новый пакет попадает под линт в тот же день, когда появляется; отдельной
  проверки строке не нужно, ей нужен был только номер. Номер уехал в
  doc-комментарий `internal/engine/callsite_test.go`.
- **W30 — ложь.** Строка поведенческая: отказ дозвона из датаплейна обязан дойти
  до живости и уменьшить её. Тест разбирает AST и не дозванивается никуда.
  Больше того, такого пути нет и в продукте: `internal/agent/dialer.go`
  намеренно не зовёт `ReportFailure`, вердикт ставит
  `internal/engine/classify.go`.
- **W31 — ложь по той же причине.** Отказ целевого сайта живость не трогает — это
  держат T20 в `internal/l2` и `TestStreamErrorIsNotFatal` в `internal/engine`,
  но ни один из них не идёт сквозь связку, а строка требует именно сквозь.

Обе оставлены в `docs/not-yet-written.md` с этой причиной вместо унаследованной.
Подгонять документ под удобство («тройка закрыта, строки убрать») было бы ровно
той гнилью, против которой линтер и заведён.

**Ловушка, стоившая одного круга.** Первая редакция doc-комментария объясняла
словами «W30 и W31 этот тест не закрывает». `cmd/doclint` немедленно покраснел на
`docs/not-yet-written.md`: номер в doc-комментарии теста — это и есть утверждение
«закрыто», и линтер посчитал обе строки лишними. Отсюда правило, которого раньше
никто не записывал: **в doc-комментарии теста номер называют только тогда, когда
тест этот номер закрывает.** Объяснить, чего тест не закрывает, приходится
словами.

**Исход по второй задаче: научить линтер, а не ужать прозу.** `HANDOFF.json`
называл два выхода — сжать абзац §6.1 до причин с указателем на машинный список,
либо научить `doclint` обратному направлению. Выбрано второе, и вот довод.
Сжатие абзаца устраняет сегодняшнее расхождение, но не механизм: причины всё
равно останутся прозой, номера при них — тоже, и следующий проход, написавший
тест, снова не вернётся в раздел. Расхождение ловилось бы дисциплиной, а
дисциплина здесь уже проиграла трижды подряд. Проверка стоила ~40 строк в
`internal/doclint/doclint.go` и двух фикстур — дешевле, чем один разбор
разъехавшегося абзаца.

Заодно из §6.1 убран перечень зелёных номеров («W1–W3, W5, W11, …»). Это был
второй источник истины худшего сорта — устаревал на каждой новой строке регистра
и не проверялся ничем. Вместо него сказано «всё, кроме перечисленного ниже»: это
утверждение как раз исполнимое, его держат `cmd/doclint` (номер без теста и без
строки списка — находка) и `go test ./...` (тест, который не зелен).

**Форма проверки.** Краснеет ровно один случай: номер объявлен ненаписанным, а
Go-тест с ним есть и строки в `docs/not-yet-written.md` нет. Два остальных
перекрыты и без того — «нет теста и нет строки» ловит проверка номеров, «есть
строка и есть тест» ловит проверка лишних строк списка, — и повторять их значило
бы печатать одну гниль дважды.

Две границы распознавания, обе в ту же сторону «пропустить сомнительное», что и
у четырёх старых проверок:

- **Участок размечает документ, а не догадка.** Пометка `doclint:unwritten`
  отдельной строкой открывает участок; заголовок закрывает его всегда, обычный
  абзац — после того, как список начался. Догадаться по прозе нельзя: жирным
  номером начинаются пункты и в `PLAN.md`, и в `SPEC.md`, где они значат совсем
  другое. Пометка признаётся только целой строкой `<!-- doclint:unwritten -->` —
  иначе абзац, объясняющий саму пометку (а объяснять её в том же разделе
  обязательно), открывал бы участок посреди прозы.
- **Объявление — только жирная голова пункта.** Номера в теле причины ссылаются
  на то, чем свойство закрыто уровнем ниже («покрыто W23 по счётчику
  инстансов»), и читать их как объявление значило бы краснеть на каждом честном
  доводе.

**Что проверка нашла на живых документах.** Три расхождения, а не два, как
считал `HANDOFF.json`: кроме W14 и W33, ненаписанным числился ещё и W8, чью
вторую половину закрыл этап 8 (`internal/netstack/interrupt_test.go`). Ни одно
из трёх не было враньём — каждый раз проход писал тест и не возвращался в прозу.
Отдельно стоит W33: там устарела не запись, а довод. «Свойство `netstack`, а не
связки» оказалось неверным — шов лежит ровно в связке, и до
`TestW33WaitingHoldsTrafficInsteadOfRejecting` трафик в стартовом окне получал
RST там, где §5.6 требует ожидания. Довод, которым откладывают проверку,
ошибается так же, как код, и стоит это дороже: его никто не запускает.

Closes: пункты очереди «Дать номера регистра тестам, закрывающим W29-W31» и
«Свести §6.1 регистра и docs/not-yet-written.md в один источник»
(`HANDOFF.json`, `queue`).

### Этап 9 — списки §6.10 и апстримы §5.7 на диске (`settings_file`, W52, W53)

#### Что замерено (и что из замера вышло)

Замер, а не дизайн, — первым делом. `grep -rn 'Routing' --include='*.go'
internal cmd` даёт четыре места: тип `netstack.Routing` и `resolveRouting`
(`internal/netstack/routing.go`), проброс в `netstack.Config`, поле
`agent.Config.Routing` и его копия в `agent.Stack` (`internal/agent/wire.go`).
Ни одного присваивания снаружи тестов. `cmd/hop/main.go` собирает
`agent.Config` литералом из десяти полей, и `Routing` среди них нет.
`agent.Config.DNSUpstreams` — ровно та же картина, и это записано в самом файле:
«CLI и диск до него ещё не доросли». В `internal/store` четвёртого файла нет
вовсе — раскладка §2 это `groups.json`, `nodes.json`, `health.json` и `.lock`.

Отсюда вывод, из-за которого проход вообще есть: **§6.10 обещает «списки
приходят из конфигурации, а не из кода», а конфигурации не существует.**
Обещание держалось на `netstack.DefaultRouting()` и на том, что тесты умеют
подставить `Routing` руками. Пользователь не умеет.

Второй замер — инварианты стора, чтобы не изобретать их заново. `store.Open`
читает три файла без замка (rename атомарен, читатель видит либо всё старое,
либо всё новое), заводит недостающие пустыми (иначе права §6.14 непроверяемы),
выравнивает права существующих (`fixPerms`), убирает временный мусор убитого
процесса (`sweep`), а грязные секции пишет по отдельности через один
`writer` — временный файл, `fsync`, `rename`, `fsync` каталога. Настройки
встроены в этот же механизм четвёртой секцией, а не рядом с ним.

Третий замер — как стор обходится с порчей. Он **несимметричен** (Р13):
`health.json` нечитаем — молча пусто, `nodes.json` нечитаем — громкий отказ
старта. Довод в коде: пустой список узлов при живом файле выглядит как
исчезнувшая подписка и провоцирует пользователя добавить её заново, потеряв
всё. Настройки лежат на стороне `nodes.json`, и по тому же доводу: молча
отменённое правило `block udp/137` пользователь заметит не сообщением, а чужим
трафиком.

#### Решение

**Формат — `settings.json`, четвёртый файл раскладки §2, права 0644.** Права
публичные, потому что секретов в нём нет по построению: правила маршрутизации и
адреса резолверов. Правило на диске несёт те же три поля, что и
`netstack.Rule`, — `prefix`, `proto`, `port`, — протокол словом, а не числом
(приём `unsup_reason` и `state`: перенумерование не должно молча переназначать
смысл записанного), порт числом типа `int`, а не `uint16`, чтобы «70000» дало
отказ про диапазон, а не про то, что JSON не лёг в поле.

**`Settings.Routing` — указатель.** «Раздела нет» и «раздел есть и пуст» —
разные состояния, и разница наблюдаема: `resolveRouting` при пустом конфиге
отдаёт `DefaultRouting()`, а при непустом подмешивает к нему только исключения
§5.6, то есть обнаружение служб исчезает. §6.10 это прямо разрешает
(«обнаружение служб — умолчание, а не пол»), и формат обязан уметь это
выразить. Срез вместо указателя схлопнул бы оба состояния в одно и отнял бы у
пользователя право, которое спека ему дала. Охраняет S43.

**Тип на диске — `netstack.Rule`, а не свой близнец в `store`.** Пакет
`internal/store` теперь импортирует `internal/netstack`; цикла нет — netstack
знает про `bypass`, `clock`, `packet`, `policy`, `reject` и не знает про стор.
Свой параллельный тип пришлось бы отображать в чужой, и отображение разошлось
бы с оригиналом на первом же новом поле правила. Константы `ProtoTCP` и
`ProtoUDP` для этого и вынесены в netstack — «чтобы тот, кто пишет
конфигурацию снаружи netstack, не тянул gvisor ради двух чисел»; стор и есть
этот «кто-то».

**Проверка ввода отказывает и называет причину** (§5.6, обращённый к человеку).
Что делает `hop` с каждым видом кривизны:

| вход                                   | что происходит                                        |
| -------------------------------------- | ------------------------------------------------------ |
| битый JSON, пустой файл                | отказ старта, файл не тронут                           |
| `version` больше известной             | отказ: файл писала сборка новее — половина полей нам неизвестна |
| `prefix` не разбирается                | отказ с текстом `netip`                                |
| `prefix` не по маске (`192.168.10.5/24`) | отказ, и в тексте обе годные формы                   |
| `proto` не `tcp`/`udp`/пусто           | отказ со списком допустимого                           |
| `port` вне `0..65535`, в том числе `-1` | отказ про диапазон                                    |
| правило `{}`                           | отказ: «напишите явно `prefix: 0.0.0.0/0`»             |
| апстрим именем, без порта, с портом 0  | отказ: имя разрешать нечем — резолвер §5.7 собирается из этого же списка |

Немаскированный префикс — единственная строка, где отказ не самоочевиден.
`netip.Prefix.Contains` смотрит только на биты маски, поэтому
`192.168.10.5/24` работает как вся подсеть, а читается глазами как один адрес.
Это молчаливое расхождение написанного и действующего, и оно опаснее опечатки:
опечатка не притворяется работающей.

Пустое правило отвергнуто отдельным условием, хотя §6.10 разрешает выразить
конфигурацией «выпустить наружу вообще всё». Разрешено там **явное решение
человека**; `{}` в списке неотличимо от опечатки, а явная форма никуда не
делась — `prefix: "0.0.0.0/0"`, и она говорит сама за себя при чтении файла.
IPv6 до вердикта в v1 не доходит вовсе (§6.9), так что «всё» тут и есть `/0`.

**Поверхность CLI — `-routing`**, в одном ряду с `-sub`, `-node`, `-nodes`,
`-rm`, `-probe`: подкомандами §5.9 они станут все разом и наденутся поверх тех
же вызовов. Команда читающая, и она же — проверка файла: кривой файл до вывода
не доводит, потому что отказывает `store.Open`. Отдельного `routing check`
поэтому нет.

Печатается не файл, а то, что из файла следует, и **двумя половинами**, а не
одним «действующим списком». Половина первая — настоящие умолчания
`netstack.DefaultRouting()`, половина вторая — то, что в файле, плюс словами:
исключения §5.6 подмешиваются всегда и конфигурацией не убираются, а
обнаружение служб — наоборот, действует только пока раздела `routing` нет.
Слить их в один список было бы честнее для глаза, но слияние живёт в
`resolveRouting`, наружу не вынесено, и переписать его в `cmd/hop` руками
значило бы завести второй экземпляр правды — тот самый, который расходится
молча.

#### Где проходит граница `settings_file`

Флаг гасит **чтение файла**: с выключенной политикой `readSettings` не
открывает `settings.json`, `Store.Settings()` отдаёт пустое, `applySettings`
переносит в `agent.Config` два `nil`, и продукт живёт на умолчаниях §6.10 и
§5.7 — ровно как до этого прохода. Разбор и проверка при выключенной политике
тоже не происходят: проверять нечего там, где ничего не читают.

Не гасит: заведение пустого `settings.json` при `Open` и его права. Это §6.14 и
§2, они не ветвятся; файл с правами 0644 и телом `{"version": 1}` не меняет
поведения ничем.

Флаг **свой, а не `routing_lists`.** Тот гасит вердикт `netstack` —
конфигурация игнорируется стеком целиком, — и охрана проброса краснела бы под
ним по чужой причине: не «диск не доехал», а «стек не смотрит». Ровно тот довод,
которым `bypass_rebind` не стал частью `bypass_sink`.

Флаг **один на два поля**, а не два. Это один файл, один разбор и один шов;
выключить половину значило бы описать состояние, которого у продукта нет.

**Отказ на кривом файле флага не имеет** намеренно — это обработка ошибки, а не
ветвление поведения. Тот же довод, по которому его не получили S29 и S30
(`docs/verification-store.md` §6): несимметричность Р13 — про то, как отвечать
на порчу, а не про то, что можно выключить.

#### Новые проверки

- **S40, S41** (`internal/store`) — списки и апстримы приезжают с диска.
  Краснеют без `settings_file`.
- **S42–S46** (`internal/store`) — умолчания при отсутствии файла, разница
  «нет раздела» / «раздел пуст», двенадцать видов кривого ввода, явное
  `0.0.0.0/0`, копия при отдаче. Без флага по доводам выше.
- **W52, W53** (`cmd/hop`) — проброс до `agent.Config`. Отдельно от S40 и S41
  по доводу W47: поля необязательны, `nil` означает умолчания, поэтому забытая
  строка сборки не ломает ни компиляцию, ни один модульный тест — она молча
  оставляет конфигурацию пользователя лежать на диске без действия. Ради них в
  `cmd/hop` заведён `applySettings`: шов, на который можно смотреть, не поднимая
  ни туннеля, ни сервиса.

Две проверки вывода `-routing` охраной не служат: они держат то, что вывод
называет неочевидные следствия §6.10 (обнаружение служб исчезает, исключения
§5.6 — нет), и краснеют от правки формулировок, а не политики.

#### Deviations

**§6.10 и §5.9 дописаны, а не исправлены.** Замер спеке не противоречил — он
показал, что обещанного в ней просто нет в коде. §6.10 получил абзацы «Где
лежит конфигурация» и «Кривая конфигурация — отказ, а не молчаливые
умолчания»; §5.9 — глагол `routing` в перечислении подкоманд и абзац о том,
почему настройки правятся файлом, а не глаголами `routing add`/`routing rm`:
правило это выбор списка плюс три поля, и флаги завели бы вторую грамматику
рядом с файлом.

**`internal/store` импортирует `internal/netstack`.** Правка соседнего пакета
не понадобилась, но граница пакетов сдвинулась: стор теперь тянет netstack, а
через него gvisor. Довод — выше, в решении про тип. Обратный вариант (свой
тип правила в сторе плюс отображение в `cmd/hop`) отвергнут: отображение
разойдётся с оригиналом молча, а тесты стора его не поймают, потому что живёт
оно не в сторе.

**Версия из будущего отвергается, хотя `decodeGroups` и `decodeNodes` версию не
смотрят вовсе.** Несимметрично с соседями по файлу, и осознанно: у тех полей
меньше и все обязательные, а настройки — это разрешения, и разобранная
половина новых настроек выглядела бы как полностью применённая конфигурация.
Сузить в консервативную сторону здесь дешевле, чем угадывать.

**`--json` у `-routing` нет.** §5.9 требует его у всех читающих команд, но его
нет и у `-nodes`, и у `-status`: он приедет вместе с подкомандами, а S33
регистра стора уже записан как «держится на функции формирования вывода, а не
на команде». Заводить один `--json` в одной команде раньше остальных значило бы
зафиксировать схему до того, как есть на чём её проверять.

**Записи в настройки из CLI нет.** Закрыт цельный срез — формат, чтение,
проверка, одна читающая команда; `routing add`/`routing rm` и любая запись в
`settings.json` со стороны `hop` не сделаны и в спеке помечены как намеренно
отсутствующие в v1. Файл правится редактором.

### Этап 9 — уборка простоя natTable без трафика (`nat_idle_sweep`, W59)

Пункт очереди, который прошлый проход назвал вслух, доводя ту же болезнь до
конца у `bypass.NAT` (`bypass_idle_sweep`, W51): `natTable`
(`internal/netstack/udp.go`) убирала простой только на чужом событии — на
следующем пакете (`mapping`) или на внешнем `Sweep()`, а последний в продукте
не зовётся ни разу, только в замере B3. Клиент, который замолчал навсегда,
оставлял запись и сокет NAT жить до `close()` всего стека.

#### Что замерено (и что из замера вышло)

1. **«Запись и сокет живут до `close()`» — не предположение, а падение
   теста.** `TestW59IdleEntryIsCollectedWithoutTraffic` на исходном коде даёт
   `NATEntries=1 NATSockets=1`, ожидались `0/0`, через 3×`UDPIdle` полного
   молчания клиента. После первой датаграммы не зовётся ни `mapping` (то есть
   ни один новый пакет), ни `Sweep()`, ни `Close()` — идут только часы. Тест
   закоммичен красным отдельно, до всякой реализации.

2. **Тикер в конструкторе, а не в горутине — ловушка уже стоила времени
   соседнему проходу, и здесь тикер сразу заведён в `newNATTable`.**
   `clock.Fake` назначает первый тик от момента `NewTicker`, и `Advance`,
   обогнавший планировщик, не доставил бы ни одного тика вовсе, если бы тикер
   заводился внутри `sweepLoop`. Заведён он до возврата из `newNATTable`, пока
   никакая горутина ещё не читает часы. Проверено прогоном
   `go test -race -count=20 ./internal/netstack/` — 20/20 зелёных.

3. **Собственная `sync.WaitGroup`, а не `Stack.wg` — находка этого прохода,
   которой не было у `bypass.NAT`.** Первая редакция добавляла горутину
   уборщика в `s.wg`, ту же группу, что считает горутины чтения NAT и потоков
   DNS. `TestD7IdleStreamIsClosed` (`internal/netstack/dnsstream_test.go`)
   ждёт опустошения именно `s.wg` **без** `Stack.Close()`, проверяя, что
   простой освобождает горутину сам — а фоновый уборщик простоя живёт до
   `close()` всего NAT, не «освобождается простоем», и его добавление в общую
   группу превращало этот тест в вечное ожидание. Падение поймано полным
   `go test ./...`, а не только пакетным прогоном: `TestD7IdleStreamIsClosed`
   стабильно падал 5/5 при изолированном `-run`. Уборщик получил свою
   `natTable.sweepWG`; общий с `Stack` остался только сигнал останова
   (`s.done`), не счётчик.

4. **`Stats()` осталась чистым чтением — измерено, а не заявлено.**
   `TestW59IdleEntryIsCollectedWithoutTraffic` опрашивает `h.st.Stats()` в
   цикле, ожидая уборки без единого её собственного вызова, кроме чтения; сама
   уборка приходит от фонового тикера. Тот же довод, что закрыл `bypass.NAT`
   (`Stats`, попутно прокручивавший уборку, однажды уже пришлось откатывать) —
   здесь он соблюдён с первой редакции: `natTable.stats()` под мьютексом
   только читает три числа.

#### Решение

Тот же приём, что у `bypass.NAT.startIdleSweeper` (`internal/bypass/bypass.go`):
фоновый тикер на `clock.Clock`, заведённый в конструкторе, период `Idle/2` —
шаг, которым `sweepLocked` и так себя ограничивает. На тике прокрутка
принудительная (`sweepNow`): свой ограничитель `sweepLocked` снимается, потому
что частоту уже ограничил тикер снаружи.

Останов — по `s.done`, который `Stack.Close()` закрывает ДО вызова
`s.nat.close()`, так что к моменту, когда `close()` дожидается
`t.sweepWG.Wait()`, уборщик, скорее всего, уже вышел сам; ожидание — сторож
порядка, а не гонка. Второго `done`/`closeOnce` не заведено — используется тот
же канал, что уже останавливает насос стека.

#### Где проходит граница `nat_idle_sweep`

Флаг гасит только фоновую половину. Прокрутка внутри `mapping()` и внешний
`Sweep()` остаются включёнными при любом его состоянии — у `mapping()` своя
роль (NAT не может не завести запись на пакете) и свои зелёные проверки
(T15, `TestT13FailCloseAnswersICMP` и другие идут через него постоянно), а
`Sweep()` нужен замеру B3. Увести любой из них под новый флаг означало бы
красить чужую, давно проверенную охрану заодно со своей.

Выключенный флаг не оставляет ни горутины, ни тикера — измерено:
`TestW59SweepDoesNotOutliveClose` заводит стек, не отправив ни одной
датаграммы, и видит счётчик горутин ровно на уборщика; при выключенной
политике тест сам себя пропускает (`t.Skip`), потому что утверждать нечего.

#### Новые проверки

- **W59** (`internal/netstack`) — `TestW59IdleEntryIsCollectedWithoutTraffic`
  (охраняет `nat_idle_sweep`, красный без флага: `NATEntries=1 NATSockets=1`
  вместо `0/0`) и `TestW59SweepDoesNotOutliveClose` (цена механизма, не
  охрана: пропускается при выключенном флаге).

#### Deviations

Нет: правка не вышла за `internal/netstack/udp.go`,
`internal/policy/policies.go` и документы реестра — `natTable` и так знала
своего `*Stack`, и его `done` хватило без второго канала останова.

#### Правка при слиянии: счётчик горутин не различает горутины

`TestW59SweepDoesNotOutliveClose` в присланном виде сравнивал
`runtime.NumGoroutine()` до и после `New`. Замер на слиянии: проверка
оставалась **зелёной с закомментированным `startIdleSweeper`** — в счётчик
попадает всё, что рантайм в этот момент заводит или доживает, и «горутин стало
больше» не значит «завелась именно та». Механизм, ради которого тест написан,
он таким образом не наблюдал вовсе.

Заменено на счёт по имени функции в дампе `runtime.Stack(all)`
(`sweepLoop`), и по дороге всплыли ещё два факта, каждый — источник флака:

- дамп в буфер фиксированного размера **молча обрезается**, и обрезанный даёт
  заниженное число, то есть зелёную проверку при живой горутине. Буфер теперь
  растёт, пока дамп не влезет целиком;
- горутина видна в дампе не мгновенно: снимок сразу после `New` видел ноль
  примерно на одном прогоне из двадцати, а после `Close` горутина, чей
  `defer Done()` уже выполнен, ещё мгновение доживает. Обе стороны теперь
  ожидание с потолком, а не снимок.

Утверждение теста от ожидания не слабеет: незаведённая уборка не заведётся и
за две секунды, а пережившая владельца — не исчезнет. Отрицательный контроль
после правки: с закомментированным `startIdleSweeper` проверка краснеет
(«уборщиков 0, ожидалось 1»), 60 прогонов подряд и `-race` — зелены.

### Этап 9 — поверхность CLI: подкоманды, коды возврата, `--json` (`exit_codes`, `json_schema`, W55–W58)

Шесть временных флагов Р40 (`-sub`, `-node`, `-nodes`, `-rm`, `-probe`,
`-routing`) плюс `-down` и `-status` сняты и заменены грамматикой §5.9.

#### Порядок был обязателен: сперва грамматика и коды, потом схема

HANDOFF требовал решить форму до `--json`, и требование оказалось не
формальностью. Схема — производная от того, кто её формирует: пока грамматики
нет, «читающая команда» не определена, и `--json` пришлось бы заводить по
одному на команду. Именно это и записано в S33 регистра стора: проверка
держится на функции формирования вывода, а не на команде.

#### Грамматика

`hop <глагол> [подглагол] [аргументы] [--флаги]`. Двусловные пары ищутся
первыми, иначе `node` заслонил бы `node add`. Таблица `commands`
(`cmd/hop/cli.go`) — единственное место, где перечислены глаголы; `usage`
читает её же, поэтому список в помощи не может разойтись с реализацией.

Написаны: `agent`, `down`, `status`, `nodes`, `node add`, `node rm`,
`sub add`, `probe`, `routing`. Ждут сокета §3.3 и отказывают с названной
причиной: `up`, `events`, `bypass`, `auto`, `autoconnect`.

**Отсутствующий глагол назван, а не убран.** «Неизвестная команда `events`» на
глагол, который спека обещает, — ложь про продукт: пользователь решит, что
опечатался. Строка таблицы с полем `waits` говорит, чего именно не хватает, и
она же ставит точку в помощи. Цена — тринадцать строк таблицы вместо девяти;
получено — W55, который краснеет в обе стороны: и на пропавшем глаголе §5.9, и
на выросшем мимо документа.

**`hop up` не сделан псевдонимом `hop agent`.** Соблазн был: обе команды про
«поднять туннель». Но `agent` блокируется до сигнала, а `up` из §5.9 обязан
вернуться сразу — это разные команды с одинаковым названием намерения, и
псевдоним пришлось бы менять на несовместимый ровно тогда, когда появится
сокет §3.3.

#### Что стало со старыми флагами

Удалены, а не оставлены псевдонимами. Решение принял PLAN.md ещё на этапе 9
(«два интерфейса к одному стору разойдутся»), и довод подтвердился буквально:
подкоманды растут — `node rm` уже отдельный глагол, — а флаг `-rm`, чтобы за
ними успевать, должен был бы обзавестись своей грамматикой значений.

Цена решения — чужой скрипт, который перестанет работать, и платить её молча
нельзя. Поэтому `retiredFlags` — таблица переезда: `hop -sub …` отказывает
текстом «флаг -sub снят вместе с временным интерфейсом Р40: теперь
`hop sub add <url>` (§5.9)». Пользователь узнаёт не только что интерфейс
сменился, но и на что. Полноту таблицы держит W55.

#### Карта кодов возврата

Одна функция `codeFor` на весь бинарь, а не `os.Exit` по месту:

| код | когда                            | где наблюдаем сегодня                          |
| --- | -------------------------------- | ---------------------------------------------- |
| 0   | выполнено                        | любая написанная команда                       |
| 2   | фоновой половины нет             | `status`, `down`, `agent` — отказ `ipc.Connect` |
| 3   | живых узлов нет (fail-close §5.6) | `probe`: узлы есть, ни один не ответил         |
| 1   | всё остальное                    | кривой ввод, кривой `settings.json`, отказ стора |

**Код 3 наблюдаем на `probe`, а не на `status`, и это не подделка.** Фазу
трафика (`agent.Snapshot`, `TrafficPhase`) знает связка, а сокета «клиенты ↔
агент» (§3.3) ещё нет; клиент до `PhaseFailing` не дотягивается никак.
Изобразить его в клиенте значило бы проверять собственную заглушку. `probe` же
меряет живость по-настоящему — движком и пробером продукта, тем же путём §6.7,
— и «ни один узел не ответил» есть ровно то состояние, которое §5.6 называет
fail-close. Проверяется без сети и без прав: узел на `127.0.0.1:1`.

Ноль живых узлов при этом отделён от пустого стора: «узлов нет вовсе» — код 1,
ошибка конфигурации. Разные коды потому, что от человека они требуют разного.

**Вывод печатается до кода 3, а не вместо него.** Мониторинг читает код,
человек читает строки, и человеку нужно видеть, какие именно узлы молчат.

#### `--json`: одна точка формирования

`emit(out, view, asJSON)` в `cmd/hop/output.go` — единственное место, где
работает `encoding/json`. Значение у команды одно, подачи две: `Text` печатает
человеку, теги полей — машине. Разойтись молча они не могут по построению;
раздельные ветки «сначала таблица, потом отдельно JSON» расходятся именно так —
поле есть в одной и забыто в другой.

Держит это не договорённость, а `TestW58JSONHasOneFormationPoint`: разбор AST
пакета, находка на любой вызов `json.Marshal`/`NewEncoder` вне `emit`. Тот же
приём, что у `TestReportFailureHasOneCallSite` (W29).

Схема закреплена литералами (`TestW58JSONSchemaIsFixed`), а не «тем, что
вышло»: переименованное поле обязано краснить, а не переезжать в ожидание
вместе с кодом. Узлы и группы при этом берутся готовыми из `store.NodeView` и
`store.GroupView` — список показываемых полей есть явное перечисление того, что
показывать **можно** (Р12, §6.14), и второй его экземпляр в `cmd/hop` разошёлся
бы с первым молча, а сторожит его S33.

#### Найдено замером: машинный канал был занят чужим логом

`hop probe --json` печатал в `stdout` строку `[Warning] common/errors: The
feature WebSocket transport … is deprecated` **перед** JSON. Пишет её Xray
своим глобальным логом (`common/log`), и `loglevel: none` в конфиге инстанса
её не гасит: предупреждение о конфигурации появляется раньше, чем инстанс со
своим логом.

Ни одна проверка схемы этого не видела и не могла: они смотрят на значение, а
мусор приходит в поток мимо наших писателей. Поэтому охраной стоит
`TestW58MachineOutputIsAloneOnStdout`, который подменяет настоящий `os.Stdout`
на трубу и разбирает то, что действительно оказалось в канале.

Проверка эта намеренно узкая: кода возврата она не касается (его держит W56), а
без `json_schema` пропускается — машинного вывода в такой сборке нет, и
утверждение о канале невыразимо. Обе оговорки об одном: краснеющая за двоих
проверка не говорит, что именно сломано; замер это и показал — до сужения она
краснела под обоими флагами.

Лечится в `internal/engine` (`takeXrayLogOffStdout`): обработчик глобального
лога Xray уводит его в `stderr`. Именно перенаправление, а не глушение —
диагностика чужой библиотеки полезна, но не в том канале, который разбирает
автоматика. Место — `internal/engine`, потому что Xray принадлежит этому пакету
(§3.4); гасить чужой глобальный лог из `cmd/hop` значило бы знать про Xray там,
где про него знать не положено. `sync.Once`, а не `init`: смена глобального
обработчика — действие владельца инстанса, а не побочный эффект импорта.

#### Границы двух политик

`exit_codes` гасит карту, а не отказы: команда отказывает одинаково при любом
его состоянии, меняется только число, которое видит вызывающий. Выключенная
политика описывает существовавший продукт — `fail()` этапа С отвечал единицей
на всё подряд.

`json_schema` гасит подачу, а не сбор: значения собираются и печатаются
человеку при любом состоянии флага, а `--json` отказывает. Молчаливый откат к
таблице был бы худшим из ответов — автоматика получила бы нулевой код и
неразбираемый вход. Так проведённая граница не даёт охране краснеть за двоих:
«схемы больше нет» и «команда сломалась» — разные поломки.

`event_broadcast` не заведён. Рассылка событий нескольким клиентам живёт в
сокете §3.3, которого этот проход не написал; политика без кода — это политика,
чей охраняющий тест зелен при любом её состоянии, то есть `fixture_bad` в
реестре продукта. Строка остаётся в `docs/not-yet-written.md` с той же
причиной, уточнённой до «рассылать некому и некуда».

#### Deviations

**§5.9 дописан, а не исправлен.** В перечисление глаголов добавлен `probe`:
команда написана раньше спеки и оказалась нужна ровно там, где отказ агента не
отвечает на вопрос, чей он. Правило проекта решает расхождение замера со спекой
в пользу замера. Там же записано, что код 3 сегодня наблюдаем на `probe`, что
карта кодов — одна функция, и что машинный канал занят только выводом команды.

**`hop status` показывает половину того, что требует §2.** Фазы трафика и
активного узла в выводе нет. Причин две, и обе стоят того, чтобы их назвать.
Первая: их знает связка, а сокета §3.3 нет. Вторая — замер, а не рассуждение:
стор держит эксклюзивный `flock` всё время жизни (`internal/store/lock.go`), и
связка держит его, пока агент работает. Проверено на живом бинаре: пока чужой
процесс держит `.lock`, `hop nodes` ждёт 5 с и отказывает («стор занят другим
процессом… идёт другая команда hop или работает агент»), код 1. Команда, которая на пути к ответу
открывает стор, отказывает ровно тогда, когда `hop status` нужнее всего — при
поднятом туннеле. Поэтому `store.StatusView` в `hop status` не приклеен:
правильный владелец этой половины — агент, он стор уже открыл. Пустого поля
вместо неё тоже нет: поле, которое всегда пусто, читается как «трафика нет», а
это неправда, — вместо него команда говорит словами, чего не знает.

**Правка соседнего пакета: `internal/engine`.** Добавлен `xraylog.go` и одна
строка вызова в `NewWithConfig`. Довод — выше, в разделе про машинный канал:
владелец Xray один, и это не `cmd/hop`.

**`hop nodes` по-прежнему читает стор напрямую** и потому отказывает при
работающем агенте — тот же `flock`. Это не регрессия прохода (`-nodes` вёл себя
так же) и не чинится грамматикой: чинится сокетом §3.3, где узлы отдаёт агент.

**`--json` у `events` нет, потому что нет `events`.** Из читающих команд §5.9
машинный вывод получили все написанные: `status`, `nodes`, `routing`, `probe`.

#### Правка при слиянии: список глаголов читается из спеки, а не переписан в тест

`specVerbs` приехал литералом в `cmd/hop/cli_test.go` — то есть вторым
экземпляром того же списка, что стоит в §5.9. Проверка «грамматика названа
целиком» держалась при этом на копии: правка §5.9 не краснит ничего, и
расхождение документа с кодом снова становится молчаливым — ровно то, против
чего в этом репозитории написан `cmd/doclint`.

Теперь список разбирается из `SPEC.md`: строка вида «`hop a | b | c`» внутри
раздела §5.9, найденная тем же приёмом, что у `TestReportFailureHasOneCallSite`
(`negcheck.ModuleRoot`). Отсутствие раздела или строки — падение, а не пустой
список: иначе переписанная спека делала бы проверку зелёной, ничего не
проверяя. `agent` по-прежнему добавляется явно — спека называет его отдельным

Отрицательный контроль, все три направления: лишний глагол в §5.9 — «глагола
"вымысел" нет в грамматике»; глагол, убранный из §5.9, — «глагол "routing"
есть в грамматике и не назван в §5.9»; удалённая строка перечисления — «в §5.9
нет строки перечисления глаголов».

#### Review finding: лишний аргумент даёт ложный успех

Безаргументные обработчики в `cmd/hop/cli.go` игнорируют остаток `fs.Args()`.
Одновременно стандартный `flag.FlagSet` перестаёт разбирать флаги после первого
позиционного аргумента. Живое воспроизведение:

```

```

Команда возвращает 0, печатает человеческую таблицу в `stdout` и ничего в

разобран. Это не блокирует принятый объём W55–W59, но нарушает собственную
грамматику CLI и опасно для автоматики ровно тем же ложным успехом, от которого
W55 защищает неизвестный глагол. Следующая правка CLI должна централизованно
зафиксировать допустимое число позиционных аргументов и добавить отрицательную
проверку хотя бы для одной читающей команды.

### Этап 9 — сокет «клиенты ↔ агент» §3.3 (`event_broadcast`, W60–W64)

Пять глаголов §5.9 существовали в грамматике и отказывали по одной причине:
клиентского сокета не было. Он написан, и вместе с ним закрылись три
следствия, названные в HANDOFF: `hop status` знает обе фазы, третий код
возврата наблюдаем не только на `probe`, и у политики `event_broadcast`
появился код.

#### Форма: тот же транспорт, отдельный сокет, свой набор операций

Вопрос стоял так: второй сервер на транспорте `internal/ipc` (§3.1) или
отдельный. Ответ — тем же доводом, которым §6.1 отвечает hiddify: **не TCP**.
hiddify слушает gRPC на `127.0.0.1:18020` без всякой проверки, и любой процесс
любого пользователя машины поднимает чужой туннель. Локальный порт не умеет
ответить на вопрос «кто на том конце»; unix-сокет с правами владельца и named
pipe с SDDL умеют — ровно поэтому транспорт §3.1 написан так, как написан, и
переписывать его второй раз значило бы завести вторую реализацию того же
ответа, чтобы однажды разойтись с первой.

Поэтому взят транспорт `internal/ipc` целиком — `Listen`, `Dial`, `Conn`, кадр
«длина + JSON» — и **отдельный сокет** со своим набором операций. Это и есть
то, что PLAN.md называет «поверх готового `internal/ipc` — свой набор Op, не
второй протокол». Три причины, по которым он не второй сервер на том же файле:

1. **Разные владельцы.** `/run/hop.sock` создаёт привилегированный сервис и
   открывает группе (агенту под обычным пользователем нужен доступ к сервису
   под root). Клиентский сокет создаёт непривилегированный агент в каталоге
   пользователя (§3.3). Один файл означал бы, что клиенты ходят в сокет
   сервиса, а §3.3 запрещает это буквально: «клиенты никогда не говорят с
   привилегированным сервисом напрямую — только через агент. Одна
   привилегированная граница, одна точка аудита».
2. **Разные множества операций.** Через §3.1 не проходит ни один узел и ни
   один ключ — это записано в спеке как свойство границы. Через §3.3 проходит
   вся наблюдаемая картина. Общий набор `Op` свёл бы два перечисления в одно, и
   «сервис не знает, куда идёт трафик» перестало бы держаться типом.
3. **Разные адресаты в двоичных файлах.** `cmd/hopd` импортирует
   `internal/ipc` и работает под root. Сервер §3.3 спрашивает связку; положи
   его в `internal/ipc` — и привилегированный демон утащит в себя весь агент
   вместе с Xray по графу импортов. Поэтому код границы живёт в
   `internal/agent/clients.go`, а из `internal/ipc` берётся только транспорт.

Путь по умолчанию — `$XDG_RUNTIME_DIR/hop/agent.sock`
(`ipc.DefaultClientPath`), запасной — `$TMPDIR/hop-<uid>/agent.sock`. Runtime, а
не каталог конфигурации, где лежит стор: сокет не настройка, он обязан
исчезать вместе с сессией. UID в имени запасного пути — чтобы первый
пользователь машины не занял `/tmp/hop` для всех остальных.

#### Несколько клиентов с первого дня

§3.3 требует этого прямо, и требование выполнено не обещанием, а формой:
подписка заводится на **соединение**, а не на сервер, каждое соединение
обслуживается своей горутиной, а кольцо связки (`eventRing.subscribe`) с этапа
С умеет отдавать накопленное и свой канал каждому подписчику под одним замком.
Сервер здесь только не мешает.

Проверяет это W60 — два клиента на одном сокете, оба получают одно и то же
событие. Подписка каждого подтверждается накопленным событием ДО появления
проверяемого: иначе тест сравнивал бы не рассылку, а то, кто успел подписаться
первым.

`event_broadcast` выключает ровно это: живая подписка остаётся одна, второй
клиент получает историю и молчание. Форма честная — так выглядит связка с
одним каналом событий на всех, — и снаружи она хуже поломки: `hop events
--follow` во втором окне не отказывает, он просто ничего не показывает, пока
переключения идут.

#### Что проведено через сокет

| глагол                | что делает связка                       |
| --------------------- | --------------------------------------- |
| `status`              | `Snapshot` → обе фазы §2, активный узел с живостью, счётчики, автоматика, фиксация, последнее переключение |
| `events`, `--follow`  | `History` и `Events(buf)`               |
| `up`, `up --node <id>` | `Up`, затем `Pin` (§1/С3)              |
| `down`                | `Down`                                  |
| `bypass on\|off`      | `Bypass` (§1/С6)                        |
| `auto on\|off`        | `Auto` (§1/С3)                          |

**`status` спрашивает связку, а сервис остаётся запасным адресатом для одного
состояния, и оно названо: `orphaned`.** Там связки нет по определению — ребро в
orphaned и есть смерть её соединения (§6.2), — а туннель жив, и остаток до
снятия знает только сервис. Поэтому в выводе две половины и ровно одна из них
непуста: `tunnel` — то, что сказал сервис, `agent` — то, что сказала связка.
`null` у половины значит «этот не отвечал», а не «показывать нечего»: пустое
поле читалось бы как «трафика нет», а это другое утверждение.

**`down` тоже идёт через связку**, а не через сервис, как раньше: снятие
туннеля мимо неё оставило бы связку в состоянии «туннель поднят», которого
больше нет. Прямой путь к сервису сохранён под тем же флагом `-socket` для
уборки осиротевшего туннеля и говорит об этом в stderr.

**Код 3 у `status`.** §1/С6 требует его буквально: «status показывает no
healthy nodes и возвращает код 3». До сокета третий код был наблюдаем только на
`probe`, потому что фазу трафика знает связка. Вывод печатается до кода, а не
вместо него, — тот же порядок, что у `probe`.

#### Чего сокет не открыл

**`autoconnect` остался отказом, и причина сменилась.** Ему нужно не соединение
со связкой, а поле в сторе: §6.13 говорит «состояние в сторе» и объясняет,
почему не флаг агента — флаг пришлось бы править в unit-файле или plist, то
есть под root, ради пользовательской настройки. Поля такого в `store.Settings`
нет, а читать его некому: автозапуск ставит инсталлятор (§5.10, §6.13), и
инсталляторы — остаток этого же этапа. Прежняя формулировка `waits` («придёт
вместе с сокетом клиентов») стала бы ложью в тот момент, когда сокет появился,
поэтому она переписана вместе с ним.

**`hop nodes` по-прежнему читает стор напрямую** и потому отказывает при
работающем агенте — тот же `flock`, замеренный прошлым проходом. Сокет это
чинит не сам по себе: узлы пришлось бы отдавать `store.NodeView`-ами через
границу, а кадр транспорта §3.1 ограничен 64 КБ и рассчитан на управляющие
сообщения; двести узлов (§6.5) — другой порядок. `status` при этом отвечает на
вопрос «сколько узлов живо» без списка, а §1/С5 список отдаёт именно `hop
nodes`. Осталось задачей, а не сделано наполовину.

#### Найдено по дороге: `Snapshot.Pinned` не заполнялся ни разу

Поле было в снимке связки с этапа С и всегда оставалось пустым: `health.Snapshot`
фиксацию не отдаёт, `m.pinned` наружу не выходит. §1/С5 требует показывать
фиксацию отдельной строкой, и пустое поле здесь — ровно та ложь, которой в этом
репозитории уже стоило времени: «узел не зафиксирован» вместо «не знаю».

Заполняется вычислением, а не вторым полем: фиксация в живости и есть
«автовыбор выключен, активный узел не заменяется» — `health.Pin` ставит
`auto=false` и `active=id` одним присваиванием, `health.Auto(false)` даёт то же
наблюдаемое поведение. Своё поле было бы вторым источником правды о том, что
уже выражено парой (`Auto`, `Active`), и разошлось бы с ней на первом же
`hop auto off`. Правка — три строки в `Agent.Snapshot`; `internal/health` не
тронут.

#### Кардинальность аргументов — находка приёмки, закрытая централизованно

Безаргументные обработчики игнорировали остаток `fs.Args()`, а `flag.FlagSet`
прекращает разбор флагов на первом позиционном аргументе. Живое
воспроизведение: `hop nodes лишнее --json` возвращал 0 и печатал человеческую
таблицу, а `--json` не был даже разобран как флаг.

Чинится полем `argc` в таблице `commands` и одной функцией `checkArgs`: у
каждого глагола §5.9 число позиционных аргументов известно точно, поэтому это
«ровно столько», а не «не больше». Проверки внутри обработчиков (`sub add`,
`node add`, `node rm`) сняты — иначе кардинальность жила бы в двух местах.

Отдельная строка отказа появилась из-за второй половины замера: флаг после
аргумента `flag` даже не разбирает, и «лишний аргумент --json» без объяснения
читается как «--json тут не бывает», хотя бывает — только левее. Отказ теперь
это и говорит.

#### Deviations

**`hop bypass on|off` и `hop auto on|off` — аргументом, а не флагом `--on`.**
§1/С6 записан как `hop bypass --on`, и это расхождение выбрано сознательно.
Довод — сам §5.9: «флаги только модификаторы», и глагол с аргументом флагом не
выражается. «Включить» и «выключить» — это то, что глагол делает, а не как;
§6.13 записывает ту же форму прямо (`hop autoconnect on|off`), то есть спека
внутри себя уже несогласована. Выбрана форма, совпадающая с §6.13 и с общим
правилом §5.9; вторую грамматику (`--on` псевдонимом) не заводили по тому же
доводу, по которому Р40 сняли флаги, а не оставили псевдонимами.

**Схема `--json` у `status` изменилась.** Было `{"tunnel":{…}}`, стало
`{"tunnel":…,"agent":…}` с ровно одной непустой половиной. Это не переезд
ожидания вслед за кодом: поле `agent` несёт то, чего в выводе не было вовсе, а
`tunnel` осталось тем же значением сервиса. Золотой литерал W58 обновлён и
дополнен второй половиной, потоком `--follow` и журналом `events`.

**Поток `--follow` — последовательность значений, а не растущий массив.** У
потока нет конца, и JSON-документом он невыразим; каждое событие печатается
отдельным значением через ту же единственную точку `emit`. `jq` такой поток
читает (проверено живым прогоном), а схема события — та же, что в `events`.

**Правка соседнего пакета: `internal/policy`.** Добавлена политика
`event_broadcast` с охраной `TestW60EventReachesEverySubscriber` и строка в
`All()`. Обойти нельзя: реестр — единственное место, где политики перечислены,
и `negcheck` читает его напрямую.

#### Замеры, а не рассуждения

Живой прогон настоящего бинаря против настоящего сокета (по ту сторону —
заглушка связки, потому что `hop agent` требует `hopd` и прав root):
`status`, `status --json`, `events --json`, `events --follow --json` —
`stdout` разбирается `jq` целиком, диагностики в машинном канале нет.
Управляющие глаголы дозвались до заглушки в том же порядке, в каком их
позвали (`up`, `pin n7`, `bypass true`, `auto false`, `down`). Два
одновременных `hop events --follow` получили одинаковые потоки — по пять
строк каждый, — что и требует §3.3.

### Сквозной путь «отказ трафика → живость» (W30, W31)

Пункт очереди `HANDOFF.json` называл два законных исхода: сквозной тест через
собранную связку либо аргументированное утверждение, что строки описывают путь,
которого у продукта нет. Выбран первый, и вот замер, который выбрал.

**Пути не было на бумаге, а не в продукте.** Прежний довод (`docs/not-yet-written.md`
до этого прохода) складывался из двух утверждений: `internal/agent/dialer.go`
намеренно не зовёт `ReportFailure`, вердикт ставит `internal/engine/classify.go`.
Оба верны и оба ничего не говорят о существовании пути. Он собирается из пяти
звеньев, и все пять уже стояли на месте:

1. `netstack` зовёт `Dialer.DialTCP` — объект из `newDialer(a.hm, a.engine)`,
   `internal/agent/wire.go`, сборка стека в `Up`;
2. диалер связки уходит в текущий инстанс движка (`holder.current`);
3. `engine.DialTCP` отдаёт ленивое соединение, а настоящий дозвон до узла делает
   перехваченный системный диалер Xray (`internal/engine/dialer.go`);
4. отказ этого дозвона под тегом `node-*` уходит в `reportDialFailure` →
   `classifyDial` — единственная точка классификации §6.15;
5. вердикт принимает замыкание в `New` (`internal/agent/wire.go`): `de.Report(a.hm)`,
   единственный call-site `ReportFailure` в продукте.

Не хватало не кода, а стенда. `internal/agent/harness_test.go` собирает связку на
поддельном движке — и это записано там намеренно, шаги 3–6 регистра проверяют
арифметику владения инстансами. Но фейк, который зовёт `onFailure`, доказывает
существование фейка: звено 3 и звено 4 в таком стенде просто отсутствуют.

**Стенд.** `internal/agent/traffic_liveness_test.go` собирает связку без
подстановки `Config.NewXray`, то есть на настоящем `engine.NewWithConfig`:
подставить фабрику значило бы вырезать проверяемый шов. Поддельны ровно две
вещи, и обе вне проверяемого пути — пакетное устройство (TUN требует прав, §8.1)
и пробер. Пробер поддельный не ради скорости: он отвечает «жив» на всё, и это
условие осмысленности W30. С настоящим пробером узел умер бы по собственному
счёту живости, и зелёный тест не отличал бы «вердикт по трафику доехал» от
«живость сама догадалась».

**Замер первый: одного SYN достаточно.** Форвардер gvisor отдаёт SYN-ACK только
из `CreateEndpoint`, поэтому исходящее соединение устанавливается раньше
рукопожатия с приложением (`internal/netstack/tcp.go`). Дозвон до узла случается,
даже если клиент не пришлёт больше ни байта, — стенду не нужно доигрывать
рукопожатие руками.

**Замер второй, стоивший переделки W31: локальный адрес до узла не доходит.**
Первая редакция целилась SYN'ом в закрытый порт `127.0.0.1`, ожидая «узел
дозвонился до сайта и получил отказ». Инжектор перед инбаундом увидел одно
соединение вместо трёх. Причина в §6.10: `127.0.0.0/8` стоит в `alwaysBypass`, а
`resolveRouting` подмешивает этот список к любой конфигурации, поэтому такой
поток уходит мимо туннеля и до узла не доходит вовсе. Отсюда разделение внутри
W31: из датаплейна идёт запрос на документационный адрес RFC 5737 (он
проксируется, узел его принимает), а мгновенный и наблюдаемый отказ сайта идёт
через тот же диалер, который `netstack` получает в `Up`.

**Что доказывает, что стенд не простоял без дела.** «Живость не тронута» зелено и
тогда, когда до узла не дошло ни байта. Поэтому узел W31 стоит за
`faultinject.Injector`, который считает принятые соединения, и тест требует их не
меньше трёх: одно из датаплейна, одно на отказавший сайт, одно на настоящий 502.

**Отрицательные контроли.** Каждый прогонялся с восстановлением исходника после.

- W30, проводка вырезана (`de.Report(a.hm)` → `_ = de` в `internal/agent/wire.go`):
  `счётчик ошибок трафика узла "мёртвый" остался 0, ожидалось 1` — FAIL за 15 с
  (потолок ожидания).
- W30, `HOP_DISABLE=traffic_kills`: тот же FAIL. Строка §6 «связка обязана
  краснить флаг сквозным путём, а не только модульным» стала исполнимой — и
  тем же прогоном проверяемой машиной: W30 добавлен третьим охраняющим к
  `policy.TrafficKills` (`internal/policy/policies.go`). Это правка соседнего
  пакета, и она названа здесь намеренно: без неё утверждение документа про
  сквозной путь держалось бы на дисциплине. Прежние два охраняющих, A5 и A29,
  зовут `ReportFailure` сами — они проверяют политику от места, куда вердикт
  уже доехал.
- W31, атрибуция без тега (`nodeFromContext` возвращает единственный
  наблюдаемый узел, когда тега `node-*` нет): FAIL —
  `через живой узел не дозвонились до сайта: agent: живого узла нет`. Узел
  умирает за дозвон чужого outbound'а, ровно как обещает §6.15.

**Отрицательный контроль, который остался зелёным, и что из этого следует.**
Строка W31 регистра называла флагом `error_classify`. Замерено: с
`HOP_DISABLE=error_classify` оба теста зелены. Проверено и сильнее — стрим-ошибка
докладывается в живость принудительно (`reportDialFailure` в
`classifiedConn.wrap`, в двух вариантах: только для не-EOF и вместе с EOF) —
по-прежнему зелено. Причина одна и та же: отказ целевого сайта приезжает клиенту
концом потока, `classify` отдаёт на него `KindNone`, а `DialError.Report` при
`KindNone` не делает ничего. Выключать политике здесь нечего: вердикта нет вовсе.

Вывод записан в документ, а не оставлен в голове: в строке W31 стоит прочерк
вместо имени флага, а под таблицей §6 названа причина. Это то же расхождение,
которое `internal/policy/policies.go` уже держит про T20 — там охраняющей названа
`TestStreamErrorIsNotFatal`, а не T20, по этой же причине. Сквозь связку W31
держит не политика, а граница атрибуции по тегу outbound'а: она и краснеет.

**Отклонений от `SPEC.md` нет.** §6.15 описывает ровно измеренное: вердикт
ставится на перехваченном диалере, атрибуция по тегу `node-X`, из трафика
наблюдаем только `DialTimeout`. Из четырёх видов §6.15 сквозной путь предъявляет
один — это следствие, названное самой спекой, а не расхождение.

**Стоимость.** Оба теста — 1,0 с на прогон вместе (`-count=20` — 20,5 с,
`-race -count=5` — 6,2 с, без флейка).

### Этап 8 — T25, T26 и T27 на L3: стенд со вторым интерфейсом

Три теста §8.4 ждали одного и того же — стенда, у которого есть вторая сеть.
Пир из `internal/l3/routecache_test.go` был большей его частью, но не годился
целиком, и причина не в объёме работы.

**Почему 10.9.9.0/24 не подходил.** `platform.LocalPrefixes` содержит
`10.0.0.0/8`: §5.6 выпускает локальные сети мимо туннеля правилом приоритета
31000, выше туннельного 32000. Узел, поставленный на 10.9.9.2, обходил бы
туннель по исключению, а не по защите от петли, — и T25 был бы зелен, даже если
бы §6.8 не существовало вовсе. То же и для T27: «интернет-сервер, доступный
напрямую» на 10.x достижим при поднятом туннеле законно, и «0 соединений» стало
бы утверждением, которое нечем нарушить. И для T26: подставной системный
резолвер на 192.168.x — а именно так он и выглядит в жизни, это домашний
роутер — до TUN не доходит вовсе, так что «перехват» проверялся бы на
маршруте, а не на вердикте.

Поэтому вторая сеть стенда — TEST-NET-2 (`198.51.100.0/24`, RFC 5737), которую
ни одно исключение §5.6 не называет. Проверка, что стенд способен утечь, стоит
в каждом из трёх тестов и не предполагается: `ip route get 198.51.100.2` при
поднятом туннеле обязан вести в `hopt0`, иначе тест падает до самого
утверждения. Замер отрицательного контроля это подтвердил: с
незарегистрированным правилом туннеля (`internal/platform/linux.go`, шаг
`tunnel rule`) первой краснеет именно эта проверка.

**Что добавлено к пиру.** Второй адрес на `veth1` плюс третий для подставного
резолвера; четыре слушателя — «узел» (принимает и записывает адрес источника),
«интернет-сервер», резолвер за узлом и подставной системный резолвер; и
управляющий протокол поверх того же stdin/stdout, которым `startPeer` уже
обменивается с пиром сигналом и `ready`. Отдельный сокет для счётчиков завести
было нельзя: адресовать его пришлось бы через ту самую сеть, которую тест
ломает туннелем, и счётчики отвечали бы «не дошло» ровно тогда, когда тест их
спрашивает.

**Живой узел.** T26 без него неполон: §5.7(б) подчиняет DNS fail-close, и без
живого узла запрос до апстрима не доходит — проверялась бы только первая
половина строки §8.4. Узел стенда — настоящий VLESS-инбаунд с
freedom-выходом в netns пира. Оживить его в netns удалось не сразу: три
хостнейма `probeURLs` (`cmd/hop/prober.go`) там не резолвятся ничем. Решение —
статическая таблица имён в конфигурации самого узла (`"dns": {"hosts": …}`)
плюс `domainStrategy: "UseIP"` у freedom: с `AsIs` freedom отдал бы имя
системному резолверу netns пира, которого там нет, и таблицу не спросили бы.
Регистрация обработчиков Xray для узла своя и более узкая, чем у продукта; в
неё пришлось добавить `app/dns` — без него конфигурация принимается, а
статическая таблица молча не заводится.

**Как меряются «пакеты на TUN» (T25).** Через `/proc/net/dev`, а не через
`/sys/class/net`. Замер: `unshare -Urn` не трогает mount namespace, sysfs
остаётся смонтированным от исходного netns, и файла `hopt0` там просто нет —
первая редакция теста падала на `no such file or directory`. `/proc/net` из
procfs и отдаёт netns вызывающего. Складываются `tx_packets` и `tx_dropped`:
пакет, вошедший в устройство и не забранный читателем, для T25 такой же пакет
на TUN, как доставленный.

**Отрицательный контроль T25 нашёл не тот механизм с первого раза.** Привязка
§6.8 у дозвона до узла живёт не в `outbound.Selector.Control`, а в
`internal/engine/dialer.go` — `sockopt.Interface = iface`, дальше Xray сам
раскладывает это в системный вызов. С закомментированным `Control` тест остался
зелёным (6 дозвонов до узла, 0 пакетов на TUN), и это было бы ровно то ложное
подтверждение, против которого написан этот раздел; красным он стал только с
закомментированным `sockopt.Interface`.

**Что T27 краснит, а что нет.** Отрицательных контролей три, и они краснят
разные половины. `if !healthy { return Reject }` закомментирован — датаграмма
молчит вместо ICMP unreachable, а вот TCP всё равно отказывает: вердикт
становится `Proxy`, релей упирается в мёртвый узел и отказ приходит не от
fail-close. `HOP_DISABLE=reject_mode` — TCP висит две секунды до `i/o timeout`.
Правило туннеля не раскладывается — краснеет проверка «адрес забран туннелем».
То есть утверждение «0 соединений на прямой путь» держится маршрутизацией, а
«отказ, а не молчание» — вердиктом и `reject_mode`; в одну проверку они не
сводятся.

#### Стенд L3 брал стор разработчика, и на этом стоял зелёный T24

`unshare -Urn` изолирует сеть, но не `$HOME`. `HOP_STORE` стенд не задавал, и
агент открывал настоящий стор пользователя (`os.UserConfigDir`,
`cmd/hop/store.go`), забирая его межпроцессный `flock` на всё время теста.

Цена оказалась не только гигиенической. Последняя проверка T24 — «после
реаттача трафик больше не отвергается» — была зелена по чужой причине: в сторе
разработчика есть узлы, ни один из них в netns недостижим, но §5.6 держит
трафик открытым первые 30 секунд стартового бюджета (Р5), пока хотя бы один
узел не проверен. На пустом сторе, то есть в CI, та же проверка обязана была
краснеть, и краснела: fail-close отвергает соединение так же, как респондер
сервиса в `orphaned`, и по одному `ECONNREFUSED` их не различить. Теперь стор у
каждого теста свой, а T24 различает состояния успехом, а не отказом: трафик
после реаттача обязан дойти до «интернет-сервера» за узлом.

Замер по дороге: стек терминирует TCP у себя и отвечает `SYN-ACK` раньше, чем
релей дойдёт до узла. `connect` возвращает успех, а на том конце ещё пусто —
первая же проверка счётчика после успешного `connect` давала ноль. Проверять
надо оба условия разом, и с записью в сокет: соединение, закрытое сразу после
`connect`, до пира не доходит вовсе.

#### Стенд L3 не говорил с продуктом с прохода CLI

Переход на подкоманды §5.9 (ef9027d) снял флаги `-socket` и `-status`, а стенд
их всё ещё передавал. `hop -socket …` печатал usage и выходил с кодом 1;
интерфейс не появлялся, и весь пакет падал на «не дождались появления
интерфейса hopt0» — то есть шаг `l3-linux` в CI был красен с того прохода.
Замерено живым прогоном на a6221d3, а не выведено из чтения диффа.

Починка — не только имя команды. Фазу стенд спрашивает теперь через
`hop status --json`: человеческая строка стала «туннель: up», подстроки
`phase=up` в ней нет ни в каком виде, а схему `--json` охраняет `json_schema`.
Урок общий: стенд, который зовёт продукт через CLI, обязан ходить через
машинный вывод — он контракт, а человеческий вывод оформление.


### Этап 9 — `hop nodes` через сокет §3.3 (W65, W66)

#### Замер: держит ли агент flock всю жизнь

Задача пришла с готовым доводом: «`hop nodes` открывает стор напрямую, а агент
держит эксклюзивный `flock` всю свою жизнь, поэтому команда отказывает кодом 1
ровно тогда, когда пользователь её больше всего хочет». Довод стоял и в коде —
в комментарии к `agent.ClientStatus` и к `statusOut` в `cmd/hop/output.go`, — и
в этих заметках, в разделе про поверхность CLI. Правило 1 требует замерить
такое до того, как из него выведен выбор формы. Замерено, и **довод неверен**.

Замер первый, живыми процессами. Собран `cmd/hop`, рядом запущена модель агента
(отдельный процесс, который открывает стор с 200 узлами и в цикле пишет
живость, как `persistHealth`), и во время её работы сорок раз подряд запущен
настоящий `hop nodes --json`:

```
агент: стор открыт, узлов 200
агент: транзакций 559, замок держался в среднем 1.05ms, дольше всего 3.402ms
hop nodes при живом «агенте»: успехов 40, отказов 0, дольше всего 38 мс
```

Тот же замер сохранён исполнимым — `TestW65MeasureAgentDoesNotHoldTheLock` в
`cmd/hop/measure_test.go`, `go test ./cmd/hop -run TestW65Measure -v -count=1`.
Модель агента там второй `*store.Store` на том же каталоге, а не второй
процесс: `flock` конфликтует и у двух описаний открытого файла внутри одного
процесса, а мерится здесь именно замок. Порядок величин тот же:

```
модель агента: транзакций 49, замок держался в среднем 543µs, дольше всего 1.107ms
hop nodes при живом «агенте»: успехов 40, отказов 0, дольше всего 5ms
```

Отказов нет ни одного. Причина — в `internal/store/store.go`: `load()` читает
все три файла **без замка** и берёт его только тогда, когда обязан что-то
изменить (создать недостающие файлы, убрать мусор от убитого процесса), а
`transact` берётся на время одной транзакции и отпускается — 1 мс на сторе в
200 узлов. Агент не держит замок «всю жизнь»: он держит стор открытым, а замок
берёт на миллисекунду за транзакцию.

Прежний замер при этом не был выдуман — он был верен ровно в том, что мерил.
Воспроизводится и сейчас:

```
$ flock -x /tmp/measure-store/.lock sleep 8 &
$ hop nodes
код 1, ждал 5043 мс
hop: store: стор занят другим процессом: замок … не освободился за 5s —
идёт другая команда hop или работает агент
```

Чужой процесс, держащий `.lock` дольше `lockTimeout`, действительно валит
команду. Неверен был **вывод** из этого замера: что так себя ведёт агент.
Строка отказа сама несёт эту ошибку («…или работает агент»).

Второй замер того же прогона нашёл настоящий дефект, и он не тот, который
искали:

```
$ flock -x .lock sleep 8 & hop nodes
код 1
строк в stdout: 201
группа sub-0123456789ab (200 узлов)
  cb6b51ec… 🇳🇱 nl-Amsterdam-00 | 1.5x  …:443  alive
```

Команда напечатала **весь ответ** и вернула код 1. Читает она без замка, но
`Store.Close` брал замок безусловно — то есть отказ приходил уже после того,
как работа сделана. Для мониторинга вокруг кодов возврата (§5.9) это худший вид
ошибки: код говорит «утилита упала», а вывод полон и верен. Починено там же:
`Close` берёт замок, только когда есть что писать (`writeDirtyLocked` при
пустом `dirty` не делает ничего, так что поведение сохранено). Охраняет
`TestW65ReadingCommandDoesNotLieAboutItsOwnSuccess`.

**Что после этого осталось от задачи.** Задача осталась целиком, но её причина
другая, и она тоже замерена: стор хранит **срез** живости (§2), доходящий до
диска не чаще раза в `healthDebounce` и переписываемый тикером
`healthPersistEvery` — по тридцать секунд. §2 называет срез «тем, чему можно
верить после паузы», а не «прямо сейчас», и окна с `traffic_failures` в нём нет
намеренно. Клиент, читающий стор при живом агенте, видит состояние
получасовой давности ровно тогда, когда актуальное есть у того, кого он не
спросил. Плюс §5.9 буквально: «остальные подкоманды — тонкий клиент к нему
через сокет §3.3». Комментарии, повторявшие опровергнутый довод, переписаны в
обоих местах; в `SPEC.md` правки не потребовалось — §2 про замок говорит верно
(«берётся на время транзакции»), неверным был пересказ.

#### Замер: 200 узлов и предел кадра §3.1

Кадр транспорта ограничен 65536 байтами (`maxFrame`, `internal/ipc/proto.go`);
§6.5 считает цену подписки «в 200 узлов». Замер на настоящем сторе — 200 узлов,
разобранных из ссылок `vless://…?type=ws&security=tls#🇳🇱 nl-Amsterdam-07 | 1.5x`,
с живостью на каждый узел:

```
узлов 200; JSON компактный 64941 байт; с отступами 97429; предел кадра §3.1 65536
один NodeView: 325 байт
кадр переполняется на 202 узлах этой формы (65593 байт)
200 узлов, имя длиннее на 10 символов: 66941 байт — НЕ влезает
200 узлов, имя длиннее на 20 символов: 68941 байт — НЕ влезает
```

Воспроизводится `TestW65MeasureNodesAgainstTheFrameLimit` в
`cmd/hop/measure_test.go` той же командой. Отметка `last_probe_at` в замере
фиксированная, но с наносекундами: у настоящей пробы они есть почти всегда, а
RFC3339 без них короче на десять байт на узел — две тысячи байт на подписке
§6.5, то есть разница, меняющая сам вывод. Настоящее «сейчас» дало бы то же
число с прыжком в ±12 байт от прогона к прогону, и записанное здесь число
перестало бы сходиться с командой.

То есть одним кадром обещание §6.5 держится с запасом в 595 байт — меньше
процента — и держится случайно: двести вторая строка подписки или десять лишних
символов в имени его ломают. На форме, которой узлы называют настоящие
провайдеры (`🇳🇱 nl-Amsterdam-07 | 1.5x — премиум`), те же 200 узлов весят
66698 байт и не влезают уже сегодня.

#### Форма ответа: поток кадров, а не страницы

Выбрано **по кадру на элемент**, закрытых кадром `End`, — та же форма, что у
`Events`. Постраничная отдача поверх существующего кадра отвергнута, и довод
не про удобство: странице нужен курсор, то есть смещение в списке, который
между запросами меняется (обновление подписки §5.8 переставляет состав), и
вторая страница приезжает из другого состава, чем первая. Картина, собранная из
двух обращений, не существовала ни в один момент времени — тот самый довод,
ради которого в этом коде есть `Snapshot` и ради которого `status()` не
спрашивает связку дважды. Поток снимает состав **один раз** и режет на кадры
уже снятое.

Гранулярность — кадр на узел, а не пачка узлов в кадре. У пачки есть размер,
который придётся пересчитывать всякий раз, когда в `NodeView` добавится поле, и
который однажды разъедется с пределом молча; у кадра на узел константы нет
вовсе — 325 байт против 65536 — двести кратов запаса.

Предел это не отменяет, а отодвигает: узел с именем в шестьдесят килобайт
остаётся выразимым, потому что имя приходит из чужой подписки. Замер показал,
как такой отказ выглядит снаружи: клиент получает голый `EOF` и код 1, то есть
§5.6 «отказ с названной причиной» не выполняется, хотя причина известна ровно
на сервере. Добавлен `abortStream`: кадр отказа крошечный и уходит по тому же
соединению.

**Одна сборка на обоих вызывающих.** Печатающих стало двое — `cmd/hop` читает
стор, пока связки нет, связка отдаёт то же самое через сокет, — поэтому тип
`store.GroupNodesView` и функция `Store.FullView(live)` живут в сторе, а не у
печатающего. Второй экземпляр сборки разошёлся бы с первым по одному полю за
раз. `LiveHealth` — необязательный источник живости свежее диска: `nil` значит
«свежее нечему быть», и это ровно путь без агента. Схема `--json` от выбора
адресата не зависит: `nodesOut.Groups` — это `[]store.GroupNodesView` в обоих
случаях, и золотой литерал W58 не изменился ни на байт.

**`hop nodes` без связки читает стор, а не отдаёт код 2.** Это буквальное
исключение §3.3: «`hop sub add` из §1/С2 существует раньше `hop up`, то есть
раньше живого агента». Команда, показывающая добавленное, обязана работать там
же, где работает добавляющая.

#### `hop probe` остаётся читателем стора

Решено осознанно и записано здесь, потому что ловушка названа в очереди. Три
довода, из которых решает третий:

1. `probe` существует ради случая, когда связки нет или ей не верят: §5.9
   называет её «нужной ровно там, где отказ агента не отвечает на вопрос, чей
   он». Диагностика последней надежды, идущая через диагностируемого, отвечает
   на другой вопрос.
2. Она — единственное место, где код 3 наблюдаем БЕЗ агента, и на этом стоит
   W56 (`exit_codes`). Уведи её в сокет — и проверка кодов возврата станет
   требовать поднятой связки, то есть перестанет проверять границу между кодом
   2 и кодом 3.
3. При живом агенте она не нужна: §6.5 уже опрашивает те же узлы по
   расписанию, и вторая проба поверх неё — это ровно тот «полный обход
   подписки», против которого §6.5 и написан (4000 соединений в час против
   870). Живую картину показывают `status` и `nodes`, и обе берут её у связки.

Замок ей при этом не мешает — см. первый замер.

#### Отрицательные контроли

**W65, нарезка на кадры.** Сервер собран так, чтобы отвечать одним кадром, и
кадр этот клиент понимает: во время контроля в протокол добавлено поле
`All []store.GroupNodesView`, которое обе половины читают и пишут, — иначе
краснота могла бы означать «клиент не разобрал», а не «кадр не влез».

```
=== RUN   TestW65NodesStreamThroughTheSocketPastTheFrameLimit
```

#### Deviations

**Правка соседнего файла: `internal/store/store.go`.** `Store.Close` больше не
берёт замок, когда писать нечего. Довод — замер выше: без этого читающая
команда печатает ответ и отдаёт код 1. Правка консервативна (`writeDirtyLocked`
при пустом `dirty` не делает ничего) и охраняется W65.

**Сокет связки назван явно в W56.** Первая ветка W56 запускала `hop nodes` без
`-client-socket`, а команда теперь сперва спрашивает связку: на машине с
запущенным агентом проверка ушла бы в чужой стор вместо тестового. Тот же
приём и та же причина, что у ветки `status` ниже в том же тесте.

**Опровергнутый довод остался в `internal/l3`.** `internal/l3/harness_test.go`
и `stand_test.go` повторяют «стор берёт эксклюзивный flock на всё время жизни
агента». Зона чужого прохода, поэтому не тронуто. Практический вывод там всё
ещё верный (свой `HOP_STORE` на тест нужен: два агента на одном сторе — это
две транзакции и потерянная запись), неверна названная механика.
