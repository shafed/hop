Главный вывод. Ядро проекта на Linux получилось рабочим, но продукт стал менее кроссплатформенным и местами более консервативным, чем задумывался. Самые существенные остатки — Windows, ограниченный bypass и задержка обнаружения «молчащего» мёртвого узла.

Актуальные расхождения и ограничения

Не закончено

Windows пока не является полноценной платформой

ХотелиРабочий сервис, Wintun и передача пакетов через named pipe.
Получилосьhopd остаётся консольной программой без обработчика Windows SCM, а Windows-датаплейн не завершён.

Простыми словами: установщик может зарегистрировать службу, но Windows не сможет нормально запустить её как системную службу. Проверка библиотеки Wintun есть, полноценного движения трафика — ещё нет.

Не закончено

Полноценные L3-тесты есть только на Linux

ХотелиПроверять реальное сетевое поведение на Linux, macOS и Windows.
ПолучилосьРеальный L3-стенд написан только для Linux; для macOS и Windows остались каркасы и отдельные проверки поставки.

То есть поведение с настоящим виртуальным интерфейсом на двух системах пока не доказано автоматическими тестами.

Ограничение v1

Bypass — не универсальный обход туннеля

ХотелиЛокальный трафик из списка исключений отправлять мимо туннеля.
ПолучилосьРеально наружу через bypass проходит UDP. TCP в локальную сеть получает RST, а не идёт напрямую.

Для обнаружения устройств по UDP этого хватает, но правило bypass для TCP означает «быстро отказать», а не «соединить напрямую».

Крайний случай

DHCP и IPv6 mDNS через туннель не поддержаны честно

DHCP требует сохранить служебный исходный порт 68, чего текущий непривилегированный UDP NAT не делает. IPv6 mDNS ff02::fb не доходит до классификатора, потому что у туннельного интерфейса нет IPv6-адреса. Обычную настройку сети самой ОС это не ломает, но транзитные сценарии не соответствуют первоначальному обещанию.

Бюджет времени

Переключение с мёртвого узла может начаться позже обещанных 5 секунд

ХотелиПереключиться не позже пяти секунд после отказа.
ПолучилосьПять секунд считаются от первой неудачной проверки, а она при отсутствии трафика может начаться лишь через период опроса — до 30 секунд.

Если трафик активно идёт, его ошибки ускоряют обнаружение. Проблема остаётся для соединения, которое просто замолчало.

Не закончено

Автоподключение пока нельзя включить командой

Команда autoconnect отказывает: нужного поля ещё нет в пользовательских настройках. Автозапуск пока определяется установщиком, а не переключателем в хранилище, как требовала спецификация.

Безопасность модели

Full-cone UDP принимает ответ от любого адреса

Такова выбранная модель NAT: она нужна для корректных ответов mDNS и full-cone поведения, но устройство в локальной сети, знающее временный порт, теоретически может подложить UDP-пакет. В заметках это признано допустимым свойством, а не ошибкой.

Осознанно поменяли архитектуру

Осознанное решение

UDP обходит gVisor

План предполагал netstack поверх всего PacketDevice. На практике gVisor обслуживает TCP, а UDP разбирается вручную и проходит через собственную full-cone NAT-таблицу. Причина: готовый UDP-forwarder gVisor привязывает состояние к паре «отправитель + получатель» и тем самым нарушает требуемую NAT-модель.

Осознанное решение

Отказ после смерти агента делает сервис, а не маршруты ОС

Reject-маршруты хорошо закрывали новые соединения, но уже открытые молча зависали. Поэтому сервис продолжает читать пакеты и сам отвечает RST/ICMP. Это сложнее, зато одинаково работает по смыслу на всех ОС и не оставляет молчаливое окно.

Осознанное решение

Attach-token хранится на диске

Изначально токен хотели держать только в памяти. Но после kill -9 новый процесс не смог бы узнать старый токен и повторно подключиться. Теперь он лежит в защищённом runtime-каталоге с правами 0700/0600. Это означает, что главной границей безопасности остаются права пользователя и проверка UID/SID.

Осознанное решение

«Чистый рестарт» всё равно кратко включает отказ

План обещал полностью миновать окно отказа. Реализация лишь сокращает его до времени перезапуска: иначе в зазоре пакеты молча исчезали бы, что хуже короткого явного отказа.

Осознанное решение

Доступ к IPC дан группе пользователей

Сокет, доступный только владельцу, не подходит: сервис работает от root, агент — от обычного пользователя. На Unix используется группа hop, на Windows — класс интерактивных пользователей. Владение конкретным туннелем всё равно проверяется отдельно по UID/SID.

Осознанное решение

Вердикт принимается до gVisor и хранится в таблице потоков

Спецификация не описывала отдельную таблицу потоков. Она появилась, чтобы один поток не менял маршрут посреди жизни и чтобы новые потоки можно было немедленно закрывать при fail-close.

Осознанное решение

Появился пятый вердикт: block

Кроме четырёх исходных решений понадобился молчаливый дроп для multicast/broadcast-трафика, где ответ сам по себе был бы неправильным. Это отличается от reject: reject сообщает отправителю об отказе, block намеренно ничего не отвечает.

Изменение интерфейса

CLI местами отличается от примеров спецификации

hop bypass on|off и hop auto on|off используют аргумент, а не флаг --on. Добавлена команда probe. Потоковый JSON — это последовательность отдельных JSON-значений, а не один бесконечно растущий массив. Схема status расширена половинами tunnel и agent.

Изменение поставки

Пакеты v1 не подписаны и не ставятся двойным кликом

Вместо полностью «нативной» установки выбрана установка из командной строки с явным подтверждением. Для первой версии это уменьшило объём инфраструктуры подписи, но пользовательский опыт проще не стал.
