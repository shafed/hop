# Установка: что ставится, куда, с какими правами и как это снять

Скрипты — в `packaging/`. Модель одна на три ОС и следует §5.2: **права
запрашиваются один раз, при установке**. Дальше привилегированный сервис живёт
под системным менеджером служб, агент — под пользователем, и повышения не
требуется больше ни разу.

Установка **не поднимает туннель**. Она регистрирует сервис и автозапуск агента
(§6.13); первый туннель появляется, когда агент стартует при логине или когда
его запустили руками. Инсталлятор, меняющий маршруты машины, — это инсталлятор,
который нельзя прогнать в CI.

Перед установкой нужно собрать бинари в `dist/`:

```
go build -o dist/hopd ./cmd/hopd
go build -o dist/hop  ./cmd/hop
```

## Linux

```
sudo packaging/linux/install.sh          # PREFIX=/usr/local по умолчанию
sudo packaging/linux/uninstall.sh        # снять, сохранив профили
sudo packaging/linux/uninstall.sh --purge # снять вместе с профилями
```

| что                            | куда                              | владелец     | режим |
| ------------------------------ | --------------------------------- | ------------ | ----- |
| сервис                         | `/usr/local/sbin/hopd`            | `root:root`  | 0755  |
| агент и CLI                    | `/usr/local/bin/hop`              | `root:root`  | 0755  |
| юнит сервиса                   | `/etc/systemd/system/hopd.service`| `root:root`  | 0644  |
| юнит агента                    | `/etc/systemd/user/hop.service`   | `root:root`  | 0644  |
| автозагрузка модуля `tun`      | `/etc/modules-load.d/hop.conf`    | `root:root`  | 0644  |
| стор агента (профили, история) | `~/.local/share/hop`              | пользователь | 0700  |
| управляющий сокет (рантайм)    | `/run/hop.sock`                   | `root:hop`   | 0660  |

**Группа `hop`.** Создаётся системной; в неё добавляется тот, кто позвал
установку. Она и есть право открыть управляющий канал (§6.1): сокет — `0660
root:hop`, и посторонний пользователь машины получает `EACCES`, а не чужой
туннель. Членство подхватывается при следующем логине — до перелогина агент
запустить не выйдет.

**Модуль `tun`.** `/dev/net/tun` появляется только вместе с модулем, а открытие
несуществующего пути автозагрузку не запускает. Отсюда `modules-load.d`: без
него сервис, поднявшийся при старте ОС, упирался бы в отсутствующее устройство.

**Привилегии сервиса.** Юнит режет набор до `CAP_NET_ADMIN` (интерфейс, адреса,
маршруты, `ip rule`) и `CAP_CHOWN` (отдать сокет группе), плюс
`NoNewPrivileges`. §8.4 требует, чтобы демону хватало `CAP_NET_ADMIN`, а агент
проходил тесты вообще без capabilities.

**Что снимается.** Всё из таблицы выше, кроме стора, плюс группа `hop` и
оставшийся сокет. Стор удаляется только по `--purge`. Персональные включения
агента (`systemctl --user enable`, сделанные пользователем в своём
`~/.config/systemd/user`) деинсталлятор не трогает — он их не ставил.

## macOS

```
sudo packaging/macos/install.sh
sudo packaging/macos/uninstall.sh
sudo packaging/macos/uninstall.sh --purge
```

| что                            | куда                                                        | владелец      | режим |
| ------------------------------ | ----------------------------------------------------------- | ------------- | ----- |
| демон                          | `/usr/local/libexec/hopd`                                    | `root:wheel`  | 0755  |
| агент и CLI                    | `/usr/local/bin/hop`                                         | `root:wheel`  | 0755  |
| LaunchDaemon                   | `/Library/LaunchDaemons/io.github.shafed.hopd.plist`         | `root:wheel`  | 0644  |
| LaunchAgent                    | `~/Library/LaunchAgents/io.github.shafed.hop.plist`          | пользователь  | 0644  |
| лог демона                     | `/var/log/hopd.log`                                          | `root:wheel`  | —     |
| стор агента                    | `~/.local/share/hop`                                         | пользователь  | 0700  |
| управляющий сокет (рантайм)    | `/var/run/hop.sock`                                          | `root:hop`    | 0660  |

Всё как в §5.10: демон в `/usr/local/libexec`, plist в `/Library/LaunchDaemons`
с владельцем `root:wheel` и режимом 644, загрузка через `launchctl bootstrap
system`, `RunAtLoad` и `KeepAlive`. `PREFIX` можно переопределить — например,
на префикс Homebrew.

**Сокет — `/var/run/hop.sock`, а не `/run/hop.sock`.** Умолчание кода
(`ipc.DefaultPath`) на macOS неприменимо: каталога `/run` нет, а корневая
файловая система только для чтения. Путь задан явно в обоих plist и обязан в
них совпадать.

**Группа `hop`.** Заводится через `dseditgroup`, смысл тот же, что на Linux.

**Логина может не быть.** На машине без GUI-сессии (ssh, CI) домена `gui/UID`
не существует, и `launchctl bootstrap gui/…` отказывает. Установка это не
считает провалом: §6.13 выполнен тем, что plist лежит на месте с `RunAtLoad`, —
агент стартует при следующем логине.

## Windows

```
powershell -ExecutionPolicy Bypass -File packaging\windows\fetch-wintun.ps1
powershell -ExecutionPolicy Bypass -File packaging\windows\install.ps1     # из консоли администратора
powershell -ExecutionPolicy Bypass -File packaging\windows\uninstall.ps1
powershell -ExecutionPolicy Bypass -File packaging\windows\uninstall.ps1 -Purge
```

| что                          | куда                                             |
| ---------------------------- | ------------------------------------------------ |
| служба, агент, библиотека    | `C:\Program Files\hop\{hopd.exe,hop.exe,wintun.dll}` |
| лицензия Wintun              | `C:\Program Files\hop\wintun-LICENSE.txt`        |
| служба                       | `hopd`, автозапуск, LocalSystem                  |
| автозапуск агента            | задача планировщика `hop-agent`, триггер «при входе», уровень «обычный» |
| стор агента                  | `%USERPROFILE%\.local\share\hop`                 |
| управляющая труба (рантайм)  | `\\.\pipe\hop`                                   |

**Откуда берётся `wintun.dll`** — `docs/wintun.md` (закрытый вопрос §7.2):
закреплённая версия и sha256, скачивание при сборке, в репозитории бинаря нет.

**SDDL трубы (§6.1)** ставит сам сервис (`internal/ipc/conn_windows.go`):
дескриптор безопасности рождается вместе с объектом трубы, и инсталлятору
менять его нечем. Установка после старта службы **проверяет** два условия — те
же, что проверены тестом в `internal/ipc`: труба не открыта `Everyone` и
допущены интерактивные пользователи. Не сошлось — установка падает.

**Агент — задача планировщика, а не ключ `Run`.** У задачи есть принципал и
уровень прав, поэтому агент стартует без повышения (§5.2) независимо от того,
какими правами обладает вошедший. Ключ `Run` этого не гарантирует.

**Права на каталог стора.** Режимов `0700` на Windows нет: `MkdirAll(0700)` в
Go там ничего не значит. Гарантия §6.14 держится профилем пользователя —
`%USERPROFILE%` уже закрыт для других непривилегированных учётных записей, и
стор наследует его ACL. Каталог создаёт сам агент при первом запуске;
инсталлятор в чужой профиль не лезет.

### Windows: что ещё не сделано

Служба регистрируется правильно, но **не стартует**: у `hopd` нет обработчика
диспетчера служб (`golang.org/x/sys/windows/svc`), поэтому SCM получает ошибку
1053 «служба не ответила». Плюс отсутствует платформенный слой (адаптер,
маршруты, DNS) — этап 8. Инсталлятор об этом говорит прямо в тексте ошибки, а
не делает вид, что всё хорошо.

## Автозапуск (§6.13)

| ОС      | сервис при старте ОС                   | агент при логине                                |
| ------- | --------------------------------------- | ----------------------------------------------- |
| Linux   | `systemctl enable hopd.service`         | `systemctl --global enable hop.service`         |
| macOS   | LaunchDaemon, `RunAtLoad` + `KeepAlive` | LaunchAgent, `RunAtLoad`                        |
| Windows | служба с автозапуском                   | задача планировщика с триггером «при входе»     |

Автоподключение к последнему активному профилю (§6.13) включено по умолчанию:
агент, поднятый автозапуском, сам поднимает туннель. Отдельного флага
«стартовать, но не подключаться» в CLI пока нет — чтобы агент не запускался
вовсе, автозапуск выключается штатными средствами ОС
(`systemctl --user disable hop.service`, `launchctl bootout gui/$UID/…`,
`Disable-ScheduledTask hop-agent`). Команда `hop auto off` — про другое: она
выключает автопереключение между узлами, а не автоподключение.

## Секреты и каталоги (§6.14)

Стор агента — `0700`, файлы с ключами — `0600`; это выставляет сам стор, а
инсталлятор дополнительно приводит каталог к `0700` с правильным владельцем при
установке и обновлении. Сервису ключи не передаются вообще (§3.1): он не знает
ни об узлах, ни о подписках. Attach-token лежит в `$XDG_RUNTIME_DIR/hop`
(`0700`/`0600`) и исчезает с перезагрузкой.

## Обновление поверх предыдущей версии

Скрипты идемпотентны и рассчитаны на I4 (§8.5): сервис останавливается **до**
подмены бинаря, файлы заменяются, юниты перегенерируются, служба стартует
снова. Группа, членство и стор пользователя не трогаются — профили и история
проб переживают обновление.

## Чем это проверено

`.github/workflows/l4-install.yml`, по расписанию (§8.4: L4 — не на каждый PR):

- **I1** — установка на чистую машину: сервис активен и включён в автозапуск,
  сокет на месте с правами `root:hop 0660`, агент включён на логин; член группы
  `hop` до сокета достучался, посторонний получил отказ.
- **I2** — перезагрузка. На hosted-раннере настоящей перезагрузки нет:
  проверяется, что юнит включён в `multi-user.target`, и что убитый `SIGKILL`
  сервис возвращается сам. Настоящая перезагрузка — только на своём железе или
  в VM.
- **I3** — снятие: файлов, юнитов, группы и сокета нет, снимок сети совпал с
  доустановочным, стор пользователя цел; повторный запуск деинсталлятора не
  ошибка.
- **I4** — установка поверх: канарейка в сторе на месте, права `0700`, сервис
  перезапущен (`MainPID` сменился).

Датаплейн L4 не проверяет — это работа L3 (§8.4), которая на Linux идёт в своём
netns. Поднимать туннель на общем раннере значит отобрать у него сеть.
