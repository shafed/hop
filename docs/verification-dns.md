# Верификация резолвера

Этап 6 отвечает за §5.7: перехваченный :53, реальный резолв через активный узел,
кэш с TTL и bootstrap мимо туннеля. §8.3 задаёт для него две строки (T14, T16).
T16 был зелён против заглушки — то есть было проверено, что запрос до резолвера
доезжает, и ничего из того, что резолвер делает; теперь T14 и T16 проверены и
против настоящего резолвера (`internal/l2/dns_test.go`) — шаг 10 ниже. Решения о
том, что отвечать клиенту, пока живого узла нет, что делать с ответом без TTL,
кэшируется ли NXDOMAIN и чем ходит bootstrap, в спеке не приняты. Документ
доводит верификацию до состояния, из которого тесты пишутся механически, и,
поскольку написан до кода, диктует, каким код обязан быть, чтобы проверяться.

Правило §8 действует и здесь: **проверка валидна, только если она краснеет без
той логики, которую охраняет.** У каждой строки регистра указан флаг из
`internal/policy`, отключение которого её ломает. Флаг без охраняющей проверки
запрещён `TestEveryPolicyIsGuarded`, проверка без флага — этим документом.

Почти всё здесь — уровень L1: сообщение DNS, кэш и апстрим не нуждаются ни в
сети, ни в TUN, ни в правах. Апстрим на стенде — поддельный сервер, отвечающий
заготовленными сообщениями; узел и туннель нужны только там, где проверяется
стык (T14, T16 против настоящего резолвера).

Нумерация решений (`Р15…`) продолжает `verification-autoswitch.md` (`Р1–Р6`) и
`verification-store.md` (`Р7–Р14`): все три серии — кандидаты в `SPEC.md` §5.7 и
§6 после ревью, и ссылаться на них удобнее сквозным номером. Проверки — `D*`,
чтобы не сталкиваться с `A*` и `S*`.

## 1. Что именно утверждается

§5.7 и §1/С4 распадаются на семь утверждений. Ниже — они, а не сценарии.

- **У1. Ни один запрос не уходит мимо резолвера, и путь резолва — путь
  трафика.** Всё, что пришло на порт 53, обслуживает наш резолвер (§3.4, п. 1),
  а наверх идёт через активный узел (§5.7). Исключение ровно одно — bootstrap, —
  и оно названо, ограничено именами узлов и проверяется отдельно (У7).
- **У2. Клиент всегда получает ответ, и отказ выражен кодом, а не молчанием.**
  Это тот же принцип, что §5.6 применяет к трафику: молчаливый дроп подвешивает
  приложение до таймаута стаба. Отказ — `SERVFAIL`, и он отличим от «такого
  имени нет».
- **У3. Кэш уважает TTL и не переживает смену того, через что резолвили.**
  Запись живёт столько, сколько назвал апстрим (в границах §4), а переключение
  узла и вход-выход из `bypass` обнуляют кэш целиком (§5.7в).
- **У4. Усечение обработано на обоих концах.** Флаг TC от апстрима означает
  повтор по TCP (§5.7); ответ, не влезающий в буфер клиента, означает TC
  **клиенту**, а не молча урезанный RRset.
- **У5. Стоимость резолва ограничена сверху.** Число одновременных запросов
  наверх и число записей в кэше имеют потолки, а поток одинаковых вопросов стоит
  одного запроса наверх. Иначе одно приложение с плохим ретраем превращает
  резолвер в генератор ассоциаций UDP через узел (§5.3, B3).
- **У6. Искажения ответа перечислимы.** Мы меняем в ответе ровно три вещи:
  идентификатор сообщения, вырезанный EDNS Client Subnet в запросе и
  синтезированный пустой ответ на AAAA (§6.9). Всё остальное проходит байт в
  байт, включая TTL (C4) и записи, которых мы не понимаем.
- **У7. Bootstrap работает ровно тогда, когда не работает туннель.** Он не
  зависит от живости узлов, не сбрасывается при смене сети и ходит своим прямым
  диалером — иначе §5.7(а) даёт петлю на старте и недоступность всей подписки
  при первой же смене сети.

У1–У6 проверяются на L1 целиком. У1 дополнительно на L2 (T16 против настоящего
резолвера), У3 — на L2 (T14), У4 — на L2 (усечённый ответ от настоящего апстрима
через настоящий узел). У7 — на L1 счётчиками диалеров.

## 2. Поверхность наблюдения

Верификация написана раньше кода, поэтому вправе требовать от кода
наблюдаемости. Ниже — часть контракта этапа 6, а не пожелание к тестам.

Интерфейс со стороны netstack уже заморожен и не обсуждается:

```go
// internal/netstack, этап 3. server — адрес, на который слал клиент: ответ
// обязан прийти именно с него, иначе резолвер клиента его не примет.
type Resolver interface {
    Query(query []byte, client, server netip.AddrPort) ([]byte, error)
}
```

Всё остальное — предложение этого документа:

```go
package resolver

type Config struct {
    Upstreams []netip.AddrPort   // §5.7: 1.1.1.1:53, затем 8.8.8.8:53
    HeadStart time.Duration      // фора второму, 150 мс

    // Путь наверх через активный узел. Этап 4 подставляет сюда core.DialUDP и
    // core.Dial; на стенде — поддельный апстрим. Оба поля, а не вызовы движка:
    // иначе L1 требует Xray.
    DialUDP func(ctx context.Context, dst netip.AddrPort) (net.PacketConn, error)
    Dial    func(ctx context.Context, dst netip.AddrPort) (net.Conn, error)

    // Путь мимо туннеля — тот же, которым ходит bootstrap и фаза bypass (§6.8).
    DialDirect func(ctx context.Context, dst netip.AddrPort) (net.Conn, error)

    Phase  func() TrafficPhase           // waiting | proxied | failing | bypass
    Events <-chan health.SwitchEvent     // подписка §5.7, не вызов из связки
    Clock  clock.Clock
}

func New(cfg Config) *Resolver
func (r *Resolver) Query(query []byte, client, server netip.AddrPort) ([]byte, error)
func (r *Resolver) Snapshot() Stats
func (r *Resolver) Close() error

type Stats struct {
    Generation    uint64     // растёт на каждом сбросе кэша
    Entries       int        // записей в кэше, из них
    Negative      int        // отрицательных
    Hits, Misses  uint64
    Upstream      []uint64   // запросов наверх, по апстримам, в порядке Config
    UpstreamDirect uint64    // запросов мимо туннеля (bootstrap и bypass)
    TCPRetry      uint64     // повторов по TCP на флаг TC
    TruncToClient uint64     // ответов, отданных клиенту с TC
    Coalesced     uint64     // запросов, склеенных с уже летящим
    ServFail      uint64
    InFlight      int
    Held          int        // ждущих в traffic_phase: waiting
}

// Bootstrap — отдельный тип, а не режим того же резолвера (Р22).
type Bootstrap interface {
    Resolve(host string) ([]netip.Addr, error)
    Stats() BootstrapStats   // Entries, Hits, Stale, Upstream
}
```

Семь требований к реализации, без которых проверки нестабильны или невозможны:

1. **Сброс кэша наблюдаем счётчиком, а не последствием.** `Generation` растёт на
   единицу при каждом сбросе. Без него T14 («после переключения адрес другой»)
   зелен и в реализации, где кэша нет вовсе, — то есть не охраняет ничего.
2. **Апстрим инъектируем, и путей два разных поля.** `DialUDP`/`Dial` — через
   узел, `DialDirect` — мимо. Проверка «bootstrap ходит мимо туннеля» тогда
   смотрит на счётчики диалеров, а не на договорённость об аргументе. Это то же
   требование, что A34 предъявляет пробам в §6.7, и по той же причине.
3. **Фаза трафика приходит функцией, а не булевым `Healthy`.** `waiting`,
   `failing` и `bypass` — три разных ответа резолвера (Р15, Р16, Р25), и свести
   их к одному биту нельзя. Это правка провода: `netstack.Config.Healthy` —
   `func() bool`, резолверу нужен `func() TrafficPhase`, и связка обязана дать
   ему именно фазу.
4. **Часы — единственный источник времени** (§8.1, линт уже есть). TTL, фора 150
   мс, удержание в `waiting`, простой TCP-соединения клиента — всё от
   `clock.Clock`. Иначе проверка потолка TTL стоит десять минут.
5. **Кэш вскрывается для теста только через `Stats` и `Query`.** Никакого
   `PutForTest`: проверка «запись протухла» ставится сдвигом фейковых часов, а
   не подкладыванием записи, иначе она проверяет тестовый код.
6. **Bootstrap — отдельный тип со своим кэшем.** Один объект с флагом «этот
   запрос служебный» означал бы, что сброс кэша при переключении узла обязан
   помнить, какие записи не трогать, — а это ровно та развилка, которую забывают
   в новой ветке кода.
7. **Ответ клиенту собирается копированием.** Секция вопроса берётся из запроса
   байт в байт, идентификатор подставляется, остальное — как пришло от апстрима.
   Тогда У6 проверяется сравнением срезов, а не разбором обеих сторон.

Стенд L1: поддельный апстрим (программируемые ответы, задержки, флаг TC,
молчание), `clock.Fake`, фейковая фаза трафика, канал событий переключения.
Стенд L2 — из §8.1 целиком: настоящий узел, настоящий Xray, поддельный
`PacketDevice`, а апстрим-сервер поднимается за узлом.

## 3. Решения, которых нет в спеке

Выбран консервативный вариант (CLAUDE.md). Все двенадцать — кандидаты в
`SPEC.md` §5.7 после ревью.

**Р15. Fail-close для DNS живёт в резолвере, а не в вердикте netstack.** §5.7(б)
требует «нет живых узлов — нет резолва», но порядок вердиктов §3.4 ставит
`hijack-dns` **первым**: до пункта 3 (`reject`) DNS-поток не доходит никогда, и
fail-close к нему не применяется вообще. Значит §5.7(б) обязан быть выполнен
внутри резолвера, иначе он не выполнен нигде. Решение: в фазе `failing` резолвер
отвечает `SERVFAIL`, наверх не ходит и **не отдаёт даже попадание в кэш**.
Причина отказа от кэша: иначе наблюдаемое поведение fail-close зависит от того,
что успело осесть в кэше до отказа, и проверка становится функцией истории
прогона. Причина `SERVFAIL`, а не `NXDOMAIN`: второе означает «такого имени
нет», приложение и стаб ОС кэшируют это как факт о мире и продолжают верить в
него после того, как узлы ожили. Цена — приложение не отличает «VPN закрылся» от
«DNS сломался», и внятная причина видна только в `hop status` (§1/С6).

**Р16. В `traffic_phase: waiting` запрос удерживается, но не дольше 4 секунд.**
§5.6 отводит стартовому бюджету 30 с и говорит «трафик ждёт»; для DNS это
буквально означало бы удержание на 30 с. Решение: запрос ждёт появления живого
узла, но не дольше `min(остаток стартового бюджета, 4 с)`, после чего —
`SERVFAIL`. Причина: типовой стаб ОС ждёт ответа 5 секунд и затем спрашивает
следующий сервер (тоже нас), то есть удержание дольше 4 с не выигрывает ничего,
а проигрывает право стаба на собственный ретрай и держит наши горутины сверх
потолка У5. Цена — приложение, стартовавшее одновременно с агентом, видит до
четырёх секунд задержки резолва, а в худшем случае один `SERVFAIL` там, где
через секунду всё заработало.

**Р17. Ответ без TTL, пол и потолок.** §5.7(в) требует уважать TTL и молчит о
границах. Решение: время жизни записи — **минимум TTL по секции ANSWER**; ответ
с TTL 0 не кэшируется вовсе (RFC 1035 прямо запрещает); потолок — 600 с; пола
нет (0 значит 0). Причина потолка именно такая, а не «сутки»: C4 отдаёт клиенту
исходный TTL без уменьшения, поэтому клиент держит запись дольше нас не более
чем на потолок, и суммарная несвежесть равна удвоенному потолку. Причина
отсутствия пола: пол ломает DNS-переключение с TTL в секунду — приём, на котором
живут балансировщики, — а от шторма одинаковых вопросов защищает не пол, а
склейка запросов в полёте (Р24). Цена — домен с TTL сутки перезапрашивается раз
в десять минут, то есть кэш стоит дороже, чем мог бы.

**Р18. Отрицательные ответы кэшируются.** Спека молчит. Решение: `NXDOMAIN` и
`NOERROR` с пустой секцией ANSWER (NODATA) кэшируются на
`min(SOA.MINIMUM, TTL записи SOA, 300 с)`, а если SOA в секции AUTHORITY нет —
на 30 с. Причина: без отрицательного кэша приложение, ищущее несуществующее имя
в цикле (а так ведут себя поиск по суффиксам и всякий сломанный ретрай),
отправляет каждый свой запрос через узел, и это самый дешёвый способ превратить
резолвер в источник трафика. Потолок 300 с и умолчание 30 с выбраны короткими
намеренно: цена ошибки здесь — «я только что создал запись, а она не
резолвится», и она платится ожиданием. Цена решения — ровно эти 30 секунд
невидимости только что появившегося имени.

**Р19. AAAA при заблокированном IPv6 — `NOERROR` с пустым ANSWER, и наверх
запрос не идёт.** §6.9 блокирует IPv6, §5.7 про типы запросов молчит. Решение:
на вопрос типа AAAA резолвер синтезирует пустой ответ сам, не спрашивая апстрим;
`NXDOMAIN` не используется. Причина: `NXDOMAIN` означает «имени нет», и стаб
имеет право распространить это на **все** типы, то есть заодно убить A-запись
того же имени; проброс настоящих AAAA даёт приложению адреса, которые §6.9
дропает молча, и приложение платит за это таймаутом Happy Eyeballs на каждом
соединении. Пустой ответ — единственный из трёх вариантов, который приложение
понимает как «здесь IPv6 нет», и именно так ведут себя сети без IPv6. Цена
записана прямо: это **ложь** — `dig AAAA` через hop отвечает не то, что ответила
бы сеть, — и в тот день, когда §6.9 отменят, флаг придётся выключить. Записи
HTTPS/SVCB (тип 65) при этом не переписываются: `ipv6hint` внутри них уезжает
клиенту как есть, потому что переписывание требует разбора и пересборки RR, от
которого отказался C4.

**Р20. Смерть узла посреди резолва: один повтор, и резолвер не судит узел.**
Спека молчит. Решение: запрос, оставшийся без ответа из-за отказа пути наверх,
повторяется **ровно один раз** — уже через нового активного узла, если
переключение состоялось в пределах общего бюджета клиентского запроса (5 с);
живых узлов не осталось — немедленно `SERVFAIL` по Р15. И отдельно: резолвер
**никогда** не вызывает `health.ReportFailure`. Причина второй половины:
молчание апстрима через живой узел — это отказ целевого хоста, а §6.15 такие
отказы узлу не засчитывает; отказ диала до самого узла классифицируется
перехваченным диалером движка сам, без нашего участия, и второй источник
вердиктов означал бы второй ответ на тот же вопрос. Цена первой половины — один
лишний запрос наверх на каждое переключение, случившееся в неудачный момент.

**Р21. Bootstrap-кэш переживает смену сети, основной — тоже.** §5.7 говорит о
сбросе кэша при смене узла и молчит о §6.6. Решение: смена сети не сбрасывает ни
один из двух кэшей. Bootstrap вдобавок отдаёт просроченную запись, если апстрим
недоступен (serve-stale), и не сохраняется на диск. Причина: адреса, полученные
через узел, зависят от узла, а не от того, через какой Wi-Fi мы к нему пришли;
для bootstrap же промах стоит недоступности всей подписки ровно в момент, когда
сеть только что сменилась, — то есть в самый частый момент отказа. Если узел
действительно переехал, его записи протухнут по TTL, а до тех пор он будет
признан мёртвым пробами (§6.3) — механизм на это уже есть. Цена — узел,
сменивший адрес одновременно со сменой сети, остаётся недоступным до истечения
TTL, и лечится это перезапуском агента.

**Р22. Bootstrap ходит на те же настроенные апстримы, а не на системные.** §5.7
отвергает системный резолвер для пути через узел и про bootstrap не говорит.
Решение: bootstrap использует тот же список `Upstreams`, но своим прямым
диалером (§6.8), и системную конфигурацию не читает. Причина: системная
конфигурация к этому моменту уже наша — на macOS и Windows DNS выставлен на
адаптере (§5.10, §8.4), — и чтение её обратно даёт либо адрес TUN, либо гонку с
собственной установкой. Цена высокая и её надо понимать: в сети, где исходящий
53 наружу закрыт (корпоративный фильтр, captive portal), bootstrap не
резолвится, а значит подписка целиком недоступна; единственный выход —
`hop bypass --on` (§1/С6) и §7, п. 2. Узлы, заданные по IP, этой ценой не
затронуты вовсе.

**Р23. Кэш общий для всех клиентов, ключ —
`(имя без учёта регистра, тип, класс)`.** Спека молчит. Решение: одна карта на
процесс; ответ клиенту несёт идентификатор и написание имени **из его запроса**,
а не из кэша. Причина: все клиенты локальны и ходят в одну и ту же сеть через
один и тот же узел, поэтому делить кэш по клиентам не за чем; регистр же нельзя
ни нормализовать в ответе (стаб, применяющий 0x20-рандомизацию, отбросит ответ с
другим написанием), ни учитывать в ключе (тогда `EXAMPLE.com` и `example.com` —
две записи и два запроса наверх). Наверх наш запрос уходит со **своим**
идентификатором, а не клиентским: иначе локальный процесс задаёт идентификаторы
наших исходящих запросов. Цена — единственная: `hop` не умеет отвечать разным
приложениям по-разному, и не должен уметь в v1.

**Р24. Одинаковые вопросы в полёте склеиваются, а число летящих ограничено.**
Спека молчит. Решение: вопрос, уже отправленный наверх, не отправляется второй
раз — второй клиент ждёт того же ответа; общее число одновременных запросов
наверх — 256, сверх потолка клиент получает `SERVFAIL` немедленно. Причина: без
склейки один старт браузера даёт десятки одинаковых вопросов, а без потолка
приложение с плохим ретраем создаёт неограниченное число ассоциаций UDP через
узел — ровно та деградация, которую меряет B3. Цена — под шквалом легитимный
запрос может получить `SERVFAIL` наравне с мусорным: потолок не различает, кто
именно шумит.

**Р25. Вход в `bypass` и выход из него сбрасывают кэш так же, как смена узла.**
§5.7(в) называет только смену узла. Решение: тот же сброс на каждом изменении
`traffic_phase` между `bypass` и не-`bypass`; в фазе `bypass` резолвер ходит
наверх прямым диалером (это уже описано C8: «в фазе bypass TCP и перехваченный
DNS идут мимо узлов»). Причина ровно та, что в §5.7(в): адрес, полученный
напрямую, указывает на CDN нашего настоящего региона, и после возврата в туннель
трафик пойдёт туда же — то есть выключение bypass не вернуло бы защиту
полностью. Цена — один полный перерезолв после каждого переключения bypass.

**Р26. DNSSEC не валидируется, EDNS Client Subnet вырезается.** Спека молчит.
Решение: резолвер — форвардер, а не валидатор: DO-бит и записи RRSIG проходят
насквозь, флаг AD от себя не выставляется и не снимается; EDNS Client Subnet из
клиентского запроса вырезается, свой не добавляется. Причина: валидация — это
корневые ключи, время и своя модель отказа, то есть отдельный продукт, а ECS
сообщает апстриму подсеть, которую мы как раз и прячем. Цена — доверие к
апстриму полное: узел, через который идёт резолв, видит все наши вопросы и
физически способен подменить ответы, и никакая проверка этого этапа такую
подмену не заметит.

## 4. Числа и границы

| параметр                           | старт                            | откуда          |
| ---------------------------------- | -------------------------------- | --------------- |
| апстримов                          | 2                                | §5.7            |
| фора второму апстриму              | 150 мс                           | §5.7            |
| таймаут одной попытки наверх (UDP) | 2 с                              | здесь           |
| общий бюджет клиентского запроса   | 5 с                              | здесь           |
| удержание в `waiting`              | ≤ 4 с                            | Р16             |
| потолок TTL                        | 600 с                            | Р17             |
| пол TTL                            | 0                                | Р17             |
| TTL отрицательного ответа          | SOA, потолок 300 с; без SOA 30 с | Р18             |
| записей в кэше                     | 4096, вытеснение LRU             | здесь           |
| одновременных запросов наверх      | 256                              | Р24             |
| приём от клиента по UDP            | буфер EDNS0 клиента, иначе 512   | RFC 6891        |
| буфер EDNS0 в нашем запросе наверх | 4096                             | здесь           |
| максимум сообщения по TCP          | 64 КиБ                           | RFC 1035 §4.2.2 |
| простой TCP-соединения клиента     | 10 с                             | RFC 7766        |
| записей в bootstrap-кэше           | 256                              | здесь           |
| пол TTL в bootstrap-кэше           | 300 с                            | Р21             |

**Откуда 5 секунд общего бюджета.** Это меньше типового таймаута стаба ОС, и
именно поэтому: клиент должен получить наш `SERVFAIL` раньше, чем решит, что мы
не отвечаем вовсе. Внутрь этого бюджета обязаны поместиться две попытки наверх
(2 с + фора 150 мс + 2 с) и один повтор по Р20 — то есть бюджет задаёт таймаут
попытки, а не наоборот.

**Откуда 2 секунды на попытку.** Апстрим спрашивается **через узел**, то есть
RTT здесь — это RTT до узла плюс RTT узла до апстрима; порог 5 с у пробы (§6.5)
измеряет ту же дорогу целиком. Две секунды оставляют место второй попытке внутри
общего бюджета и при этом заведомо больше любого нормального резолва.

**Откуда 4096 записей.** Кэш держит ответы целиком, средний ответ — сотни байт,
то есть потолок стоит единиц мегабайт. Он существует не ради памяти, а ради
предсказуемости: кэш без границы — это утечка, которую видно только через сутки
работы и только на машине пользователя.

**Почему потолок TTL важнее пола.** C4 отдаёт клиенту исходный TTL, не уменьшая
его. Значит наша запись живёт до `TTL`, а клиентская — до `TTL` от момента,
когда он её получил, и суммарная несвежесть ограничена именно потолком. Это
единственное число здесь, которое охраняет чужое решение, а не своё.

**Стоимость резолва в единицах §6.5.** Один клиентский промах кэша — один
UDP-пакет через узел (и второй, если сработала фора). Это дешевле одной пробы
живости, и поэтому в бюджете У5 меряется не трафик, а **число одновременно
летящих запросов**: именно оно, а не объём, деградирует в NAT-таблице (§5.3).

D34б добавлена после реализации, и вот почему. Усечённый ответ мы не пропускаем,
а **сочиняем**, и присутствие OPT в нём определяется тем, объявил ли EDNS0
клиент (RFC 6891 §6.1.1), — а не тем, была ли OPT у апстрима. Взять её от
апстрима значило бы объявить клиенту чужой размер буфера; не приписать вовсе —
сказать клиенту с EDNS0, что мы EDNS0 не понимаем, после чего он опустит буфер
до 512 и станет усекаться чаще. Неверного ответа ни то, ни другое не даёт — TC
уводит клиента на TCP в любом случае, — поэтому строка стоит без флага и её цена
измеряется лишними переходами на TCP, а не ошибками резолва.

D34 — та проверка, из-за которой формулировка этапа 6 в `PLAN.md` («резолвер
обязан повторить по TCP и вернуть полный RRset») верна только наполовину.
Клиенту, пришедшему по UDP с 512-байтовым буфером, полный RRset вернуть нельзя
физически: ему возвращается TC, и он приходит снова по TCP — который мы тоже
перехватываем (§3.4). Без D34 реализация, отдающая в UDP обрезанные байты без
TC, проходит T14 и «тест усечённого ответа» из плана.

| `dns_cache_flush_on_switch` | подписка на события `health` снята                   | T14, D19, D20       |
| `dns_failclose`             | резолвер отвечает и без живых узлов                  | D9, D10, D11, D17   |
| `dns_waiting_hold`          | в `waiting` сразу `SERVFAIL`, без удержания          | D12, D13            |
| `dns_aaaa_nodata`           | AAAA уходит наверх и возвращается как есть           | D45, D46            |
| `dns_negative_cache`        | отрицательные ответы не кэшируются                   | D26, D27, D28       |
| `dns_single_flight`         | каждый клиентский запрос идёт наверх своим           | D38                 |
| `dns_switch_retry`          | запрос, застигнутый переключением, отдаёт `SERVFAIL` | D16                 |

Десять флагов на один этап — много, и это осознанно: `negcheck` гоняет каждый
охранник дважды, и его время растёт линейно по их числу. Список сжат тем, что в
колонке стоят только **зарегистрированные** охранники; краснеют при выключении и
другие проверки (D21 при `dns_single_flight`, D22 при `dns_negative_cache`), но
в регистр политик они не идут.

Без флага намеренно оставлены: D1–D8 (форма сообщения и адрес ответа — не
политика, а контракт с клиентским стабом), D34–D37 (усечение к клиенту —
обязанность, а не переключаемое поведение), D39, D40, D44 (потолки и утечки
ресурсов), D47–D50 (отсутствие самодеятельности нельзя «выключить», можно только
нарушить), D53–D58 (асимметрия двух резолверов и свойства кэша). Проверка без
флага — норма; флаг без краснеющей проверки — нет, и это ловит `negcheck`.

## 7. Порядок реализации

Регистр упорядочен так, чтобы каждый следующий кусок кода имел красную проверку
до его написания. Первые пять шагов не требуют ни сети, ни Xray, ни узла — это
L1 на поддельном апстриме.

1. **Сообщение и форма ответа.** Разбор заголовка и вопроса, сборка ответа
   копированием, коды отказа, DNS поверх TCP с префиксом длины → D2–D8, D14,
   D15. Апстрима ещё нет: на его месте функция, возвращающая заготовленные
   байты.
2. **Один апстрим по UDP.** Таймаут попытки, общий бюджет → D1, D40, D44.
3. **Второй апстрим с форой.** Счётчики по апстримам → D41, D42, D43.
4. **Усечение.** TC от апстрима → повтор по TCP; TC клиенту по его буферу →
   D33–D37.
5. **Кэш.** TTL и его границы, отрицательный кэш, ключ и регистр, потолок и LRU,
   склейка в полёте → D21–D32, D38, D39.
6. **Фаза трафика.** `waiting`, `failing`, `bypass`; удержание, fail-close,
   сброс кэша на смене фазы → D9–D13, D17, D20. Здесь же правится провод: связка
   обязана дать резолверу фазу, а не бит (§2, требование 3).
7. **Подписка на события `health`.** Сброс кэша самим резолвером, `Generation`,
   повтор при переключении → D19, D16, D18, D55.
8. **AAAA и прочие искажения.** Синтез пустого ответа, вырезание ECS → D45–D50.
9. **Bootstrap.** Отдельный тип, прямой диалер, долгий кэш, serve-stale →
   D51–D58.
10. **L2.** T14 и T16 против настоящего резолвера, усечённый ответ через
    настоящий узел. После этапа 4 (Xray) и вместе со связкой, которая даёт фазу.
    Готово: `internal/l2/dns_test.go` — `TestT14SwitchResolvesToNewIP`,
    `TestT16DNSToLocalRouterIsHijackedRealResolver`,
    `TestD33TruncatedAnswerRetriesOverTCPRealNode`.

Шаг 6 — единственный, который нельзя закончить внутри этапа: фазу `waiting` и
`bypass` приносит связка (этап С), и до неё D12, D13 и D20 гоняются на фейковой
функции фазы. Это тот же шов, что S37 в регистре стора, и обходить его здесь
незачем: контракт формулируется сейчас, а склеивается там, где §3.4 велит — в
`agent`.

## 8. Чего эта верификация не проверяет

Продолжение честного списка §8.7, для той же цели — чтобы зелёный регистр не
считался гарантией.

- **Что узел не подменяет ответы.** Весь резолв идёт через узел в открытом виде:
  провайдер узла видит каждый наш вопрос и способен ответить чем угодно. Р26
  отказывается от DNSSEC осознанно, и ни одна проверка здесь подмены не заметит.
  Это верхняя граница приватности продукта, и она задана §5.7, а не этим
  документом.
- **Приложения со своим DoH.** Firefox и Chrome умеют ходить за именами по HTTPS
  мимо порта 53. Такой трафик уйдёт в туннель как обычный (§3.4, п. 4), то есть
  утечки не будет, но и нашего кэша, и §5.7(в) для него не существует — после
  переключения узла такое приложение продолжит держать старые адреса столько,
  сколько считает нужным.
- **Поведение конкретных стабов.** `systemd-resolved`, `mDNSResponder` и клиент
  Windows по-разному обходят несколько серверов, по-разному трактуют `SERVFAIL`
  и по-разному кэшируют отрицательные ответы. Р15, Р16 и Р18 рассуждают о
  типовом стабе; на настоящих проверен не будет ни один.
- **Реальные апстримы.** `1.1.1.1` и `8.8.8.8` на стенде не участвуют: апстрим —
  поддельный сервер. Фильтрация, rate limit и региональные ответы настоящих
  резолверов не измерены.
- **Captive portal.** Р22 прямо говорит, что при закрытом исходящем 53 bootstrap
  не резолвится; проверить это на стенде можно, а вот годится ли
  `hop bypass --on` как выход для пользователя — вопрос §7, п. 2, и он открыт.
- **Фрагментацию больших UDP-ответов.** Мы объявляем апстриму буфер 4096, а путь
  до него идёт через узел с чужим MTU. Что происходит с ответом на 2500 байт на
  настоящей сети, стенд не покажет.
- **0x20-рандомизацию и стойкость к отравлению.** Свой идентификатор запроса
  (Р23) — это всё, что здесь есть. Полноценная защита не нужна ровно потому, что
  путь наверх идёт внутри туннеля, — но это рассуждение, а не проверка.
- **Что кэш вообще ускоряет.** Ни одного измерения латентности резолва в
  регистре нет: D21 доказывает, что повторный вопрос не идёт наверх, и молчит о
  том, сколько это стоит пользователю. Бенчмарка на резолв §8.6 не заводит, и
  это осознанный пропуск — цена ошибки здесь измеряется в миллисекундах.
