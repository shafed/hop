# §7.2 — откуда берётся wintun.dll

Открытый вопрос спеки: «Windows: распространение `wintun.dll`. Подписанная
библиотека рядом с бинарём; как это укладывается в инсталлятор и обновления».
План держит его блокером этапа 8: без адаптера Wintun не проходит ни один
L3-Windows.

## Решение

**Библиотека не хранится в репозитории. Она скачивается при сборке по
закреплённой версии и обязана совпасть с закреплённой контрольной суммой; в
установку едет официальный подписанный бинарь, ничего не пересобирается.**

| что                     | значение                                                           |
| ----------------------- | ------------------------------------------------------------------ |
| версия                  | `0.14.1`                                                            |
| источник                | `https://www.wintun.net/builds/wintun-0.14.1.zip`                   |
| sha256 архива           | `07c256185d6ee3652e09fa55c0b673e2624b565e02c4b9091c79ca7d2f24ef51`  |
| что берётся из архива   | `wintun/bin/amd64/wintun.dll` и файл лицензии готовых бинарей       |
| куда кладётся при сборке| `dist\wintun.dll` рядом с `hopd.exe` и `hop.exe`                    |
| куда кладётся при установке | `C:\Program Files\hop\wintun.dll`                               |
| чем делается            | `packaging/windows/fetch-wintun.ps1`                                |

Версия и сумма закреплены в одном месте — `packaging/windows/common.ps1`.
Несовпадение суммы — отказ сборки, а не предупреждение.

## Почему так

**Пересобирать нельзя — это меняет лицензию продукта.** Исходники Wintun под
GPL-2.0; готовые подписанные бинарники выпущены под более мягкой лицензией,
которая лежит в самом архиве. Собери мы DLL из исходников и положи рядом с
`hopd.exe` — в поставке оказался бы GPL-2.0-артефакт, ровно тот случай, против
которого написан раздел про лицензии в `CLAUDE.md`. Официальный бинарь этой
проблемы не создаёт: он приходит под своей лицензией, которая едет вместе с ним
(`wintun-LICENSE.txt` в каталоге установки).

**Пересобирать нельзя и технически.** Драйвер грузится только с действительной
подписью; самосборная библиотека на машине с включённой проверкой подписи
драйверов не поднимет адаптер. Upstream прямо называет подписанные DLL
единственным поддерживаемым способом распространения Wintun.

**В репозиторий бинарь не кладётся.** Git — не средство доставки бинарей: у
файла в дереве нет ни версии, ни проверяемого происхождения, а обновление
раздувает историю навсегда. Закреплённая сумма даёт то, чего файл в дереве не
даёт вовсе, — проверку цепочки поставки на каждой сборке.

**Скачивание — при сборке, не при установке и не при первом запуске.**
Инсталлятор, лезущий в сеть, отказывает там, где сети нет (а первое, что делает
пользователь VPN-утилиты, — ставит её на машине с плохой сетью), и добавляет в
установку недоверенный шаг под правами администратора. Сборка — единственное
место, где сеть уже нужна и где отказ виден инженеру, а не пользователю.

**Рядом с бинарём — рядом с сервисом.** Адаптер открывает `hopd`, а не агент
(§3.2, §5.3: агенту приезжают пакеты, а не хендл драйвера), поэтому библиотека
кладётся в каталог службы. Отдельная копия агенту не нужна.

## Обновления

1. Поменять `$WintunVersion` и `$WintunSha256` в `packaging/windows/common.ps1`.
2. Прогнать `packaging/windows/fetch-wintun.ps1` — он свалится, если сумма не
   совпала.
3. Проверить, что файл лицензии в архиве не изменился: условия распространения
   готовых бинарей — часть решения, а не деталь.
4. `install.ps1` останавливает службу до подмены файлов, поэтому обновление DLL
   штатное: загруженная библиотека освобождается вместе с процессом службы.

Wintun давно не выпускает новых версий; закрепление на `0.14.1` — не заморозка
из осторожности, а фиксация текущего состояния upstream. Появится новая версия —
шаги выше.

## Что отвергнуто

- **Бинарь в git.** Нет происхождения, нет проверки, растёт история.
- **Сборка из исходников.** GPL-2.0 в поставке и неподписанный драйвер.
- **MSI с драйверным пакетом.** Wintun ставится не как драйверный пакет
  (`.inf`), а библиотекой, которая создаёт адаптер на лету; отдельная установка
  драйвера дала бы ещё одну сущность, которую надо снимать при удалении.
- **Скачивание на машине пользователя.** См. выше: сеть под администратором в
  момент установки.

## Что этим не закрыто

Решение снимает блокер §7.2 в части поставки. L3-Windows по-прежнему не
запускается, и причин теперь две, обе — код, а не вопрос:

1. платформенный слой Windows (адаптер, маршруты, DNS) — этап 8;
2. `hopd` не умеет быть службой Windows: обработчика SCM
   (`golang.org/x/sys/windows/svc`) в `cmd/hopd` нет, поэтому
   зарегистрированная служба не отвечает диспетчеру и `Start-Service` падает с
   1053. Регистрацию инсталлятор делает правильно, запуск упирается в это.
