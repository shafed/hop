# Верификация стора и подписок

Этап 7 отвечает за обещание §1/С8: «узлы, которые остались, сохраняют свою
историю проб; исчезнувшие удаляются». §8.3 задаёт для него две строки (T18,
T19) — этого мало, чтобы писать код: решения о том, что такое «тот же узел»,
что делать с недокачанной подпиской и кто имеет право писать в стор, в спеке не
приняты. Документ доводит верификацию до состояния, из которого тесты пишутся
механически, и, поскольку написан до кода, диктует, каким код обязан быть,
чтобы проверяться.

Правило §8 действует и здесь: **проверка валидна, только если она краснеет без
той логики, которую охраняет.** У каждой строки регистра указан флаг из
`internal/policy`, отключение которого её ломает. Флаг без охраняющей проверки
запрещён `TestEveryPolicyIsGuarded`, проверка без флага — этим документом.

Почти всё здесь — уровень L1: разбор ссылок и слияние не нуждаются ни в сети,
ни в TUN, ни в Xray. Диск нужен, но `t.TempDir()` — не привилегия.

Нумерация решений (`Р7…`) продолжает `verification-autoswitch.md`, где заняты
`Р1–Р6`: обе серии — кандидаты в `SPEC.md` §6 после ревью, и ссылаться на них
удобнее сквозным номером. Проверки — `S*`, чтобы не сталкиваться с `A*` того
регистра.

## 1. Что именно утверждается

Обещание §1/С8 и §5.8 распадается на шесть утверждений.

- **У1. Обновление подписки сохраняет тождество узла.** Узел, оставшийся у
  провайдера, остаётся тем же объектом: тот же `id`, та же история проб, тот же
  выбор. Косметическая правка у провайдера не наблюдаема изнутри (§5.8, §6.16).
- **У2. Одна битая строка не рушит импорт.** Подписка из ста ссылок, где одна
  негодна, даёт девяносто девять узлов и одну учтённую причину, а не ошибку
  целиком (§6.11).
- **У3. Нормализация ссылок воспроизводима и разложима.** Каждое правило §6.12
  проверяется отдельно от остальных, и каскад распознавания — тоже: «не
  распозналось» и «распозналось не тем» — разные отказы.
- **У4. Стор не теряет данные и не отдаёт полуправды.** Обрыв в любой момент
  записи оставляет читаемым либо прежнее состояние целиком, либо новое целиком.
  Третьего наблюдаемого состояния нет.
- **У5. Ключи не покидают стор.** Ни в лог, ни в `status`, ни сервису — ни на
  каком уровне подробности (§6.14, §3.1).
- **У6. Живость переживает рестарт ровно настолько, насколько ей можно
  верить.** Срез восстанавливается, окно — нет, и восстановленное состояние не
  выдаёт себя за проверенное (§2, Р5 регистра решений).

У1–У3 проверяются целиком без диска. У4 — на `t.TempDir()` с инъекцией отказов
записи. У5 — тестами формата плюс линтом. У6 — на фейковых часах.

## 2. Поверхность наблюдения

Верификация написана раньше кода, поэтому вправе требовать от кода
наблюдаемости. Ниже — часть контракта этапа 7, а не пожелание к тестам.

```go
// Разбор — чистая функция. Ни диска, ни сети, ни стора.
package subscription

type Parsed struct {
    Nodes       []store.Incoming     // в порядке подписки
    Unsupported []Unsupported        // link + reason, по одной на строку
    Format      Format               // какая ступень каскада взяла вход
}

func Parse(body []byte) (Parsed, error)

// Стор — конкретный тип, не интерфейс: второй реализации не предвидится,
// а интерфейс ради тестов прячет как раз то, что тесты проверяют, — диск.
package store

func Open(root string, clk clock.Clock) (*Store, error)

func (s *Store) Groups() []Group
func (s *Store) Nodes(groupID string) []Node          // в порядке node_order
func (s *Store) Node(id string) (Node, bool)
func (s *Store) MergeGroup(groupID string, in []Incoming) (MergeResult, error)
func (s *Store) Health(nodeID string) (health.NodeHealth, bool)
func (s *Store) PutHealth([]health.NodeHealth)         // дебаунс внутри
func (s *Store) Flush() error                          // синхронно, для тестов и выхода
func (s *Store) Close() error

type MergeResult struct {
    Added, Kept, Removed []string              // id узлов, а не количества
    Unsupported          map[UnsupReason]int
}
```

Шесть требований к реализации, без которых проверки нестабильны или невозможны:

1. **Разбор отделён от стора.** `Parse` не касается диска, поэтому
   golden-корпус — это таблица «файл → ожидаемые узлы», а не сценарий с
   файловой системой. Без этого У3 стоит на порядок дороже и гоняется на порядок
   реже.
2. **`MergeResult` перечисляет `id`, а не считает их.** Проверка «узел остался
   тем же» — это `Kept` содержит конкретный `id`; счётчики позволяют слиянию
   удалить и добавить один и тот же узел, не изменив ни одного числа.
3. **Корень стора задаётся снаружи.** `Open(root)` — значит `t.TempDir()`,
   значит тесты идут параллельно и не мешают друг другу и настоящему стору
   разработчика.
4. **Часы — единственный источник времени.** Дебаунс живости идёт через
   `clock.Clock` (линт уже есть). Иначе S34 стоит тридцать секунд реального
   времени.
5. **`Flush` синхронен.** Вернулся — данные на диске. Тест не спит и не
   опрашивает файл в цикле.
6. **Запись инъектируема на отказ.** Слой записи принимает функцию «создать
   временный файл» и «переименовать», чтобы У4 проверялась отказом в
   назначенной точке, а не убийством процесса в надежде попасть в окно.

**Направление импорта фиксируется здесь.** `store` импортирует `health` ради
типа `NodeHealth` — только тип данных, ни одной функции; обратного импорта нет
и быть не должно. §3.4 говорит «store не знает ни про кого», но он же вменяет
стору персистентность `NodeHealth`, а модель принадлежит `health`: окно,
состояние и счётчик трафика меняет только он. Дубль структуры в `store` означал
бы две модели одного состояния и ручную конверсию на каждой пробе. Это уже
записано как отклонение C1; регистр закрепляет его как контракт, чтобы
следующий читатель не «починил» импорт обратно.

## 3. Решения, которых нет в спеке

Выбран консервативный вариант (CLAUDE.md). Все восемь — кандидаты в `SPEC.md`
§5.8/§6.11–§6.16 после ревью.

**Р7. Недокачанная или пустая подписка не применяется вовсе.** §5.8 описывает
diff-обновление и молчит о том, что делать с телом, которое кончилось
посередине. Решение: тело читается целиком в память (потолок 8 МиБ, таймаут
30 с), разбирается целиком, и только полностью разобранный результат идёт в
слияние. Разбор, давший **ноль** узлов, — тоже отказ: группа остаётся прежней,
команда возвращает ошибку. Причина: обрезанная подписка неотличима от подписки,
из которой провайдер убрал половину узлов, а diff-слияние на этом удалит их
вместе с историей. Цена ошибки несимметрична — лишний отказ обновления стоит
строки в выводе, лишнее удаление стоит всей статистики.

**Р8. Порядок узлов переписывается на каждом слиянии.** §2 держит
`Group.node_order`, §6.4 делает его наблюдаемым: при равных `rtt` выигрывает
первый по порядку. Решение: `node_order` — список `id`, переписываемый из
порядка входящей подписки; выжившие узлы встают туда, куда их поставил
провайдер, новые — на своё место в подписке. Причина: порядок принадлежит
провайдеру, а не истории нашего стора, и «первый по `node_order`» обязан
означать «первый в подписке», иначе воспроизводимость выбора (A11) держится на
том, в каком порядке узлы когда-то добавлялись.

**Р9. Слияние не пересекает границу группы.** §6.16 задаёт ключ и не говорит,
где он уникален. Решение: ключ действует внутри группы, то есть настоящий ключ
— пара `(group_id, merge_key)`. Причина: две подписки от разных провайдеров
законно содержат один и тот же сервер, а история проб измерена **через
провайдера** — перенос её между группами приписал бы одному провайдеру
измерения другого.

**Р10. В группе `manual` слияния нет.** Прямое следствие Р9 и закрытие
известного дефекта: `manual` — не подписка, диффать не с чем. Решение: каждый
`hop node add` создаёт узел с новым `id`, `hop node rm <id>` удаляет по `id`, и
ключ слияния в этой группе не участвует ни в чём. Причина: при слиянии два
вручную добавленных узла с совпавшим ключом неразличимы, и удаление третьего
переставляет `id` у оставшихся — поведение, которое пользователь не сможет ни
предсказать, ни объяснить. Это устраняет цену, записанную в C14.

**Р11. Clash YAML в v1 распознаётся, но не разбирается.** §6.12 ставит его
второй ступенью каскада. Решение: ступень на месте и обязана срабатывать — тело
с ключом `proxies:` определяется и отвергается **одной внятной ошибкой**, — но
конвертации YAML в узлы в v1 нет. Причина: она тянет YAML-зависимость и вторую,
независимую от ссылок, модель разбора, а YAML вдобавок разворачивает якоря и
алиасы — на недоверенном теле это класс атак «миллиард смеющихся», от которого
пришлось бы защищаться самим. Ссылки такой поверхности не имеют: плоская строка
без вложенности и подстановок, стоимость разбора линейна по длине.

Консервативно здесь именно явный отказ: без ступени тот же файл уехал бы в
построчный разбор и дал бы по бессмысленной ошибке на строку, а настоящая
причина утонула бы. Записано как C5; регистр превратил это из отклонения в
решение с проверкой (S23).

_Принято и перенесено в спеку:_ §4 пополнен строкой «Clash YAML как формат
подписки», §6.12 дописан. Единственное из Р7–Р14, что меняло границу продукта,
а не только реализацию, — поэтому решалось отдельно.

**Р12. Секретом считается весь `nodes.json`, а не перечисленные поля.** §6.14
говорит «файлы с ключами 0600» и не перечисляет ключи. Решение: файл целиком
0600, потому что `params` несёт `uuid`, пароли и `pbk`, а перечисление по полям
— это список, который устаревает на каждом новом протоколе. Плюс `Node`
форматируется заглушкой по образцу `tunnel.Token`: в лог он не попадает ни
через один глагол `fmt`, включая `%#v` по объемлющей структуре.

**Р13. Битые файлы стора обрабатываются несимметрично.** Спека молчит.
Решение: нечитаемый `health.json` — не ошибка, живость считается пустой, и
первый же раунд проб её восстановит. Нечитаемый `nodes.json` или `groups.json`
— громкий отказ старта. Причина в цене: потерянная живость стоит одного раунда
проб, а пустой список узлов при живом файле выглядит как «подписка исчезла» и
провоцирует пользователя добавить её заново, потеряв всё окончательно.

**Р14. У стора один писатель, и это проверяется замком.** §3.3 говорит «вся
логика в агенте», но §1/С2 (`hop sub add`) идёт раньше §1/С3 (`hop up`):
требовать живого агента для добавления подписки значило бы требовать туннеля до
появления первого узла. Значит писать будут двое — процесс команды и агент.
Решение: файловый рекомендательный замок в каталоге стора (`flock` на Unix,
эксклюзивное открытие на Windows) на время «прочитать — изменить — записать»;
второй писатель ждёт до таймаута и затем **падает с внятной ошибкой**, а не
пишет поверх.

Причина, по которой это решается сейчас, а не позже: отклонение C12 отмечало,
что окна гонки пока нет, поскольку агент в стор не пишет. Решение Р5 регистра
решений (живость персистится) создаёт это окно по построению — агент начинает
писать `health.json` каждые тридцать секунд. Замок дешевле, чем перенос
`sub add` в агент, и не ломает §1/С2.

## 4. Числа и границы

У4 и У1 требуют чисел, а не слов «быстро» и «не течёт».

| параметр                          | старт    | откуда |
| --------------------------------- | -------- | ------ |
| потолок тела подписки             | 8 МиБ    | Р7     |
| таймаут скачивания                | 30 с     | Р7     |
| дебаунс записи живости            | 30 с     | §2     |
| таймаут ожидания замка стора      | 5 с      | Р14    |
| узлов в эталонной подписке        | 200      | §6.5   |
| узлов в проверке линейности       | 2000     | здесь  |

**Слияние линейно по числу узлов.** Ключ кладётся в карту, входящая подписка
проходится один раз. Проверка S7 меряет слияние 200 и 2000 узлов и требует,
чтобы отношение времён было ближе к 10, чем к 100. Число не порог сборки, а
защита от наивного двойного цикла: на 200 узлах квадрат незаметен, на подписке
провайдера с тысячами — заметен сразу и в самом неудобном месте.

**Запись стоит трёх системных вызовов на файл**, а не одного: временный файл,
`fsync` файла, `rename`. На Unix добавляется `fsync` каталога — без него
`rename` может пережить переименование, но не появление содержимого. Это
единственное место в этапе, где имеет значение, какая под нами файловая
система, и потому оно вынесено в один слой, а не размазано по вызовам.

**Дебаунс не отменяет запись при выходе.** Тридцать секунд — это про частоту, а
не про право потерять последнее состояние: `Close` всегда пишет.

## 6. Новые флаги политик

В `internal/policy/policies.go` этап 7 добавляет шесть.

| флаг                | что делает выключение                                | охраняющие проверки |
| ------------------- | ------------------------------------------------------ | ------------------- |
| `merge_key`         | ключ = полный отпечаток узла                          | T18, S1             |

`merge_key` в `PLAN.md` значился одним флагом с двумя режимами
(`full_fingerprint` и `addr_only`). Механизм `HOP_DISABLE` двоичный, поэтому

флага — норма; флаг без краснеющей проверки — нет, и это ловит `negcheck`.

## 9. Чего эта верификация не проверяет

Продолжение честного списка §8.7.

- **Настоящие подписки настоящих провайдеров.** Golden-корпус собран из формы,
  описанной §6.12 и разбором nekoray, а не из выборки живых ссылок. Ключ §6.16
  опровергнет только реальность: если провайдер переиспользует один `user_id`
  на разных серверах, мы узнаем это от пользователя.
- **Подписку, отдающую разный состав на каждый запрос.** Балансировщик на
  стороне провайдера превратит обновление в «удалено 40, добавлено 40», история
  будет теряться каждые несколько часов, и ни одна проверка здесь этого не
  увидит — с точки зрения слияния это корректная работа.
- **Что `unsup_reason` угадывает правильно.** Он говорит, чего не хватило
  **нашему разбору**, а не чего не хватает сборке Xray. Пересборка с новым
  протоколом не пересчитывает поле автоматически, и узел останется
  `supported: false` до следующего обновления подписки.
- **Как часто провайдеры отдают Clash YAML и от чего это зависит.** После §4
  такое тело мы отвергаем, и вопрос «сколько подписок это отсекает» становится
  практическим. Известно, что часть бэкендов выбирает формат по `User-Agent`:
  клиенту, похожему на v2ray, приходят ссылки, клиенту с Clash-овским UA —
  YAML. Наш HTTP-клиент UA пока не задаёт вовсе, и это не измерено ни на одной
  живой подписке. Если догадка верна, правильный UA обесценивает проблему; если
  нет — Р11 стоит дороже, чем кажется здесь.
- **Кодировки в `#fragment`.** Имена узлов приходят в UTF-8 по факту, а не по
  стандарту; что делать с иным — не решено и не проверено.
- **Больше двух писателей.** Замок Р14 проверен на паре процессов. Три
  одновременных `hop sub update` — не проверяются.
- **`quota_info`.** Хранится сырым заголовком и не разбирается: показывать ли
  остаток и исключать ли узел с исчерпанной квотой — открытый вопрос §7, п. 3.
