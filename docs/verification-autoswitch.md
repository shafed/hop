# Верификация автопереключения

Главная функция продукта — «сам находит рабочий узел и переключается на него»
(§1/С4). §8.2 задаёт для неё восемь строк (T1–T8); этого мало, чтобы писать
код: половина решений, от которых зависит поведение, в спеке не принята вообще.
Документ доводит верификацию до состояния, из которого тесты пишутся механически
— и, поскольку он написан до кода, он же диктует, каким код обязан быть, чтобы
проверяться.

Правило §8 действует и здесь: **проверка валидна, только если она краснеет без
той логики, которую охраняет.** У каждой строки регистра указан флаг из
`internal/policy`, отключение которого её ломает. Флаг без охраняющей проверки
запрещён `TestEveryPolicyIsGuarded`, проверка без флага — этим документом.

Уровни — из §8: L1 — фейковый пробер и фейковые часы, без сети; L2 — настоящий
VLESS через fault injector поверх поддельного `PacketDevice`; L3 — TUN и права.

---

## 1. Что именно утверждается

Обещание из §1/С4 распадается на шесть утверждений. Ниже — они, а не сценарии:
сценарий проверяет один путь, утверждение — все.

- **У1. Живость измеряется, а не угадывается.** Состояние узла — функция окна
  последних результатов, а не последнего результата. Одиночный сбой не меняет
  ничего наблюдаемого (§6.3).
- **У2. Выбор устойчив.** Пока активный узел жив и не проигрывает лучшему
  кандидату больше `tolerance`, он остаётся активным. Число переключений
  ограничено сверху числом настоящих изменений сети, а не числом циклов
  проб (§6.4).
- **У3. Смерть активного узла ограничена по времени сверху, и граница известна.**
  Она разная при активном трафике и в простое, и обе записаны здесь числом
  (§4 ниже).
- **У4. Отсутствие живых узлов — наблюдаемое снаружи состояние, а не пустой
  выбор внутри.** Пустой выбор обязан доезжать до `netstack` как fail-close, а
  до пользователя — как `no healthy nodes` (§5.6, §1/С6).
- **У5. Стоимость измерения ограничена.** Число исходящих соединений за час
  растёт не пропорционально размеру подписки — иначе подписка на 200 узлов
  превращает утилиту в сканер (§6.5).
- **У6. Переключение несёт причину, и от причины зависит судьба активных
  соединений.** `dead` рвёт, `faster` не рвёт (§5.5).

У1–У2 проверяются на L1 целиком. У3 — на L1 в модельном времени и на L2 в
настоящем. У4 — на L1 (провод `health` → `netstack`) и на L2 (T12, T13).
У5 — на L1 счётчиками проб и на L2 бенчмарком B2. У6 — на L1 полем события, на
L2 судьбой соединения (T9, T10).

## 2. Поверхность наблюдения

Верификация написана раньше кода, поэтому она вправе требовать от кода
наблюдаемости. Требования ниже — часть контракта модуля `health`, а не
пожелание к тестам.

```go
// Состояние и вердикт — наружу, целиком, одним снимком.
type Snapshot struct {
    Active   string        // id активного узла; пусто — живых нет
    Auto     bool          // автовыбор включён (§1/С3)
    Nodes    []NodeHealth  // state, rtt, окно, traffic_failures, last_error
    Round    uint64        // номер завершённого раунда проб
}

type Manager interface {
    Snapshot() Snapshot
    Healthy() bool                                  // провод в netstack (§3.4, п.3)
    Events() <-chan SwitchEvent                     // from, to, reason, at, interrupted
    ReportFailure(nodeID string, kind FailureKind)  // §6.15, замкнутое перечисление
    NetworkChanged()                                // §6.6
    Pin(nodeID string) error                        // hop up --node
    Auto(on bool)                                   // hop auto on
}
```

Четыре требования к реализации, без которых проверки становятся нестабильными
или невозможными:

1. **Раунд проб наблюдаем.** `Round` растёт на единицу, когда все пробы раунда
   завершены и выбор пересчитан. Тест ждёт роста счётчика, а не спит.
   Без этого каждая L1-проверка превращается в гонку.
2. **Часы — единственный источник времени** (§8.1, линт уже есть). Ни один
   таймаут пробы, ни один интервал расписания не берётся из `time`.
3. **Пробер получает `node_id` и обязан ходить через outbound этого узла**
   (§6.7). Фейковый пробер считает вызовы по узлам — это делает У5 проверяемым
   без сети.
4. **События не теряются.** Канал событий читают несколько подписчиков
   (§3.3), и тест — один из них; переполнение канала не должно молча
   съедать переключение, иначе У6 недоказуема.

Стенд L1: фейковый пробер (программируемые результаты и задержки по узлам,
счётчики вызовов), `clock.Fake`, набор узлов без сети. Стенд L2 — из §8.1
целиком, добавлять нечего.

## 3. Решения, которых нет в спеке

Каждое из них меняет тесты, поэтому принимается здесь. Выбран консервативный
вариант (CLAUDE.md); все шесть — кандидаты в `SPEC.md` §6 после ревью.

**Р1. Воскрешение мёртвого узла.** §6.3 говорит, когда узел умирает, и молчит о
том, когда оживает. Решение: **правило симметрично и единственно** — узел `dead`
ровно тогда, когда в последних `n` результатах не меньше `k` неудач. При
`k=2, n=3` возврат стоит двух успехов подряд. Отдельного порога воскрешения нет:
второй порог — это второй набор граничных случаев и второй источник дребезга.

**Р2. Ошибки трафика и окно проб.** §2 держит `window` и `traffic_failures`
раздельно, §5.4 требует, чтобы вклад давали оба. Решение: узел мёртв, если
`k` неудач в окне проб **или** `traffic_failures ≥ k` в текущем окне. Счётчик
трафика обнуляется при каждой успешной пробе и при переходе в `alive`. Причина
раздельности: одна успешная проба не должна стирать историю проб, но обязана
стирать подозрение, возникшее из трафика, — иначе узел копит смертельные очки от
редких сетевых икот и умирает спустя часы после того, как всё починилось.

**Р3. Семантика мульти-URL.** §5.4 требует нескольких URL и не говорит, как
сводить результаты. Решение: проба узла успешна, если **успешен хотя бы один
URL**; `rtt` — минимальный из успешных; URL опрашиваются параллельно, и вердикт
не зависит от порядка. Причина: цель мульти-URL — пережить блокировку одного
тестового домена (§5.4), а «большинство» или «все» ровно этого не переживают.

**Р4. Холодный старт.** На старте все узлы `untested`, и полный обход подписки —
десятки секунд. Решение: **первый успешно ответивший узел становится активным
немедленно**, не дожидаясь конца раунда; по завершении раунда применяется обычное
правило с `tolerance`. Причина: обещание §1/С3 — «`hop up` выбирает узел
автоматически», и пользователю нужен интернет, а не оптимальный узел.

_Следствие, найденное реализацией._ Стартовый обход даёт **не одно событие, а
несколько**: сперва `«» → первый ответивший` с причиной `dead`, затем
`faster`-переключения по мере того, как отвечают узлы получше. Соединения при
этом не рвутся (§5.5), а сходимость видна в `hop events`. Поэтому «число
переключений» имеет смысл считать от установившегося состояния, а не от запуска
— все проверки устойчивости выбора так и написаны.

**Р5. Fail-close на старте.** Прямое следствие Р4: `Healthy()` не должен быть
`false` только потому, что раунд ещё не кончился. Решение: fail-close наступает,
когда **каждый** `supported`-узел проверен хотя бы раз и ни один не жив, либо
истёк стартовый бюджет (30 с модельного времени) — что раньше. До этого момента
трафик ждёт, а не получает RST.

**Р6. Ручная фиксация.** §1/С3: `hop up --node` выключает автопереключение до
`hop auto on`. Решение читается буквально: **зафиксированный узел не заменяется,
даже когда умирает** — пользователь получает fail-close и `status`, где видно,
что узел мёртв и автоматика выключена. Причина: «зафиксирован» и «зафиксирован,
пока работает» — разные обещания, и второе тихо возвращает автоматику ровно в
тот момент, когда пользователь её выключал осознанно. Пробы при этом не
прекращаются: `status` обязан показывать живость всех узлов.

## 4. Бюджеты времени

У3 требует чисел, а не слова «быстро». Стартовые значения расписания (§6.5) и
бюджеты, которые из них следуют:

| параметр                       | старт            | откуда              |
| ------------------------------ | ---------------- | ------------------- |
| интервал проб активного узла   | 20 с             | §6.5 «десятки секунд» |
| интервал проб пула кандидатов  | 60 с             | §6.5                |
| размер пула кандидатов         | 5                | здесь               |
| интервал проб хвоста подписки  | 1800 с ± 20% джиттера | §6.5           |
| таймаут одной пробы            | 5 с              | здесь               |
| `k` из `n`                     | 2 из 3           | §6.3                |
| `tolerance`                    | 50 мс            | §6.4                |

Отсюда два бюджета, и они разные:

- **Узел умер под трафиком** — ошибки трафика §6.15 приходят немедленно, порог
  `traffic_failures ≥ 2` берётся за время одного-двух неудачных соединений:
  **≤ 5 с** до переключения. Это и есть порог T9/T11.
- **Узел умер в простое** — обнаружение стоит двух неудачных проб:
  **≤ 2 × (20 с + 5 с) = 45 с**. Пользователь не замечает этого по определению:
  трафика в этот момент нет, а первый же запрос попадает в первый бюджет.

И арифметика У5 для подписки в 200 узлов: 180 проб активного + 5 × 60 проб
кандидатов + 195 × 2 проб хвоста ≈ **870 соединений в час** против 4000 у
полного обхода раз в 3 минуты, которым §6.5 пугает. Это порог A25 и он же —
порог B2 на настоящей сети.

Числа — стартовые, и первый же прогон T3 на джиттере 80–120 мс (`PLAN.md`,
этап 5) вправе их опровергнуть. Верификация фиксирует не значения, а то, что
бюджет существует и измеряется.

A27 — про ресурсы, а не про логику: `blackhole` из §8.1 без этой проверки копит
горутины ровно в том сценарии, ради которого продукт написан.

A25 и A26 считают **расписание, а не прогон модельного часа**. Причина
механическая: прогон часа — это гонка цикла проб с фейковыми часами, и его
результат зависит от того, успел ли цикл обработать тик до следующего сдвига
времени. Расписание же детерминировано: сумма `3600 / интервал(узел)` по всем
узлам — та же величина, что меряет B2 на настоящей сети, и порог у них общий.

### 5.7 Пробы идут тем же путём, что и трафик (§6.7)

| #   | Сценарий                                        | Ожидание                                                     | Уровень |
| --- | ------------------------------------------------ | ------------------------------------------------------------- | ------- |
| A33 | Проба узла X                                    | фейковый пробер получил `node_id` = X, счётчик вырос у X      | L1      |

## 6. Новые флаги политик

В `internal/policy/policies.go` этап 5 добавляет четыре. Имена — из `PLAN.md`,
этап 5, плюс два, которых там нет.

| флаг              | что делает выключение                                    | охраняющие проверки        |
| ----------------- | --------------------------------------------------------- | -------------------------- |
| `k_of_n`          | `k = 1`: одна неудача убивает узел                        | T2, A3                     |
| `tolerance`       | `tolerance = 0`: переключение на любое улучшение          | T3                         |
| `switch_reason`   | причина не передаётся, соединения рвутся всегда            | A19 (и T10 на L2)          |
| `forced_probe`    | события сети игнорируются, работает только тикер           | T6, A24                    |
| `multi_url`       | остаётся один URL                                          | T5, A31                    |
| `probe_tiers`     | ярусы схлопываются в полный обход на каждом тике           | A25, A26                   |
| `traffic_kills`   | ошибки трафика не влияют на живость                        | A5, A29                    |

В колонке — только **зарегистрированные** охранники: те, что перечислены в
`internal/policy` и которые `negcheck` гоняет дважды. Краснеют при выключении и
другие проверки (например A2 и A6 при `k_of_n` и `traffic_kills`), но регистр
держится узким намеренно: негативная задача прогоняет каждый охранник по два
раза, и её время растёт линейно по их числу.

Флаг требует охранника, который краснеет **именно от него**. Три проверки из
регистра оказались без флага, хотя доклад по ним ожидался: A10 (равные `rtt`
проходят и при нулевом `tolerance` — строгое «меньше» само по себе не даёт
переключиться), A14 (провод `Healthy()` не зависит от `reject_mode`: тот живёт в
`netstack`) и A28 (бюджет простоя только сокращается при `k = 1`). Это не
дефект, а следствие правила: проверка без флага — нормально, флаг без
краснеющей проверки — нет.

`probe_tiers` и `traffic_kills` в `PLAN.md` не значатся — они появились из У5 и
Р2. Пять флагов из плана оставлены с теми же именами.

## 7. Состояние регистра

L1 целиком реализован: `internal/health`, 41 проверка, зелёные под `-race` на
трёх ОС. Что осталось и почему:

| проверка         | состояние                     | где                    |
| ---------------- | ----------------------------- | ---------------------- |
| T1–T8, A1–A33    | зелёные (L1)                  | `internal/health`      |
| T9, T10, T11     | зелёные (L2)                  | `internal/l2`          |
| T20              | зелёный (L2)                  | `internal/l2`          |
| A34, A35         | зелёные (L2)                  | `internal/l2`          |
| B2               | не написан                    | порог совпадает с A25  |

L2 гоняет настоящие VLESS-соединения до настоящих инбаундов Xray за fault
injector — моков между health и узлом нет ни одного. Расписание проб там сжато
до сотен миллисекунд: бюджеты §4 сформулированы как «k неудач по интервалу», и
на L2 проверяется механизм, а числа §6.5 остаются на A25 и B2.

Пробер v1 — `MultiProber` поверх `Target`; реализация для настоящего HTTP —
`health.HTTPTarget`, ходит через outbound узла (§6.7).

**Чего L2 добавил к §6.15.** Вердикт нельзя поставить по ошибке, которую видит
приложение: она одинакова для мёртвого узла и мёртвого сайта. Он ставится на
перехваченном диалере Xray, и из трафика наблюдаем только `DialTimeout` —
подробно в SPEC.md §6.15. Бюджет «5 секунд под трафиком» держится на нём.

## 8. Порядок реализации

Регистр упорядочен так, чтобы каждый следующий кусок кода имел красную проверку
до его написания. Этап 5 прошёл этим порядком:

1. Окно, `k`-из-`n`, `FailureKind` → T1, T2, A1–A8.
2. Выбор, `tolerance`, холодный старт → T3, T4, A9–A13.
3. Провод `Healthy()` в `netstack`, стартовый бюджет → A14–A17.
4. События, причины, разрыв, `Pin` → T7, T8, A18–A23.
5. Расписание, ярусы, коалесцирование, бюджеты → T6, A24–A29.
6. Мульти-URL → T5, A30–A32.
7. Пробер поверх настоящего outbound → A33; L2 (A34, A35, T9–T11, T20) — после
   этапа 4, когда появится Xray и инжектор.

Шаги 1–6 не требуют ни сети, ни Xray, ни TUN: это L1 на фейках, и он идёт на
всех трёх ОС на каждый PR.

## 9. Чего эта верификация не проверяет

Продолжение честного списка §8.7, для той же цели — чтобы зелёный регистр не
считался гарантией.

- **Что пробы измеряют то, что нужно пользователю.** Проба видит 204 от
  тестового домена; сайт пользователя может не открываться при живой пробе. §5.4
  снижает вероятность мульти-URL, но не устраняет её.
- **Реальную статистику отказов.** Стартовые `k=2, n=3` и `tolerance = 50 мс`
  взяты у sing-box, а не измерены на настоящих провайдерах. T3 покажет только,
  хватает ли 50 мс на смоделированном джиттере.
- **Поведение при частичной деградации.** Узел, теряющий 30% пакетов, отвечает
  на пробы и остаётся `alive`. Модель живости двоичная; потери не измеряются.
- **Одновременную смерть всех узлов подписки** как отличимую от смерти самой
  сети. Утилита в обоих случаях уходит в fail-close, и это правильное поведение,
  но пользователю нужен разный текст — а различать эти случаи мы не умеем.
- **Стоимость проб для провайдера узлов.** B2 считает соединения от нас; сколько
  их считает провайдер и не сработает ли у него антифрод — вне стенда.
