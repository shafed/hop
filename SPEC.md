# xray-vpn

Кроссплатформенная VPN-утилита поверх Xray-core: перехватывает весь трафик
системы через TUN, гоняет его через набор узлов (VLESS и прочее), постоянно
проверяет их живость и сама переключается на работающий.

Документ описывает v1. Разделы отсортированы по вероятности изменений: то, что
будет меняться чаще всего, — наверху.

---

## 1. Пользовательские сценарии v1

Поверхность v1 — CLI и фоновый агент. GUI не входит в v1.

**С1. Первый запуск.** Пользователь ставит пакет. Инсталлятор регистрирует
привилегированный сервис (`xrayvpnd`) и запускает его. Агент (`xrayvpn`)
работает от обычного пользователя и стартует при логине.

**С2. Добавление подписки.**
`xrayvpn sub add <url>` — скачивает, парсит, создаёт группу, показывает сводку
(сколько узлов добавлено, сколько неподдерживаемых). Ссылки на отдельные узлы —
`xrayvpn node add <link>`, попадают в группу `manual`.

**С3. Подключение.**
`xrayvpn up` — поднимает туннель, выбирает узел автоматически.
`xrayvpn up --node <id>` — фиксирует конкретный узел, автопереключение выключено
до `xrayvpn auto on`.

**С4. Работа в фоне.** Агент опрашивает узлы, при смерти активного узла
переключается сам. Пользователь ничего не делает и в норме ничего не замечает,
кроме обрыва соединений, шедших через умерший узел.

**С5. Наблюдение.**
`xrayvpn status` — активный узел, его латентность, состояние туннеля, причина
последнего переключения.
`xrayvpn nodes` — список с латентностью и состоянием (alive / dead / untested).
`xrayvpn events --follow` — поток событий переключения.

**С6. Все узлы умерли.** Трафик блокируется (fail-close), `status` показывает
`no healthy nodes`. Пользователь либо чинит подписку, либо осознанно выпускает
трафик напрямую: `xrayvpn bypass --on` (сохраняется до перезапуска, `status`
показывает предупреждение).

**С7. Отключение.** `xrayvpn down` — туннель снят, все маршруты, правила и
настройки DNS возвращены в исходное состояние.

**С8. Обновление подписки.** По таймеру или `xrayvpn sub update`. Узлы, которые
остались, сохраняют свою историю проб и статистику; исчезнувшие удаляются.

## 2. Модели данных

Хранилище агента — каталог пользователя, права `0700`; файлы с секретами `0600`.

### Node

Один узел. `id` устойчив и переживает обновление подписки.

```
id            стабильный идентификатор (генерируется при первом появлении)
group_id      группа-владелец
merge_key     ключ слияния при обновлении подписки (см. §7)
name          отображаемое имя из ссылки (#fragment)
protocol      vless | vmess | trojan | shadowsocks | hysteria2 | wireguard | ...
server        хост или IP
port
transport     raw | ws | xhttp | grpc | httpupgrade | mkcp | hysteria
security      none | tls | reality
params        всё остальное, специфичное для протокола и транспорта
supported     умеет ли это наша сборка Xray (см. §5)
raw_link      исходная ссылка целиком, для отладки и переэкспорта
```

### NodeHealth

Живёт отдельно от `Node`: обновляется часто, `Node` — редко.

```
node_id
state             untested | alive | dead
rtt_ms            последняя успешная латентность
window            кольцо последних N результатов проб (ok / fail / timeout)
traffic_failures  счётчик ошибок реального трафика в текущем окне
last_probe_at
last_error
```

### Group

Группа = одна подписка либо специальная группа `manual`.

```
id
name
source_url        пусто для manual
last_updated_at
quota_info        сырой заголовок Subscription-UserInfo, если пришёл
node_order         порядок узлов как в подписке
auto_update       вкл/выкл, интервал
```

### TunnelState

Состояние, которым обмениваются агент и сервис.

```
phase          down | starting | up | failing | bypass
active_node    id или пусто
last_switch    { from, to, reason: dead|faster|manual, at }
device         как агент получает пакеты: fd (Linux, macOS) | pipe (Windows)
```

### Событие переключения

```
at, from_node, to_node, reason, interrupted_connections
```

`reason` — не украшение, а часть контракта: от него зависит, рвать ли активные
соединения (§6.5).

## 3. Интерфейсы

### 3.1 Граница «агент ↔ сервис» (управляющая)

Unix-сокет `/run/xrayvpn.sock` с правами владельца (Linux, macOS) и named pipe с
явным SDDL (Windows). **Не TCP.** Операции:

```
StartTunnel(TunnelParams) -> TunnelHandle   параметры TUN; на Linux/macOS
                                            ответ несёт файловый дескриптор
StopTunnel() -> error
Status() -> TunnelState
Heartbeat() -> ok                           агент шлёт периодически
```

`TunnelParams` не содержит ни одного узла и ни одного ключа. Сервис не знает,
куда идёт трафик, — он знает только параметры интерфейса и маршрутов. Ключи
узлов никогда не покидают агента.

### 3.2 Граница «сервис → агент» (трафик)

Через границу идут **сырые IP-пакеты**, за одной абстракцией:

```
PacketDevice {
    ReadPackets(bufs [][]byte) (n int, err error)
    WritePackets(bufs [][]byte) error
    MTU() int
}
```

Две реализации:

- **Linux, macOS** — дескриптор TUN, полученный от сервиса через `SCM_RIGHTS`.
  Агент читает и пишет напрямую; границы в горячем пути нет. Сервис держит свою
  копию дескриптора открытой, поэтому перезапуск агента не убивает интерфейс.
- **Windows** — named pipe. Сервис перекачивает пакеты между сессией Wintun и
  трубой батчами. Дескриптор передать нельзя: Wintun — это хендл драйвера с
  кольцевым буфером, привязанный к процессу-владельцу адаптера.

Выше этой абстракции кода, зависящего от ОС, нет.

### 3.3 Граница «клиенты ↔ агент»

Отдельный unix-сокет/pipe в каталоге пользователя. CLI — тонкий клиент, вся
логика в агенте.

Сокет с первого дня рассчитан на **несколько одновременных клиентов**: в v1 это
один CLI, но позже к нему подключатся GUI и трей одновременно. События (смена
узла, смена состояния туннеля) рассылаются всем подписчикам, а не одному.

Клиенты никогда не говорят с привилегированным сервисом напрямую — только через
агент. Одна привилегированная граница, одна точка аудита.

### 3.4 Внутренние границы агента

```
subscription   → загрузка, парсинг ссылок, diff-слияние
store          → Node / Group / NodeHealth, персистентность
health         → пробер, окно, политика смерти, выбор узла
netstack       → PacketDevice → потоки TCP/UDP, вердикт на первом пакете
engine         → генерация JSON для Xray, core.Dial / core.DialUDP
resolver       → перехваченный DNS, кэш, bootstrap
supervisor     → связь с сервисом, heartbeat, реакция на смену сети
```

`health` не знает про Xray, `engine` не знает про подписки, `store` не знает ни
про кого. Пробер и часы — интерфейсы, а не прямые вызовы (нужно для §8).

**Вердикт на первом пакете потока.** `netstack` принимает по первому пакету одно
из решений, и порядок проверки — часть контракта:

```
1. hijack-dns   dst-порт 53 (UDP или TCP)      → в resolver, всегда,
                                                  до всякой маршрутизации
2. bypass       loopback, RFC1918 и аналоги,
                link-local, mDNS, SSDP          → напрямую, мимо туннеля
3. reject       нет живых узлов (fail-close)    → TCP RST / ICMP unreachable
4. proxy        всё остальное                   → core.Dial / core.DialUDP
```

Модель заимствована из `sing-tun/flow.go:24` (`ActionHijackDNS`, `ActionBypass`,
`ActionReject`). Порядок 1 перед 2 обязателен: системный DNS обычно и есть
локальный роутер, и при обратном порядке запросы уходят провайдеру мимо
резолвера при формально работающем перехвате.

## 4. Что явно НЕ входит в v1

- GUI и трей. Только CLI.
- Мобильные платформы (Android, iOS).
- Split-tunneling по приложениям и по процессам.
- Роутинг по доменам и geoip/geosite базы. В v1 правило одно: всё в туннель,
  кроме локальных сетей.
- Fake-IP.
- Протоколы, которых нет в Xray-core: TUIC, AnyTLS, ShadowTLS, Hysteria v1, SSH.
- Режим системного прокси без TUN.
- Автоопределение captive portal.
- Цепочки прокси и несколько одновременных туннелей.
- Network Extension на macOS и Mac App Store (см. §5.10).
- Подпись Developer ID и нотаризация. v1 ставится через Homebrew или
  `sudo ./install.sh`; и то, и другое работает без подписи.
- Полноценный IPv6 в туннеле (см. §6.9).
- Оптимизации пропускной способности: GSO/GRO, batch read/write, offload.

## 5. Принятые решения — архитектурные

### 5.1 Движок: Xray-core как Go-библиотека, TUN-слой собственный

**Причина.** Xray-core под MPL-2.0 линкуется в проприетарный или любой другой
бинарь без последствий. sing-box и sing-tun под GPL-3.0 — их линковка сделала бы
весь продукт GPLv3. Кроме того, свой TUN-слой убирает второй netstack в горячем
пути и даёт полный контроль над политикой переключения.

**Следствие-ограничение.** Код sing-tun можно читать как референс, но нельзя
копировать. Из wireguard-go (MIT) копировать можно. netstack брать из
`gvisor.dev/gvisor` (Apache-2.0), не из форка `sing-tun/gtcpip` (GPL-3.0).

**Отвергнуто.** Нативный TUN Xray (`proxy/tun`): его собственный README прямо
говорит, что он для роутеров — нет DNS-хайджека, маршруты задаются вручную
плоским списком CIDR, защиты от петли нет, и TUN-стек всегда рапортует
успешное соединение, что ломает любой health-check на его основе.

### 5.2 Два процесса: привилегированный сервис и пользовательский агент

**Причина.** Туннель переживает перезапуск и обновление агента; права
запрашиваются один раз при установке, а не при каждом запуске; парсер подписок,
HTTP-клиент и разбор недоверенного JSON не работают под root.

**Следствие.** Нужен инсталлятор под три ОС и корректный teardown при смерти
агента (§6.2).

### 5.3 Граница между процессами — сырые IP-пакеты, не SOCKS

Через границу идут пакеты за абстракцией `PacketDevice` (§3.2). Netstack один и
живёт в агенте; Xray вызывается программно через `core.Dial` и `core.DialUDP`
(`core/functions.go:49`, `:76`). SOCKS-инбаунда в системе нет вообще.

**Причина — UDP.** Xray socks inbound держит отдельное TCP-соединение на каждую
UDP-ассоциацию как якорь: «Associated TCP keeps the UDP alive; Close UDP if TCP
connection is closed» (`proxy/socks/server.go:177`). Full-cone требует одну
ассоциацию на исходный порт клиента, поэтому браузер с QUIC, торрент или DHT
дают сотни ассоциаций, каждая с TCP-якорем и парой UDP-сокетов. Показательно,
что sing-box, столкнувшись с этим, написал нестандартный UDP-over-TCP
(`protocol/socks/outbound.go:102`) — то есть обошёл проблему, а не решил её.

**Вторая причина.** SOCKS-граница означала двойной netstack: пакет разбирается в
сервисе, пакуется в SOCKS-кадр, разбирается в агенте и снова превращается в
поток для Xray. Пакетная граница убирает целый слой.

**Следствие.** UDP full-cone получается естественно: `core.DialUDP` возвращает
`net.PacketConn`, один на исходный порт — ровно та же модель, что в собственном
TUN Xray (`proxy/tun/udp_fullcone.go`, NAT по source addr:port).

**Цена.** На Windows остаётся копирование пакетов через named pipe. Оценка —
свыше гигабита при батчинге, то есть заведомо выше пропускной способности
VLESS-канала, но это **оценка, а не измерение**: она проверяется бенчмарком B1
(§8.6) до того, как на границу нарастёт код.

### 5.4 Health-check: активные пробы по нескольким URL плюс ошибки трафика

**Причина.** Только пробы дают ложно-зелёный статус, когда узел отвечает на
`generate_204`, но реальные сайты не открываются. Только трафик не даёт знать
ничего о резервных узлах — переключение получилось бы вслепую. Несколько
тестовых доменов нужны потому, что единственный тестовый домен может быть
заблокирован, и тогда все узлы одновременно выглядят мёртвыми. Hiddify пришёл к
этому же после отказа от простого `urltest`.

### 5.5 Разрыв активных соединений зависит от причины переключения

**Причина.** Узел признан мёртвым — его соединения уже мертвы, и разрыв даёт
приложению переподключиться за секунды вместо минут TCP-таймаута. Нашли узел
быстрее — рвать нечего и незачем: обрыв загрузки или звонка ради 30 мс
раздражает сильнее, чем сами 30 мс.

**Следствие.** Сигнал переключения несёт `reason`. В sing-box его нет
(`performUpdateCheck` знает только «выбор изменился»), поэтому там разрыв
пришлось делать глобальным флагом.

### 5.6 Отказ всех узлов: fail-close плюс явная команда обхода

**Причина.** Fail-open молча раскрывает реальный IP и все запросы ровно в тот
момент, когда сеть ведёт себя странно — то есть когда вероятность блокировки
максимальна. Пользователь должен выпускать трафик напрямую осознанно, а не
узнавать об этом постфактум.

**Исключения, разрешённые всегда:** локальные сети (RFC1918 и аналоги), DHCP,
NTP. Без них fail-close ломает саму сеть, а не только выход в интернет.

**Закрытие — отказ, а не молчание.** Заблокированный поток получает TCP RST либо
ICMP port/host unreachable (`sing-tun/flow_reject.go` строит и то, и другое).
Молчаливый дроп подвешивает приложения до таймаута — та же ошибка, из-за которой
мы решили рвать соединения при смерти узла (§5.5).

### 5.7 DNS: перехват :53 в TUN, резолв через активный узел

**Причина.** Без перехвата запросы уходят системному резолверу мимо туннеля —
это и утечка, и неработающий роутинг по именам в будущем. Реальный резолв, а не
fake-IP: fake-IP оседает в кэшах приложений и переживает выключение VPN, после
чего сайты перестают открываться необъяснимым для пользователя образом.

**Следствия.** (а) Нужен bootstrap-резолвер в обход туннеля для хостнеймов самих
узлов, иначе на старте петля. (б) DNS подчиняется fail-close: нет живых узлов —
нет резолва. (в) Кэш уважает TTL и сбрасывается при смене узла, иначе после
переключения трафик уходит в CDN чужого региона.

### 5.8 Профили: подписка = группа, обновление через diff

**Причина.** Полная замена стирает историю проб и текущий выбор при каждом
обновлении — автопереключение начинало бы с нуля каждые несколько часов и
переопрашивало всю подписку. Устойчивые `id` сохраняют состояние. Несколько
групп нужны потому, что типичный пользователь держит две-три подписки от разных
провайдеров именно ради отказоустойчивости — то есть ради главной функции этой
утилиты.

### 5.9 Поверхность v1 — CLI

**Причина.** Все риски проекта лежат в TUN, DNS и автопереключении, ни один — в
UI. CLI делает всё поведение проверяемым машиной без UI-тестов. Автозапуск и
автоподключение при этом работают полностью: их обеспечивает сервис, а не GUI.

### 5.10 macOS: LaunchDaemon, поставленный инсталлятором

Демон `xrayvpnd` живёт в `/usr/local/libexec` (или префиксе Homebrew), plist —
в `/Library/LaunchDaemons`, владелец `root:wheel`, режим 644, загрузка через
`launchctl bootstrap system`, `RunAtLoad` и `KeepAlive`. Агент — LaunchAgent в
`~/Library/LaunchAgents`, без привилегий. Единственный запрос прав за всё время
жизни — `sudo` при установке.

**Причина.** hiddify не поддерживает macOS (`isSupportedOS()` в
`admin_service_commander.go:24` возвращает только windows и linux) не из-за
macOS, а из-за формы продукта: их GUI в `.app`-бандле должен установить демон
изнутри себя, а для этого нужен `SMJobBless`/`SMAppService` и Developer ID.
Инсталлятор, работающий под `sudo`, идёт мимо этого ограничения полностью.

**Что требует root и потому живёт в демоне:** создание utun через
`socket(AF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)` с control-именем
`com.apple.net.utun_control`; адрес через `SIOCAIFADDR`; маршруты через
`PF_ROUTE`; сброс кэша DNS. **Что не требует и остаётся в агенте:** чтение
route-сокета `AF_ROUTE` для реакции на смену сети — `monitor_darwin.go:56`
открывает его обычным `unix.Socket`.

**Маршруты — восемь подсетей, не `0.0.0.0/0`.** `tun_rules.go:107` включает
`autoRouteUseSubRanges` только на darwin: два default route на macOS
конфликтуют, и после падения процесса система остаётся без маршрута. Восемь
подсетей (`1.0.0.0/8`, `2/7`, `4/6`, `8/5`, `16/4`, `32/3`, `64/2`, `128/1`)
покрывают всё адресное пространство, выигрывают по longest-prefix и оставляют
системный дефолт нетронутым.

**Подпись.** На Apple Silicon бинарь обязан быть подписан хотя бы ad-hoc — это
делает сам Go-линкер. Нотаризация и Developer ID нужны только при
распространении скачиваемого `.pkg`/`.dmg`; Homebrew и `curl | sh` атрибут
quarantine не ставят. Диалогов TCC нет: ни utun, ни маршруты разрешений
пользователя не требуют.

**Отвергнуто.** Network Extension (`NEPacketTunnelProvider`) требует entitlement,
который выдаётся Apple по заявке, а не автоматически по подписке. Отказ от него
закрывает Mac App Store — это осознанная цена.

**Что будет, когда появится GUI.** Архитектура не меняется при одном правиле:
демон ставит **инсталлятор, а не приложение**; GUI — такой же клиент сокета
агента, как CLI (§3.3), и привилегий не касается никогда. Изменится только
поставка: `.pkg` с `postinstall` вместо `.dmg`, плюс Developer ID и нотаризация,
чтобы Gatekeeper пропустил скачанный установщик. App Sandbox при этом должен
остаться выключенным — из песочницы `.app` не достучится до сокета агента
(у hiddify ровно так: `app-sandbox = false`).

## 6. Принятые решения — механические

### 6.1 Аутентификация IPC

Unix-сокет с правами владельца / named pipe с SDDL. hiddify слушает gRPC на
`127.0.0.1:18020` вообще без проверки — любой процесс любого пользователя машины
может поднять чужой туннель и направить трафик куда угодно. Не повторяем.

### 6.2 Teardown и watchdog

Сервис владеет маршрутами и правилами. Агент шлёт heartbeat; при потере связи
дольше порога сервис снимает туннель и восстанавливает сеть. Без этого падение
агента оставляет машину без интернета и с мусором в таблице маршрутизации.

### 6.3 Политика смерти узла

Мёртв при `k` неудач из `n` последних проб (стартовые значения: 2 из 3). Одна
ошибка не убивает: в sing-box одна неудачная проба стирает узел
(`DeleteURLTestHistory`), из-за чего на нестабильной сети он мечется.

### 6.4 Гистерезис выбора

Переключаемся на более быстрый узел, только если он быстрее текущего более чем
на `tolerance` (старт: 50 мс, как в sing-box). Иначе два узла с 90 и 95 мс
перекидывают пользователя туда-сюда на каждом цикле.

### 6.5 Расписание проб

Активный узел и пул кандидатов — часто (десятки секунд). Остальная подписка —
редко и вразнобой. Полный обход подписки на 200 узлов раз в 3 минуты — это 4000
TLS-хендшейков в час к одному провайдеру: заметный паттерн и лишняя нагрузка.

### 6.6 Форс-проверка на событиях

Смена интерфейса, пробуждение из сна, изменение таблицы маршрутизации — немедленный
прогон проб, не дожидаясь тикера.

### 6.7 Пробы идут тем же путём, что и трафик

Через тот же outbound и тот же роутинг. Проба в обход измеряет не то, что нужно.

### 6.8 Защита от петли

Агент непривилегирован, поэтому механизм различается по ОС.

**macOS и Windows** — исходящие сокеты ядра биндятся к текущему дефолтному
интерфейсу через `sockopt.interface` (Xray: `IP_BOUND_IF` и `IP_UNICAST_IF`,
`transport/internet/sockopt_darwin.go:136`, `sockopt_windows.go:35`). Обе опции
не требуют привилегий.

**Linux** — bind не годится: `SO_BINDTODEVICE` исторически требует
`CAP_NET_RAW`, и полагаться на это из процесса под обычным пользователем нельзя.
Вместо этого **сервис создаёт `ip rule` с UID-диапазоном агента и `goto` мимо
TUN-таблицы**. Механизм готов в `sing-tun/tun_linux.go:791`
(`netlink.NewRuleUIDRange`) — там он применяется к исключённым приложениям, у нас
к самому агенту. Агенту не требуется ничего, и правило переживает смену
интерфейса, в отличие от bind-to-device.

**Следствие.** Хостнейм узла может резолвиться в любые адреса и менять их — на
защиту от петли это не влияет: трафик агента не попадает в туннель по
конструкции, а не по совпадению маршрута.

**Отвергнуто.** Правило по имени процесса (путь nekoray и hiddify): ломается при
переименовании бинаря и требует поддержки process-matching на каждой ОС.

### 6.9 IPv6 в v1

IPv4 в туннеле; IPv6 блокируется на уровне маршрутов TUN. **Причина:** частично
поднятый IPv6 хуже отсутствующего — трафик молча утекает мимо туннеля, и
пользователь этого не видит. Полноценный IPv6 — после v1.

### 6.10 Роутинг v1

Всё в туннель, кроме перечисленного ниже. Порядок вердиктов — в §3.4, и перехват
:53 стоит выше этого списка.

**Мимо туннеля, в локальную сеть:** loopback, RFC1918 и аналоги, link-local,
DHCP, а также обнаружение служб — mDNS (`224.0.0.251:5353`, `[ff02::fb]:5353`) и
SSDP. Блокировать их нельзя: сломаются Bonjour, AirPlay, AirPrint и поиск
принтеров, что заметнее всего на macOS. У nekoray 5353 в списке блокировок
(`res/vpn/sing-box-vpn.json`), но их сценарий — роутер, а не десктоп.

**Блокируем:** широковещательный NetBIOS (UDP 135/137/138/139) и прочий
multicast и broadcast за пределами перечисленного (`224.0.0.0/3`, `ff00::/8`).

### 6.11 Неподдерживаемые протоколы

Ссылки на TUIC, AnyTLS и прочее парсятся, узел попадает в список с
`supported: false` и не участвует в выборе. Импорт подписки не падает целиком
из-за одной строки.

### 6.12 Нормализация ссылок

Берём разбор nekoray построчно (`fmt/Link2Bean.cpp`): `security` может прийти
как `none`/`0`/`false`/`1`/`true`; `reality` → `tls` плюс `pbk`/`sid`/`spx`;
`h2` → `http`; если сервер задан как IP, `sni` пуст, а `host` есть — подставить
`sni = host`; порт по умолчанию 443. Каскад распознавания: base64 → Clash YAML
(по наличию `proxies:`) → построчно → по схеме. Список транспортов расширяем:
у nekoray нет `xhttp`.

### 6.13 Автозапуск

Сервис — при старте ОС. Агент — при логине пользователя. Автоподключение к
последнему активному профилю — включено по умолчанию, отключается флагом.

### 6.14 Секреты

Каталог агента `0700`, файлы с ключами `0600`. Секреты не пишутся в логи (ни на
уровне debug), не передаются сервису и не попадают в вывод `status`.

### 6.15 Какие ошибки трафика убивают узел

Смертью считаются только отказы на пути к узлу и внутри него:

```
DialTimeout       не установилось соединение с узлом
HandshakeFailed   разрыв во время рукопожатия с узлом
TLSError          ошибка TLS или REALITY от узла
ProxyRefused      узел принял соединение, но отказался проксировать
```

Отказы целевого хоста — connection refused от сайта, HTTP 5xx, NXDOMAIN — узел
не убивают. Интерфейс: `health.ReportFailure(nodeID, kind)`, где `kind` —
замкнутое перечисление, а не строка: иначе классификация расползётся по коду и
однажды тихо начнёт считать смертью упавший сайт.

### 6.16 Ключ слияния подписок

`protocol + server + port + user_id`. Смена транспорта, SNI или имени на том же
сервере — тот же узел, история проб сохраняется. Смена сервера, порта или ключа
— новый узел.

**Причина.** nekoray предлагает два варианта (`ProfileFilter_ent_key`): по
адресу и по полному отпечатку. Полный отпечаток не переживает косметическую
правку у провайдера и обнуляет историю на ровном месте; ключ только по адресу
склеивает узлы, различающиеся ключом доступа.

## 7. Открытые вопросы

Ни один из них не двигает границы модулей — все решаются, когда работа до них
дойдёт. Вопросы, которые границы двигали, закрыты и переехали в §5 и §6:
привилегии на macOS (§5.10), граница между процессами и UDP (§5.3), защита от
петли под непривилегированным агентом (§6.8), классификация ошибок трафика
(§6.15), ключ слияния подписок (§6.16).

1. **Captive portal.** При fail-close пользователь не сможет авторизоваться в
   Wi-Fi отеля. Нужен ли автодетект или достаточно `xrayvpn bypass --on`?
2. **Windows: распространение wintun.dll.** Подписанная библиотека рядом с
   бинарём; как это укладывается в инсталлятор и обновления.
3. **Квоты.** `Subscription-UserInfo` даёт остаток трафика. Показывать ли, и
   должен ли узел с исчерпанной квотой автоматически исключаться из выбора.
4. **Роутинг по доменам после v1.** Откуда брать базы и сколько они весят.
   Смягчено тем, что при собственном резолвере (§5.7) маппинг домен→IP известен
   нам, и роутить можно обратным поиском, без внешних баз.
5. **Пропускная способность границы на Windows.** Оценка в §5.3 не измерена;
   бенчмарк B1 (§8.6) закрывает вопрос до того, как на границу нарастёт код.

## 8. Оракул: чем машина проверит, что автопереключение работает

Правило для всего раздела: **тест валиден, только если он падает без фикса.**
Для каждого теста ниже указано, что именно должно сломаться. В репозитории для
каждой проверяемой политики есть флаг её отключения, и отдельная CI-задача
убеждается, что с выключенной политикой соответствующий тест краснеет. Тест,
который проходит при отключённой логике, считается сломанным и чинится.

### 8.1 Стенд

Три управляемых компонента, всё локально, без интернета:

**Fault injector.** TCP-прослойка перед настоящим VLESS-инбаундом Xray.
Форвардит байты и по команде переключает режим:

| режим | что делает | какой отказ имитирует |
|---|---|---|
| `pass` | прозрачно | норма |
| `rst` | немедленный RST | сервер снят |
| `blackhole` | принимает и молчит | пакеты дропаются, соединение висит |
| `slow(ms)` | задержка на каждой записи | деградация латентности |
| `cut-after-handshake` | рвёт после TLS | DPI-подобное поведение |

`rst` и `blackhole` — обязательно разные тесты: это разные пути в коде, и
blackhole ловит отсутствие таймаута там, где RST его маскирует.

**Тестовые узлы.** Настоящие VLESS-инбаунды Xray-core в том же процессе теста.
Путь сквозной, без моков: агент реально устанавливает VLESS-соединение.

**Управляемый пробе-таргет.** HTTP-сервер, отдающий 204; по команде переключается
на 403, зависание или медленный ответ. Их несколько — под мульти-URL.

**Часы.** Интервалы, окна и гистерезис тестируются инъектируемыми часами, а не
реальным временем: иначе один тест окна «2 из 3» занимает минуты. Пробер и
таймер — интерфейсы.

**Поддельный `PacketDevice`.** Реализация абстракции §3.2 поверх пары буферов в
памяти: тест кладёт в неё сырые IP-пакеты и читает, что вышло. Позволяет
проверять весь netstack, вердикты и fail-close **без TUN и без прав** — то есть
уровнем L2, на всех трёх ОС, на каждом PR. Именно ради этого граница между
процессами вынесена за узкий интерфейс.

### 8.2 Тесты логики (уровень L1, без прав, на всех трёх ОС)

Работают на фейковом пробере и фейковых часах, без сети и без TUN.

| # | Сценарий | Ожидание | Падает без чего |
|---|---|---|---|
| T1 | Узел A: 2 неудачи из 3 | A помечен `dead`, активным стал B | политики k-из-n |
| T2 | Узел A: 1 неудача, потом успех | активный узел не менялся ни разу | политики k-из-n (при k=1 переключится) |
| T3 | A=100 мс, B колеблется 80–120 мс, 20 циклов | переключений ≤ 1 | гистерезиса tolerance |
| T4 | Все узлы мертвы | состояние `no healthy nodes`, выбор пуст | обработки пустого множества |
| T5 | Пробе-URL №1 отдаёт 403 всем, №2 отдаёт 204 | узлы живы | мульти-URL (с одним URL всё умрёт) |
| T6 | Событие смены интерфейса | прогон проб начался немедленно, не по тикеру | обработчика смены сети |
| T7 | Активный узел умер, переключение | событие с `reason: dead` | передачи причины в сигнале |
| T8 | Найден узел быстрее | событие с `reason: faster` | того же |

### 8.3 Тесты датаплейна (уровень L2, без прав, на всех трёх ОС)

Через поддельный `PacketDevice`, без TUN и без прав. Реальные VLESS-соединения
через fault injector: путь сквозной, моков между netstack и узлом нет.

| # | Сценарий | Ожидание | Падает без чего |
|---|---|---|---|
| T9 | Долгое соединение через A, A → `blackhole` | соединение получает ошибку за ≤ 5 с | разрыва по причине `dead` |
| T10 | Долгое соединение через A, A → `slow(900)`, B быстр | соединение доживает, новое идёт через B | разделения причин (если рвём всегда — упадёт) |
| T11 | A → `rst`, затем `blackhole` | оба случая дают переключение за ≤ 5 с | обработки таймаута (blackhole пройдёт только при наличии таймаута) |
| T12 | Все узлы → `blackhole`, TCP-запрос наружу | клиент получил **RST**, не таймаут; соединений к «интернету» 0 | fail-close именно через reject (при `drop` тест ждёт таймаута и падает) |
| T13 | То же, UDP-запрос наружу | пришёл **ICMP port unreachable** | того же |
| T14 | Домен резолвится в IP1 через A и IP2 через B; переключение | следующий резолв даёт IP2 | сброса DNS-кэша при смене узла |
| T15 | UDP от одного исходного порта на три разных адреса | одна NAT-запись, ответы дошли со всех трёх | full-cone (при NAT по паре src+dst ответы потеряются) |
| T16 | DNS-запрос на `192.168.1.1:53` | ушёл в наш резолвер, а не в локальную сеть | приоритета hijack-dns над bypass (§3.4) |
| T17 | mDNS-запрос на `224.0.0.251:5353` | ушёл в локальную сеть, не заблокирован и не в туннель | правила bypass для обнаружения служб (§6.10) |
| T18 | Обновление подписки, узел остался, но сменился SNI | `id` и история проб те же | ключа слияния §6.16 (при полном отпечатке история обнулится) |
| T19 | Обновление подписки, узел исчез | удалён; активный узел переизбран, если это был он | diff-слияния |
| T20 | Целевой сайт отвечает 502 через живой узел | узел остался `alive`, счётчик смертей не вырос | классификации ошибок §6.15 |

### 8.4 Тесты TUN (уровень L3, требуют прав, специфичны для ОС)

**Общий платформенный контракт.** До старта снимается снапшот состояния сети
(адреса, маршруты, правила, настройки DNS). После `down` снапшот снимается снова
и должен совпасть побайтово. Любое расхождение — падение теста. Это единственный
способ ловить утечки состояния до того, как их найдёт пользователь.

| # | Сценарий | Ожидание | Падает без чего |
|---|---|---|---|
| T21 | `up` | интерфейс существует, адреса назначены, маршруты добавлены | создания TUN |
| T22 | `up`, затем `down` | снапшот сети совпал с исходным | корректного teardown |
| T23 | `up`, `kill -9` агента | сервис снял туннель за ≤ N с, снапшот совпал | watchdog по heartbeat |
| T24 | `up`, перезапуск агента без `down` | интерфейс не исчезал, туннель продолжил работу | того, что сервис держит свою копию дескриптора (§3.2) |
| T25 | `up`, считать пакеты на TUN с dst = IP узла | 0 пакетов | защиты от петли (§6.8) |
| T26 | `up`, DNS-запрос из тестового приложения | 0 запросов на подставной системный резолвер; запрос виден только на резолвере за узлом | перехвата :53 |
| T27 | `up`, все узлы мертвы, запрос наружу | 0 соединений на «интернет-сервер», доступный напрямую | fail-close на уровне TUN |
| T28 | `up`, IPv6-запрос | заблокирован, не ушёл мимо туннеля | блокировки IPv6 (§6.9) |

**Как это гоняется на каждой ОС.**

*Linux* — сетевые namespace. В отдельном netns поднимается всё: «интернет»,
узлы, TUN, агент. Полная изоляция, воспроизводимость, работает в CI под root в
контейнере. Единственная платформа, где полный e2e дёшев — поэтому там гоняется
весь набор T21–T28 на каждый PR.

Проверяемые платформенные детали: отдельная таблица маршрутизации существует и
содержит ожидаемые маршруты; `ip rule` содержит правило с UID-диапазоном агента
(§6.8) и все правила исчезают после `down`; дескриптор действительно приехал
через `SCM_RIGHTS`, а не был открыт агентом самостоятельно; демону достаточно
`CAP_NET_ADMIN` без полного root, а агент проходит тест **вообще без
capabilities** — если он их требует, разделение привилегий сломано.

*Windows* — раннер с правами администратора. Namespace-изоляции нет, поэтому
тесты работают в выделенном адресном диапазоне и T22 (снапшот) идёт первым: если
teardown сломан, остальные тесты не запускаются, чтобы не оставить машину без
сети. Проверяемые детали: адаптер Wintun создан с ожидаемым именем; маршруты
добавлены с метрикой 0; DNS выставлен на адаптере; named pipe имеет ожидаемый
SDDL и недоступен другому пользователю; после `down` адаптер удалён.

*macOS* — раннер с sudo. Изоляции нет, таблица маршрутизации общая. Набор:
T21, T22, T24, T25, T26. Проверяемые детали: интерфейс имеет имя вида `utunN`;
маршруты добавлены **восемью подсетями, а не одним `0.0.0.0/0`** (иначе
перебивается системный дефолт и раннер теряет сеть — этот тест защищает сам
CI); LaunchDaemon загружается через `launchctl bootstrap system` и переживает
перезагрузку; после `down` маршруты сняты и кэш DNS сброшен.

**Матрица запуска.** L1 и L2 — на всех трёх ОС при каждом PR. L3-Linux — при
каждом PR. L3-Windows и L3-macOS — по расписанию и обязательно перед релизом.

### 8.5 Тест установки (уровень L4, по расписанию)

Проверяет то, что ломается чаще всего и незаметнее всего — поставку.

| # | Сценарий | Ожидание |
|---|---|---|
| I1 | Чистая машина, установка штатным способом | демон зарегистрирован и запущен, агент стартует при логине |

### 8.6 Бенчмарки

Не тесты «да/нет», а измерения с зафиксированным порогом; падение ниже порога
ломает сборку.

- **B1. Пропускная способность границы.** Прогон синтетического потока через
  `PacketDevice` на каждой ОС: пакетов в секунду и мегабит в секунду для 1400
  байт. Закрывает единственную неизмеренную оценку в §5.3. Порог: не ниже
  500 Мбит/с на Windows (named pipe) и не ниже 2 Гбит/с на Linux и macOS
  (прямой дескриптор). Прогоняется **до** того, как на границу нарастёт код.
- **B2. Стоимость проб.** Число исходящих соединений за час при подписке в 200
  узлов. Порог задаётся §6.5; рост означает, что расписание проб деградировало
  до полного обхода.
- **B3. UDP full-cone под нагрузкой.** 500 одновременных исходящих UDP-портов,
  каждый на несколько адресов. Проверяет, что NAT-таблица не деградирует и не
  течёт.

### 8.7 Чего эти тесты не проверяют

Честный список, чтобы зелёный CI не воспринимался как гарантия:

- Поведение при реальной цензуре: DPI, троттлинг, подмена сертификатов.
- Взаимодействие с конкретными реализациями systemd-resolved, NetworkManager,
  сторонними VPN-клиентами и корпоративными фильтрами.
- Пробуждение из сна и смену физической сети на настоящем железе (T6 проверяет
  только реакцию на событие, а не то, что событие вообще придёт).
- Поведение на macOS при обновлении мажорной версии системы — исторически именно
  там ломаются utun и маршруты.
